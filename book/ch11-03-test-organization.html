The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

테스트 구성

이 장의 도입부에서 언급했듯이, 테스트는 복잡한 분야이며 사람마다 사용하는 용어와 구성 방식이 다릅니다. Rust 커뮤니티는 테스트를 두 가지 주요 범주로 구분합니다. 단위 테스트와 통합 테스트입니다. 단위 테스트는 작고 집중도가 높아 한 번에 하나의 모듈을 격리하여 테스트하며, 비공개 인터페이스도 테스트할 수 있습니다. 통합 테스트는 라이브러리 외부에서 완전히 독립적으로 동작하며, 다른 외부 코드와 동일한 방식으로 코드를 사용합니다. 통합 테스트는 공개 인터페이스만 사용하며, 하나의 테스트에서 여러 모듈을 함께 검증할 수 있습니다.

라이브러리의 각 부분이 개별적으로도, 함께 동작할 때도 기대한 대로 작동하는지 확인하려면 두 종류의 테스트를 모두 작성하는 것이 중요합니다.

단위 테스트

단위 테스트의 목적은 코드의 나머지 부분과 격리된 각 코드 단위를 테스트하여, 코드가 어디에서 기대한 대로 작동하고 어디에서 작동하지 않는지를 빠르게 파악하는 것입니다. 단위 테스트는 테스트 대상 코드와 같은 파일의 src 디렉터리에 작성합니다. 관례적으로 각 파일에 tests라는 이름의 모듈을 만들어 테스트 함수를 포함하고, 이 모듈에 tests를 붙여 cfg(test)를 지정합니다.

tests 모듈과 #[cfg(test)]

테스트 모듈에 붙인 #[cfg(test)] 주석은 Rust에게 tests 모듈의 테스트 코드를 cargo test 명령을 실행할 때만 컴파일하고 실행하라고 알려 줍니다. cargo build 명령을 실행할 때는 컴파일하지 않습니다. 이렇게 하면 라이브러리만 빌드할 때 컴파일 시간을 절약할 수 있고, 테스트 코드가 포함되지 않으므로 최종 컴파일 결과물인 아티팩트의 용량도 줄일 수 있습니다. 통합 테스트는 다른 디렉터리에 있으므로 #[cfg(test)] 주석이 필요하지 않습니다. 하지만 단위 테스트는 코드와 같은 파일에 있으므로 #[cfg(test)] 주석을 사용해 컴파일 결과에 포함되지 않도록 지정해야 합니다.

이 장의 첫 번째 섹션에서 새로운 adder 프로젝트를 생성했을 때, Cargo가 이 코드를 생성해 주었습니다.

파일명: src/lib.rs

pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        let result = add(2, 2);
        assert_eq!(result, 4);
    }
}

자동으로 생성된 tests 모듈, 속성 cfg 스탠드 for 설정 그리고 러스트에게 다음 항목은 특정 설정 옵션이 주어졌을 때만 포함되어야 한다고 말합니다. 이 경우, 설정 옵션은 다음과 같습니다. test러스트는 컴파일 및 실행 테스트를 위해 러스트에서 제공합니다. cfg 속성, Cargo는 우리가 적극적으로 테스트를 실행하는 경우에만 테스트 코드를 컴파일합니다. cargo test. 이것은 주석이 달린 기능 이외에 이 단위 안에 있을지도 모른 어떤 조수 기능든지, 포함합니다 #[test].

비공개 함수 테스트

테스트 커뮤니티에서는 비공개 함수를 직접 테스트해야 하는지에 대해 논쟁이 있습니다. 다른 언어에서는 비공개 함수를 테스트하는 것이 어렵거나 불가능한 경우도 있습니다. 어떤 테스트 철학을 따르든, Rust의 프라이버시 규칙은 비공개 함수를 테스트할 수 있도록 허용합니다. Listing 11-12의 코드와 비공개 함수 internal_adder를 살펴보세요.

내부 함수인 internal_adder가 pub로 표시되어 있지 않다는 점에 유의하세요. 테스트는 단순히 Rust 코드이며, tests 모듈은 또 다른 모듈일 뿐입니다. 모듈 트리에서 항목을 가리키는 경로에서 논의했듯이, 자식 모듈의 항목은 조상 모듈의 항목을 사용할 수 있습니다. 이 테스트에서는 tests를 사용하여 use super::*모듈의 부모에 속하는 모든 항목을 현재 범위로 가져오고, 이후 테스트에서 internal_adder를 호출할 수 있습니다. 비공개 함수를 테스트해야 한다고 생각하지 않는다면, Rust에는 그렇게 하도록 강요하는 규칙이 없습니다.

통합 테스트

Rust에서 통합 테스트는 라이브러리 외부에 완전히 존재합니다. 통합 테스트는 다른 코드와 동일한 방식으로 라이브러리를 사용하므로, 라이브러리의 공개 API에 포함된 함수만 호출할 수 있습니다. 통합 테스트의 목적은 라이브러리의 여러 부분이 함께 올바르게 작동하는지 확인하는 것입니다. 개별적으로 올바르게 작동하는 코드 단위도 통합될 때 문제가 발생할 수 있으므로, 통합된 코드의 테스트 커버리지도 중요합니다. 통합 테스트를 만들려면 먼저 tests 디렉토리가 필요합니다.

tests 디렉터리

프로젝트 디렉토리의 최상위 레벨, src 옆에 tests 디렉토리를 만듭니다. Cargo는 이 디렉토리에서 통합 테스트 파일을 찾습니다. 원하는 만큼 테스트 파일을 만들 수 있으며, Cargo는 각 파일을 개별 크레이트로 컴파일합니다.

통합 테스트를 만들어 보겠습니다. Listing 11-12의 코드가 src/lib.rs 파일에 있는 상태에서 tests 디렉토리를 만들고, tests/integration_test.rs라는 이름의 새 파일을 생성합니다. 디렉토리 구조는 다음과 같아야 합니다:

adder
├── Cargo.lock
├── Cargo.toml
├── src
│   └── lib.rs
└── tests
    └── integration_test.rs

Listing 11-13의 코드를 tests/integration_test.rs 파일에 입력합니다.

tests 디렉토리의 각 파일은 별도의 크레이트이므로, 라이브러리를 각 테스트 크레이트의 스코프에 가져와야 합니다. 이 때문에 단위 테스트에서는 필요하지 않았던 use adder::add_two;를 코드 상단에 추가합니다.

tests/integration_test.rs의 코드에 #[cfg(test)]를 붙일 필요가 없습니다. Cargo는 tests 디렉토리를 특별히 취급하여, cargo test를 실행할 때만 이 디렉토리의 파일을 컴파일합니다. 지금 cargo test를 실행해 보세요:

$ cargo test

running 1 test
test tests::internal ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

     Running tests/integration_test.rs (target/debug/deps/integration_test-1082c4b063a8fbe6)

running 1 test
test it_adds_two ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests adder

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

출력의 세 섹션에는 단위 테스트, 통합 테스트, 문서 테스트가 포함됩니다. 한 섹션의 테스트가 실패하면 이후 섹션은 실행되지 않습니다. 예를 들어, 단위 테스트가 실패하면 통합 테스트와 문서 테스트의 출력이 없습니다. 이는 모든 단위 테스트가 통과해야만 해당 테스트들이 실행되기 때문입니다.

단위 테스트 섹션의 첫 번째 부분은 지금까지 확인한 내용과 동일합니다. 각 단위 테스트에 한 줄씩 표시되며(예: Listing 11-12에서 추가한 internal), 마지막에 단위 테스트의 요약 줄이 표시됩니다.

통합 테스트 섹션은 Running tests/integration_test.rs 줄로 시작합니다. 다음으로, 해당 통합 테스트 파일 내의 각 테스트 함수에 대한 줄이 표시되고, Doc-tests adder 섹션이 시작되기 직전에 통합 테스트 결과에 대한 요약 줄이 표시됩니다.

각 통합 테스트 파일은 자체 섹션을 가지므로, tests 디렉토리에 파일을 더 추가하면 통합 테스트 섹션도 더 많이 표시됩니다.

테스트 함수의 이름을 cargo test의 인수로 지정하여 특정 통합 테스트 함수만 실행할 수 있습니다. 특정 통합 테스트 파일의 모든 테스트를 실행하려면 --test의 cargo test 인수를 파일 이름과 함께 사용합니다.

$ cargo test --test integration_test

    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.64s
     Running tests/integration_test.rs (target/debug/deps/integration_test-82e7799c1bc62298)

running 1 test
test it_adds_two ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

이 명령은 tests/integration_test.rs 파일에 있는 테스트만 실행합니다.

통합 테스트의 하위 모듈

통합 테스트를 더 많이 추가하면 tests 디렉토리에 파일을 만들어 정리하는 것이 좋습니다. 예를 들어, 테스트하는 기능별로 테스트 함수를 그룹화할 수 있습니다. 앞서 언급했듯이, tests 디렉토리의 각 파일은 별도의 크레이트로 컴파일됩니다. 이는 최종 사용자가 크레이트를 사용하는 방식을 더 정확하게 모방하기 위해 별도의 스코프를 만드는 데 유용합니다. 하지만 이는 tests 디렉토리의 파일이 src 디렉토리의 파일과 동일한 동작을 공유하지 않음을 의미합니다. 7장에서 모듈과 파일로 코드를 분리하는 방법에 대해 배운 내용과 관련이 있습니다.

tests 디렉터리 파일의 동작이 다른 점은 여러 통합 테스트 파일에서 사용할 보조 함수 집합이 있을 때, 7장의 “모듈을 다른 파일로 분리하기” 섹션의 단계를 따라 이를 공통 모듈로 추출하려고 할 때 가장 뚜렷하게 드러납니다. 예를 들어, tests/common.rs을 만들고 setup이라는 이름의 함수를 넣으면, 여러 테스트 파일의 여러 테스트 함수에서 호출하려는 코드를 setup에 추가할 수 있습니다:

파일 이름: tests/common.rs

pub fn setup() {
    // setup code specific to your library's tests would go here
}

테스트를 다시 실행하면, 이 파일에 테스트 함수가 없고 setup 함수를 어디에서도 호출하지 않았음에도 common.rs 파일에 대한 새로운 섹션이 테스트 출력에 표시됩니다.

$ cargo test

    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.89s
     Running unittests src/lib.rs (target/debug/deps/adder-92948b65e88960b4)

running 1 test
test tests::internal ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

     Running tests/common.rs (target/debug/deps/common-92948b65e88960b4)

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

     Running tests/integration_test.rs (target/debug/deps/integration_test-92948b65e88960b4)

running 1 test
test it_adds_two ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests adder

테스트 결과에 common가 표시되고 running 0 tests이 표시되는 것은 우리가 원하지 않는 결과입니다. 우리는 다른 통합 테스트 파일과 일부 코드를 공유하고 싶었을 뿐입니다. 테스트 출력에 common가 나타나지 않도록 하려면 tests/common.rs를 만드는 대신 tests/common/mod.rs를 만듭니다. 이제 프로젝트 디렉토리는 다음과 같은 구조를 가집니다.

├── Cargo.lock
├── Cargo.toml
├── src
│   └── lib.rs
└── tests
    ├── common
    │   └── mod.rs
    └── integration_test.rs

이것은 7장에서 “대체 파일 경로”에서 언급한, Rust가 이해하는 오래된 명명 규칙입니다. 이렇게 파일을 이름 붙이면 Rust는 common 모듈을 통합 테스트 파일로 취급하지 않습니다. setup 함수 코드를 tests/common/mod.rs로 이동하고 tests/common.rs 파일을 삭제하면, 테스트 출력에 해당 섹션이 더 이상 표시되지 않습니다. tests 디렉토리의 하위 디렉토리에 있는 파일은 별도의 크레이트로 컴파일되지 않으며, 테스트 출력에 섹션이 생성되지도 않습니다.

우리가 창조된 후 테스트/공통/mod.rs, 우리는 모듈로 통합 테스트 파일에서 사용할 수 있습니다. 다음은 호출의 예입니다 setup 에서 기능 it_adds_two 시험에서 테스트/통합_test.rs:

파일 이름: tests/integration_test.rs

use adder::add_two;

mod common;

#[test]
fn it_adds_two() {
    common::setup();

    let result = add_two(2);
    assert_eq!(result, 4);
}

mod common; 선언은 Listing 7-21에서 보여준 모듈 선언과 동일합니다. 그런 다음 테스트 함수에서 common::setup() 함수를 호출할 수 있습니다.

바이너리 크레이트에 대한 통합 테스트

프로젝트가 src/main.rs 파일만 포함하고 src/lib.rs 파일이 없는 바이너리 크레이트라면, tests 디렉토리에 통합 테스트를 만들 수 없고 use 문으로 src/main.rs 파일에 정의된 함수를 스코프에 가져올 수도 없습니다. 라이브러리 크레이트만이 다른 크레이트에서 사용할 수 있는 함수를 노출하며, 바이너리 크레이트는 단독으로 실행되도록 설계되어 있습니다.

바이너리를 제공하는 Rust 프로젝트가 src/lib.rs 파일에 있는 로직을 호출하는 간단한 src/main.rs 파일 구조를 갖는 이유 중 하나가 바로 이것입니다. 이 구조를 사용하면 통합 테스트에서 use를 통해 라이브러리 크레이트의 핵심 기능을 스코프에 포함시켜 테스트할 수 있습니다. 핵심 기능이 정상적으로 작동한다면 src/main.rs 파일의 소량의 코드도 자연스럽게 작동하므로, 이 소량의 코드를 별도로 테스트할 필요가 없습니다.

요약

Rust의 테스트 기능은 코드가 어떻게 동작해야 하는지 명시하여, 코드를 변경하더라도 예상대로 계속 작동하는지 확인할 수 있는 방법을 제공합니다. 단위 테스트는 라이브러리의 각 부분을 독립적으로 실행하며 비공개 구현 세부 사항까지 테스트할 수 있습니다. 통합 테스트는 라이브러리의 여러 부분이 함께 올바르게 작동하는지 확인하며, 외부 코드가 사용하는 것과 동일한 방식으로 라이브러리의 공개 API를 통해 코드를 테스트합니다. Rust의 타입 시스템과 소유권 규칙이 일부 버그를 방지하는 데 도움이 되지만, 코드가 기대하는 대로 동작하는지와 관련된 논리 버그를 줄이기 위해 테스트는 여전히 중요합니다.

이 장과 이전 장에서 배운 지식을 결합하여 프로젝트를 진행해 보겠습니다!
