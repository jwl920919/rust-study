The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

모듈화 및 오류 처리 개선하기 위한 리팩토링

프로그램을 개선하기 위해, 프로그램의 구조와 잠재적 오류 처리 방식과 관련된 네 가지 문제를 해결하겠습니다. 첫째, main 함수는 현재 두 가지 작업을 수행합니다. 인수를 파싱하고 파일을 읽는 것입니다. 프로그램이 커질수록 main 함수가 담당하는 개별 작업의 수도 늘어납니다. 함수가 담당하는 책임이 많아지면, 해당 함수를 이해하고, 테스트하며, 일부 기능을 깨뜨리지 않고 변경하는 것이 어려워집니다. 따라서 각 함수가 하나의 작업만 담당하도록 기능을 분리하는 것이 가장 좋습니다.

이 문제는 두 번째 문제와도 관련이 있습니다. query와 file_path는 프로그램의 설정 변수이지만, contents와 같은 변수는 프로그램의 로직을 수행하는 데 사용됩니다. main 함수가 길어질수록 스코프에 포함해야 하는 변수의 수도 많아집니다. 스코프에 있는 변수가 많을수록 각 변수의 목적을 추적하기가 어려워집니다. 설정 변수를 하나의 구조체로 묶어두면 그 목적을 명확히 할 수 있습니다.

세 번째 문제는, 파일 읽기 실패 시 오류 메시지를 출력하기 위해 expect를 사용했지만, 출력되는 오류 메시지는 단순히 Should have been able to read the file일 뿐이라는 점입니다. 파일 읽기는 여러 가지 이유로 실패할 수 있습니다. 예를 들어 파일이 존재하지 않거나, 파일을 열 권한이 없을 수 있습니다. 현재는 어떤 상황이든 동일한 오류 메시지만 출력하므로, 사용자에게 유용한 정보를 제공하지 못합니다.

넷째, expect를 사용하여 오류를 처리합니다. 사용자가 충분한 인수를 지정하지 않고 프로그램을 실행하면 Rust에서 index out of bounds 오류가 발생하며, 이 오류 메시지는 문제를 명확하게 설명하지 못합니다. 오류 처리 코드가 모두 한 곳에 모여 있으면 향후 유지보수 담당자가 오류 처리 로직을 변경할 때 코드를 한 곳만 확인하면 되므로 가장 좋습니다. 또한 오류 처리 코드를 한 곳에 모으면 최종 사용자에게 의미 있는 메시지를 출력할 수 있도록 보장할 수 있습니다.

프로젝트를 리팩토링하여 이 네 가지 문제를 해결해 보겠습니다.

바이너리 프로젝트에서 관심사 분리하기

여러 작업을 main 함수에 할당하는 조직적 문제는 많은 바이너리 프로젝트에서 흔히 볼 수 있습니다. 그 결과, 많은 Rust 개발자들은 main 함수가 커지기 시작하면 바이너리 프로그램의 개별 관심사를 분리하는 것이 유용하다고 생각합니다. 이 과정은 다음과 같은 단계를 포함합니다.

  • 프로그램을 main.rs 파일과 lib.rs 파일로 나누고, 프로그램 로직을 lib.rs로 이동하십시오.
  • 명령줄 파싱 로직이 작다면 main 함수에 그대로 두어도 됩니다.
  • 명령줄 파싱 로직이 복잡해지기 시작하면 main 함수에서 다른 함수나 타입으로 추출하십시오.

이 과정을 거친 후 main 함수에 남아 있는 책임은 다음으로 제한되어야 합니다:

  • 인자 값을 전달하여 명령줄 파싱 로직을 호출하는 것
  • 기타 설정을 구성하는 것
  • lib.rs의 run 함수를 호출하는 것
  • run가 오류를 반환하는 경우 오류를 처리하는 것

이 패턴은 관심사를 분리하는 것입니다. main.rs는 프로그램 실행을 담당하고, lib.rs는 해당 작업의 모든 로직을 담당합니다. main 함수를 직접 테스트할 수 없기 때문에, 이 구조를 사용하면 프로그램의 모든 로직을 main 함수에서 분리하여 테스트할 수 있습니다. main 함수에 남아 있는 코드는 읽어서 정확성을 확인할 수 있을 정도로 충분히 작습니다. 이제 이 과정을 따라 프로그램을 재구성해 보겠습니다.

설정 값 그룹화

parse_config 함수를 한 단계 더 개선할 수 있습니다. 현재 이 함수는 튜플을 반환하지만, 반환된 튜플을 즉시 개별 요소로 분해하고 있습니다. 이는 아직 적절한 추상화를 찾지 못했음을 시사합니다.

개선 여지가 있음을 보여주는 또 다른 지표는 config 함수의 parse_config 부분입니다. 이 부분은 반환하는 두 값이 서로 관련이 있으며, 둘 다 하나의 구성 값에 속한다는 의미를 내포합니다. 현재 우리는 두 값을 튜플로 묶는 것 외에는 데이터 구조를 통해 이러한 의미를 전달하지 못하고 있습니다. 대신 두 값을 하나의 구조체에 넣고, 각 구조체 필드에 의미 있는 이름을 부여하겠습니다. 이렇게 하면 이 코드를 유지보수할 후속 개발자가 서로 다른 값들이 어떻게 관련되어 있는지, 그리고 각 값의 목적을 이해하기 쉬워집니다.

우리의 build 함수는 성공 시 Result 인스턴스를, 실패 시 문자열 리터럴을 포함하는 Config 을 반환합니다. 오류 값은 항상 'static 라이프타임을 가진 문자열 리터럴이 됩니다. 'static

함수 본문에서 두 가지 변경 사항을 했습니다. 사용자가 충분한 인수를 전달하지 않을 때 panic!를 호출하는 대신 Err 값을 반환하고, Config 반환 값을 Ok로 감쌌습니다. 이러한 변경 사항은 함수가 새로운 타입 시그니처에 맞게 조정되도록 합니다.

Err에서 Config::build 값을 반환하면, main 함수가 Result 함수에서 반환된 build 값을 처리하고 오류인 경우 프로세스를 더 깔끔하게 종료할 수 있습니다.

Config::build 호출 및 오류 처리

오류 케이스를 처리하고 사용자 친화적인 메시지를 출력하려면 Listing 12-10에서 보인 것처럼 main가 반환하는 Result을 처리하도록 Config::build를 업데이트해야 합니다. 또한 panic!에서 0이 아닌 오류 코드로 커맨드 라인 도구를 종료하는 책임을 제거하고, 대신 직접 구현합니다. 0이 아닌 종료 상태는 우리 프로그램을 호출한 프로세스에게 프로그램이 오류 상태로 종료되었음을 알리는 관례입니다.

이 목록에서 아직 자세히 다루지 않은 메서드인 unwrap_or_else을 사용했습니다. 이 메서드는 표준 라이브러리에 의해 Result<T, E>에 정의되어 있습니다. unwrap_or_else을 사용하면 사용자 정의, 비panic! 오류 처리를 정의할 수 있습니다. Result가 Ok 값인 경우, 이 메서드의 동작은 unwrap과 유사합니다. Ok이 감싸고 있는 내부 값을 반환합니다. 그러나 값이 Err 값인 경우, 이 메서드는 클로저의 코드를 호출합니다. 클로저는 우리가 정의하고 unwrap_or_else의 인수로 전달하는 익명 함수입니다. 클로저에 대해 더 자세히 다루는 내용은 13장에서 확인하세요. 지금은 unwrap_or_else이 Err의 내부 값을 클로저에 전달한다는 것만 알면 됩니다. 이 경우 12-9 목록에서 추가한 정적 문자열 "not enough arguments"이며, 세로 파이프 사이에 나타나는 인수 err를 통해 전달됩니다. 그러면 클로저의 코드는 실행될 때 err 값을 사용할 수 있습니다.

표준 라이브러리의 use을 스코프에 포함시키기 위해 새로운 process 문을 추가했습니다. 오류 발생 시 실행될 클로저의 코드는 단 두 줄입니다. err 값을 출력한 후 process::exit을 호출합니다. process::exit 함수는 프로그램을 즉시 중단하고 전달된 숫자를 종료 상태 코드로 반환합니다. 이는 panic!에 기반한 처리와 유사하지만, Listing 12-8에서 사용했던 경우와 달리 추가적인 출력이 발생하지 않습니다. 다음을 시도해 보겠습니다:

run에서 오류 반환하기

나머지 프로그램 로직을 run 함수로 분리했으므로, Listing 12-9에서 Config::build에 적용했던 것처럼 오류 처리를 개선할 수 있습니다. expect를 호출하여 프로그램을 패닉에 빠뜨리는 대신, run 함수는 문제가 발생하면 Result<T, E>를 반환합니다. 이를 통해 오류 처리 로직을 사용자 친화적인 방식으로 main에 더 통합할 수 있습니다. Listing 12-12는 run의 시그니처와 본문에 필요한 변경 사항을 보여줍니다.

우리는 여기서 세 가지 중요한 변화를 만들었습니다. 첫째, 우리는 반환 유형을 변경했습니다. run 기능 2 Result<(), Box<dyn Error>>. 이 기능은 이전에 단위 유형을 돌려보냈다, ()그리고 우리는 그 값을 다음과 같이 반환합니다. Ok 사례.

오류 타입으로 트레이트 객체인 Box<dyn Error>을 사용했습니다(그리고 상단의 use 문장으로 std::error::Error을 스코프에 가져왔습니다). 트레이트 객체에 대해 더 자세히 다루는 내용은 18장에서 확인하세요. 지금은 Box<dyn Error>이 함수가 Error 트레이트를 구현하는 타입을 반환하지만, 반환 값이 어떤 특정 타입인지 지정할 필요가 없다는 것만 알면 됩니다. 이를 통해 서로 다른 오류 상황에서 서로 다른 타입의 오류 값을 반환할 수 있는 유연성을 제공합니다. dyn 키워드는 동적의 줄임말입니다.

둘째, 9장에서 논의했듯이, expect 호출을 ? 연산자로 대체했습니다. 오류에서 panic!하는 대신, ?은 호출자가 처리하도록 현재 함수에서 오류 값을 반환합니다.

셋째, run 함수는 성공 케이스에서 Ok 값을 반환합니다. 시그니처에서 run 함수의 성공 타입을 ()로 선언했으므로, 유닛 타입 값을 Ok 값으로 감싸야 합니다. 이 Ok(()) 구문은 처음에는 다소 낯설 수 있습니다. 하지만 이렇게 ()를 사용하는 것은 run을 부수 효과(side effect)만을 위해 호출한다는 것을 나타내는 관용적인 방식입니다. 즉, 우리가 필요로 하는 값을 반환하지 않는다는 뜻입니다.

run에서 반환된 오류를 main에서 처리하기runmain

오류를 확인하고 처리하는 방법은 Listing 12-10에서 Config::build에 사용했던 것과 유사하지만, 약간의 차이가 있습니다:

파일 이름: src/main.rs

use std::env;
use std::error::Error;
use std::fs;
use std::process;

fn main() {
    // --snip--

    let args: Vec<String> = env::args().collect();

    let config = Config::build(&args).unwrap_or_else(|err| {
        println!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    println!("Searching for {}", config.query);
    println!("In file {}", config.file_path);

    if let Err(e) = run(config) {
        println!("Application error: {e}");
        process::exit(1);
    }
}

fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;

    println!("With text:\n{contents}");

    Ok(())
}

struct Config {
    query: String,
    file_path: String,
}

impl Config {
    fn build(args: &[String]) -> Result<Config, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();

        Ok(Config { query, file_path })
    }
}

if let 대신 unwrap_or_else을 사용하여 run가 Err 값을 반환하는지 확인하고, 해당 값이 process::exit(1)인 경우 run을 호출합니다. unwrap 함수는 Config::build이 Config 인스턴스를 반환하는 것과 같은 방식으로, 우리가 언래핑(unwrap)을 원하는 값을 반환하지 않습니다. run은 성공 시 ()을 반환하므로, 우리는 오류 감지에만 관심이 있을 뿐 unwrap_or_else을 통해 언래핑된 값(())을 반환할 필요가 없습니다.

if let와 unwrap_or_else 함수의 본문은 두 경우 모두 동일합니다.

코드를 라이브러리 크레이트로 분리하기

우리의 minigrep 프로젝트는 지금까지 좋아 보입니다! 이제 src / main.rs 파일을 분할하고 일부 코드를 src / lib.rs 파일에 넣습니다. 그렇게하면 코드를 테스트하고 src / main.rs 파일을 가질 수 있습니다.

src/main.rs 대신 src/lib.rs에서 텍스트 검색을 담당하는 코드를 정의해 보겠습니다. 이렇게 하면 우리(또는 minigrep 라이브러리를 사용하는 다른 사용자)는 minigrep 바이너리보다 더 다양한 컨텍스트에서 검색 함수를 호출할 수 있습니다.

먼저 Listing 12-13과 같이 src/lib.rs에 search 함수 서명을 정의하고, unimplemented! 매크로를 호출하는 함수 본문(body)을 작성하겠습니다. 구현을 채울 때 서명을 더 자세히 설명하겠습니다.

함수 정의에 pub 키워드를 붙여 search을 라이브러리 크레이트의 공개 API 일부로 지정했습니다. 이제 바이너리 크레이트에서 사용할 수 있고 테스트할 수 있는 라이브러리 크레이트를 갖추게 되었습니다!

이제 src/lib.rs에 정의된 코드를 src/main.rs에 있는 바이너리 크레이트의 스코프(scope)로 가져와서 Listing 12-14와 같이 호출해야 합니다.

use minigrep::search을 추가하여 라이브러리 크레이트의 search 함수를 바이너리 크레이트의 스코프에 가져옵니다. 그런 다음, run 함수에서 파일의 내용을 출력하는 대신, search 함수를 호출하고 config.query 값과 contents를 인자로 전달합니다. 이후 run는 for 루프를 사용하여 search에서 반환된 쿼리에 일치하는 각 줄을 출력합니다. 이 시점에서 오류가 발생하지 않는 경우 프로그램이 검색 결과만 출력하도록, println! 함수에 있는 쿼리와 파일 경로를 표시하던 main 호출도 제거하는 것이 좋습니다.

검색 함수는 출력이 일어나기 전에 모든 결과를 반환할 벡터에 수집합니다. 이 구현 방식은 큰 파일을 검색할 때 결과를 찾은 즉시 출력하지 않기 때문에 결과를 표시하는 데 느릴 수 있습니다. 13장에서 반복자를 사용하여 이 문제를 해결하는 가능한 방법에 대해 논의하겠습니다.
