The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

Crates.io에 크레이트 게시

우리는 크레이트.io의 패키지를 프로젝트의 종속성으로 사용했지만 자체 패키지를 게시하여 다른 사람들과 코드를 공유 할 수도 있습니다. 크레이트.io의 크레이트 레지스트리는 패키지의 소스 코드를 배포하므로 주로 오픈 소스 코드를 호스팅합니다.

러스트와 Cargo는 사람들이 쉽게 찾고 사용할 수 있게 해주는 기능들을 가지고 있습니다. 이 기능들 중 몇 가지에 대해 다음에 이야기하고 패키지를 게시하는 방법을 설명하겠습니다.

유용한 문서 코멘트 만들기

패키지를 정확하게 문서화하면 다른 사용자가 언제 어떻게 사용하는지 알 수 있으므로 문서를 작성하는 데 시간을 투자 할 가치가 있습니다. 3 장에서는 두 개의 슬래시 인 //를 사용하여 러스트 코드를 주석하는 방법에 대해 논의했습니다. 러스트는 또한 HTML 문서를 생성하는 편리한 문서 주석으로 알려진 문서 주석에 대한 특정 종류의 주석을 가지고 있습니다. HTML은 크레이트에 관심이있는 프로그래머가 크레이트를 사용하는 방법에 반대하는 프로그래머를위한 문서 주석의 내용을 표시합니다.

문서 주석은 두 개 대신 세 개의 슬래시인 ///를 사용하고 텍스트 서식 지정을 위한 마크다운 표기법을 지원합니다. 문서 주석을 항목 바로 앞에 배치합니다. 목록 14-1은 add_one라는 이름의 상자에서 my_crate 함수에 대한 문서 주석을 보여줍니다.

여기서, 우리는 무엇에 대한 설명을 제공합니다. add_one 함수는 제목으로 섹션을 시작합니다. Examples그리고 어떻게 사용하는지를 보여주는 코드를 제공한다. add_one 함수. 우리는 실행하여이 문서 주석에서 HTML 문서를 생성할 수 있습니다 cargo doc. 이 명령은 rustdoc 러스트와 함께 배포된 툴은 생성된 HTML 문서를 목표/의사 디렉토리.

편의를 위해 cargo doc --open를 실행하면 현재 크레이트의 문서 (뿐만 아니라 크레이트의 모든 종속성에 대한 문서)에 대한 HTML을 작성하고 웹 브라우저에서 결과를 엽니 다. add_one 기능으로 이동하면 그림 14-1과 같이 문서 주석의 텍스트가 렌더링되는 방법을 볼 수 있습니다.

일반적으로 사용되는 섹션

Listing 14-1에서 # Examples Markdown 제목을 사용하여 HTML에서 "Examples"라는 제목을 가진 섹션을 만들었습니다. 다음은 크레이트 작성자가 문서에서 일반적으로 사용하는 몇 가지 다른 섹션입니다.

  • 패닉: 이 시나리오에서는 문서화된 함수가 패닉에 빠질 수 있습니다. 자신의 프로그램이 패닉에 빠지지 않도록 하려면 이러한 상황에서 함수를 호출하지 않아야 합니다.
  • 오류: 함수가 Result를 반환하는 경우 발생할 수 있는 오류의 종류와 이러한 오류가 반환될 수 있는 조건을 설명하는 것이 호출자에게 도움이 될 수 있습니다.
  • 안전: 함수가 unsafe를 호출하는 경우 (20 장에서 안전에 대해 논의함), 함수가 안전하지 않은 이유를 설명하는 섹션이 있어야하며 함수가 호출자가 유지하기를 기대하는 불변을 포함해야합니다.

대부분의 문서 코멘트는 이러한 모든 섹션을 필요로 하지 않지만, 이것은 코드 사용자가 알고 싶어하는 측면을 상기시키기 위한 좋은 체크리스트입니다.

문서 주석을 테스트로

문서 주석에 예제 코드 블록을 추가하면 라이브러리를 사용하는 방법을 보여주는 데 도움이 될 수 있으며 추가 보너스가 있습니다. cargo test documentation에서 tests로 코드 예제를 실행합니다! example을 사용한 documentation보다 더 좋은 것은 없습니다. 그러나 documentation이 작성된 이후 코드가 변경되었기 때문에 작동하지 않는 예제보다 더 나쁜 것은 없습니다. 실행하면 cargo test 상기 문서화하는 단계는 Wherein the documentation for the add_one Listing 14-1의 함수에서, 우리는 다음과 같은 테스트 결과에서 한 섹션을 볼 것입니다:

   Doc-tests my_crate

running 1 test
test src/lib.rs - add_one (line 5) ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.27s

이제 함수나 예제를 변경하여 예제 패닉에서 assert_eq!를 실행하고 cargo test를 다시 실행하면 doc 테스트에서 예제와 코드가 서로 동기화되지 않았음을 알 수 있습니다!

편리한 공용 API 내보내기

공개 API의 구조는 크레이트를 게시할 때 중요한 고려 사항입니다. 크레이트를 사용하는 사람들은 당신보다 구조에 익숙하지 않으며 크레이트에 모듈 계층 구조가 큰 경우 사용하고자 하는 조각을 찾는 데 어려움이 있을 수 있습니다.

7 장에서 우리는 다음을 사용하여 항목을 공개하는 방법을 다루었습니다. pub 키워드와 함께 범위로 항목을 가져 오는 방법 use keyword. 그러나 크레이트를 개발하는 동안 의미가있는 구조는 사용자에게 매우 편리하지 않을 수 있습니다. 여러 레벨이 포함 된 계층 구조에서 구조체를 구성 할 수도 있지만 계층 구조에서 깊이 정의 한 유형을 사용하려는 사람들은 해당 유형을 찾는 데 어려움을 겪을 수 있습니다. 그들은 또한 입력해야 할 때 짜증이 날 수도 있습니다. use my_crate::some_module::another_module::UsefulType; 보다는 use my_crate::UsefulType;.

좋은 소식은 다른 사람들이 다른 라이브러리에서 사용하는 구조가 편리하지 않다면 내부 조직을 재배열 할 필요가 없다는 것입니다. 대신 pub use를 사용하여 개인 구조와 다른 공용 구조를 만들기 위해 항목을 다시 내보낼 수 있습니다. 재수출은 한 위치에서 공용 항목을 가져 와서 다른 위치에서 대신 정의 된 것처럼 다른 위치에서 공개합니다.

예를 들어, 우리가 이름을 가진 도서관을 만들었다고 합시다. art 이 라이브러리에는 두 개의 모듈이 있습니다. a kinds 두 개의 열거형을 포함하는 모듈Name PrimaryColor 그리고 SecondaryColor 그리고 A utils 이름이 지정된 함수를 포함하는 모듈 mixListing 14-3에 나와 있는 내용입니다.

그림 14-3은 cargo doc에 의해 생성된 이 크레이트에 대한 문서의 첫 페이지가 어떻게 생겼는지 보여줍니다.

Figure 14-3: 문서의 첫 페이지 art 상기 리스트는 The list is kinds 그리고 utils 모듈

이 라이브러리에 의존하는 또 다른 크레이트는 use 상기 아이템들은 The items from art into scope, 현재 정의된 모듈 구조를 지정합니다. Listing 14-4는 다음을 사용하는 크레이트의 예를 보여줍니다. PrimaryColor 그리고 mix 상기 아이템은 From the art 크레이트.

많은 중첩 된 모듈이있는 경우 pub use를 사용하여 최상위 수준의 유형을 다시 내보내면 크레이트를 사용하는 사람들의 경험에 큰 차이를 만들 수 있습니다. pub use의 또 다른 일반적인 용도는 크레이트의 정의 부분을 크레이트의 공개 API로 만들기 위해 현재 크레이트의 종속성에 대한 정의를 다시 내보내는 것입니다.

유용한 공개 API 구조를 만드는 것은 과학보다 더 예술이며 사용자에게 가장 적합한 API를 찾기 위해 반복 할 수 있습니다. pub use를 선택하면 내부적으로 크레이트를 구성하는 방법에 유연성을 제공하고 사용자에게 제시하는 것과 내부 구조를 분리 할 수 있습니다. 내부 구조가 공개 API와 다른지 확인하기 위해 설치 한 크레이트 코드를 살펴보십시오.

Crates.io 계정 설정

크레이트를 게시하기 전에 계정을 만들어야 합니다. 크레이트.io 무시 그리고 API 토큰을 얻을. 이렇게하려면에서 홈 페이지를 방문 크레이트.io 무시 그리고 GitHub 계정을 통해 로그인합니다. (GitHub 계정은 현재 필수이지만 나중에 계정을 만드는 다른 방법을 지원할 수 있습니다.) 로그인 한 후에는 다음에서 계정 설정을 방문하십시오. https://crates.io/me/에서 다운로드 무시 그리고 API 키를 검색합니다. 그런 다음 cargo login 메시지가 표시되면 다음과 같이 명령 및 API 키를 붙여 넣습니다.

$ cargo login
abcdefghijklmnopqrstuvwxyz012345

이 명령은 Cargo에게 API 토큰을 알리고 ~/.cargo/credentials.toml에 로컬로 저장합니다. 이 토큰은 비밀입니다. 다른 사람과 공유하지 마십시오. 어떤 이유로 든 다른 사람과 공유하면 취소하고 크레이트.io에 새 토큰을 생성해야합니다.

새 상자에 메타데이터 추가

게시하려는 크레이트가 있다고 가정 해 봅시다. 게시하기 전에 크레이트의 Cargo.toml 파일의 [package] 섹션에 메타데이터를 추가해야합니다.

크레이트는 고유 한 이름이 필요합니다. 크레이트에서 작업하는 동안 현지에서 원하는대로 크레이트의 이름을 지정할 수 있습니다. 그러나 크레이트 이름은 크레이트.io 무시 선착순으로 할당됩니다. 크레이트 이름이 지정되면 다른 사람이 그 이름을 가진 크레이트를 게시 할 수 없습니다. 크레이트를 게시하기 전에 사용하려는 이름을 검색하십시오. 이름이 사용 된 경우 다른 이름을 찾고 편집해야합니다. name 에서 필드는 카고.toml 아래 파일 [package] 섹션은 다음과 같이 게시를 위해 새 이름을 사용합니다.

파일명: Cargo.toml

[package]
name = "guessing_game"

SPDX에 표시되지 않는 라이센스를 사용하려면 해당 라이센스의 텍스트를 파일에 배치하고 프로젝트에 파일을 포함시킨 다음 license-file를 사용하여 license 키를 사용하는 대신 해당 파일의 이름을 지정해야 합니다.

프로젝트에 적합한 라이선스가 무엇인지에 대한 지침은 이 책의 범위를 벗어납니다. 러스트 커뮤니티의 많은 사람들이 MIT OR Apache-2.0의 이중 라이선스를 사용하여 러스트와 같은 방식으로 프로젝트를 라이선스합니다. 이 연습은 프로젝트에 대한 여러 라이선스를 가지기 위해 OR로 구분된 여러 라이선스 식별자를 지정할 수도 있음을 보여줍니다.

고유한 이름, 버전, 설명 및 라이센스를 추가하면 게시할 준비가 된 프로젝트의 Cargo.toml 파일이 다음과 같이 보일 수 있습니다.

파일명: Cargo.toml

[package]
name = "guessing_game"
version = "0.1.0"
edition = "2024"
description = "A fun game where you guess what number the computer has chosen."
license = "MIT OR Apache-2.0"

[dependencies]

Crates.io에 게시

계정을 만들고, API 토큰을 저장하고, 크레이트 이름을 선택하고, 필요한 메타데이터를 지정했으니 이제 게시할 준비가 되었습니다! 크레이트 게시는 다른 사람들이 사용할 수 있도록 크레이트.io에 특정 버전을 업로드합니다.

게시는 영구적이기 때문에 주의해야 합니다. 버전을 덮어쓸 수 없으며 특정 상황을 제외하고는 코드를 삭제할 수 없습니다. Crates.io의 주요 목표 중 하나는 크레이트.io의 크레이트에 의존하는 모든 프로젝트의 빌드가 계속 작동하도록 코드의 영구 아카이브 역할을 하는 것입니다. 버전 삭제를 허용하면 해당 목표를 달성할 수 없습니다. 그러나 게시할 수 있는 크레이트 버전의 수에는 제한이 없습니다.

기존 크레이트의 새 버전 게시

크레이트를 변경하고 새 버전을 출시 할 준비가되면 Cargo.toml 파일에 지정된 version 값을 변경하고 다시 게시하십시오. 시맨틱 버전 규칙를 사용하여 변경 한 종류의 변경 사항에 따라 적절한 다음 버전 번호를 결정하십시오. 그런 다음 cargo publish를 실행하여 새 버전을 업로드하십시오.

Crates.io에서 버전 제거

이전 버전의 크레이트를 제거 할 수는 없지만 향후 프로젝트가 새로운 종속성으로 추가되는 것을 막을 수 있습니다. 이것은 크레이트 버전이 한 가지 이유 또는 다른 이유로 깨질 때 유용합니다. 이러한 상황에서 Cargo는 크레이트 버전을 yanking하는 것을 지원합니다.

Yanking 버전은 새 프로젝트가 해당 버전에 따라 달라지는 것을 방지하면서 기존 프로젝트에 의존하는 모든 프로젝트가 계속 진행되도록 합니다. 기본적으로 yank는 Cargo.lock을 사용하는 모든 프로젝트가 중단되지 않으며 생성 된 향후 Cargo.lock 파일은 yanked 버전을 사용하지 않음을 의미합니다.

크레이트의 버전을 yank하려면 이전에 게시 한 크레이트의 디렉토리에서 cargo yank를 실행하고 yank를 원하는 버전을 지정하십시오. 예를 들어 guessing_game 버전 1.0.1이라는 크레이트를 게시하고 yank를 원한다면 guessing_game의 프로젝트 디렉토리에서 다음을 실행합니다.

$ cargo yank --vers 1.0.1
    Updating crates.io index
        Yank guessing_game@1.0.1

--undo를 명령에 추가하면 yank를 실행 취소하고 버전에 따라 프로젝트를 다시 시작할 수 있습니다.

$ cargo yank --vers 1.0.1 --undo
    Updating crates.io index
      Unyank guessing_game@1.0.1

yank는 어떤 코드도 삭제하지 않습니다. 예를 들어, 실수로 업로드 된 비밀을 삭제할 수 없습니다. 그런 일이 발생하면 즉시 그 비밀을 재설정해야합니다.
