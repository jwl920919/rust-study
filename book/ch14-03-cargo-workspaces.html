The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

화물 작업 영역

12장에서는 바이너리 크레이트와 라이브러리 크레이트를 포함한 패키지를 만들었습니다. 프로젝트가 개발됨에 따라 라이브러리 크레이트가 계속 커질 수 있으며 패키지를 여러 라이브러리 크레이트로 더 분할하고 싶을 수도 있습니다. Cargo는 동시에 개발되는 여러 관련 패키지를 관리하는 데 도움이 되는 작업 공간이라는 기능을 제공합니다.

작업 공간 만들기

A 작업 영역 같은 것을 공유하는 패키지의 집합입니다. 화물.잠금 그리고 출력 디렉토리. 작업 공간을 사용하여 프로젝트를 만들어 봅시다. 작업 공간의 구조에 집중할 수 있도록 사소한 코드를 사용할 것입니다. 작업 공간을 구성하는 데는 여러 가지 방법이 있으므로 하나의 일반적인 방법을 보여 드리겠습니다. 바이너리와 두 개의 라이브러리를 포함하는 작업 공간을 갖게 될 것입니다. 주요 기능을 제공하는 바이너리는 두 개의 라이브러리에 따라 다릅니다. 하나의 라이브러리는 add_one 도서관 및 다른 도서관 add_two 함수. 이 세 개의 크레이트는 동일한 작업 공간의 일부가 될 것입니다. 우리는 작업 공간을위한 새로운 디렉토리를 만드는 것으로 시작할 것입니다.

$ mkdir add
$ cd add

다음으로, In the 추가 디렉토리, 우리는 카고.toml 전체 작업 공간을 구성합니다 파일. 이 파일은이 없습니다 [package] 섹션. 대신 a로 시작합니다. [workspace] 작업 공간에 멤버를 추가할 수 있는 섹션입니다. 또한 작업 공간에서 Cargo의 가장 훌륭한 최신 버전의 Resolver 알고리즘을 사용할 수 있는 지점을 만듭니다. resolver 가치 "3":

파일명: Cargo.toml

[workspace]
resolver = "3"

다음으로, 우리는 adder 실행하여 이진 크레이트 cargo new 내부 The 추가 디렉터리:

$ cargo new adder
     Created binary (application) `adder` package
      Adding `adder` as member of workspace at `file:///projects/add`

실행 중 cargo new 또한 작업 공간 내부에는 새로 만든 패키지가 자동으로 추가됩니다. members 에 있는 열쇠 [workspace] 작업 공간에서의 정의 카고.toml, 이렇게:

[workspace]
resolver = "3"
members = ["adder"]

이 시점에서 cargo build를 실행하여 작업 공간을 빌드할 수 있습니다. add 디렉토리의 파일은 다음과 같아야 합니다.

├── Cargo.lock
├── Cargo.toml
├── adder
│   ├── Cargo.toml
│   └── src
│       └── main.rs
└── target

작업 공간에는 컴파일 된 아티팩트가 배치 될 최상위 레벨의 하나의 대상 디렉토리가 있습니다. adder 패키지에는 자체 대상 디렉토리가 없습니다. adder 디렉토리 내부에서 cargo build를 실행하더라도 컴파일 된 아티팩트는 add/adder/target이 아닌 add/target으로 끝납니다. 각 크레이트에 각 크레이트의 작업 영역이 있어야하기 때문에 대상 디렉토리를 재구성합니다.

작업 공간에서 두 번째 패키지 만들기Create the second package in the workspace

다음으로 작업 공간에 다른 멤버 패키지를 만들고 add_one라고 부르겠습니다. add_one라는 이름의 새 라이브러리 크레이트를 생성합니다.

$ cargo new add_one --lib
     Created library `add_one` package
      Adding `add_one` as member of workspace at `file:///projects/add`

이제 최상위 Cargo.toml에는 add_one 경로가 members 목록에 포함됩니다.

파일명: Cargo.toml

[workspace]
resolver = "3"
members = ["adder", "add_one"]

이제 add 디렉토리에 다음과 같은 디렉토리와 파일이 있어야 합니다:

├── Cargo.lock
├── Cargo.toml
├── add_one
│   ├── Cargo.toml
│   └── src
│       └── lib.rs
├── adder
│   ├── Cargo.toml
│   └── src
│       └── main.rs
└── target

add_one/src/lib.rs 파일에 add_one 함수를 추가해 보겠습니다.

파일 이름: add_one/src/lib.rs

pub fn add_one(x: i32) -> i32 {
    x + 1
}

이제 우리는 가질 수 있습니다. adder 우리의 이진과 패키지는에 따라 달라집니다 add_one 라이브러리가 있는 패키지입니다. 먼저 경로 의존성을 추가해야 합니다. add_one 오시는 길 가산기/Cargo.toml.

파일 이름: adder/Cargo.toml

[dependencies]
add_one = { path = "../add_one" }

Cargo는 작업 공간의 크레이트가 서로 의존한다고 가정하지 않으므로 종속 관계에 대해 명시적이어야 합니다.

다음 다음 글: Use the add_one 함수 (From) add_one 크레이트)에서 adder 크레이트. 열기 애드너/src/main.rs 파일 및 변경 main 전화 걸기 Function to Call add_one Listing 14-7과 같은 기능입니다.

최상위 추가 디렉토리에서 cargo build를 실행하여 작업 공간을 구축합시다!

$ cargo build
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.22s

add 디렉토리에서 바이너리 크레이트를 실행하기 위해, 작업 공간에서 -p 인수와 cargo run를 사용하여 실행할 패키지를 지정할 수 있습니다:

$ cargo run -p adder
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running `target/debug/adder`
Hello, world! 10 plus one is 11!

이것은 add_one 크레이트에 의존하는 adder/src/main.rs에서 코드를 실행한다.

외부 패키지에 따라 다름

작업 공간은 하나만 가지고 있음을 주목하십시오. 화물.잠금 a 를 갖는 것보다는, 상위 레벨에서의 파일 화물.잠금 각 크레이트의 디렉토리에. 이것은 모든 크레이트가 모든 의존성의 동일한 버전을 사용하고 있음을 보장한다. rand 패키지는 The 가산기/Cargo.toml 그리고 add_one/Cargo.toml(하나 추가) 파일, 화물은 1개의 버전에 그 둘 다의 결심할 것이다 rand 그리고 그 중 하나에 기록 화물.잠금. 작업 공간의 모든 크레이트를 동일한 종속성을 사용하여 만들면 크레이트가 항상 서로 호환된다는 것을 의미합니다. rand 크레이트에 의하여 [dependencies] 에 있는 단면도 add_one/Cargo.toml(하나 추가) 우리가 사용할 수 있도록 파일 rand 에 있는 크레이트 add_one 크레이트:

파일 이름: add_one/Cargo.toml

[dependencies]
rand = "0.10.1"

이제 add_one/src/lib.rs 파일에 use rand;를 추가 할 수 있으며 추가 디렉토리에서 cargo build를 실행하여 전체 작업 공간을 빌드하면 rand 크레이트가 가져 와서 컴파일됩니다. 우리가 가져온 rand를 언급하지 않기 때문에 하나의 경고를 받게됩니다.

$ cargo build
    Updating crates.io index
  Downloaded rand v0.10.1
   --snip--
   Compiling rand v0.10.1
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
warning: unused import: `rand`
 --> add_one/src/lib.rs:1:5
  |
1 | use rand;
  |     ^^^^
  |
  = note: `#[warn(unused_imports)]` (part of `#[warn(unused)]`) on by default

warning: `add_one` (lib) generated 1 warning (run `cargo fix --lib -p add_one` to apply 1 suggestion)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.95s

최상위 레벨 화물.잠금 이제 의존성에 대한 정보가 있습니다. add_one 온 rand. 그러나, 비록 rand 작업 공간의 어딘가에 사용되며, 추가하지 않는 한 작업 공간의 다른 크레이트에서 사용할 수 없습니다. rand 그들의 카고.toml 파일도 마찬가지입니다. 예를 들어, use rand; 에 대하여 애드너/src/main.rs 파일명 The adder 패키지, 우리는 오류를 얻을 것이다 :

$ cargo build
  --snip--
   Compiling adder v0.1.0 (file:///projects/add/adder)
error[E0432]: unresolved import `rand`
 --> adder/src/main.rs:2:5
  |
2 | use rand;
  |     ^^^^ no external crate `rand`

이 문제를 해결하려면 Edit 카고.toml 파일명 The adder 패키지 및 그 표시 rand 이에 대한 의존성 또한 중요합니다. adder 패키지 추가 rand 에 대한 종속성의 목록에 adder 에서 화물.잠금, 그러나 추가 사본 없음 rand 화물은 작업 공간의 모든 패키지에 있는 모든 상자가 rand 패키지는 호환되는 버전을 지정하는 한 동일한 버전을 사용합니다. rand, 저희에게 공간을 절약하고 작업 공간에 있는 크레이트가 서로 양립할 것이라는 점을 보증.

작업 공간의 크레이트가 동일한 종속성의 호환되지 않는 버전을 지정하면 Cargo는 각 버전을 해결하지만 가능한 한 적은 버전을 해결하려고 시도합니다.

Workspace에 테스트 추가

또 다른 향상을 위해, 의 테스트를 추가하자 add_one::add_one 기능 내부 add_one 크레이트:

파일 이름: add_one/src/lib.rs

pub fn add_one(x: i32) -> i32 {
    x + 1
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        assert_eq!(3, add_one(2));
    }
}

이제 최상위 add 디렉토리에서 cargo test를 실행하십시오. 이와 같이 구성된 작업 공간에서 cargo test를 실행하면 작업 영역의 모든 크레이트에 대한 테스트를 실행합니다.

$ cargo test
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.20s
     Running unittests src/lib.rs (target/debug/deps/add_one-93c49ee75dc46543)

running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

     Running unittests src/main.rs (target/debug/deps/adder-3a47283c568d2b6a)

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests add_one

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

출력의 첫 번째 섹션은 it_works 크레이트에서 add_one 테스트가 통과했음을 보여줍니다. 다음 섹션은 adder 크레이트에서 제로 테스트가 발견되었고 마지막 섹션은 add_one 크레이트에서 제로 문서화 테스트가 발견되었음을 보여줍니다.

또한 -p 플래그를 사용하고 테스트하려는 크레이트의 이름을 지정하여 최상위 디렉토리에서 작업 공간의 특정 크레이트에 대한 테스트를 실행할 수 있습니다.

$ cargo test -p add_one
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running unittests src/lib.rs (target/debug/deps/add_one-93c49ee75dc46543)

running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests add_one

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

이 출력은 cargo test가 add_one 크레이트에 대한 테스트만 실행하고 adder 크레이트 테스트를 실행하지 않았음을 보여줍니다.

작업 공간에 있는 크레이트를 크레이트.io에 게시하는 경우 작업 공간에 있는 각 크레이트를 별도로 게시해야 합니다. cargo test와 마찬가지로 -p 플래그를 사용하여 게시하려는 크레이트의 이름을 지정하여 작업 공간에 특정 크레이트를 게시할 수 있습니다.

추가 연습을 위해 add_two 상자와 비슷한 방식으로이 작업 공간에 add_one 상자를 추가하십시오!

프로젝트가 성장함에 따라 작업 공간 사용을 고려하십시오. 하나의 큰 코드 블록보다 작고 이해하기 쉬운 구성 요소로 작업 할 수 있습니다. 또한 작업 공간에 상자를 보관하면 크레이트간에 쉽게 조정 할 수 있습니다.
