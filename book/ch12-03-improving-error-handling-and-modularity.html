The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

모듈화 및 오류 처리를 개선하기 위한 리팩토링

프로그램을 개선하기 위해 프로그램의 구조와 잠재적 오류를 처리하는 방법에 관한 네 가지 문제를 해결합니다. 첫째, main 함수는 이제 두 가지 작업을 수행합니다. 인수를 구문 분석하고 파일을 읽습니다. 프로그램이 성장함에 따라 main 함수가 처리하는 별도의 작업의 수가 증가합니다. 기능이 책임을 얻으면 각 기능을 추론하기가 더 어려워지고 변경하기가 더 어려워집니다.

이 문제는 두 번째 문제와도 관련이 있습니다. query 및 file_path는 프로그램의 구성 변수이지만 contents와 같은 변수는 프로그램의 논리를 수행하는 데 사용됩니다. main가 길수록 더 많은 변수를 범위로 가져와야 할 것입니다. 범위가 많을수록 각 구성의 목적을 추적하는 것이 더 어려워집니다.

세 번째 문제는 expect를 사용하여 파일을 읽을 때 오류 메시지를 인쇄했지만 오류 메시지는 Should have been able to read the file를 인쇄한다는 것입니다. 파일을 읽는 것은 여러 가지 방법으로 실패 할 수 있습니다. 예를 들어 파일이 누락되었거나 파일을 열 권한이 없을 수 있습니다. 현재 상황에 관계없이 모든 사용자에 대해 동일한 오류 메시지를 인쇄 할 수 있습니다.

넷째, expect를 사용하여 오류를 처리하고, 사용자가 충분한 인수를 지정하지 않고 프로그램을 실행하면 러스트에서 index out of bounds 오류가 발생하여 문제를 명확하게 설명하지 못합니다. 모든 오류 처리 코드가 한 곳에 있어 향후 관리자들이 변경이 필요한 경우 코드를 참조할 수 있다면 가장 좋습니다.

이 4가지 문제를 우리 프로젝트를 통해 해결하고자 한다.

이진 프로젝트에서 관심사를 분리

여러 작업을 main 함수에 할당하는 조직적인 문제는 많은 바이너리 프로젝트에 공통적입니다. 그 결과, 많은 러스트 프로그래머들은 main 함수가 커지기 시작할 때 바이너리 프로그램의 개별적인 관심사를 나누는 것이 유용하다는 것을 알게 됩니다. 이 프로세스는 다음과 같은 단계를 거칩니다:

  • 프로그램을 main.rs 파일과 lib.rs 파일로 나누고 프로그램의 로직을 lib.rs로 이동하십시오.
  • 명령줄 구문 분석 로직이 작은 경우 main 함수에 남아 있을 수 있습니다.
  • 명령줄 파싱 로직이 복잡해지기 시작하면 main 함수에서 다른 함수나 유형으로 추출합니다.

이 과정 후에 main 기능에서 남아 있는 책임은 뒤에 오는 것으로 제한되어야 합니다:

  • 논리를 인자 값으로 파싱하는 명령줄 호출
  • 다른 설정 설정
  • lib.rs에서 run 함수 호출하기
  • run가 오류를 반환하는 경우 오류 처리

이 패턴은 관심사를 분리하는 것입니다. main.rs는 프로그램 실행을 처리하고 lib.rs는 작업의 모든 논리를 처리합니다. main 함수를 직접 테스트 할 수 없기 때문에이 구조를 사용하면 프로그램의 모든 논리를 main 함수에서 이동하여 테스트 할 수 있습니다. main 함수에 남아있는 코드는이 프로세스를 확인하여 충분히 작습니다.
