The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

부록 G - Rust의 개발 방식과 “Nightly Rust”

이 부록은 Rust가 어떻게 만들어지는지, 그리고 그것이 Rust 개발자인 여러분에게 어떤 영향을 미치는지에 대해 설명합니다.

정체 없는 안정성

Rust는 코드의 안정성을 매우 중시합니다. Rust는 여러분이 신뢰하고 구축할 수 있는 견고한 기반이 되기를 원하며, 만약 상황이 끊임없이 변한다면 그것은 불가능할 것입니다. 동시에, 새로운 기능을 실험할 수 없다면 릴리스 이후에야 중요한 결함을 발견하게 될 수 있으며, 그때는 더 이상 변경할 수 없는 상황이 됩니다.

이 문제에 대한 우리의 해결책은 “정체 없는 안정성”이라고 부르는 것입니다. 우리의 지침 원칙은 다음과 같습니다. 안정적인 Rust의 새 버전으로 업그레이드하는 것을 두려워해서는 안 됩니다. 각 업그레이드는 고통스럽지 않으면서도 새로운 기능, 버그 감소, 그리고 더 빠른 컴파일 시간을 제공해야 합니다.

추, 추! 릴리스 채널과 기차 타기

Rust 개발은 열차 일정에 따라 진행됩니다. 즉, 모든 개발은 Rust 저장소의 메인 브랜치에서 이루어집니다. 릴리스는 Cisco IOS 및 기타 소프트웨어 프로젝트에서 사용된 소프트웨어 릴리스 기차 모델을 따릅니다. Rust에는 세 가지 릴리스 채널이 있습니다:

  • Nightly
  • 베타
  • 안정

대부분의 Rust 개발자는 주로 안정 채널을 사용하지만, 실험적인 새로운 기능을 시도하려는 개발자는 nightly 또는 beta를 사용할 수 있습니다.

개발 및 릴리스 프로세스가 어떻게 작동하는지 예를 들어 설명하겠습니다. Rust 팀이 Rust 1.5의 릴리스를 준비하고 있다고 가정해 보겠습니다. 이 릴리스는 2015년 12월에 이루어졌지만, 현실적인 버전 번호를 보여줄 수 있습니다. Rust에 새로운 기능이 추가되었습니다. 메인 브랜치에 새로운 커밋이 반영되었습니다. 매일 밤 새로운 nightly 버전의 Rust가 생성됩니다. 매일이 릴리스일이며, 이러한 릴리스는 릴리스 인프라에 의해 자동으로 생성됩니다. 따라서 시간이 지남에 따라 릴리스는 다음과 같이 한밤마다 생성됩니다:

nightly: * - - * - - *

6주마다 새로운 릴리스를 준비할 때가 됩니다! Rust 저장소의 beta 브랜치는 nightly에서 사용되는 메인 브랜치에서 분기됩니다. 이제 두 가지 릴리스가 있습니다:

nightly: * - - * - - *
                     |
beta:                *

대부분의 Rust 사용자는 beta 릴리스를 적극적으로 사용하지 않지만, Rust가 가능한 회귀 문제를 발견할 수 있도록 CI 시스템에서 beta를 대상으로 테스트합니다. 그 동안에도 매일 밤 nightly 릴리스가 계속 생성됩니다:

nightly: * - - * - - * - - * - - *
                     |
beta:                *

회귀가 발견되었다고 가정해 보겠습니다. 다행히도 회귀가 안정 릴리스에 포함되기 전에 베타 릴리스를 테스트할 시간이 있었습니다! 수정 사항이 메인 브랜치에 적용되어 나이트리가 수정되고, 이후 수정 사항이 베타 브랜치로 백포트되며 새로운 베타 릴리스가 생성됩니다: beta

nightly: * - - * - - * - - * - - * - - *
                     |
beta:                * - - - - - - - - *

첫 번째 beta가 생성된 지 6주 후, 안정 릴리스를 할 때가 되었습니다! stable 브랜치는 beta 브랜치에서 생성됩니다:

nightly: * - - * - - * - - * - - * - - * - * - *
                     |
beta:                * - - - - - - - - *
                                       |
stable:                                *

Hooray! Rust 1.5가 완료되었습니다! 하지만 한 가지를 잊었습니다. 6주가 지났으므로 다음 버전인 Rust 1.6의 새로운 베타 버전도 필요합니다. 따라서 stable이 beta에서 분기된 후, 다음 beta 버전은 다시 nightly에서 분기됩니다: stable가 beta에서 분기한 후, beta의 다음 버전은 nightly에서 다시 분기합니다.

nightly: * - - * - - * - - * - - * - - * - * - *
                     |                         |
beta:                * - - - - - - - - *       *
                                       |
stable:                                *

이것은 6주마다 릴리스가 '역을 떠나는' 과정을 거치지만, 안정적인 릴리스로 도착하기 전에 베타 채널을 통해 여정을 마쳐야 하기 때문에 '기차 모델(train model)'이라고 불립니다.

Rust는 매 6주마다 시계처럼 정확하게 릴리스됩니다. 한 번의 Rust 릴리스 날짜를 안다면 다음 릴리스 날짜도 알 수 있습니다. 바로 6주 후이기 때문입니다. 6주마다 릴리스가 예정되어 있는 좋은 점은 다음 기차가 곧 온다는 것입니다. 만약 어떤 기능이 특정 릴리스에 포함되지 못하더라도 걱정할 필요가 없습니다. 곧 다음 릴리스가 있기 때문입니다! 이는 릴리스 마감일이 가까워질 때 아직 다듬어지지 않은 기능을 몰래 포함시키려는 압박을 줄이는 데 도움이 됩니다.

이 프로세스 덕분에 항상 Rust의 다음 빌드를 확인하고, 업그레이드가 쉬운지 스스로 검증할 수 있습니다. 만약 베타 릴리스가 예상대로 작동하지 않으면 팀에 보고하여 다음 stable 릴리스가 나오기 전에 수정될 수 있도록 할 수 있습니다! 베타 릴리스에서 문제가 발생하는 경우는 비교적 드물지만, rustc 역시 소프트웨어이므로 버그가 존재할 수 있습니다.

유지보수 기간

Rust 프로젝트는 가장 최근의 stable 버전을 지원합니다. 새로운 stable 버전이 릴리스되면 이전 버전은 수명 종료(EOL)에 도달합니다. 즉, 각 버전은 6주 동안 지원됩니다.

안정화되지 않은 기능

이 릴리스 모델에는 한 가지 더 고려해야 할 점이 있습니다. 바로 안정화되지 않은 기능입니다. Rust는 'feature flags'라는 기술을 사용하여 특정 릴리스에서 어떤 기능이 활성화되는지 결정합니다. 새로운 기능이 활발히 개발 중이라면 main 브랜치에 머지되고, 따라서 nightly에도 포함되지만 feature flag 뒤에 숨겨져 있습니다. 사용자가 진행 중인 기능을 사용해 보고 싶다면, Rust의 nightly 릴리스를 사용하고 소스 코드에 적절한 플래그를 명시하여 옵트인(opt-in)해야 합니다.

Rust의 베타 버전이나 안정 버전(stable)을 사용 중이라면 기능 플래그를 사용할 수 없습니다. 이 플래그는 새로운 기능을 영구적으로 안정 버전으로 선언하기 전에 실용적으로 사용할 수 있게 해주는 핵심 요소입니다. 최첨단 기능을 원하면 이를 선택할 수 있고, 안정적이고 견고한 환경을 원하면 안정 버전을 유지하면서 코드가 깨지지 않는다는 확신을 가질 수 있습니다. 정체되지 않는 안정성입니다.

진행 중인 기능은 계속 변화하고 있으며, 이 책이 작성된 시점과 안정 빌드에서 활성화되는 시점 사이에 확실히 차이가 있을 것이므로, 이 책에는 안정 버전의 기능에 대한 정보만 포함되어 있습니다. 나이트리(nightly) 전용 기능에 대한 문서는 온라인에서 찾을 수 있습니다.

Rustup과 Rust Nightly의 역할

Rustup을 사용하면 전역 또는 프로젝트별로 Rust의 다양한 릴리스 채널을 쉽게 변경할 수 있습니다. 기본적으로 안정 버전의 Rust가 설치되어 있습니다. 예를 들어 나이트리(nightly)를 설치하려면 다음과 같이 합니다:

$ rustup toolchain install nightly

rustup 명령을 사용하면 설치한 모든 툴체인(Rust 릴리스 및 관련 구성 요소)을 확인할 수 있습니다. 다음은 저자의 Windows 컴퓨터 중 하나에서 실행한 예시입니다:

> rustup toolchain list
stable-x86_64-pc-windows-msvc (default)
beta-x86_64-pc-windows-msvc
nightly-x86_64-pc-windows-msvc

보시다시피, 안정 버전의 툴체인이 기본값입니다. 대부분의 Rust 사용자는 대부분의 시간을 안정 버전으로 사용합니다. 대부분의 시간은 안정 버전을 사용하되, 최첨단 기능에 관심이 있어 특정 프로젝트에서는 나이트리(nightly)를 사용해야 할 수도 있습니다. 이를 위해 해당 프로젝트의 디렉토리에서 rustup override를 사용하여 rustup가 해당 디렉토리에 있을 때 사용할 툴체인을 나이트리(nightly)로 설정할 수 있습니다:

$ cd ~/projects/needs-nightly
$ rustup override set nightly

이제 ~/projects/needs-nightly 디렉토리 내에서 rustc 또는 cargo를 호출할 때마다, rustup는 기본값인 안정 버전의 Rust 대신 나이트리(nightly) Rust를 사용하고 있는지 확인합니다. Rust 프로젝트가 많을 때 이 기능이 유용합니다!

RFC 프로세스와 팀

그렇다면 이러한 새로운 기능을 어떻게 배울 수 있을까요? Rust의 개발 모델은 RFC(Request For Comments) 프로세스를 따릅니다. Rust를 개선하고 싶다면 RFC라고 불리는 제안을 작성할 수 있습니다.

누구나 Rust를 개선하기 위해 RFC를 작성할 수 있으며, 제안은 Rust 팀에 의해 검토되고 논의됩니다. Rust 팀은 여러 주제별 하위 팀으로 구성됩니다. Rust 웹사이트에는 팀의 전체 목록이 있으며, 여기에는 언어 설계, 컴파일러 구현, 인프라, 문서 등 프로젝트의 각 영역에 대한 팀이 포함됩니다. 해당 팀은 제안과 의견을 읽고 자체적인 의견을 작성한 후, 해당 기능을 수용하거나 거부하는 데 합의하게 됩니다.

기능이 수용되면 Rust 저장소에서 이슈가 열리고, 누군가가 이를 구현할 수 있습니다. 이 기능을 아주 잘 구현한 사람은 처음에 이 기능을 제안한 사람이 아닐 수도 있습니다! 구현이 준비되면 “불안정 기능” 섹션에서 논의한 바와 같이, 기능 게이트 뒤에 있는 메인 브랜치에 머지됩니다.

일정 시간이 지난 후, 나이트리 릴리스를 사용하는 Rust 개발자들이 새로운 기능을 사용해 볼 수 있게 되면, 팀원들은 이 기능의 나이트리에서의 동작 방식을 논의하고, 이를 안정판 Rust에 포함할지 여부를 결정합니다. 진행하기로 결정되면 기능 게이트가 제거되고, 그 기능은 이제 안정된 것으로 간주됩니다! 이 기능은 트레인을 통해 새로운 안정판 Rust 릴리스에 포함됩니다.
