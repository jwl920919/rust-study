The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

고급 트레이트

먼저 10장의 “트레이트로 공유된 동작 정의” 섹션에서 트레이트에 대해 다루었지만, 더 발전된 세부 사항에 대해서는 논의하지 않았습니다. 이제 Rust에 대해 더 많이 알게 되었으므로, 세부적인 내용을 다룰 수 있습니다.

연관 타입으로 트레이트 정의

연관 타입은 타입 플레이스홀더와 트레이트를 연결하여, 트레이트 메서드 정의가 서명에서 이러한 플레이스홀더 타입을 사용할 수 있도록 합니다. 트레이트 구현자는 특정 구현을 위해 플레이스홀더 타입 대신 사용할 구체적인 타입을 지정합니다. 이렇게 하면 트레이트가 구현될 때까지 해당 타입이 정확히 무엇인지 알 필요 없이, 일부 타입을 사용하는 트레이트를 정의할 수 있습니다.

이 장의 대부분의 고급 기능은 거의 필요하지 않다고 설명했습니다. 연관 타입은 그 중간에 위치합니다. 이 책의 나머지 부분에서 설명한 기능보다 드물게 사용되지만, 이 장에서 논의한 다른 많은 기능보다 더 일반적으로 사용됩니다.

상기 연관된 타입은, The associated type, Iterator 표준 라이브러리가 제공하는 트레잇입니다. 연관된 타입의 이름은 Item 를 구현하는 타입의 값의 타입을 나타냅니다. Iterator 특성이 반복됩니다. 의 정의는 Iterator 특성은 Listing 20-13에 나와 있습니다.

Item 타입은 플레이스홀더이며, next 메서드의 정의는 Option<Self::Item> 타입의 값을 반환할 것임을 보여줍니다. Iterator 트레이트의 구현자는 Item에 대한 구체적인 타입을 지정하고, next 메서드는 해당 구체적인 타입의 값을 포함하는 Option을 반환합니다.

연관 타입은 제네릭과 비슷한 개념으로 보일 수 있습니다. 제네릭은 어떤 타입을 처리할 수 있는지 지정하지 않고 함수를 정의할 수 있습니다. 두 개념의 차이를 검토하기 위해 Iterator라는 이름의 타입에 대한 Counter 트레잇의 구현을 살펴 보겠습니다. Item 유형은 u32입니다.

이 문법은 제네릭의 문법과 비슷해 보입니다. 그렇다면 Listing 20-14에 보인 것처럼 제네릭을 사용하여 Iterator 트레잇을 정의하지 않는 이유는 무엇일까요?

차이점은 Listing 20-14에서와 같이 제네릭을 사용할 때 각 구현에서 타입을 명시해야 한다는 점입니다. Iterator<String> for Counter 또는 다른 타입에 대해 Iterator을(를) 구현할 수도 있기 때문에, Counter에 대한 여러 구현이 존재할 수 있습니다. 즉, 트레이트에 제네릭 파라미터가 있으면 제네릭 타입 파라미터의 구체적인 타입을 매번 변경하여 해당 타입에 대해 여러 번 구현할 수 있습니다. next에서 Counter 메서드를 사용할 때, 어떤 Iterator 구현을 사용하고자 하는지 나타내기 위해 타입 주석을 제공해야 합니다.

연관된 타입을 사용하면 타입을 명시적으로 지정할 필요가 없습니다. 이는 특정 타입에 대해 하나의 트레이트를 여러 번 구현할 수 없기 때문입니다. Listing 20-13의 연관된 타입을 사용한 정의에서, Item의 타입을 선택할 수 있는 시점은 단 한 번뿐입니다. impl Iterator for Counter이 단 하나만 존재할 수 있기 때문입니다. 따라서 u32의 next을 호출하는 모든 곳에서 Counter 반복자를 원한다고 지정할 필요가 없습니다.

연관 타입은 또한 트레잇 계약의 일부가 됩니다. 트레잇을 구현하는 쪽은 연관 타입 플레이스홀더를 대신할 타입을 제공해야 합니다. 연관 타입은 보통 해당 타입이 어떻게 사용될지를 설명하는 이름을 가지며, API 문서에서 연관 타입을 문서화하는 것은 좋은 관행입니다.

기본 제네릭 파라미터와 연산자 오버로딩 사용

제네릭 타입 파라미터를 사용할 때, 제네릭 타입에 대한 기본 구체적인 타입을 지정할 수 있습니다. 기본 타입이 적합한 경우, 트레이트 구현자가 구체적인 타입을 명시적으로 지정할 필요가 없게 됩니다. 제네릭 타입을 선언할 때 <PlaceholderType=ConcreteType> 문법을 사용하여 기본 타입을 지정합니다.

이 기법이 유용한 상황의 좋은 예는 연산자 오버로딩입니다. 연산자 오버로딩은 특정 상황에서 연산자(예: +)의 동작을 사용자 정의하는 것입니다.

Rust는 사용자가 직접 새로운 연산자를 만들거나 임의의 연산자를 오버로드하는 것을 허용하지 않습니다. 하지만 std::ops에 나열된 연산자와 해당 트레잇을 오버로드할 수 있습니다. 이를 위해 해당 연산자와 연관된 트레잇을 구현하면 됩니다. 예를 들어, Listing 20-15에서는 두 + 인스턴스를 더하기 위해 Point 연산자를 오버로드합니다. Add 구조체에 Point 트레잇을 구현하여 이 작업을 수행합니다.

add 메서드는 두 x 인스턴스의 Point 값과 두 y 인스턴스의 Point 값을 더하여 새로운 Point을 생성합니다. Add 트레잇에는 Output이라는 연관 타입이 있으며, 이 타입은 add 메서드에서 반환되는 타입을 결정합니다.

이 코드에서 기본 제네릭 타입은 Add 트레잇 내에 있습니다. 그 정의는 다음과 같습니다:

#![allow(unused)]
fn main() {
trait Add<Rhs=Self> {
    type Output;

    fn add(self, rhs: Rhs) -> Self::Output;
}
}

이 코드는 일반적으로 익숙해 보일 것입니다: 하나의 메서드와 연관 타입을 가진 트레잇입니다. 새로운 부분은 Rhs=Self입니다. 이 구문은 기본 타입 매개변수라고 합니다. Rhs 제네릭 타입 매개변수(“right-hand side”의 줄임말)는 rhs 메서드의 add 매개변수의 타입을 정의합니다. Rhs 트레잇을 구현할 때 Add에 구체적인 타입을 지정하지 않으면, Rhs의 타입은 기본적으로 Self가 됩니다. 이는 Add 트레잇을 구현하는 대상 타입이 됩니다.

Add에 대해 Point을 구현할 때, 두 Rhs 인스턴스를 더하고 싶었기 때문에 Point의 기본값을 사용했습니다. 이제 기본값 대신 Add 타입을 사용자 정의하고 싶은 Rhs 트레잇 구현 예를 살펴보겠습니다.

우리는 서로 다른 단위의 값을 저장하는 두 구조체, Millimeters과 Meters을 가지고 있습니다. 기존 타입을 다른 구조체로 얇게 감싸는 이러한 방식은 newtype 패턴이라고 하며, “외부 트레잇을 newtype 패턴으로 구현하기” 섹션에서 더 자세히 설명합니다. 우리는 밀리미터 단위의 값을 미터 단위의 값에 더하고, Add 구현부가 변환을 올바르게 수행하기를 원합니다. Listing 20-16에 나와 있듯이, Add에 대해 Millimeters을 Meters로 설정하여 Rhs을 구현할 수 있습니다.

Millimeters과 Meters를 더하려면, impl Add<Meters>를 지정하여 Rhs의 기본값인 Self 대신 Self 타입 매개변수의 값을 설정합니다.

기본 타입 매개변수는 주로 두 가지 방식으로 사용합니다.

  1. 기존 코드를 깨지 않고 타입을 확장할 때
  2. 대부분의 사용자가 필요로 하지 않는 특정 경우에 사용자 지정이 가능하도록 할 때

표준 라이브러리의 Add 트레이트는 두 번째 목적의 예시입니다. 일반적으로 같은 타입 두 개를 더하지만, Add 트레이트는 그 이상의 사용자 지정 기능을 제공합니다. Add 트레이트 정의에서 기본 타입 매개변수를 사용하면 대부분의 경우 추가 매개변수를 지정할 필요가 없습니다. 즉, 일부 구현 템플릿 코드가 필요 없으므로 트레이트를 사용하는 것이 더 쉬워집니다.

첫 번째 목적은 두 번째 목적과 유사하지만 반대입니다. 기존 트레이트에 타입 매개변수를 추가하고 싶다면, 기본값을 지정하여 기존 구현 코드를 깨지 않고 트레이트의 기능을 확장할 수 있습니다.

동일한 이름의 메서드 구분하기

Rust에서는 트레이트가 다른 트레이트의 메서드와 동일한 이름을 가진 메서드를 가지는 것을 막지 않으며, 한 타입에 두 트레이트를 모두 구현하는 것도 막지 않습니다. 또한 트레이트의 메서드와 동일한 이름을 가진 메서드를 타입에 직접 구현하는 것도 가능합니다.

동일한 이름을 가진 메서드를 호출할 때는 Rust에게 어떤 메서드를 사용할지 알려야 합니다. Listing 20-17의 코드에서는 Pilot과 Wizard라는 두 트레이트를 정의했으며, 이 두 트레이트 모두 fly라는 메서드를 가지고 있습니다. 그런 다음 Human 타입에 두 트레이트를 모두 구현했는데, 이 타입에는 이미 fly라는 이름의 메서드가 구현되어 있습니다. 각 fly 메서드는 서로 다른 동작을 수행합니다.

fly 인스턴스에서 Human을 호출하면, 컴파일러는 기본적으로 Listing 20-18에 나와 있는 것처럼 타입에 직접 구현된 메서드를 호출합니다.

이 코드를 실행하면 *waving arms furiously*이 출력되며, 이는 Rust가 fly에 직접 구현된 Human 메서드를 호출했음을 보여줍니다.

fly 메서드를 Pilot 트레이트 또는 Wizard 트레이트에서 호출하려면, 어떤 fly 메서드를 의미하는지 지정하기 위해 더 명시적인 구문을 사용해야 합니다. Listing 20-19는 이 구문을 보여줍니다.

메서드 이름 앞에 트레잇 이름을 지정하면 Rust가 어떤 fly 구현을 호출하길 원하는지 명확히 알 수 있습니다. Human::fly(&person)처럼 작성하는 것도 가능하며, 이는 Listing 20-19에서 사용했던 person.fly()와 동등합니다. 하지만 구분이 필요하지 않다면 이렇게 작성하는 것이 조금 더 길어집니다.

fly 메서드는 self 파라미터를 받으므로, 하나의 트레잇을 구현하는 두 가지 타입이 있는 경우 Rust는 self의 타입을 기준으로 사용할 트레잇 구현을 결정할 수 있습니다.

그러나 메서드가 아닌 연관 함수에는 a가 없습니다. self 파라미터. 메서드가 아닌 함수를 정의하는 여러 타입이나 트레잇이 있을 때, 완전한 문법을 사용하지 않는 한, 러스트는 항상 어떤 타입을 의미하는지 알지 못합니다. 예를 들어, Listing 20-20에서, 우리는 모든 아기 개들의 이름을 지정하고자 하는 동물 보호소에 대한 트레잇을 만듭니다. 우리는 Animal 관련 non-method 기능을 가진 특성 baby_name. 그 Animal 트레잇은 구조체를 위해 구현된다. Dog우리는 또한 관련되지 않은 기능을 제공합니다. baby_name 직접.

우리는 모든 강아지의 이름을 지정하기위한 코드를 구현 baby_name 에 정의되어 있는 연관 함수 Dog. 그 Dog type은 또한 트레잇을 구현합니다. Animal, 이는 모든 동물이 가지고있는 특성을 설명합니다. 아기 개는 강아지라고하며, 그 구현에 표현 Animal 트레잇 켜짐 Dog 다음에서 baby_name 이와 관련된 기능 Animal 특성.

main에서 Dog::baby_name 함수를 호출하면, Dog에 정의된 연관 함수가 직접 호출됩니다. 이 코드는 다음과 같이 출력합니다.

Rust에게 Animal 타입에 대한 Dog 트레이트 구현을 사용하라고 명확히 알려주기 위해, 다른 타입에 대한 구현이 아닌 Animal 타입에 대한 구현을 지정해야 합니다. 이를 위해 전체 자격 지정 문법(fully qualified syntax)을 사용해야 합니다. 목록 20-22에서는 전체 자격 지정 문법을 사용하는 방법을 보여줍니다.

우리는 러스트에 angle bracket 내의 type 주석을 제공하고 있는데, 이는 우리가 baby_name 상기 방법 From the Animal 에 구현되는 트레잇 Dog 우리가 치료하기를 원한다고 말하면서 Dog 타입 A Animal 이 함수 호출을 위해. 이 코드는 이제 우리가 원하는 것을 출력할 것입니다:

일반적으로 전체 자격 지정 문법은 다음과 같이 정의됩니다:

<Type as Trait>::function(receiver_if_method, next_arg, ...);

메소드가 아닌 연관 함수의 경우 receiver가 없을 것입니다: 다른 인수 목록만 있을 것입니다. 함수나 메소드를 호출하는 모든 곳에서 정규화된 문법을 사용할 수 있습니다. 그러나, 러스트가 프로그램의 다른 정보로부터 알아낼 수 있는 이 문법의 어떤 부분도 생략할 수 있습니다. 같은 이름과 구현을 사용하는 여러 구현이 필요한 경우에만 이 더 많은 동사 구문을 사용해야 합니다.

슈퍼트레이트(Supertraits) 사용하기

때로는 다른 트레이트에 의존하는 트레이트 정의를 작성할 수도 있습니다. 어떤 타입이 첫 번째 트레이트를 구현하려면, 해당 타입이 두 번째 트레이트도 구현하도록 요구할 수 있습니다. 이렇게 하면 트레이트 정의에서 두 번째 트레이트의 연관 항목을 사용할 수 있습니다. 자신의 트레이트 정의가 의존하는 트레이트를 해당 트레이트의 supertrait라고 합니다.

예를 들어, 주어진 값을 별표로 테두리를 치도록 포맷하여 출력하는 outline_print 메서드를 가진 OutlinePrint 트레이트를 만들고 싶다고 가정해 보겠습니다. 즉, 표준 라이브러리 트레이트 Display을 구현하여 (x, y)가 되는 Point 구조체가 있을 때, x이 1이고 y이 3인 Point 인스턴스에 outline_print를 호출하면 다음을 출력해야 합니다:

**********
*        *
* (1, 3) *
*        *
**********

outline_print 메서드의 구현에서 Display 트레이트의 기능을 사용하려고 합니다. 따라서, OutlinePrint 트레이트는 Display을 구현하는 타입에서만 동작하도록 지정해야 하며, OutlinePrint에 필요한 기능을 제공해야 합니다. OutlinePrint: Display를 지정하여 트레이트 정의에서 이를 수행할 수 있습니다. 이 기법은 트레이트에 트레이트 바운드를 추가하는 것과 유사합니다. Listing 20-23은 OutlinePrint 트레이트의 구현을 보여줍니다.

왜냐하면 우리는 그것을 명시했기 때문입니다. OutlinePrint 필요 The Display 특성, 우리는 사용할 수 있습니다 to_string 모든 종류의 구현에 대해 자동으로 구현되는 기능 Display. 우리가 사용하려고하면 to_string 콜론을 추가하지 않고 Display 트레잇 이름 뒤에는 메소드 이름이 없다는 오류가 발생합니다. to_string 형식에 대 한 발견 &Self 현재의 범위에서.

Display을 구현하지 않은 타입, 예를 들어 Point 구조체에 OutlinePrint을 구현하려고 하면 어떤 일이 일어나는지 살펴봅시다:

Newtype 패턴으로 외부 트레잇 구현

10장 “유형에 트레잇 구현하기” 절에서, 트레잇이나 타입, 또는 둘 다 모두 현재 크레이트에 로컬인 경우에만 해당 타입에 트레잇을 구현할 수 있다는 고아 규칙(orphan rule)을 언급했습니다. “유형에 트레잇 구현하기” 튜플 구조체 안에 새로운 타입을 만들어내는 newtype 패턴을 사용하면 이 제한을 우회할 수 있습니다. (5장 “튜플 구조체를 사용해 다양한 타입 만들기” 절에서 튜플 구조체에 대해 다루었습니다.) “튜플 구조체를 사용해 다양한 타입 만들기” 이 튜플 구조체는 하나의 필드를 가지며, 트레잇을 구현하려는 타입을 감싸는 얇은 래퍼 역할을 합니다. 그러면 이 래퍼 타입은 현재 크레이트에 로컬이므로, 래퍼 타입에 트레잇을 구현할 수 있습니다. Newtype이라는 용어는 Haskell 프로그래밍 언어에서 유래했습니다. Newtype 이 패턴을 사용하면 런타임 성능 저하가 없으며, 래퍼 타입은 컴파일 타임에 제거됩니다.

예를 들어, Display을 Vec<T>에 구현하고 싶다고 가정해 보겠습니다. Display 트레잇과 Vec<T> 타입은 모두 우리 크레이트 외부에서 정의되어 있으므로, 고아 규칙에 따라 직접 구현할 수 없습니다. Wrapper 인스턴스를 포함하는 Vec<T> 구조체를 만들 수 있습니다. 그러면 Display을 Wrapper에 구현하고, Vec<T> 값을 사용할 수 있습니다. Listing 20-24를 참고하세요.

Display의 구현은 self.0을 사용하여 내부의 Vec<T>에 접근합니다. Wrapper은 튜플 구조체이고, Vec<T>은 튜플의 인덱스 0에 있는 항목이기 때문입니다. 그러면 Display에 대해 Wrapper 트레잇의 기능을 사용할 수 있습니다.

이 기법을 사용하는 단점은 Wrapper이 새로운 타입이므로, 그 안에 담고 있는 값의 메서드를 가지고 있지 않다는 것입니다. Vec<T>의 모든 메서드를 Wrapper에 직접 구현하여 메서드가 self.0에 위임하도록 해야 하며, 이렇게 하면 Wrapper를 Vec<T>와 정확히 같은 방식으로 취급할 수 있습니다. 새로운 타입이 내부 타입이 가진 모든 메서드를 가지고 있기를 원한다면, Wrapper에 Deref 트레이트를 구현하여 내부 타입을 반환하는 것이 해결책이 될 수 있습니다(15장에서 “스마트 포인터를 일반 참조처럼 취급하기” 섹션에서 Deref 트레이트 구현에 대해 논의했습니다). Wrapper 타입이 내부 타입의 모든 메서드를 가지지 않기를 원한다면, 예를 들어 Wrapper 타입의 동작을 제한하기 위해, 원하는 메서드만 수동으로 구현해야 합니다.

이 newtype 패턴은 트레잇이 관여하지 않는 경우에도 유용합니다. 이제 초점을 전환하여 Rust의 타입 시스템과 상호 작용하는 몇 가지 고급 방법을 살펴보겠습니다.
