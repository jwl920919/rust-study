The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

라이프타임으로 참조 검증

라이프타임은 우리가 이미 사용해 온 또 다른 종류의 제네릭입니다. 타입이 우리가 원하는 동작을 하는지 보장하는 대신, 라이프타임은 우리가 필요로 하는 동안 참조가 유효한지 보장합니다.

4장의 “참조와 빌림” 섹션에서 다루지 않은 세부 사항이 하나 있습니다. Rust의 모든 참조에는 라이프타임이 있으며, 이는 해당 참조가 유효한 범위를 의미합니다. 대부분의 경우 타입이 추론되는 것과 마찬가지로, 라이프타임도 암시적으로 추론됩니다. 여러 타입이 가능할 때만 타입을 명시적으로 지정해야 하는 것처럼, 참조의 라이프타임이 여러 가지 방식으로 관련될 수 있을 때 라이프타임을 명시적으로 지정해야 합니다. Rust는 제네릭 라이프타임 매개변수를 사용하여 이러한 관계를 명시적으로 지정하도록 요구하며, 이를 통해 런타임에 사용되는 실제 참조가 반드시 유효함을 보장합니다.

라이프타임에 주석을 다는 것은 대부분의 다른 프로그래밍 언어에조차 없는 개념이므로, 낯설게 느껴질 것입니다. 이 장에서는 라이프타임의 모든 내용을 다루지는 않겠지만, 라이프타임 문법을 접하게 될 일반적인 상황에 대해 논의하여 이 개념에 익숙해지도록 하겠습니다.

라이프타임 주석 문법

라이프타임 주석은 참조가 얼마나 오래 지속되는지를 변경하지 않습니다. 대신, 라이프타임 자체에는 영향을 미치지 않으면서 여러 참조의 라이프타임이 서로 어떻게 관련되는지를 설명합니다. 함수 서명이 일반 타입 매개변수를 지정하면 함수가 어떤 타입이든 받을 수 있듯이, 일반 라이프타임 매개변수를 지정하면 함수가 어떤 라이프타임이든 가진 참조를 받을 수 있습니다.

라이프타임 주석에는 약간 특이한 문법이 있습니다. 라이프타임 매개변수의 이름은 아포스트로피(')로 시작해야 하며, 일반적으로 일반 타입과 마찬가지로 모두 소문자이고 매우 짧습니다. 대부분의 사람은 첫 번째 라이프타임 주석에 'a이라는 이름을 사용합니다. 라이프타임 매개변수 주석은 참조의 & 뒤에 배치하며, 공백을 사용하여 주석과 참조의 타입을 구분합니다.

다음은 몇 가지 예시입니다. 라이프타임 매개변수가 없는 i32에 대한 참조, i32이라는 이름의 라이프타임 매개변수가 있는 'a에 대한 참조, 그리고 i32라는 라이프타임이 있는 가변 참조인 'a입니다:

&i32        // a reference
&'a i32     // a reference with an explicit lifetime
&'a mut i32 // a mutable reference with an explicit lifetime

라이프타임 주석 하나만으로는 큰 의미가 없습니다. 주석은 여러 참조의 일반 라이프타임 매개변수가 서로 어떻게 관련되는지를 Rust에게 알려주기 위한 것이기 때문입니다. longest 함수의 컨텍스트에서 라이프타임 주석이 서로 어떻게 관련되는지 살펴봅시다.

함수에서 라이프타임을 주석으로 표시할 때, 이 주석은 함수 본문이 아니라 함수 서명에 들어갑니다. 라이프타임 주석은 서명의 타입과 마찬가지로 함수 계약의 일부가 됩니다. 함수 서명에 라이프타임 계약이 포함되어 있으면 Rust 컴파일러가 수행하는 분석이 더 단순해질 수 있습니다. 함수의 주석 방식이나 호출 방식에 문제가 있는 경우, 컴파일러 오류는 우리 코드의 해당 부분과 제약 조건을 더 정확하게 가리킬 수 있습니다. 반대로 Rust 컴파일러가 라이프타임 관계에 대해 우리가 의도한 바를 더 추론해야 한다면, 컴파일러는 문제의 원인과 멀리 떨어진 곳에서 코드가 사용된 위치만 가리킬 수 있을 것입니다.

구체적인 참조를 longest에 전달할 때, 'a에 대입되는 구체적 라이프타임은 x의 스코프와 y의 스코프가 겹치는 부분입니다. 다시 말해, 제네릭 라이프타임 'a은 x과 y의 라이프타임 중 더 짧은 것과 동일한 구체적 라이프타임을 갖게 됩니다. 반환되는 참조에 동일한 라이프타임 매개변수 'a을 명시했으므로, 반환되는 참조도 x과 y의 라이프타임 중 더 짧은 것의 길이만큼 유효합니다.

라이프타임 주석이 longest 함수를 어떻게 제한하는지, 서로 다른 구체적인 라이프타임이 있는 참조를 전달하는 방식으로 살펴 보겠습니다. Listing 10-22는 간단한 예제입니다.

이 예제에서 string1는 외부 스코프가 끝날 때까지 유효하고, string2는 내부 스코프가 끝날 때까지 유효하며, result는 내부 스코프가 끝날 때까지 유효한 값을 참조합니다. 이 코드를 실행하면 빌림 검사기가 승인하는 것을 확인할 수 있습니다. 컴파일이 성공하며 The longest string is long string is long가 출력됩니다.

지금까지 정의한 구조체는 모두 소유권을 가진 타입을 담고 있습니다. 구조체가 참조를 담도록 정의할 수도 있지만, 이 경우 구조체 정의에 있는 모든 참조에 라이프타임 주석을 추가해야 합니다. Listing 10-24에는 문자열 슬라이스를 담고 있는 ImportantExcerpt라는 구조체가 있습니다.

라이프타임 생략

모든 참조에는 라이프타임이 있으며, 참조를 사용하는 함수나 구조체에는 라이프타임 파라미터를 지정해야 한다는 것을 배웠습니다. 하지만 Listing 4-9에 있는 함수는 라이프타임 주석 없이 컴파일되었습니다. 이 함수는 Listing 10-25에 다시 표시됩니다.

이 함수가 라이프타임 주석 없이 컴파일되는 이유는 역사적인 배경 때문입니다. Rust의 초기 버전(1.0 이전)에서는 모든 참조에 명시적인 라이프타임이 필요했기 때문에 이 코드는 컴파일되지 않았습니다. 당시 함수 서명은 다음과 같이 작성되었을 것입니다:

fn first_word<'a>(s: &'a str) -> &'a str {

Rust 코드를 많이 작성한 후 Rust 팀은 Rust 개발자들이 특정 상황에서 동일한 라이프타임 주석을 반복적으로 입력하고 있음을 발견했습니다. 이러한 상황은 예측 가능했으며 몇 가지 결정론적인 패턴을 따랐습니다. 개발자들은 이러한 패턴을 컴파일러 코드에 구현하여 빌림 검사기가 이러한 상황에서 라이프타임을 추론할 수 있도록 하고, 명시적인 주석이 필요 없게 했습니다.

이러한 Rust의 역사는 더 많은 결정론적인 패턴이 발견되어 컴파일러에 추가될 수 있기 때문에 관련이 있습니다. 미래에는 라이프타임 주석이 더 적게 필요할 수도 있습니다.

Rust의 참조 분석에 프로그래밍된 이러한 패턴은 라이프타임 생략 규칙(lifetime elision rules)이라고 합니다. 이는 개발자가 따라야 할 규칙이 아니라, 컴파일러가 고려하는 특정 사례들의 집합입니다. 코드가 이러한 사례에 해당하면 라이프타임을 명시적으로 작성할 필요가 없습니다.

생략 규칙은 완전한 추론을 제공하지 않습니다. Rust가 규칙을 적용한 후에도 참조의 라이프타임에 대해 모호한 부분이 남아 있다면, 컴파일러는 나머지 참조의 라이프타임을 추측하지 않습니다. 대신 컴파일러는 라이프타임 주석을 추가하여 해결할 수 있는 오류를 보고합니다.

함수 또는 메서드 매개변수의 라이프타임은 입력 라이프타임(input lifetimes)이라고 하고, 반환 값의 라이프타임은 출력 라이프타임(output lifetimes)이라고 합니다.

명시적인 주석이 없을 때 컴파일러는 세 가지 규칙을 사용하여 참조의 라이프타임을 파악합니다. 첫 번째 규칙은 입력 라이프타임에 적용되며, 두 번째와 세 번째 규칙은 출력 라이프타임에 적용됩니다. 세 가지 규칙을 모두 적용한 후에도 라이프타임을 파악할 수 없는 참조가 남아 있다면, 컴파일러는 오류를 발생시켜 중단합니다. 이러한 규칙은 fn 정의와 impl 블록에도 적용됩니다.

첫 번째 규칙은 컴파일러가 참조인 각 매개 변수에 라이프타임 매개 변수를 할당한다는 것입니다. 즉, 매개 변수가 하나인 함수는 라이프타임 매개 변수를 하나 가지며 fn foo<'a>(x: &'a i32)입니다. 매개 변수가 두 개인 함수는 서로 다른 라이프타임 매개 변수를 두 개 가지며 fn foo<'a, 'b>(x: &'a i32, y: &'b i32)입니다. 이어서 같은 방식으로 적용됩니다.

두 번째 규칙은 입력 라이프타임 매개 변수가 정확히 하나인 경우, 해당 라이프타임이 모든 출력 라이프타임 매개 변수에 할당된다는 것입니다. 예를 들어 fn foo<'a>(x: &'a i32) -> &'a i32와 같습니다.

세 번째 규칙은 여러 개의 입력 라이프타임 매개변수가 있는 경우, 이 중 하나가 &self 또는 &mut self인 경우(이는 메서드이므로) self의 라이프타임이 모든 출력 라이프타임 매개변수에 할당된다는 것입니다. 이 세 번째 규칙 덕분에 필요한 기호가 줄어들어 메서드를 읽고 작성하기가 훨씬 쉬워집니다.

우리가 컴파일러라고 가정해 보겠습니다. Listing 10-25의 first_word 함수 서명에서 참조의 라이프타임을 파악하기 위해 이 규칙들을 적용해 보겠습니다. 처음에는 참조에 라이프타임이 연결되어 있지 않은 상태로 시작합니다:

입력 라이프타임이 하나 이상 있으므로 두 번째 규칙은 적용되지 않습니다. 세 번째 규칙도 적용되지 않습니다. longest는 메서드가 아닌 함수이므로 매개변수 중 어느 것도 self이 아니기 때문입니다. 세 가지 규칙을 모두 적용해 보았음에도 불구하고 반환 타입의 라이프타임이 무엇인지 여전히 알 수 없습니다. 이것이 Listing 10-20의 코드를 컴파일하려고 했을 때 오류가 발생한 이유입니다. 컴파일러는 라이프타임 생략 규칙을 적용해 보았지만, 시그니처에 있는 참조의 모든 라이프타임을 파악하지 못했기 때문입니다.

세 번째 규칙은 실제로 메서드 서명에서만 적용되므로, 다음으로 메서드 서명에서 라이프타임 주석이 거의 필요 없는 이유를 살펴볼 것입니다.

메서드 정의에서

라이프타임이 있는 구조체에 메서드를 구현할 때는 Listing 10-11에 나와 있듯이 제네릭 타입 매개변수와 동일한 문법을 사용합니다. 라이프타임 매개변수를 선언하고 사용하는 위치는 구조체 필드와 관련이 있는지, 아니면 메서드 매개변수 및 반환 값과 관련이 있는지에 따라 달라집니다.

구조체 필드의 라이프타임 이름은 항상 impl 키워드 뒤에 선언한 다음 구조체 이름 뒤에 사용해야 합니다. 이는 해당 라이프타임이 구조체의 타입 일부이기 때문입니다.

impl 블록 안의 메서드 서명에서 참조는 구조체 필드의 참조 라이프타임과 연관될 수도 있고 독립적일 수도 있습니다. 또한 라이프타임 생략 규칙 덕분에 메서드 서명에서 라이프타임 주석이 필요 없는 경우가 많습니다. Listing 10-24에서 정의한 ImportantExcerpt 구조체를 사용하여 몇 가지 예제를 살펴 보겠습니다.

먼저, level라는 메서드를 사용할 것입니다. 이 메서드의 유일한 매개 변수는 self에 대한 참조이며, 반환 값은 i32입니다. 이 반환 값은 어떤 값에 대한 참조가 아닙니다.

struct ImportantExcerpt<'a> {
    part: &'a str,
}

impl<'a> ImportantExcerpt<'a> {
    fn level(&self) -> i32 {
        3
    }
}

impl<'a> ImportantExcerpt<'a> {
    fn announce_and_return_part(&self, announcement: &str) -> &str {
        println!("Attention please: {announcement}");
        self.part
    }
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let first_sentence = novel.split('.').next().unwrap();
    let i = ImportantExcerpt {
        part: first_sentence,
    };
}

impl 이후의 라이프타임 매개변수 선언과 타입 이름 뒤에 사용하는 것은 필수이지만, 첫 번째 생략 규칙에 따라 self에 대한 참조의 라이프타임에 주석을 달 필요는 없습니다.

다음은 세 번째 라이프타임 생략 규칙이 적용되는 예입니다.

struct ImportantExcerpt<'a> {
    part: &'a str,
}

impl<'a> ImportantExcerpt<'a> {
    fn level(&self) -> i32 {
        3
    }
}

impl<'a> ImportantExcerpt<'a> {
    fn announce_and_return_part(&self, announcement: &str) -> &str {
        println!("Attention please: {announcement}");
        self.part
    }
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let first_sentence = novel.split('.').next().unwrap();
    let i = ImportantExcerpt {
        part: first_sentence,
    };
}

입력 라이프타임이 두 개 있으므로 Rust는 첫 번째 라이프타임 생략 규칙을 적용하여 &self과 announcement 각각에 고유한 라이프타임을 부여합니다. 그런 다음 매개변수 중 하나가 &self이므로 반환 타입은 &self의 라이프타임을 가지게 되며, 모든 라이프타임이 처리되었습니다.

'static 라이프타임

다루어야 할 특별한 라이프타임 중 하나는 'static입니다. 이는 해당 참조가 프로그램의 전체 실행 기간 동안 존재할 수 있음을 나타냅니다. 모든 문자열 리터럴은 'static 라이프타임을 가지며, 다음과 같이 주석을 달 수 있습니다:

#![allow(unused)]
fn main() {
let s: &'static str = "I have a static lifetime.";
}

이 문자열의 텍스트는 프로그램의 바이너리에 직접 저장되며 항상 사용할 수 있습니다. 따라서 모든 문자열 리터럴의 라이프타임은 'static입니다.

오류 메시지에서 'static 라이프타임을 사용하라는 제안을 볼 수 있습니다. 그러나 참조의 라이프타임으로 'static를 지정하기 전에, 해당 참조가 실제로 프로그램의 전체 라이프타임 동안 존재하는지, 그리고 그렇게 하고 싶은지 생각해 보세요. 대부분의 경우, 'static 라이프타임을建议使用하는 오류 메시지는 더핑 참조를 생성하거나 사용 가능한 라이프타임이 일치하지 않아 발생합니다. 이러한 경우 해결책은 'static 라이프타임을 지정하는 것이 아니라, 해당 문제를 수정하는 것입니다.

제네릭 타입 매개변수, 트레이트 바운드, 라이프타임

제네릭 타입 파라미터, 트레이트 바운드, 라이프타임을 하나의 함수에서 모두 지정하는 문법을 간단히 살펴보겠습니다!

fn main() {
    let string1 = String::from("abcd");
    let string2 = "xyz";

    let result = longest_with_an_announcement(
        string1.as_str(),
        string2,
        "Today is someone's birthday!",
    );
    println!("The longest string is {result}");
}

use std::fmt::Display;

fn longest_with_an_announcement<'a, T>(
    x: &'a str,
    y: &'a str,
    ann: T,
) -> &'a str
where
    T: Display,
{
    println!("Announcement! {ann}");
    if x.len() > y.len() { x } else { y }
}

이것은 두 문자열 슬라이스 중 더 긴 것을 반환하는 Listing 10-21의 longest 함수입니다. 하지만 이제 제네릭 타입 T인 추가 매개변수 ann이 있습니다. 이 매개변수는 where 절에서 지정된 바와 같이 Display 트레이트를 구현하는 어떤 타입으로든 채워질 수 있습니다. 이 추가 매개변수는 {}을 사용하여 출력되므로, Display 트레이트 바운드가 필요합니다. 라이프타임은 제네릭의 한 종류이므로, 라이프타임 매개변수 'a와 제네릭 타입 매개변수 T의 선언은 함수 이름 뒤의 각괄호 안에 있는 동일한 목록에 들어갑니다.

이 장에서는 많은 내용을 다뤘습니다! 이제 제네릭 타입 파라미터, 트레이트와 트레이트 바운드, 제네릭 라이프타임 파라미터에 대해 알고 있으므로, 다양한 상황에서 작동하는 반복 없는 코드를 작성할 준비가 되었습니다. 제네릭 타입 파라미터는 코드를 다른 타입에 적용할 수 있게 해줍니다. 트레이트와 트레이트 바운드는 타입이 제네릭이더라도 코드가 필요한 동작을 갖도록 보장합니다. 여러분은 라이프타임 주석을 사용하여 이 유연한 코드에 매달린 참조가 없도록 하는 방법을 배웠습니다. 그리고 이 모든 분석은 컴파일 타임에 이루어지며, 런타임 성능에 영향을 주지 않습니다!
