The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

부록 H. 최신 Rust와 실전 보충

이 노트는 공식 책의 기준인 Rust 1.97.0 이후에 알아두면 좋은 안정화 기능을 보충합니다. Rust 공식 책은 1.97.0 이상을 대상으로 하며, 2026년 11월 7일 현재 최신 안정판은 1.99.1입니다. 책 본문과 이 보충 노트의 범위를 구분해 읽어 주세요.

비동기 클로저와 AsyncFn 트레이트

Rust 1.85부터 비동기 클로저를 안정적으로 사용할 수 있습니다. async |인자| { ... } 형태로 작성하며, 호출하면 본문을 실행하는 대신 그 계산을 나타내는 Future를 돌려줍니다. 따라서 결과를 얻으려면 비동기 문맥에서 .await해야 합니다.

일반 클로저가 Fn, FnMut, FnOnce 중 하나를 구현하는 것처럼, 비동기 클로저는 캡처한 값을 어떻게 사용하는지에 따라 AsyncFn, AsyncFnMut, AsyncFnOnce를 구현합니다. 이 트레이트 바운드를 사용하면 비동기 콜백을 인자로 받는 함수의 의도를 직접 표현할 수 있습니다.

use std::future::Future;
use std::task::{Context, Poll, Waker};

async fn run_twice(callback: impl AsyncFn(u32) -> u32) -> u32 {
    callback(2).await + callback(3).await
}

fn main() {
    let mut future = Box::pin(run_twice(async |value| value * 2));
    let mut context = Context::from_waker(Waker::noop());

    match future.as_mut().poll(&mut context) {
        Poll::Ready(result) => println!("{result}"),
        Poll::Pending => println!("아직 완료되지 않았습니다."),
    }
}

예제는 즉시 완료되는 Future만 한 번 폴링해 결과를 보여 줍니다. 실제 네트워크·파일 I/O처럼 기다림이 필요한 비동기 작업은 적절한 런타임과 실행기를 사용해야 합니다. Rust 표준 라이브러리에는 범용 async 런타임이 포함되어 있지 않습니다. 실행 결과는 10입니다.

비동기 클로저가 유용한 이유

이전에도 |값| async { ... }처럼 일반 클로저가 async 블록을 반환하게 쓸 수 있었습니다. 하지만 이 방식으로 만든 Future는 클로저가 캡처한 값을 빌릴 수 없습니다. 비동기 클로저는 호출로 만들어진 Future가 클로저의 캡처를 빌릴 수 있어, 비동기 콜백 안에서 상태를 다루는 경우를 더 자연스럽게 표현합니다.

use std::future::ready;

async fn append_ready_value(values: &mut Vec<String>) {
    let mut append = async || {
        values.push(ready(String::from("Rust")).await);
    };

    append().await;
}

여기서 비동기 클로저가 반환하는 Future는 values의 가변 빌림을 사용합니다. 그래서 이 Future가 완료되기 전에는 같은 값을 다른 곳에서 동시에 가변 빌릴 수 없습니다. 이는 기존 소유권·빌림 규칙과 동일합니다.

실전 Rust: 컬렉션과 설계 관용구

공식 책에서 Vec, String, HashMap의 기초를 배웠다면, 이제 문제에 맞는 자료구조를 고르고 타입으로 잘못된 사용을 막는 방법을 살펴볼 수 있습니다. 아래 내용은 특정 프레임워크나 유행을 소개하는 목록이 아니라, 표준 라이브러리와 Rust API 설계 지침에서 이어지는 실용적인 관용구입니다.

문제에 맞는 컬렉션 고르기

  • Vec<T>: 순서를 유지하며 값을 모으고, 끝에 추가하거나 인덱스로 접근할 때 기본으로 고려합니다. 스택으로도 쓸 수 있습니다.
  • VecDeque<T>: 앞과 뒤 양쪽에서 넣고 빼는 큐가 필요할 때 사용합니다.
  • HashMap<K, V>: 키로 값을 빠르게 찾거나 빈도·캐시를 관리할 때 적합합니다. 순회 순서는 정렬되어 있지 않습니다.
  • BTreeMap<K, V>: 키 순서대로 순회하거나 정렬된 범위 검색이 필요할 때 사용합니다.
  • HashSet<T>와 BTreeSet<T>: 값의 존재 여부만 기억할 때 씁니다. 정렬이 필요하면 BTreeSet을 선택합니다.
  • BinaryHeap<T>: 우선순위가 가장 높은 항목부터 꺼내야 할 때 유용합니다.

처음부터 복잡한 구조를 고를 필요는 없습니다. 표준 라이브러리 문서도 대부분의 범용 상황에서는 Vec이나 HashMap으로 시작하고, 실제 요구가 생길 때 다른 컬렉션을 선택하도록 안내합니다. 이중 연결 리스트인 LinkedList는 특정 연산 특성이 꼭 필요할 때 고려하는 편이 좋습니다. 더 자세한 선택 기준은 표준 컬렉션 문서를 참고하세요.

use std::collections::{BTreeMap, HashMap, VecDeque};

fn main() {
    let mut counts = HashMap::new();
    for word in ["rust", "ownership", "rust"] {
        *counts.entry(word).or_insert(0) += 1;
    }
    println!("rust 등장 횟수: {}", counts.get("rust").copied().unwrap_or(0));

    let mut queue = VecDeque::new();
    queue.push_back("첫 번째 작업");
    queue.push_back("두 번째 작업");
    println!("처리할 작업: {}", queue.pop_front().unwrap_or("없음"));

    let mut scores = BTreeMap::new();
    scores.insert("보라", 92);
    scores.insert("가람", 87);
    for (name, score) in &scores {
        println!("{name}: {score}");
    }
}

HashMap::entry는 키를 조회한 뒤 없으면 넣는 작업을 한 번의 흐름으로 표현합니다. 반면 BTreeMap은 키 순서로 순회하므로 이 예제의 이름은 정렬되어 출력됩니다. 실행 결과는 각각 rust 등장 횟수: 2, 처리할 작업: 첫 번째 작업, 가람: 87, 보라: 92입니다.

작업 흐름으로 컬렉션 선택하기

문자열에서 단어별 횟수를 세고 결과를 출력하는 상황을 생각해 봅시다. 횟수 누적은 HashMap의 entry로, 키 순서가 필요한 출력은 BTreeMap으로 표현할 수 있습니다. 중복 여부만 확인하는 태그 목록에는 HashSet이 알맞고, 먼저 들어온 작업부터 꺼내는 대기열에는 VecDeque가 자연스럽습니다. 자료구조는 “Rust에서 가장 빠른 것”을 외워 고르는 게 아니라, 필요한 순서·검색·삽입 동작을 기준으로 정합니다.

성능이 중요해지면 실제 데이터와 작업량으로 측정하세요. 예를 들어 키를 정렬할 필요가 없는데 출력 순서가 우연히 일정하다고 가정하면 안 됩니다. HashMap의 순회 순서는 보장되지 않으므로, 재현 가능한 출력이 필요하면 BTreeMap을 사용하거나 키를 별도로 정렬합니다.

뉴타입으로 값의 의미를 분명히 하기

서로 다른 의미를 같은 기본 타입으로 표현하면 인자를 뒤바꿔도 컴파일러가 알아채지 못할 수 있습니다. 튜플 구조체로 감싼 새 타입을 만들면 컴파일 시점에 구별할 수 있습니다. 예를 들어 사용자 ID와 주문 ID를 모두 u64로 저장하더라도 UserId와 OrderId를 따로 정의하면 둘을 실수로 바꾸어 전달하는 일을 막을 수 있습니다. Rust 책의 뉴타입 패턴 설명과 Rust API Guidelines에서 더 살펴볼 수 있습니다.

설정이 많은 값은 빌더로 만들기

필수 인자와 선택 설정이 많아 생성자 호출이 길어질 때는 빌더 패턴을 고려할 수 있습니다. 빌더의 설정 메서드가 빌더 자신을 돌려주면 메서드를 연결해 읽기 좋게 구성하고, 마지막 build 메서드에서 유효성 검사와 실제 값 생성을 맡길 수 있습니다. 설정이 몇 개뿐이라면 단순한 생성자나 구조체 리터럴이 더 명확합니다. 표준 라이브러리의 Command API를 비롯한 사례와 설계 지침은 빌더 권고를 참고하세요.

#[derive(Debug)]
struct ServerConfig {
    host: String,
    port: u16,
    workers: usize,
}

#[derive(Default)]
struct ServerConfigBuilder {
    host: Option<String>,
    port: Option<u16>,
    workers: Option<usize>,
}

impl ServerConfigBuilder {
    fn new() -> Self {
        Self::default()
    }

    fn host(mut self, host: impl Into<String>) -> Self {
        self.host = Some(host.into());
        self
    }

    fn port(mut self, port: u16) -> Self {
        self.port = Some(port);
        self
    }

    fn workers(mut self, workers: usize) -> Self {
        self.workers = Some(workers);
        self
    }

    fn build(self) -> Result<ServerConfig, &'static str> {
        let host = self.host.ok_or("host를 지정해야 합니다")?;
        let port = self.port.unwrap_or(8080);
        let workers = self.workers.unwrap_or(4);

        if port == 0 || workers == 0 {
            return Err("port와 workers는 0보다 커야 합니다");
        }

        Ok(ServerConfig { host, port, workers })
    }
}

fn main() {
    let result = ServerConfigBuilder::new()
        .host("127.0.0.1")
        .port(3000)
        .workers(8)
        .build();

    match result {
        Ok(config) => println!("{config:?}"),
        Err(message) => println!("설정 오류: {message}"),
    }
}

이 빌더는 필수 설정인 host가 빠졌거나 잘못된 값이 들어오면 Result로 오류를 돌려줍니다. port와 workers는 값을 지정하지 않았을 때 기본값을 사용합니다. 실행 결과는 ServerConfig { host: "127.0.0.1", port: 3000, workers: 8 }입니다.

상태는 가능한 경우 열거형으로 표현하기

상태에 따라 달라지는 데이터를 여러 bool 값으로 조합하면, 서로 모순되는 상태도 표현될 수 있습니다. 가능한 상태를 enum의 변형으로 나누고 각 상태에 필요한 데이터만 담으면 유효하지 않은 조합을 줄일 수 있습니다. 상태가 바뀌는 규칙을 메서드로 모아 두면 전이 과정을 따라가기도 쉽습니다. 이 방식은 Rust 책의 객체 지향 상태 패턴을 읽을 때도 비교해 볼 만합니다.

타입 상태로 허용되는 순서를 제한하기

상태 전이가 정해져 있고 잘못된 순서가 프로그래밍 오류라면, 각 상태를 별도 타입으로 나타내는 타입 상태(typestate) 패턴을 고려할 수 있습니다. 아래 주문은 초안에서 결제 완료를 거쳐 배송 상태로만 이동합니다. DraftOrder에는 ship 메서드가 없으므로 결제하지 않은 주문을 바로 배송하는 코드는 컴파일되지 않습니다.

#[derive(Debug)]
struct OrderId(u64);

#[derive(Debug)]
struct OrderData {
    id: OrderId,
    item_count: usize,
}

#[derive(Debug)]
struct DraftOrder(OrderData);

#[derive(Debug)]
struct PaidOrder(OrderData);

#[derive(Debug)]
struct ShippedOrder(OrderData);

impl DraftOrder {
    fn new(id: u64, item_count: usize) -> Self {
        Self(OrderData {
            id: OrderId(id),
            item_count,
        })
    }

    fn pay(self) -> PaidOrder {
        PaidOrder(self.0)
    }
}

impl PaidOrder {
    fn ship(self) -> ShippedOrder {
        ShippedOrder(self.0)
    }
}

fn main() {
    let order = DraftOrder::new(42, 2).pay().ship();
    println!("배송 완료: 주문 {}, 상품 {}개", (order.0.id).0, order.0.item_count);
}

타입 상태는 잘못된 순서를 컴파일 시점에 막지만, 상태마다 타입과 변환 메서드가 늘어납니다. 상태가 데이터에 따라 동적으로 바뀌거나 상태 수가 많다면 단일 구조체와 enum을 쓰는 편이 더 간단할 수 있습니다. 타입 상태는 중요한 불변 조건을 API 차원에서 보장할 때 선택하세요.

직접 적용해 보는 연습

  1. 컬렉션 예제에 HashSet을 추가하고, 같은 태그를 여러 번 넣어도 고유한 태그 수만 출력해 보세요.
  2. 서버 설정 빌더에 TLS 사용 여부를 선택하는 설정을 추가하세요. 기본값을 정하고, 서로 함께 쓸 수 없는 설정 조합이 있다면 build에서 오류를 반환하게 해 보세요.
  3. 주문 타입 상태 예제에 초안 주문 취소 동작을 추가하세요. 결제 완료 주문에는 취소 동작을 제공할지, 별도의 환불 상태와 타입으로 표현할지 생각해 보세요.

이 연습은 Rustlings나 Rust by Example처럼 작은 문제를 직접 풀며 익히는 방식을 참고해 새로 작성했습니다. 각 연습에는 하나의 정답만 있는 것이 아니라, 요구사항을 만족하는 타입과 컬렉션을 선택하고 그 이유를 설명하는 과정이 중요합니다.

이런 관용구는 규칙이 아니라 선택지입니다. 데이터의 크기와 접근 방식, 공개 API의 요구를 먼저 정하고, 필요한 만큼만 추상화를 도입하세요.

이어 학습하기

Comprehensive Rust는 기초를 익힌 뒤 동시성, 임베디드, Android·Chromium 연동 같은 주제로 확장하는 강의형 자료입니다. 한국어 번역도 제공됩니다. 강의실 수업을 염두에 둔 구성이라 독학에서는 설명과 연습을 보완해서 활용하세요. Rust Design Patterns는 Rust 특유의 관용구와 안티패턴을 더 깊게 찾아볼 수 있는 커뮤니티 자료입니다. 비동기 프로그래밍은 Async Book을 참고할 수 있지만, 현재 개편 중인 작업본이므로 빠진 내용이 있을 수 있습니다.

이 페이지의 설명과 코드는 이 책을 위해 새로 작성했으며, 다른 교재의 문단을 복사하거나 직역하지 않았습니다. 외부 자료는 원 저작자와 라이선스를 확인할 수 있도록 링크로 안내합니다. Rust 표준 컬렉션 문서 · Rust API Guidelines: 타입 안전성과 빌더

공식 책 기준 이후의 변경

공식 책의 기준 버전은 Rust 1.97.0 이상입니다. 현재 안정판 1.99 계열에는 FFI 경계에서 C ABI 가변 인자 함수를 정의하는 기능과, 메타데이터가 없는 원시 포인터에서 동적 크기 타입의 크기·정렬을 조회하는 저수준 API 등이 추가되었습니다. 이런 기능은 주로 FFI나 unsafe 저수준 코드에서 필요하므로 초급 학습 흐름에는 넣지 않고, 버전 변화 안내로만 기록합니다. 자세한 변경점은 각 공식 릴리스 노트에서 확인할 수 있습니다.
