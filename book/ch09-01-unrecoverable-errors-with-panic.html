The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

복구할 수 없는 오류 panic!

때때로 코드에서 나쁜 일이 발생하고, 여러분이 할 수 있는 일은 없습니다. 이러한 경우, 러스트는 panic! 매크로를 가지고 있습니다. 실제로 패닉을 일으키는 두 가지 방법이 있습니다: 코드를 패닉으로 만드는 작업을 수행하거나(종료된 배열에 접근하는 것과 같은), panic! 매크로를 명시적으로 호출하는 것입니다. 두 경우 모두, 우리는 프로그램에서 패닉을 일으킬 수 있습니다.

공황에 대한 응답으로 스택을 풀거나 중단

기본적으로, 패닉이 발생하면 프로그램은 풀기 시작합니다. 즉, 러스트는 스택을 위로 걸어 올라가서 만나는 각 함수의 데이터를 정리합니다. 그러나 뒤로 걷고 정리하는 것은 많은 작업입니다. 따라서 러스트는 즉시 중단의 대안을 선택할 수 있습니다. 이는 프로그램을 정리하지 않고 종료합니다.

프로그램이 사용했던 메모리는 운영 체제에서 정리해야 합니다. 프로젝트에서 결과 바이너리를 가능한 한 작게 만들어야 하는 경우, panic = 'abort'를 Cargo.toml 파일의 해당 [profile] 섹션에 추가하여 풀기에서 중단으로 전환할 수 있습니다. 예를 들어, 릴리스 모드에서 패닉을 중단하려면 다음을 추가하십시오.

[profile.release]
panic = 'abort'

간단한 프로그램에서 panic!를 호출해 봅시다:

프로그램을 실행하면 다음과 같은 것을 볼 수 있습니다:

$ cargo run
   Compiling panic v0.1.0 (file:///projects/panic)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.25s
     Running `target/debug/panic`

thread 'main' (6018279) panicked at src/main.rs:2:5:
crash and burn
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

panic!를 호출하면 마지막 두 줄에 포함 된 오류 메시지가 발생합니다. 첫 번째 줄은 우리의 공황 메시지와 공황이 발생한 소스 코드의 위치를 보여줍니다. src / main.rs : 2 : 5는 src / main.rs 파일의 두 번째 줄, 다섯 번째 문자임을 나타냅니다.

이 경우, 표시된 라인은 우리 코드의 일부이며, 우리가 그 라인으로 가면, 우리는 panic! 매크로 호출. 다른 경우에, panic! 호출은 우리의 코드 호출 코드에있을 수 있으며, 오류 메시지에 의해보고 된 파일 이름과 줄 번호는 다른 사람의 코드가 될 것입니다 panic! 매크로가 호출됩니다, 결국에 주도하는 우리의 코드의 라인이 아닌 panic! 전화하기.

우리는 panic! 호출이 문제를 일으키는 코드의 일부를 파악하기 위해 나온 함수의 역 추적을 사용할 수 있습니다. panic! 역 추적을 사용하는 방법을 이해하려면, 다른 예제를 살펴보고 panic! 호출이 라이브러리에서 왔을 때와 같은지 알아봅시다. 왜냐하면 우리의 코드에서 버그가 있기 때문입니다.

여기서 우리는 벡터의 100번째 요소(인덱싱은 0에서 시작하기 때문에 99번 인덱스에 있음)에 접근하려고 하지만, 벡터는 세 개의 요소만 가지고 있습니다. 이 상황에서 러스트는 패닉에 빠질 것입니다. []를 사용하면 요소를 반환해야 하지만, 유효하지 않은 인덱스를 전달하면, 러스트가 올바른 값을 반환할 수 있는 요소가 없습니다.

C에서는 데이터 구조의 끝을 넘어서서 읽는 것은 정의되지 않은 동작입니다. 메모리가 해당 구조에 속하지 않더라도 데이터 구조의 해당 요소에 해당하는 메모리 위치에있는 것을 얻을 수 있습니다. 이것은 버퍼 오버 읽기라고하며 공격자가 데이터 구조 후에 저장되는 데이터를 읽을 수있는 방식으로 인덱스를 조작 할 수 있다면 보안 취약점이 발생할 수 있습니다.

이러한 종류의 취약점으로부터 프로그램을 보호하기 위해, 존재하지 않는 인덱스의 요소를 읽으려고 한다면, 러스트는 실행을 멈추고 계속하기를 거부할 것입니다. 한번 시도해 봅시다:

$ cargo run
   Compiling panic v0.1.0 (file:///projects/panic)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.27s
     Running `target/debug/panic`

thread 'main' (6017887) panicked at src/main.rs:4:6:
index out of bounds: the len is 3 but the index is 99
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

이 오류는 v에서 벡터의 색인 99에 액세스하려고 시도하는 main.rs의 4 행을 가리 킵니다.

이름 * note: 라인은 우리가 설정할 수 있음을 알려줍니다 RUST_BACKTRACE 환경 변수는 정확히 무슨 일이 일어 났는지의 backtrace를 얻을 수 있습니다. 역추적 이 지점에 도달하기 위해 호출 된 모든 함수의 목록입니다. 러스트의 Backtraces는 다른 언어에서와 마찬가지로 작동합니다. backtrace를 읽는 열쇠는 위에서 시작하여 작성한 파일을 볼 때까지 읽는 것입니다. 문제가 발생한 지점입니다. 그 자리 위의 줄은 코드가 호출 된 코드입니다. 아래 줄은 코드를 호출 한 코드입니다. 이 전과 후의 줄은 러스트의 핵심 코드를 사용하여 코드를 가져올 수 있습니다. 많은 출력입니다! 운영체제와 러스트 버전에 따라 표시되는 정확한 출력이 다를 수 있습니다. 이 정보로 역추적을 얻으려면 디버그 기호를 활성화해야 합니다. 여기에 있는 것처럼 cargo build 또는 cargo run 플래그가 없는 --release를 사용할 때 디버그 기호가 기본적으로 활성화됩니다.

Listing 9-2의 출력에서, backtrace의 6번째 줄은 src/main.rs의 4번째 줄과 같은 문제를 일으키는 우리 프로젝트의 라인을 가리킵니다. 만약 우리 프로그램이 패닉에 빠지기를 원하지 않는다면, 우리가 작성한 파일을 언급하는 첫 번째 줄이 가리키는 위치에서 조사를 시작해야 합니다. Listing 9-1에서, 우리가 의도적으로 패닉을 일으키는 코드를 작성했을 때, 패닉을 고치는 방법은 코드를 넘어서는 것을 요구하는 것입니다.
