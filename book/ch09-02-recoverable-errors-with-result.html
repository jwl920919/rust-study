The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

복구 가능한 오류: ResultResult

대부분의 오류는 프로그램이 완전히 중단될 정도로 심각하지 않습니다. 함수가 실패하는 경우, 그 원인을 쉽게 파악하고 대응할 수 있는 경우가 있습니다. 예를 들어, 파일을 열려고 했는데 파일이 존재하지 않아 작업이 실패했다면, 프로세스를 종료하는 대신 파일을 새로 만들 수 있습니다.

2장의 “Result로 잠재적 실패 처리하기”Result에서 Result 열거형은 다음과 같이 Ok와 Err 두 가지 변형으로 정의됩니다.

#![allow(unused)]
fn main() {
enum Result<T, E> {
    Ok(T),
    Err(E),
}
}

T과 E은 제네릭 타입 파라미터입니다. 제네릭에 대해서는 10장에서 자세히 다루겠습니다. 지금 알아두어야 할 것은, T가 Ok 변형 내에서 성공 시 반환되는 값의 타입을 나타내고, E가 Err 변형 내에서 실패 시 반환되는 오류의 타입을 나타낸다는 것입니다. Result이 이러한 제네릭 타입 파라미터를 가지고 있기 때문에, 반환하려는 성공 값과 오류 값이 서로 다를 수 있는 다양한 상황에서 Result 타입과 그 위에 정의된 함수를 사용할 수 있습니다.

함수가 실패할 수 있으므로 Result 값을 반환하는 함수를 호출해 보겠습니다. Listing 9-3에서 파일을 열려고 합니다.

File::open의 반환 타입은 Result<T, E>입니다. 제네릭 파라미터 T는 File::open의 구현에서 성공 값의 타입인 std::fs::File, 즉 파일 핸들로 채워집니다. 오류 값에 사용되는 E의 타입은 std::io::Error입니다. 이 반환 타입은 File::open 호출이 성공하여 읽거나 쓸 수 있는 파일 핸들을 반환할 수도 있음을 의미합니다. 함수 호출이 실패할 수도 있습니다. 예를 들어, 파일이 존재하지 않거나 파일에 접근할 권한이 없을 수 있습니다. File::open 함수는 성공했는지 실패했는지 알려주는 방법과 동시에 파일 핸들 또는 오류 정보를 제공해야 합니다. 이 정보는 정확히 Result 열거형이 전달하는 내용입니다.

File::open이 성공하는 경우, 변수 greeting_file_result의 값은 파일 핸들을 포함하는 Ok의 인스턴스가 됩니다. 실패하는 경우, greeting_file_result의 값은 발생한 오류의 종류에 대한 추가 정보를 포함하는 Err의 인스턴스가 됩니다.

Listing 9-4의 코드는 `File::open`이 실패한 이유가 무엇이든 `panic!`을 일으킵니다. 그러나 우리는 실패 원인에 따라 다른 행동을 취하고 싶습니다. `File::open`이 파일이 존재하지 않아서 실패했다면, 우리는 파일을 생성하고 새 파일의 핸들을 반환하고 싶습니다. `File::open`이 다른 이유로, 예를 들어 파일을 열 권한이 없어서 실패했다면, 여전히 Listing 9-4와 같은 방식으로 `panic!`을 일으키도록 하고 싶습니다. 이를 위해 Listing 9-5에 나와 있는 내부 `match` 표현식을 추가합니다. panic! File::open의 Err 변형 내부에서 반환되는 값의 타입은 io::Error입니다. 이는 표준 라이브러리가 제공하는 구조체입니다. 이 구조체에는 kind이라는 메서드가 있으며, 이를 호출하면 io::ErrorKind 값을 얻을 수 있습니다. 열거형(enumeration)인 io::ErrorKind은 표준 라이브러리가 제공하며, io 작업에서 발생할 수 있는 다양한 종류의 오류를 나타내는 변형(variant)을 가지고 있습니다. 우리가 사용하려는 변형은 ErrorKind::NotFound이며, 이는 우리가 열려고 하는 파일이 아직 존재하지 않음을 나타냅니다. 따라서 우리는 greeting_file_result에 대해 매칭(match)을 수행하되, error.kind()에 대해서도 내부적으로 매칭을 수행합니다.

내부 match에서 확인하려는 조건은 error.kind()이 반환하는 값이 ErrorKind 열거형의 NotFound 변형인지 여부입니다. 해당 변형인 경우, File::create을 사용하여 파일을 생성하려고 합니다. 그러나 File::create도 실패할 수 있으므로, 내부 match 식에 두 번째 분기가 필요합니다. 파일을 생성할 수 없는 경우, 다른 오류 메시지가 출력됩니다. 외부 match의 두 번째 분기는 그대로 유지되므로, 파일 누락 오류를 제외한 모든 오류에서 프로그램이 패닉합니다.

match과 함께 Result<T, E>를 사용하는 대안

match이 많이 필요합니다! match 식은 매우 유용하지만, 동시에 매우 원시적인 문법이기도 합니다. 13장에서는 클로저에 대해 배우게 되는데, 클로저는 Result<T, E>에 정의된 많은 메서드와 함께 사용됩니다. 이러한 메서드를 사용하면 코드에서 match 값을 처리할 때 Result<T, E>를 사용하는 것보다 더 간결하게 작성할 수 있습니다.

예를 들어, 목록 9-5에 나와 있는 것과 동일한 논리를 클로저와 unwrap_or_else 메서드를 사용하여 작성하는 또 다른 방법은 다음과 같습니다:

use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let greeting_file = File::open("hello.txt").unwrap_or_else(|error| {
        if error.kind() == ErrorKind::NotFound {
            File::create("hello.txt").unwrap_or_else(|error| {
                panic!("Problem creating the file: {error:?}");
            })
        } else {
            panic!("Problem opening the file: {error:?}");
        }
    });
}

이 코드는 목록 9-5와 동일한 동작을 하지만, match 식을 포함하지 않으며 읽기에도 더 깔끔합니다. 13장을 읽은 후 이 예제로 돌아와 표준 라이브러리 문서에서 unwrap_or_else 메서드를 찾아보세요. 이러한 메서드 중 더 많은 것들이 오류를 다룰 때 거대하고 중첩된 match 식을 정리하는 데 도움이 됩니다.

오류 전파

함수 구현에서 실패할 수 있는 작업을 호출할 때, 함수 내부에서 오류를 처리하는 대신 오류를 호출한 코드로 반환할 수 있습니다. 그러면 호출한 코드가 어떻게 처리할지 결정할 수 있습니다. 이를 오류 전파라고 하며, 호출한 코드에는 현재 코드 컨텍스트에서 사용할 수 있는 것보다 오류 처리 방식을 결정하는 더 많은 정보나 로직이 있을 수 있으므로 더 많은 제어 권한을 부여합니다.

예를 들어, Listing 9-6은 파일에서 사용자 이름을 읽는 함수를 보여줍니다. 파일이 없거나 읽을 수 없는 경우, 이 함수는 해당 오류를 함수를 호출한 코드로 반환합니다.

이 함수는 훨씬 더 짧은 방식으로 작성할 수 있지만, 오류 처리를 탐색하기 위해 처음에는 많은 부분을 수동으로 수행하겠습니다. 마지막에 더 짧은 방식을 보여드리겠습니다. 먼저 함수의 반환형을 살펴보겠습니다: Result<String, io::Error>. 이는 함수가 Result<T, E> 유형의 값을 반환한다는 의미이며, 여기서 제네릭 매개변수 T에는 구체적 유형 String이, 제네릭 유형 E에는 구체적 유형 io::Error이 채워져 있습니다.

이 함수가 아무 문제 없이 성공하면, 이 함수를 호출하는 코드는 Ok 보유하는 값 A String—그 username 이 함수는 파일로부터 읽어들인다. 이 함수가 어떤 문제를 만나면, 호출 코드는 Err 인스턴스를 보유하고 있는 값 io::Error 그것은 문제가 무엇이었는지에 관하여 정보를 더 포함합니다. 우리는 선택했습니다 io::Error 이 함수의 반환 유형으로, 이 함수의 본문에서 실패할 수 있는 두 가지 작업 모두에서 반환되는 오류 값의 유형이기 때문입니다. File::open 기능 및 read_to_string 방법.

함수 본문은 File::open 함수를 호출하는 것으로 시작합니다. 그런 다음, Listing 9-4의 match과 유사한 match로 Result 값을 처리합니다. File::open이 성공하면, 패턴 변수 file의 파일 핸들이 가변 변수 username_file의 값이 되고 함수가 계속 진행됩니다. Err인 경우, panic!을 호출하는 대신 return 키워드를 사용하여 함수를 완전히 조기 반환하고, 이제 패턴 변수 e에 있는 File::open의 오류 값을 이 함수의 오류 값으로 호출 코드에 반환합니다.

따라서 username_file에 파일 핸들이 있으면, 함수는 변수 username에 새로운 String을 생성하고, username_file의 파일 핸들에 read_to_string 메서드를 호출하여 파일 내용을 username에 읽습니다. read_to_string 메서드도 실패할 수 있으므로 Result을 반환합니다. File::open이 성공했더라도 마찬가지입니다. 따라서 그 Result을 처리하기 위해 또 다른 match가 필요합니다. read_to_string이 성공하면, 함수가 성공한 것이므로, 이제 username에 있는 파일의 사용자 이름을 Ok에 감싸서 반환합니다. read_to_string이 실패하면, File::open의 반환 값을 처리한 match에서 오류 값을 반환했던 것과 동일한 방식으로 오류 값을 반환합니다. 그러나 이는 함수의 마지막 식이므로 return을 명시적으로 말할 필요가 없습니다.

이 코드를 호출하는 코드는 Ok 값으로 사용자 이름을 포함하거나, Err 값으로 io::Error 를 포함하는 결과를 처리합니다. 이 값들을 어떻게 처리할지는 호출하는 코드가 결정합니다. 호출하는 코드가 Err 값을 받으면, panic! 를 호출하여 프로그램을 중단하거나, 기본 사용자 이름을 사용하거나, 파일이 아닌 다른 곳에서 사용자 이름을 조회하는 등의 조치를 취할 수 있습니다. 호출하는 코드가 실제로 무엇을 하려는지에 대한 정보가 충분하지 않으므로, 성공 또는 오류 정보를 모두 상위 단계로 전파하여 해당 코드가 적절히 처리하도록 합니다.

이러한 오류 전파 패턴은 Rust에서 매우 일반적이므로, Rust는 이를 더 쉽게 만들기 위해 물음표 연산자 ?를 제공합니다.

? 연산자 단축기

Listing 9-7은 Listing 9-6과 동일한 기능을 가진 read_username_from_file의 구현을 보여주며, 이 구현은 ? 연산자를 사용합니다.

Result 값 뒤에 배치하는 ?은 Listing 9-6에서 Result 값을 처리하도록 정의한 match 표현식과 거의 동일한 방식으로 동작하도록 정의되어 있습니다. Result의 값이 Ok인 경우, Ok 안의 값이 이 표현식에서 반환되고 프로그램은 계속 실행됩니다. 값이 Err인 경우, Err이 return 키워드를 사용한 것처럼 전체 함수에서 반환되어 에러 값이 호출 측 코드로 전파됩니다.

리스트 9-6의 match 식이 하는 일과 ? 연산자가 하는 일 사이에는 차이가 있습니다. ? 연산자가 호출된 에러 값은 표준 라이브러리의 From 트레이트에 정의된 from 함수를 거칩니다. 이 함수는 한 타입의 값을 다른 타입으로 변환하는 데 사용됩니다. ? 연산자가 from 함수를 호출하면, 수신된 에러 타입은 현재 함수의 반환 타입에 정의된 에러 타입으로 변환됩니다. 이는 함수의 일부가 여러 다른 이유로 실패할 수 있더라도, 함수가 실패할 수 있는 모든 방식을 하나의 에러 타입으로 나타내어 반환할 때 유용합니다.

예를 들어, Listing 9-7의 read_username_from_file 함수를 우리가 정의하는 사용자 정의 에러 타입인 OurError을 반환하도록 변경할 수 있습니다. 또한 impl From<io::Error> for OurError을 정의하여 OurError에서 io::Error 인스턴스를 생성하도록 한다면, ? 함수 본문에서 read_username_from_file 연산자를 호출할 때 from를 호출하여 에러 타입을 변환하므로 함수에 추가 코드를 작성할 필요가 없습니다.

Listing 9-7의 맥락에서, ? 호출 끝의 File::open은 Ok 내부의 값을 username_file 변수에 반환합니다. 오류가 발생하면, ? 연산자는 전체 함수에서 조기에 반환하여 모든 Err 값을 호출 코드에 전달합니다. ? 호출 끝의 read_to_string에도 동일한 규칙이 적용됩니다.

? 연산자는 많은 불필요한 코드를 제거하여 이 함수의 구현을 더 간단하게 만듭니다. Listing 9-8에서 보듯이, ? 바로 뒤에 메서드 호출을 체이닝하여 이 코드를 더 짧게 만들 수도 있습니다.

String에 새로운 username 생성을 함수의 시작 부분으로 옮겼습니다. 이 부분은 변경되지 않았습니다. username_file 변수를 만드는 대신, read_to_string 호출을 File::open("hello.txt")?의 결과에 직접 체이닝했습니다. ? 호출의 끝에는 여전히 read_to_string가 있으며, Ok과 username이 모두 성공하면 오류를 반환하는 대신 File::open를 포함하는 read_to_string 값을 반환합니다. 이 기능은 Listing 9-6과 Listing 9-7과 동일하며, 단지 더 직관적으로 작성하는 다른 방식일 뿐입니다.

Listing 9-9는 fs::read_to_string을(를) 사용해 이를 더 간결하게 작성하는 방법을 보여 줍니다.

파일을 문자열로 읽는 작업은 상당히 흔하므로, 표준 라이브러리는 fs::read_to_string라는 편리한 기능을 제공합니다. 이 함수는 파일을 열고, 새로운 String을 생성한 뒤, 파일의 내용을 읽어 해당 String에 저장하고, 마지막으로 그 값을 반환합니다. 물론, fs::read_to_string를 사용하면 모든 오류 처리 과정을 자세히 설명할 수 있는 기회가 없으므로, 처음에는 더 긴 방식으로 작성했습니다.

`?` 연산자를 사용할 위치 ? 연산자

? 연산자는 반환 형식이 ?에 사용된 값과 호환되는 함수에서만 사용할 수 있습니다. 이는 ? 연산자가 Listing 9-6에서 정의한 match 표현식과 동일한 방식으로 함수에서 값을 조기 반환하도록 정의되어 있기 때문입니다. Listing 9-6에서 match 값에 대해 match를 사용했으며, 조기 반환 분기는 Result 값을 반환했습니다. 따라서 함수의 반환 형식은 이 반환값과 호환되도록 Err(e)이어야 합니다. Result return

Listing 9-10에서, ? 연산자를 main 함수에서 사용할 때 발생할 수 있는 오류를 살펴보겠습니다. 이 오류는 ?를 적용하는 값의 타입과 함수의 반환 타입이 호환되지 않을 때 발생합니다.

이 코드는 실패할 수 있는 파일을 엽니다. ? 연산자는 Result 함수가 반환하는 File::open 값을 따릅니다. 하지만 이 main 함수의 반환 형식은 main 이며, () 이 아닙니다. 이 코드를 컴파일하면 다음과 같은 오류 메시지가 나타납니다. Result

이 오류는 ? 연산자를 Result, Option 또는 FromResidual를 구현하는 다른 타입을 반환하는 함수에서만 사용할 수 있음을 지적합니다.

오류를 수정하려면 두 가지 선택지가 있습니다. 한 가지 선택지는 제한 사항이 없다면 ? 연산자를 사용하는 값과 호환되도록 함수의 반환 타입을 변경하는 것입니다. 다른 선택지는 match 또는 Result<T, E> 메서드 중 하나를 사용하여 Result<T, E>를 상황에 맞게 처리하는 것입니다.

오류 메시지는 또한 ?가 Option<T> 값과 함께 사용될 수 있음을 언급했습니다. ?에 Result를 사용하는 경우와 마찬가지로, ?에 Option를 사용할 수 있는 함수는 Option를 반환하는 함수뿐입니다. ? 연산자를 Option<T>에 호출했을 때의 동작은 Result<T, E>에 호출했을 때의 동작과 유사합니다. 값이 None인 경우, 해당 시점에서 함수에서 None를 조기에 반환합니다. 값이 Some인 경우, Some 내부의 값이 식의 결과 값이 되고 함수는 계속 진행됩니다. Listing 9-11에는 주어진 텍스트에서 첫 번째 줄의 마지막 문자를 찾는 함수의 예제가 있습니다.

이 함수는 Option<char>를 반환합니다. 왜냐하면 거기에 문자가 있을 수도 있지만, 없을 수도 있기 때문입니다. 이 코드는 text 문자열 슬라이스 인수를 받아 lines 메서드를 호출합니다. 이 메서드는 문자열의 줄에 대한 반복자를 반환합니다. 이 함수는 첫 번째 줄을 검사하려고 하므로, 반복자의 next를 호출하여 반복자에서 첫 번째 값을 가져옵니다. text가 빈 문자열인 경우, 이 next 호출은 None를 반환합니다. 이 경우 ?를 사용하여 None에서 last_char_of_first_line를 반환하고 중단합니다. text가 빈 문자열이 아닌 경우, next는 Some의 첫 번째 줄 문자열 슬라이스를 포함하는 text 값을 반환합니다.

?은 문자열 슬라이스를 추출하고, 이 문자열 슬라이스에 chars을 호출하여 문자의 반복자를 얻을 수 있습니다. 우리는 이 첫 번째 줄의 마지막 문자에 관심이 있으므로, 반복자의 마지막 항목을 반환하도록 last을 호출합니다. 이는 Option입니다. 왜냐하면 첫 번째 줄이 빈 문자열일 수 있기 때문입니다. 예를 들어, text가 빈 줄로 시작하지만 다른 줄에 문자가 있는 경우처럼 "\nhi"인 경우입니다. 그러나 첫 번째 줄에 마지막 문자가 있으면, 그것은 Some 변형으로 반환됩니다. 중간에 있는 ? 연산자는 이 논리를 간결하게 표현하는 방법을 제공하여, 함수를 한 줄로 구현할 수 있게 해줍니다. Option에 ? 연산자를 사용할 수 없다면, 더 많은 메서드 호출이나 match 표현식을 사용하여 이 논리를 구현해야 합니다.

? 반환하는 함수에서 Result에 Result 연산자를 사용할 수 있고, ? 반환하는 함수에서 Option에 Option 연산자를 사용할 수 있지만, 두 가지를 섞어 사용할 수는 없습니다. ? 연산자는 Result을 Option로, 또는 그 반대로 자동으로 변환하지 않습니다. 이러한 경우, ok의 Result 메서드나 ok_or의 Option 메서드와 같은 메서드를 사용하여 명시적으로 변환할 수 있습니다.

지금까지 사용한 모든 main 함수는 ()을 반환합니다. main 함수는 실행 가능한 프로그램의 진입점이자 종료점이므로 특별하며, 프로그램이 예상대로 동작하려면 반환 타입에 제한이 있습니다.

다행히도 main는 Result<(), E>을 반환할 수도 있습니다. Listing 9-12에는 Listing 9-10의 코드를 main의 반환 타입을 Result<(), Box<dyn Error>>으로 변경하고, 끝에 반환 값 Ok(())를 추가한 형태로 제시했습니다. 이제 이 코드는 컴파일됩니다.

Box<dyn Error> 타입은 트레이트 객체이며, 이는 18장의 “공유된 동작을 추상화하기 위한 트레이트 객체 사용”에서 다룹니다. 지금은 Box<dyn Error>을 “모든 종류의 에러”로 읽으면 됩니다. 에러 타입이 Box<dyn Error>인 main 함수에서 Result 값에 ?을 사용하는 것은 허용됩니다. 이는 어떤 Err 값이든 조기에 반환할 수 있기 때문입니다. 이 main 함수의 본문은 항상 std::io::Error 타입의 에러만 반환하지만, Box<dyn Error>을 지정함으로써, main의 본문에 다른 에러를 반환하는 코드가 추가되어도 이 시그니처는 계속 정확합니다.

때 A main 함수는 a를 반환합니다. Result<(), E>실행 파일은 다음과 같은 값으로 종료됩니다. 0 만약 main 반환 Ok(()) 0이 아닌 값으로 종료할 경우 main 반환값 Err value. C로 작성된 실행 파일은 종료할 때 정수를 반환한다: 성공적으로 종료되는 프로그램은 정수를 반환한다. 0, 그리고 에러가 다른 정수를 반환하는 프로그램들 0. 러스트는 또한 이 관례와 호환되도록 실행 파일에서 정수를 반환합니다.

main 함수는 std::process::Termination 트레이트를 구현하는 모든 타입을 반환할 수 있으며, 이 트레이트에는 ExitCode을 반환하는 report 함수가 포함되어 있습니다. 사용자 정의 타입에 대해 Termination 트레이트를 구현하는 방법에 대한 자세한 내용은 표준 라이브러리 문서를 참조하세요.

이제 panic!를 호출하거나 Result를 반환하는 세부 사항을 논의했으므로, 어떤 경우에 각각을 사용하는 것이 적절한지 결정하는 주제로 돌아가 보겠습니다.
