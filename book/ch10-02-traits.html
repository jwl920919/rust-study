The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

트레이트로 공유된 동작 정의하기

트레이트는 특정 타입이 가지고 있으며 다른 타입과 공유할 수 있는 기능을 정의합니다. 트레이트를 사용하면 추상적인 방식으로 공유된 동작을 정의할 수 있습니다. 또한 트레이트 바운드를 사용하면 제네릭 타입이 특정 동작을 가진 어떤 타입이든 될 수 있도록 지정할 수 있습니다.

참고: 트레이트는 다른 언어에서 인터페이스라고 불리는 기능과 유사하지만 몇 가지 차이점이 있습니다.

트레이트 정의하기

타입의 동작은 해당 타입에서 호출할 수 있는 메서드로 구성됩니다. 모든 타입에서 동일한 메서드를 호출할 수 있다면, 그 타입들은 동일한 동작을 공유한다고 할 수 있습니다. 트레이트 정의는 특정 목적을 달성하는 데 필요한 동작 집합을 정의하기 위해 메서드 서명을 함께 묶는 방법입니다.

예를 들어, 다양한 종류와 양의 텍스트를 포함하는 여러 구조체가 있다고 가정해 보겠습니다. 특정 위치에 제출된 뉴스 기사를 보관하는 NewsArticle 구조체와, 새 게시물인지, 재게시물인지, 아니면 다른 게시물에 대한 회신인지를 나타내는 메타데이터와 함께 최대 280자를 가질 수 있는 SocialPost 구조체입니다.

aggregator라는 이름의 미디어 집계 라이브러리 크레이트를 만들고 싶습니다. 이 크레이트는 NewsArticle 또는 SocialPost 인스턴스에 저장될 수 있는 데이터의 요약을 표시할 수 있어야 합니다. 이를 위해 각 타입으로부터 요약을 얻어야 하며, 인스턴스에서 summarize 메서드를 호출하여 그 요약을 요청할 것입니다. Listing 10-12는 이 동작을 표현하는 공개된 Summary 트레이트의 정의를 보여줍니다.

여기서 trait 키워드를 사용하여 트레잇을 선언하고, 그 뒤에 이 경우의 트레잇 이름인 Summary을 붙입니다. 또한 이 트레잇을 pub로 선언하여, 이 크레이트에 의존하는 다른 크레이트에서도 이 트레잇을 사용할 수 있도록 합니다. 몇 가지 예제에서 이를 확인할 수 있습니다. 중괄호 안에서는 이 트레잇을 구현하는 타입의 동작을 설명하는 메서드 시그니처를 선언합니다. 이 경우 해당 시그니처는 fn summarize(&self) -> String입니다.

메서드 시그니처 이후에는 중괄호 안에서 구현을 제공하는 대신 세미콜론을 사용합니다. 이 트레잇을 구현하는 각 타입은 메서드 본문에 대한 자체적인 동작을 제공해야 합니다. 컴파일러는 Summary 트레잇을 가진 모든 타입에 이 시그니처와 정확히 일치하는 summarize 메서드가 정의되도록 강제합니다.

트레잇의 본문에는 여러 메서드를 포함할 수 있습니다. 메서드 시그니처는 한 줄에 하나씩 나열하며, 각 줄은 세미콜론으로 끝납니다.

타입에 트레잇 구현하기

이제 Summary 트레잇의 메서드 시그니처를 정의했으므로, 미디어 어그리게이터의 타입에 이를 구현할 수 있습니다. Listing 10-13은 Summary 구조체에 NewsArticle 트레잇을 구현한 예시입니다. 이 구현에서는 headline, author, location을 사용하여 summarize 메서드의 반환 값을 생성합니다. SocialPost 구조체의 경우, 게시물 내용이 이미 280자로 제한되어 있다고 가정하고, 사용자 이름 뒤에 게시물의 전체 텍스트를 이어 붙이는 방식으로 summarize를 정의합니다.

타입에 트레잇을 구현하는 것은 일반 메서드를 구현하는 것과 유사합니다. 차이점은 impl 뒤에 구현하려는 트레잇 이름을 적은 다음, for 키워드를 사용하고, 마지막으로 트레잇을 구현하려는 타입의 이름을 지정한다는 점입니다. impl 블록 안에는 트레잇 정의에서 선언한 메서드 시그니처를 넣습니다. 각 시그니처 뒤에 세미콜론을 추가하는 대신, 중괄호를 사용하여 해당 타입에 대해 트레잇 메서드가 가져야 하는 구체적인 동작으로 메서드 본문을 채웁니다.

이제 라이브러리가 Summary 트레이트를 NewsArticle과 SocialPost에 구현했으므로, 크레이트 사용자는 일반 메서드를 호출하는 것과 동일한 방식으로 NewsArticle과 SocialPost 인스턴스에서 트레이트 메서드를 호출할 수 있습니다. 유일한 차이점은 사용자가 트레이트와 타입을 모두 스코프에 가져와야 한다는 것입니다. 바이너리 크레이트가 우리의 aggregator 라이브러리 크레이트를 사용하는 예시는 다음과 같습니다:

use aggregator::{SocialPost, Summary};

fn main() {
    let post = SocialPost {
        username: String::from("horse_ebooks"),
        content: String::from(
            "of course, as you probably already know, people",
        ),
        reply: false,
        repost: false,
    };

    println!("1 new post: {}", post.summarize());
}

이 코드는 1 new post: horse_ebooks: of course, as you probably already know, people를 출력합니다.

에 의존하는 다른 크레이트들 aggregator 크레이트는 또한 가져올 수 있습니다 Summary 구현 할 범위에 대한 특성 Summary 참고할 한 가지 제한 사항은 트레잇이나 타입, 또는 둘 다 크레이트에 로컬인 경우에만 트레잇을 구현할 수 있다는 것입니다. 예를 들어, 다음과 같은 표준 라이브러리 트레잇을 구현할 수 있습니다. Display 사용자 정의 형식에 SocialPost 우리의 일부로서 aggregator 크레이트 기능 때문에 유형 SocialPost 지역 우리의 aggregator 크레이트. 우리는 또한 실행해서 좋습니다 Summary 온 Vec<T> 우리의 aggregator 크레이트 특성 때문에 Summary 지역 우리의 aggregator 크레이트.

하지만 외부 타입에서는 외부 트레잇을 구현할 수 없습니다. 예를 들어, Display 트레잇 켜짐 Vec<T> 우리 안에 aggregator 크레이트, 왜냐하면 Display 그리고 Vec<T> 둘 다 표준 라이브러리에 정의되어 있으며 우리에 대한 로컬이 아닙니다. aggregator 크레이트. 이 제한은 호출 된 속성의 일부입니다. 일관성더욱 구체적으로, The more specifically, 고아 규칙부모 타입이 존재하지 않기 때문에 , 이렇게 이름지어졌습니다. 이 규칙은 다른 사람들의 코드가 여러분의 코드를 깰 수 없도록 하고, 그 반대의 경우도 마찬가지입니다. 규칙이 없다면, 두 개의 크레이트들은 같은 타입에 대해 같은 트레잇을 구현할 수 있으며, 러스트는 어떤 구현을 사용할지 알 수 없을 것입니다.

기본 구현 사용

때로는 모든 타입의 모든 메서드에 대해 구현을 요구하는 대신, 트레잇의 일부 또는 모든 메서드에 대해 기본 동작을 갖는 것이 유용합니다. 그러면 특정 타입에 대해 트레잇을 구현할 때 각 메서드의 기본 동작을 유지하거나 재정의할 수 있습니다.

Listing 10-14에서는 Listing 10-12에서처럼 메서드 시그니처만 정의하는 대신, summarize 트레잇의 Summary 메서드에 대해 기본 문자열을 지정합니다.

기본 구현을 사용하여 NewsArticle 인스턴스를 요약하려면 impl 블록을 impl Summary for NewsArticle {}로 지정합니다.

이제 더 이상 summarize에 직접 NewsArticle 메서드를 정의하지 않지만, 기본 구현을 제공하고 NewsArticle가 Summary 트레이트를 구현하도록 지정했습니다. 그 결과, 다음과 같이 summarize 인스턴스에서 NewsArticle 메서드를 호출할 수 있습니다:

use aggregator::{self, NewsArticle, Summary};

fn main() {
    let article = NewsArticle {
        headline: String::from("Penguins win the Stanley Cup Championship!"),
        location: String::from("Pittsburgh, PA, USA"),
        author: String::from("Iceburgh"),
        content: String::from(
            "The Pittsburgh Penguins once again are the best \
             hockey team in the NHL.",
        ),
    };

    println!("New article available! {}", article.summarize());
}

이 코드는 New article available! (Read more...)을 출력합니다.

기본 구현을 추가한다고 해서 Summary에 대한 SocialPost의 구현을 변경할 필요가 없습니다. 그 이유는 기본 구현을 재정의하는 문법이 기본 구현이 없는 트레이트 메서드를 구현하는 문법과 동일하기 때문입니다.

디폴트 구현체는 다른 메서드가 디폴트 구현체를 가지고 있지 않더라도, 같은 트레이트의 다른 메서드를 호출할 수 있습니다. 이를 통해 트레이트는 유용한 기능을 많이 제공하면서도, 구현자가 직접 구현해야 하는 부분은 아주 작게만 요구할 수 있습니다. 예를 들어, Summary 메서드를 구현하도록 요구하는 summarize_author 트레이트를 정의할 수 있습니다. 그리고 summarize 메서드를 호출하는 디폴트 구현을 가진 summarize_author 메서드를 정의할 수 있습니다.

pub trait Summary {
    fn summarize_author(&self) -> String;

    fn summarize(&self) -> String {
        format!("(Read more from {}...)", self.summarize_author())
    }
}

pub struct SocialPost {
    pub username: String,
    pub content: String,
    pub reply: bool,
    pub repost: bool,
}

impl Summary for SocialPost {
    fn summarize_author(&self) -> String {
        format!("@{}", self.username)
    }
}

이 버전의 Summary를 사용하려면, 특정 타입에 트레잇을 구현할 때 summarize_author만 정의하면 됩니다:

pub trait Summary {
    fn summarize_author(&self) -> String;

    fn summarize(&self) -> String {
        format!("(Read more from {}...)", self.summarize_author())
    }
}

pub struct SocialPost {
    pub username: String,
    pub content: String,
    pub reply: bool,
    pub repost: bool,
}

impl Summary for SocialPost {
    fn summarize_author(&self) -> String {
        format!("@{}", self.username)
    }
}

summarize_author을 정의한 후에는 summarize의 인스턴스에서 SocialPost를 호출할 수 있습니다. 이때 summarize의 기본 구현은 우리가 제공한 summarize_author의 정의를 호출합니다. summarize_author를 구현했기 때문에, Summary 트레이트는 추가 코드를 작성하지 않아도 summarize 메서드의 동작을 제공합니다. 그 모습은 다음과 같습니다.

use aggregator::{self, SocialPost, Summary};

fn main() {
    let post = SocialPost {
        username: String::from("horse_ebooks"),
        content: String::from(
            "of course, as you probably already know, people",
        ),
        reply: false,
        repost: false,
    };

    println!("1 new post: {}", post.summarize());
}

이 코드는 1 new post: (Read more from @horse_ebooks...)를 출력합니다.

동일한 메서드의 재정의 구현에서 기본 구현을 호출할 수 없습니다.

매개변수로 트레이트 사용하기

이제 트레이트를 정의하고 구현하는 방법을 알았으므로, 다양한 타입을 허용하는 함수를 정의하는 방법을 살펴볼 수 있습니다. Listing 10-13에서 Summary 타입과 NewsArticle 타입에 구현한 SocialPost 트레이트를 사용하여 notify 함수를 정의하겠습니다. 이 함수는 summarize 매개변수의 타입이 item 트레이트를 구현하는 경우에만 해당 타입의 Summary 메서드를 호출합니다. 이를 위해 impl Trait 구문을 다음과 같이 사용합니다.

pub trait Summary {
    fn summarize(&self) -> String;
}

pub struct NewsArticle {
    pub headline: String,
    pub location: String,
    pub author: String,
    pub content: String,
}

impl Summary for NewsArticle {
    fn summarize(&self) -> String {
        format!("{}, by {} ({})", self.headline, self.author, self.location)
    }
}

pub struct SocialPost {
    pub username: String,
    pub content: String,
    pub reply: bool,
    pub repost: bool,
}

impl Summary for SocialPost {
    fn summarize(&self) -> String {
        format!("{}: {}", self.username, self.content)
    }
}

pub fn notify(item: &impl Summary) {
    println!("Breaking news! {}", item.summarize());
}

item 매개변수에 구체적인 타입 대신 impl 키워드와 트레이트 이름을 지정합니다. 이 매개변수는 지정된 트레이트를 구현하는 모든 타입을 허용합니다. notify 함수 본문에서는 item에서 오는 Summary 트레이트의 메서드, 예를 들어 summarize를 호출할 수 있습니다. notify 함수를 호출할 때 NewsArticle 또는 SocialPost의 인스턴스를 전달할 수 있습니다. String 또는 i32와 같은 다른 타입으로 함수를 호출하는 코드는 컴파일되지 않습니다. 이는 해당 타입들이 Summary 트레이트를 구현하지 않기 때문입니다.

트레이트 바운드 구문

impl Trait 구문은 간단한 경우에 유용하지만, 실제로는 트레이트 바운드(trait bound)라고 불리는 더 긴 형태의 구문 설탕(syntax sugar)입니다. 이 구문은 다음과 같습니다:

pub fn notify<T: Summary>(item: &T) {
    println!("Breaking news! {}", item.summarize());
}

이 더 긴 형태는 이전 섹션의 예제와 동일하지만 더 자세한 표현입니다. 트레이트 바운드는 일반 타입 매개변수 선언 뒤에 콜론(:)을 붙이고, 각괄호(< >) 안에 위치시킵니다.

impl Trait 구문은 편리하며 간단한 경우 더 간결한 코드를 작성할 수 있게 해줍니다. 반면, 더 완전한 트레이트 바운드 구문은 다른 경우 더 복잡한 표현을 가능하게 합니다. 예를 들어, Summary 트레이트를 구현하는 두 개의 매개변수를 가질 수 있습니다. impl Trait 구문을 사용하여 이를 표현하면 다음과 같습니다:

pub fn notify(item1: &impl Summary, item2: &impl Summary) {

이 함수가 impl Trait와 item1가 서로 다른 타입을 갖도록 허용하기를 원한다면(단, 두 타입 모두 item2 트레이트를 구현하는 경우), Summary를 사용하는 것이 적절합니다. 그러나 두 매개변수가 동일한 타입을 갖도록 강제하려면 다음과 같이 트레이트 바운드를 사용해야 합니다:

pub fn notify<T: Summary>(item1: &T, item2: &T) {

item1과 item2 매개변수의 타입으로 지정된 제네릭 타입 T은 함수를 제약하여, item1과 item2의 인수로 전달되는 값의 구체적 타입이 동일해야 합니다.

+ 문법을 사용한 여러 트레이트 경계+

하나 이상의 트레이트 바운드를 지정할 수도 있습니다. 예를 들어, notify에서 summarize 형식뿐만 아니라 item도 사용하려고 한다고 가정해 보겠습니다. notify 정의에서 item가 Display와 Summary를 모두 구현해야 한다고 지정할 수 있습니다. 이를 위해 + 문법을 사용할 수 있습니다:

pub fn notify(item: &(impl Summary + Display)) {

+ 문법은 제네릭 타입에 대한 트레이트 바운드와 함께 사용할 때에도 유효합니다:

pub fn notify<T: Summary + Display>(item: &T) {

두 개의 트레이트 바운드가 지정되어 있으므로, notify의 본문에서는 summarize을 호출하고 {}을 사용해 item를 포맷팅할 수 있습니다.

where 절을 사용한 더 명확한 트레이트 바운드where

트레이트 바운드를 너무 많이 사용하면 단점이 있습니다. 각 제네릭은 자체 트레이트 바운드를 가지므로, 여러 제네릭 타입 파라미터를 가진 함수는 함수 이름과 파라미터 목록 사이에 많은 양의 트레이트 바운드 정보를 포함하게 되어 함수 서명을 읽기 어렵게 만듭니다. 이 때문에 Rust는 함수 서명 뒤에 where 절을 사용하여 트레이트 바운드를 지정하는 대체 문법을 제공합니다. 따라서, 이렇게 작성하는 대신:

fn some_function<T: Display + Clone, U: Clone + Debug>(t: &T, u: &U) -> i32 {

다음과 같이 where 절을 사용할 수 있습니다.

fn some_function<T, U>(t: &T, u: &U) -> i32
where
    T: Display + Clone,
    U: Clone + Debug,
{
    unimplemented!()
}

이 함수의 서명은 덜 복잡합니다. 함수 이름, 매개변수 목록, 반환 타입이 서로 가깝게 배치되어 있어, 트레이트 바운드가 많지 않은 함수와 유사합니다.

트레이트를 구현하는 타입 반환

또한 반환 위치에서 impl Trait 구문을 사용하여 특정 트레이트를 구현하는 타입의 값을 반환할 수 있습니다. 다음 예시를 참고하세요.

pub trait Summary {
    fn summarize(&self) -> String;
}

pub struct NewsArticle {
    pub headline: String,
    pub location: String,
    pub author: String,
    pub content: String,
}

impl Summary for NewsArticle {
    fn summarize(&self) -> String {
        format!("{}, by {} ({})", self.headline, self.author, self.location)
    }
}

pub struct SocialPost {
    pub username: String,
    pub content: String,
    pub reply: bool,
    pub repost: bool,
}

impl Summary for SocialPost {
    fn summarize(&self) -> String {
        format!("{}: {}", self.username, self.content)
    }
}

fn returns_summarizable() -> impl Summary {
    SocialPost {
        username: String::from("horse_ebooks"),
        content: String::from(
            "of course, as you probably already know, people",
        ),
        reply: false,
        repost: false,
    }
}

반환 타입에 impl Summary를 사용하면 returns_summarizable 함수가 구체적인 타입 이름을 명시하지 않고 Summary 트레이트를 구현하는 타입을 반환하도록 지정할 수 있습니다. 이 경우 returns_summarizable는 SocialPost를 반환하지만, 이 함수를 호출하는 코드는 이를 알 필요가 없습니다.

구현한 트레이트만으로 반환 타입을 지정하는 기능은 특히 클로저와 반복자 컨텍스트에서 유용합니다. 클로저와 반복자는 13장에서 다룹니다. 클로저와 반복자는 컴파일러만 아는 타입이거나, 명시적으로 작성하기 매우 긴 타입을 생성합니다. impl Trait 구문을 사용하면 매우 긴 타입을 작성할 필요 없이 함수가 Iterator 트레이트를 구현하는 타입을 반환하도록 간결하게 지정할 수 있습니다.

그러나 단일 타입만 반환할 때 impl Trait를 사용할 수 있습니다. 예를 들어 NewsArticle 또는 SocialPost를 반환하면서 반환 타입을 impl Summary로 지정한 다음 코드는 작동하지 않습니다.

pub trait Summary {
    fn summarize(&self) -> String;
}

pub struct NewsArticle {
    pub headline: String,
    pub location: String,
    pub author: String,
    pub content: String,
}

impl Summary for NewsArticle {
    fn summarize(&self) -> String {
        format!("{}, by {} ({})", self.headline, self.author, self.location)
    }
}

pub struct SocialPost {
    pub username: String,
    pub content: String,
    pub reply: bool,
    pub repost: bool,
}

impl Summary for SocialPost {
    fn summarize(&self) -> String {
        format!("{}: {}", self.username, self.content)
    }
}

fn returns_summarizable(switch: bool) -> impl Summary {
    if switch {
        NewsArticle {
            headline: String::from(
                "Penguins win the Stanley Cup Championship!",
            ),
            location: String::from("Pittsburgh, PA, USA"),
            author: String::from("Iceburgh"),
            content: String::from(
                "The Pittsburgh Penguins once again are the best \
                 hockey team in the NHL.",
            ),
        }
    } else {
        SocialPost {
            username: String::from("horse_ebooks"),
            content: String::from(
                "of course, as you probably already know, people",
            ),
            reply: false,
            repost: false,
        }
    }
}

NewsArticle 또는 SocialPost를 반환하는 것은 impl Trait 구문이 컴파일러에서 구현되는 방식에 대한 제한으로 인해 허용되지 않습니다. 18장의 "공유된 동작을 추상화하기 위해 트레이트 객체 사용" 섹션에서 이러한 동작을 가진 함수를 작성하는 방법을 설명합니다.

트레이트 바운드를 사용하여 조건부 메서드 구현

제네릭 타입 매개변수를 사용하는 impl 블록에 트레이트 바운드를 사용하면, 지정된 트레이트를 구현하는 타입에 대해 조건부로 메서드를 구현할 수 있습니다. 예를 들어, 목록 10-15의 타입 Pair<T>은 항상 new 함수를 구현하여 Pair<T>의 새로운 인스턴스를 반환합니다(5장의 “메서드 문법” 섹션에서 Self이 impl 블록의 타입의 타입 별칭이며, 이 경우 그 타입은 Pair<T>임을 기억하십시오). 그러나 다음 impl 블록에서, Pair<T>은 내부 타입 T이 비교를 가능하게 하는 PartialOrd 트레이트와 출력을 가능하게 하는 and Display 트레이트를 구현할 때만 cmp_display 메서드를 구현합니다.

또한, 다른 트레이트를 구현하는 모든 타입에 대해 특정 트레이트를 조건부로 구현할 수도 있습니다. 트레이트 바운드를 만족하는 모든 타입에 대한 트레이트 구현을 블랭킷 구현(blanket implementation)이라고 하며, Rust 표준 라이브러리에서 광범위하게 사용됩니다. 예를 들어, 표준 라이브러리는 ToString 트레이트를 구현하는 모든 타입에 대해 Display 트레이트를 구현합니다. 표준 라이브러리의 impl 블록은 다음과 유사합니다.

impl<T: Display> ToString for T {
    // --snip--
}

표준 라이브러리에 이 블랭킷 구현이 있으므로, Display 트레이트를 구현하는 모든 타입에서 ToString 트레이트가 정의한 to_string 메서드를 호출할 수 있습니다. 예를 들어, 정수는 Display를 구현하므로, 다음과 같이 정수를 해당 String 값으로 변환할 수 있습니다:

#![allow(unused)]
fn main() {
let s = 3.to_string();
}

블랭킷 구현은 트레이트 문서의 “Implementors” 섹션에 나타납니다.

트레이트와 트레이트 바운드를 사용하면 제네릭 타입 파라미터를 활용해 코드 중복을 줄이면서도, 컴파일러에게 제네릭 타입이 특정 동작을 가져야 함을 지정할 수 있습니다. 그러면 컴파일러는 트레이트 바운드 정보를 사용하여 코드에서 사용되는 모든 구체 타입이 올바른 동작을 제공하는지 검사합니다. 동적 타입 언어에서는 메서드를 정의하지 않은 타입에서 메서드를 호출하면 런타임에 오류가 발생합니다. 하지만 Rust는 이러한 오류를 컴파일 타임으로 이동시켜 코드가 실행되기 전에 문제를 수정하도록 강제합니다. 또한 컴파일 타임에 이미 검사가 이루어졌으므로 런타임에 동작을 확인하는 코드를 작성할 필요가 없습니다. 이를 통해 제네릭의 유연성을 포기하지 않으면서 성능을 향상시킬 수 있습니다.
