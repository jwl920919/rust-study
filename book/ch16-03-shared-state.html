The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

공유 상태 동시성

메시지 전달은 동시성을 처리하는 좋은 방법이지만 유일한 방법은 아닙니다. 또 다른 방법은 여러 스레드가 동일한 공유 데이터에 접근하는 것입니다. Go 언어 문서의 슬로건 중 하나를 다시 떠올려 보겠습니다. “메모리를 공유하여 통신하지 마십시오.”

메모리를 공유하여 통신하는 방식은 어떤 모습일까요? 또한 메시지 전달을 선호하는 사람들이 메모리 공유를 사용하지 말라고 경계하는 이유는 무엇일까요?

어떤 의미에서 모든 프로그래밍 언어의 채널은 단일 소유권과 유사합니다. 값을 채널을 통해 전달한 후에는 더 이상 해당 값을 사용해서는 안 되기 때문입니다. 공유 메모리 동시성은 다중 소유권과 같습니다. 여러 스레드가 동시에 동일한 메모리 위치에 접근할 수 있습니다. 15장에서 스마트 포인터가 다중 소유권을 가능하게 하는 방법을 살펴보았듯이, 다중 소유권은 서로 다른 소유자를 관리해야 하므로 복잡성을 더할 수 있습니다. Rust의 타입 시스템과 소유권 규칙은 이러한 관리를 올바르게 수행하는 데 큰 도움이 됩니다. 예를 들어, 공유 메모리를 위한 보다 일반적인 동시성 원시 중 하나인 뮤텍스를 살펴보겠습니다.

Mutex를 통한 접근 제어

Mutex는 상호 배제(mutual exclusion)의 약자로, Mutex는 주어진 시점에 하나의 스레드만 특정 데이터에 접근할 수 있도록 허용합니다. Mutex 내의 데이터에 접근하려면, 스레드는 먼저 Mutex의 잠금을 획득하도록 요청하여 접근을 원한다는 신호를 보내야 합니다. 잠금은 Mutex의 일부인 데이터 구조로, 현재 데이터에 독점적으로 접근하는 스레드를 추적합니다. 따라서 Mutex는 잠금 시스템을 통해 자신이 보유한 데이터를 보호한다고 설명할 수 있습니다.

Mutex는 두 가지 규칙을 기억해야 하므로 사용하기가 어렵다는 평판을 가지고 있습니다.

  1. 데이터를 사용하기 전에 잠금을 획득하려고 시도해야 합니다.
  2. 뮤텍스가 보호하는 데이터 작업을 완료하면, 다른 스레드가 잠금을 획득할 수 있도록 잠금을 해제해야 합니다.

뮤텍스에 대한 현실적인 비유로, 마이크가 하나뿐인 컨퍼런스의 패널 토론을 상상해 보세요. 패널이 발언하기 전에 마이크를 사용하고 싶다고 요청하거나 신호를 보내야 합니다. 마이크를 확보하면 원하는 만큼 발언한 후, 다음으로 발언을 요청한 패널에게 마이크를 넘겨줍니다. 만약 어떤 패널이 발언을 마치고도 마이크를 넘기는 것을 잊어버리면, 다른 패널은 발언할 수 없게 됩니다. 공유 마이크 관리에 문제가 생기면, 패널 토론은 계획대로 진행되지 못합니다!

뮤텍스 관리를 올바르게 하는 것은 매우 까다로울 수 있습니다. 그래서 많은 사람이 채널에 열광합니다. 하지만 Rust의 타입 시스템과 소유권 규칙 덕분에, 잠금과 해제 과정에서 실수를 할 수 없습니다.

의 API Mutex<T>

뮤텍스 사용법에 대한 예시로, Listing 16-12에 나와 있듯이 단일 스레드 컨텍스트에서 뮤텍스를 사용하는 것으로 시작해 보겠습니다.

많은 타입과 마찬가지로, 연관 함수 Mutex<T>을 사용하여 new을 생성합니다. 뮤텍스 내부의 데이터에 접근하려면, 락을 획득하기 위해 lock 메소드를 사용합니다. 이 호출은 현재 스레드를 차단하여 락을 가질 차례가 될 때까지 아무 작업도 수행하지 못하게 합니다.

다른 스레드가 잠금을 보유하는 동안 패닉이 발생하면 lock 호출이 실패합니다. 이 경우 아무도 잠금을 획득할 수 없으므로, 해당 상황이 발생하면 이 스레드가 패닉하도록 unwrap를 선택했습니다.

락을 획득한 후에는 이 경우 num로 명명된 반환 값을 내부 데이터에 대한 가변 참조로 취급할 수 있습니다. 타입 시스템은 m의 값을 사용하기 전에 반드시 락을 획득하도록 보장합니다. m의 타입은 i32가 아니라 Mutex<i32>이므로, i32 값을 사용하려면 반드시 lock을 호출해야 합니다. 이를 잊을 수 없으며, 그렇지 않으면 타입 시스템이 내부의 i32에 접근하는 것을 허용하지 않습니다.

전화 걸기 lock 호출된 형식을 반환합니다. MutexGuard, a에서 감싸는 LockResult [중고] 우리가 부르는 소리 unwrap. 그 MutexGuard 타입 구현들 Deref 우리의 내부 데이터를 가리 키도록; 유형에는 또한 Drop 상기 잠금을 해제하는 단계는 Release the lock automatically MutexGuard 내부 스코프의 끝에서 발생하는 스코프를 벗어납니다. 결과적으로 잠금 해제를 잊어 버리고 잠금 해제가 자동으로 발생하기 때문에 뮤텍스가 다른 스레드에서 사용되는 것을 차단할 위험이 없습니다.

락(lock)을 해제한 후 뮤텍스 값을 출력하면, 내부의 i32가 6로 변경되었음을 확인할 수 있습니다.

Arc<T>를 사용한 원자적 참조 카운팅 Arc<T>

다행히도 Arc<T>는 동시성 상황에서 안전하게 사용할 수 있는 Rc<T>와 같은 타입입니다. a는 atomic(원자적)을 의미하며, 이는 원자적 참조 카운팅 타입임을 나타냅니다. 원자(atomic)는 여기서 자세히 다루지 않는 추가적인 동시성 프라임티브입니다. 자세한 내용은 std::sync::atomic에 대한 표준 라이브러리 문서를 참고하세요. 이 시점에서 알아두어야 할 것은, 원자가 원시 타입처럼 동작하지만 스레드 간에 안전하게 공유할 수 있다는 점입니다.

그렇다면 왜 모든 원시 타입이 원자적이지 않고, 표준 라이브러리 타입이 기본적으로 Arc<T>를 사용하도록 구현되지 않는지 궁금할 수 있습니다. 그 이유는 스레드 안전성이 성능 저하를 수반하며, 이는 실제로 필요할 때만 감수해야 하는 비용이기 때문입니다. 단일 스레드 내에서 값에 대한 연산만 수행하는 경우, 원자가 제공하는 보장을 강제하지 않아도 코드가 더 빠르게 실행될 수 있습니다.

Arc<T>와 Rc<T>는 동일한 API를 가지고 있으므로 use 라인, new 호출 및 clone 호출을 변경하여 프로그램을 수정합니다. Listing 16-15의 코드는 최종적으로 컴파일되고 실행됩니다.

성공했습니다! 0에서 10까지 세어 보았지만, 이는 매우 인상적이지 않을 수 있습니다. 하지만 이 과정을 통해 Mutex<T>와 스레드 안전성에 대해 많은 것을 배울 수 있었습니다. 또한 이 프로그램의 구조를 사용하여 카운터를 증가시키는 것보다 더 복잡한 작업을 수행할 수도 있습니다. 이 전략을 사용하면 계산을 독립적인 부분으로 나누고, 그 부분을 여러 스레드에 분배한 다음, Mutex<T>을 사용하여 각 스레드가 자신의 부분으로 최종 결과를 업데이트하도록 할 수 있습니다.

단순한 수치 연산을 수행하는 경우, 표준 라이브러리의 std::sync::atomic 모듈이 제공하는 Mutex<T> 타입보다 더 간단한 타입이 있습니다. 이러한 타입은 원시 타입에 대한 안전하고 동시적이며 원자적인 접근을 제공합니다. 이 예제에서는 Mutex<T>이 어떻게 작동하는지에 집중할 수 있도록, 원시 타입과 함께 Mutex<T>을 사용하도록 선택했습니다.

counter이 불변(immutable)임에도 불구하고 그 안의 값에 가변 참조를 얻을 수 있었다는 점을 눈치챘을 것입니다. 이는 Mutex<T>이 내부 가변성(interior mutability)을 제공한다는 뜻이며, Cell 계열이 제공하는 방식과 같습니다. 15장에서 RefCell<T>을 사용해 Rc<T> 안의 내용을 변경할 수 있게 한 것과 마찬가지로, 여기서는 Mutex<T>을 사용해 Arc<T> 안의 내용을 변경합니다.
