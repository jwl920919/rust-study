I/O 프로젝트 개선

반복자에 대한 새로운 지식을 활용하면, 12장의 I/O 프로젝트에서 반복자를 사용하여 코드의 특정 부분을 더 명확하고 간결하게 만들 수 있습니다. 반복자가 Config::build 함수와 search 함수의 구현을 어떻게 개선할 수 있는지 살펴보겠습니다.

clone 호출 제거: 반복자 사용

Listing 12-6에서는 String 값들의 슬라이스를 인수로 받아 슬라이스에서 인덱싱을 통해 값을 가져오고 복제하여 Config 구조체의 인스턴스를 생성했습니다. 이를 통해 Config 구조체가 해당 값들의 소유권을 가질 수 있었습니다. Listing 13-17에서는 Listing 12-23에 있던 Config::build 함수의 구현을 그대로 재현했습니다.

그 당시에는 비효율적인 clone 호출에 대해 걱정하지 않아도 된다고 말했지만, 이제 그 시기가 왔습니다!

여기서 clone이 필요한 이유는, 매개변수인 String에 args 요소가 담긴 슬라이스가 있지만, build 함수는 args의 소유권을 가지지 않기 때문입니다. Config 인스턴스의 소유권을 반환하려면, query 구조체의 file_path 필드와 Config 필드에서 값을 복제해야 했습니다. 이렇게 하면 Config 인스턴스가 자신의 값을 소유할 수 있습니다.

반복자에 대한 새로운 지식을 활용하여, build 함수가 슬라이스를 빌리는 대신 반복자의 소유권을 인수로 받도록 변경할 수 있습니다. 슬라이스의 길이를 확인하고 특정 위치를 인덱싱하는 코드 대신 반복자 기능을 사용하겠습니다. 반복자가 값에 접근하기 때문에, 이는 Config::build 함수가 수행하는 작업을 명확하게 보여줍니다.

일단 Config::build가 이터레이터의 소유권을 취하고 차용하는 인덱싱 작업을 중단하면 String 값을 이터레이터에서 Config로 이동하고 clone를 호출하고 새 할당을 만들 수 있습니다.

반환된 반복자를 직접 사용

I/O 프로젝트의 src/main.rs 파일을 엽니다. 이 파일은 다음과 같은 내용을 포함해야 합니다:

파일 이름: src/main.rs

use std::env;
use std::error::Error;
use std::fs;
use std::process;

use minigrep::{search, search_case_insensitive};

fn main() {
    let args: Vec<String> = env::args().collect();

    let config = Config::build(&args).unwrap_or_else(|err| {
        eprintln!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    // --snip--

    if let Err(e) = run(config) {
        eprintln!("Application error: {e}");
        process::exit(1);
    }
}

pub struct Config {
    pub query: String,
    pub file_path: String,
    pub ignore_case: bool,
}

impl Config {
    fn build(args: &[String]) -> Result<Config, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();

        let ignore_case = env::var("IGNORE_CASE").is_ok();

        Ok(Config {
            query,
            file_path,
            ignore_case,
        })
    }
}

fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;

    let results = if config.ignore_case {
        search_case_insensitive(&config.query, &contents)
    } else {
        search(&config.query, &contents)
    };

    for line in results {
        println!("{line}");
    }

    Ok(())
}

먼저 Listing 12-24에 있는 main 함수의 시작 부분을 Listing 13-18의 코드로 변경하겠습니다. 이번에는 반복자를 사용합니다. Config::build도 함께 업데이트할 때까지 컴파일되지 않습니다.

env::args 함수는 반복자를 반환합니다! 반복자의 값을 벡터로 수집한 후 슬라이스를 Config::build에 전달하는 대신, 이제 env::args에서 반환된 반복자의 소유권을 직접 Config::build에 전달합니다.

다음으로 Config::build의 정의를 업데이트해야 합니다. Config::build의 시그니처를 Listing 13-19와 같이 변경해 보겠습니다. 함수 본문을 업데이트해야 하므로 여전히 컴파일되지 않습니다.

env::args 함수에 대한 표준 라이브러리 문서를 보면, 이 함수가 반환하는 반복자의 유형이 std::env::Args이며, 이 유형은 Iterator 트레이트를 구현하고 String 값을 반환한다고 나와 있습니다.

Config::build 함수의 시그니처를 업데이트하여, 매개변수 args의 타입을 &[String] 대신 트레이트 바운드 impl Iterator<Item = String>를 가진 제네릭 타입으로 변경했습니다. 10장의 “트레이트를 매개변수로 사용” 섹션에서 논의한 impl Trait 문법의 이 사용법은, args이 Iterator 트레이트를 구현하고 String 항목을 반환하는 어떤 타입이든 될 수 있음을 의미합니다.

args의 소유권을 가져오고 반복을 통해 args을 변경할 것이므로, mut 키워드를 args 매개변수 사양에 추가하여 변경 가능하게 만들 수 있습니다.

반복자 트레이트 메서드 사용Iterator

다음으로, Config::build의 본문(body)을 수정하겠습니다. args이 Iterator 트레이트를 구현하므로, next 메서드를 호출할 수 있다는 것을 알 수 있습니다! 목록 13-20은 next 메서드를 사용하도록 목록 12-23의 코드를 업데이트합니다.

반복자 어댑터를 사용하여 코드를 명확하게 하기

I/O 프로젝트의 search 함수에서도 반복자를 활용할 수 있습니다. 이 코드는 Listing 12-19와 동일하게 Listing 13-21에 다시 제시되어 있습니다.

반복자 어댑터 메서드를 사용하면 이 코드를 더 간결하게 작성할 수 있습니다. 이를 통해 가변 중간 results 벡터를 사용하지 않아도 됩니다. 함수형 프로그래밍 스타일은 코드를 명확하게 만들기 위해 가변 상태를 최소화하는 것을 선호합니다. 가변 상태를 제거하면 results 벡터에 대한 동시 접근을 관리할 필요가 없으므로, 향후 검색을 병렬로 수행하도록 기능을 확장할 수 있게 됩니다. Listing 13-22에서 이 변경 사항을 보여줍니다.

search 함수의 목적은 contents 에 포함된 모든 줄 중 query 를 포함하는 줄을 반환하는 것입니다. filter Listing 13-16의 filter 예제와 유사하게, 이 코드는 filter 어댑터를 사용하여 line.contains(query) 가 true 를 반환하는 줄만 유지합니다. 그런 다음 true 로 일치하는 줄을 다른 벡터로 수집합니다. 훨씬 더 간단해졌습니다! collect 함수에서도 반복자 메서드를 사용하도록 동일한 변경을 적용해 보세요. search_case_insensitive

더욱 개선하기 위해, collect 호출을 제거하고 반환 타입을 impl Iterator<Item = &'a str>로 변경하여 search 함수에서 반복자를 반환하도록 하면, 이 함수가 반복자 어댑터가 됩니다. 테스트도 업데이트해야 한다는 점에 유의하세요. 이 변경 사항을 적용하기 전후로 minigrep 도구를 사용하여 큰 파일을 검색하면 동작의 차이를 관찰할 수 있습니다. 이 변경 사항 이전에는 모든 결과를 수집할 때까지 프로그램이 어떤 결과도 출력하지 않지만, 변경 사항 이후에는 run 함수의 for 루프가 반복자의 지연 평가(laziness)를 활용할 수 있으므로, 각 일치하는 줄이 발견될 때마다 결과가 출력됩니다.

루프와 반복자 중 선택하기

다음으로 자연스럽게 떠오르는 질문은, 여러분 자신의 코드에서 어떤 스타일을 선택해야 하는지와 그 이유입니다. Listing 13-21의 원래 구현과 Listing 13-22의 반복자(iterator)를 사용하는 버전 중 어느 것을 선택할까요? (반복자를 반환하는 대신 모든 결과를 수집한 후에 반환한다고 가정합니다.) 대부분의 Rust 개발자는 반복자 스타일을 선호합니다. 처음에는 적응하는 데 조금 시간이 걸리지만, 다양한 반복자 어댑터와 그 동작 방식을 익히면 반복자를 사용하는 코드가 더 이해하기 쉬워집니다. 반복과 새 벡터 생성을 위한 세부적인 코드를 직접 다루지 않고, 루프의 고수준 목표를 중심으로 코드를 작성할 수 있기 때문입니다. 이 방식은 일반적인 코드를 추상화하여, 반복자의 각 요소가 통과해야 하는 필터링 조건처럼 이 코드에 고유한 개념을 더 명확하게 보여줍니다.

하지만 두 구현 방식이 정말로 동등할까요? 직관적으로는 저수준 루프가 더 빠를 것이라고 가정할 수 있습니다. 이제 성능에 대해 이야기해 보겠습니다.
