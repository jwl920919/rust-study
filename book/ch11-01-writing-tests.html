테스트를 작성하는 방법How to Write Tests

테스트는 테스트가 아닌 코드가 예상대로 동작하는지 확인하는 러스트 함수입니다. 테스트 함수의 몸체는 일반적으로 다음 세 가지 작업을 수행합니다.

  • 필요한 데이터 또는 상태를 설정합니다.
  • 테스트하려는 코드를 실행합니다.Run the code you want to test.
  • 결과는 당신이 기대하는 것이라고 말하십시오.

러스트가 test 속성, 몇 개의 매크로 및 should_panic 속성을 포함하는 이러한 동작을 수행하는 테스트를 작성하기 위해 특별히 제공하는 기능을 살펴 보겠습니다.

테스트의 평등성 assert_eq! 그리고 assert_ne!

기능을 검증하는 일반적인 방법은 테스트중인 코드의 결과와 코드가 반환 할 것으로 예상되는 값 사이의 같음을 테스트하는 것입니다. 다음을 사용하여이 작업을 수행 할 수 있습니다. assert! 매크로를 사용하여 표현식을 전달 == 그러나 이것은 표준 라이브러리가 한 쌍의 매크로를 제공하는 일반적인 테스트입니다.assert_eq! 그리고 assert_ne!—이 테스트를보다 편리하게 수행합니다. 이 매크로는 각각 같음 또는 부등식에 대한 두 개의 인수를 비교합니다. 또한 주장이 실패하면 두 값을 인쇄하여 쉽게 볼 수 있습니다. 왜 테스트 실패; 반대로, assert! 매크로는 단지 a를 얻었다는 것을 나타냅니다. false 에 대한 값 == expression, 를 이끌어 낸 값을 출력하지 않고 false 값.

Listing 11-7에서, 우리는 add_two라는 함수를 작성하여 2를 파라미터에 추가한 후, assert_eq! 매크로를 사용하여 이 함수를 테스트합니다.

일부 언어와 테스트 프레임워크에서는 equality assertion 함수에 대한 매개 변수를 호출합니다. expected 그리고 actual, 그리고 인수를 지정하는 순서가 중요합니다. 그러나 러스트에서는 호출됩니다. left 그리고 right, 그리고 우리가 기대하는 값과 코드가 생성하는 값을 지정하는 순서는 중요하지 않습니다. 이 테스트에서 어설션을 다음과 같이 작성할 수 있습니다. assert_eq!(4, result), 표시 같은 실패 메시지가 발생할 것 assertion `left == right` failed.

assert_ne! 매크로는 우리가 제공하는 두 값이 동일하지 않으면 전달되며 동일한 경우 실패합니다. 이 매크로는 값이 무엇인지 확실하지 않은 경우 가장 유용하지만 값이 확실히 없어야한다는 것을 알고 있습니다. 예를 들어, 어떤 방식으로 입력을 변경하도록 보장되는 함수를 테스트하고 있지만 입력이 변경되는 방법은 테스트 당일에 따라 다릅니다.

상기 표면에서, In the surface, the assert_eq! 그리고 assert_ne! 매크로는 연산자를 사용 == 그리고 !=, 각각. 어설션이 실패할 때, 이 매크로는 디버그 포맷팅을 사용하여 인수를 인쇄합니다. 즉, 비교되는 값이 반드시 구현되어야 합니다. PartialEq 그리고 Debug 트레잇. 모든 원시 타입과 대부분의 표준 라이브러리 타입은 이러한 트레잇을 구현합니다. 자신을 정의하는 구조체와 열거형의 경우, 구현해야 합니다. PartialEq 이러한 유형의 평등을 주장하기. 당신은 또한 구현해야합니다 Debug assertion이 실패할 때 값을 출력합니다. 두 트레잇은 모두 5장의 Listing 5-12에서 언급한 바와 같이 파생 가능한 트레잇이기 때문에, 이것은 일반적으로 다음과 같이 추가하는 것만큼 간단합니다. #[derive(PartialEq, Debug)] struct 또는 enum 정의에 대한 주석입니다. 부록 C를 참조하십시오. “탈피할 수 있는 특성” 무시 이들과 다른 파생 특성에 대한 자세한 내용은.

사용자 지정 실패 메시지 추가

또한 실패 메시지와 함께 인쇄할 사용자 지정 메시지를 옵션 인수로 추가할 수 있습니다. assert!, assert_eq!, 그리고 assert_ne! 매크로. 필요한 인수 뒤에 지정된 모든 인수는 다음과 같이 전달됩니다. format! 매크로 (Discussed in) > 함께 하는 + 또는 format!” 무시 8 장에서), 그래서 당신은 포함 하는 형식 문자열을 전달할 수 있습니다. {} placeholders와 values는 그 placeholders에 들어갈 것입니다. 사용자 지정 메시지는 assertion이 무엇을 의미하는지 문서화하는 데 유용합니다. 테스트가 실패하면 코드에 어떤 문제가 있는지 더 잘 알 수 있습니다.

예를 들어, 우리는 이름으로 사람들을 맞이하는 함수를 가지고 있고 우리가 함수에 전달하는 이름이 출력에 나타나는지 테스트하기를 원한다고 가정해 봅시다:

파일명: src/lib.rs

이 프로그램에 대한 요구 사항은 아직 합의되지 않았으며, 인사 시작시 Hello 텍스트가 변경 될 것이라고 확신합니다. 요구 사항이 변경되면 테스트를 업데이트하지 않기로 결정했습니다. 따라서 greeting 함수에서 반환 된 값에 대한 정확한 같음을 확인하는 대신 출력에 입력 매개 변수의 텍스트가 포함되어 있다고 주장 할 것입니다.

패닉에 대한 확인 should_panic

반환 값을 확인하는 것 외에도 코드가 예상대로 오류 조건을 처리하는지 확인하는 것이 중요합니다. 예를 들어, Guess 9장, Listing 9-13에서 만든 type입니다. 다른 코드는 Guess 그것은 보증에 달려 있습니다 : Guess 인스턴스는 1과 100 사이의 값만 포함합니다. 우리는 a를 만들려고 시도하는 것을 보장하는 테스트를 작성할 수 있습니다. Guess 그 범위 밖의 값을 가진 인스턴스.

should_panic 속성을 테스트 함수에 추가하여 이 작업을 수행합니다. 함수 내부의 코드가 패닉되면 테스트가 통과합니다. 함수 내부의 코드가 패닉하지 않으면 테스트가 실패합니다.

    #[test]

사용 Result<T, E> in 테스트

지금까지의 모든 테스트들은 실패할 때 패닉 상태에 있습니다. Result<T, E>를 사용하는 테스트도 작성할 수 있습니다! Listing 11-1의 테스트가 Result<T, E>를 사용하도록 다시 작성되었으며 패닉 상태에 빠지지 않고 Err를 반환합니다:

pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() -> Result<(), String> {
        let result = add(2, 2);

        if result == 4 {
            Ok(())
        } else {
            Err(String::from("two plus two does not equal four"))
        }
    }
}

이름 * it_works 함수는 현재 Result<(), String> return type. 함수를 호출하는 대신 함수의 본문에서 assert_eq! 매크로, 우리는 반환 Ok(()) 시험이 통과하고 때 Err 으로 A String 테스트가 실패 할 때 내부.

Result<T, E>를 반환하도록 테스트를 작성하면 테스트 본문에서 물음표 연산자를 사용할 수 있으며, 이는 Err 변형을 반환하는 작업이 있으면 실패하는 테스트를 작성하는 편리한 방법이 될 수 있습니다.

당신은 사용할 수 없습니다. #[should_panic] 사용하는 테스트에 대한 주석 Result<T, E>. operation이 operation을 반환한다고 주장하기 위해 Err 변형, 하지 않음 물음표 연산자 사용하기 Result<T, E> value. 대신, 사용 assert!(value.is_err()).

이제 테스트를 작성하는 몇 가지 방법을 알았으므로 테스트를 실행하고 cargo test에서 사용할 수있는 다양한 옵션을 탐색 할 때 어떤 일이 일어나는지 살펴 보겠습니다.
