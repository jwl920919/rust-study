The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

고급 형식

Rust 타입 시스템에는 지금까지 언급했지만 아직 자세히 다루지 않은 몇 가지 기능이 있습니다. 먼저, 왜 newtype이 타입으로서 유용한지 살펴보기 위해 newtype의 일반적인 개념을 논의하겠습니다. 그런 다음, newtype과 유사하지만 의미론(semantics)이 약간 다른 기능인 타입 별칭으로 넘어가겠습니다. 또한 ! 타입과 동적 크기 타입에 대해서도 논의하겠습니다.

newtype 패턴을 통한 타입 안전성 및 추상화

이 섹션은 이전 섹션인 “외부 트레이트를 newtype 패턴으로 구현하기”를 읽었다고 가정합니다. newtype 패턴은 지금까지 논의한 것 외에도 유용한 용도가 많습니다. 예를 들어, 값이 혼동되지 않도록 정적으로 강제하거나 값의 단위를 나타내는 데 사용할 수 있습니다. Listing 20-16에서 단위를 나타내기 위해 newtype을 사용하는 예를 보았습니다. Millimeters와 Meters 구조체는 u32 값을 newtype으로 감싸고 있었습니다. 만약 Millimeters 타입의 매개변수를 가진 함수를 작성했다면, 실수로 Meters 타입의 값이나 단순한 u32 값을 전달하여 그 함수를 호출하려는 프로그램은 컴파일되지 않을 것입니다.

newtype 패턴을 사용하여 타입의 일부 구현 세부 사항을 추상화할 수도 있습니다. newtype은 내부의 비공개 타입과 다른 공개 API를 노출할 수 있습니다.

Newtype은 내부 구현을 숨기는 데에도 사용할 수 있습니다. 예를 들어, People를 감싸는 HashMap<i32, String> 유형을 제공할 수 있습니다. 이 유형은 사람의 ID와 이름을 연결하여 저장합니다. People를 사용하는 코드는 우리가 제공하는 공개 API, 예를 들어 People 컬렉션에 이름 문자열을 추가하는 메서드와 같은 것만 상호 작용하게 됩니다. 따라서 해당 코드는 내부적으로 이름에 i32 ID를 할당한다는 사실을 알 필요가 없습니다. Newtype 패턴은 구현 세부 사항을 숨기기 위해 캡슐화를 달성하는 가벼운 방법입니다. 이 내용은 18장의 “구현 세부 사항을 숨기는 캡슐화” 섹션에서 다루었습니다. 구현 세부 사항을 숨기는 캡슐화

타입 동의어와 타입 별칭

Rust는 기존 타입에 다른 이름을 부여하기 위해 타입 별칭을 선언할 수 있는 기능을 제공합니다. 이를 위해 type 키워드를 사용합니다. 예를 들어, Kilometers에 대해 i32라는 별칭을 다음과 같이 만들 수 있습니다.

fn main() {
    type Kilometers = i32;

    let x: i32 = 5;
    let y: Kilometers = 5;

    println!("x + y = {}", x + y);
}

이제 별칭은 Kilometers 또는 A 동의어 에 대한 i32상기와 달리, Asin the Millimeters 그리고 Meters Listing 20-16에서 우리가 만든 타입들, Kilometers 별도의 새로운 형식이 아닙니다. 형식이 있는 값 Kilometers 타입의 값과 동일하게 취급될 것입니다. i32:

fn main() {
    type Kilometers = i32;

    let x: i32 = 5;
    let y: Kilometers = 5;

    println!("x + y = {}", x + y);
}

Kilometers과 i32은 동일한 타입이므로, 두 타입의 값을 더할 수 있고 Kilometers 매개변수를 받는 함수에 i32 값을 전달할 수 있습니다. 그러나 이 방법을 사용하면 앞서 설명한 newtype 패턴에서 얻을 수 있는 타입 검사 이점을 얻지 못합니다. 즉, 어딘가에서 Kilometers과 i32 값을 혼동하더라도 컴파일러는 오류를 보고하지 않습니다.

타입 별칭의 주요 사용 사례는 반복을 줄이는 것입니다. 예를 들어 다음과 같은 긴 타입이 있을 수 있습니다:

Box<dyn Fn() + Send + 'static>

이 긴 타입을 함수 서명이나 코드 전체의 타입 주석으로 작성하는 것은 지루하고 오류가 발생하기 쉽습니다. Listing 20-25와 같은 코드가 가득한 프로젝트를 상상해 보세요.

타입 별칭은 반복을 줄임으로써 이 코드를 더 관리하기 쉽게 만듭니다. Listing 20-26에서, 우리는 복잡한 타입에 대해 Thunk이라는 별칭을 도입했고, 타입의 모든 사용처를 더 짧은 별칭 Thunk로 대체할 수 있습니다.

이 코드는 읽기와 쓰기가 훨씬 쉽습니다! 타입 별칭에 의미 있는 이름을 선택하면 의도를 전달하는 데에도 도움이 될 수 있습니다(thunk는 나중에 평가될 코드를 의미하는 단어로, 저장되는 클로저에 적절한 이름입니다).

타입 별칭은 반복을 줄이기 위해 Result<T, E> 타입과 함께 자주 사용됩니다. 표준 라이브러리의 std::io 모듈을 생각해 보겠습니다. I/O 연산은 작업이 실패하는 상황을 처리하기 위해 종종 Result<T, E>을 반환합니다. 이 라이브러리에는 가능한 모든 I/O 에러를 나타내는 std::io::Error 구조체가 있습니다. std::io의 많은 함수는 Result<T, E>가 E인 std::io::Error을 반환합니다. 예를 들어, Write 트레이트의 이러한 함수들이 그렇습니다.

use std::fmt;
use std::io::Error;

pub trait Write {
    fn write(&mut self, buf: &[u8]) -> Result<usize, Error>;
    fn flush(&mut self) -> Result<(), Error>;

    fn write_all(&mut self, buf: &[u8]) -> Result<(), Error>;
    fn write_fmt(&mut self, fmt: fmt::Arguments) -> Result<(), Error>;
}

Result<..., Error>은 자주 반복됩니다. 이러한 이유로 std::io에는 다음과 같은 타입 별칭 선언이 있습니다.

use std::fmt;

type Result<T> = std::result::Result<T, std::io::Error>;

pub trait Write {
    fn write(&mut self, buf: &[u8]) -> Result<usize>;
    fn flush(&mut self) -> Result<()>;

    fn write_all(&mut self, buf: &[u8]) -> Result<()>;
    fn write_fmt(&mut self, fmt: fmt::Arguments) -> Result<()>;
}

이 선언이 std::io 모듈에 있으므로, 완전한 경로로 된 별칭인 std::io::Result<T>을 사용할 수 있습니다. 이는 Result<T, E>에서 E가 std::io::Error로 채워진 형태입니다. Write 트레이트의 함수 서명은 다음과 같이 됩니다:

use std::fmt;

type Result<T> = std::result::Result<T, std::io::Error>;

pub trait Write {
    fn write(&mut self, buf: &[u8]) -> Result<usize>;
    fn flush(&mut self) -> Result<()>;

    fn write_all(&mut self, buf: &[u8]) -> Result<()>;
    fn write_fmt(&mut self, fmt: fmt::Arguments) -> Result<()>;
}

타입 별칭은 두 가지 측면에서 도움이 됩니다. 코드를 작성하기 쉽게 만들어 주며, std::io 전체에서 일관된 인터페이스를 제공합니다. 별칭이므로 결국 Result<T, E>의 또 다른 형태이며, 이는 Result<T, E>에서 동작하는 모든 메서드와 ? 연산자와 같은 특수 구문을 사용할 수 있음을 의미합니다.

절대 반환하지 않는 타입

Rust에는 타입 이론에서 빈 타입(empty type)으로 알려진 !이라는 특별한 타입이 있습니다. 이 타입은 어떤 값도 가지지 않기 때문에 빈 타입이라고 불리지만, Rust에서는 함수가 절대 반환되지 않을 때 반환 타입의 자리에 사용되므로 'never 타입'이라고 부르는 것을 선호합니다. 다음은 예시입니다:

fn bar() -> ! {
    // --snip--
    panic!();
}

이 코드는 "bar가 결코 반환되지 않음"으로 읽혀집니다. 반환되는 함수는 결코 diverging 함수라고 불리지 않습니다. ! 유형의 값을 만들 수 없으므로 bar는 결코 반환 할 수 없습니다.

그런데 값을 절대 만들 수 없는 타입은 어떤 용도일까요? Listing 2-5의 숫자 추측 게임 코드 일부를 떠올려 보겠습니다. Listing 20-27에 그 일부를 다시 제시했습니다.

당시 이 코드에서 일부 세부 사항을 생략했습니다. 6장의 “match 제어 흐름 구조” 섹션에서는 match의 각 암(arm)이 모두 동일한 타입을 반환해야 한다고 설명했습니다. 예를 들어, 다음 코드는 동작하지 않습니다.

fn main() {
    let guess = "3";
    let guess = match guess.trim().parse() {
        Ok(_) => 5,
        Err(_) => "hello",
    };
}

이 코드에서 guess의 타입은 정수이면서 문자열이어야 하지만, Rust는 guess이 단 하나의 타입만 가질 것을 요구합니다. 그렇다면 continue는 무엇을 반환합니까? 어떻게 한 매치 암에서 u32를 반환하고, 리스트 20-27에서 다른 매치 암이 continue로 끝나는 것이 허용되었을까요?

짐작하셨을 수도 있겠지만, continue은 ! 타입을 가집니다. 즉, Rust가 guess의 타입을 계산할 때 두 개의 match arm을 모두 살펴봅니다. 앞쪽 arm은 u32 타입의 값을 가지며, 뒤쪽 arm은 ! 타입을 가집니다. !는 결코 값을 가질 수 없으므로, Rust는 guess의 타입을 u32로 결정합니다.

이 동작을 공식적으로 설명하면, ! 타입의 식은 다른 어떤 타입으로도 강제 변환(coerce)될 수 있습니다. match 분기(arm)를 continue로 끝낼 수 있는 이유는, continue이 값을 반환하지 않기 때문입니다. 대신 제어 흐름을 루프의 맨 위로 되돌리기 때문에, Err인 경우 guess에 값을 할당하지 않습니다.

절대 타입은 panic! 매크로와 함께 사용할 때도 유용합니다. unwrap 값에서 값을 생성하거나 패닉을 발생시키기 위해 호출하는 Option<T> 함수를 기억해 보세요. 이 함수의 정의는 다음과 같습니다:

enum Option<T> {
    Some(T),
    None,
}

use crate::Option::*;

impl<T> Option<T> {
    pub fn unwrap(self) -> T {
        match self {
            Some(val) => val,
            None => panic!("called `Option::unwrap()` on a `None` value"),
        }
    }
}

이 코드에서는 match Listing 20-27의 match에서와 동일한 일이 발생합니다. Rust는 val의 타입이 T이고 panic!의 타입이 !임을 확인하므로, 전체 match 표현식의 결과는 T가 됩니다. 이 코드가 동작하는 이유는 panic!이 값을 생성하지 않고 프로그램을 종료하기 때문입니다. None인 경우 unwrap에서 값을 반환하지 않으므로, 이 코드는 유효합니다. valTpanic!!matchTpanic!Noneunwrap

! 타입을 가지는 마지막 표현식은 루프입니다:

fn main() {
    print!("forever ");

    loop {
        print!("and ever ");
    }
}

여기서 루프는 끝이 없으므로 !가 식의 값입니다. 하지만 break을 포함하면 루프가 break에 도달했을 때 종료되므로, 이 경우 위 설명은 성립하지 않습니다.

동적 크기 타입과 Sized 트레이트

Rust는 특정 타입의 값에 대해 얼마나 많은 공간을 할당해야 하는지 등 타입에 관한 세부 정보를 알아야 합니다. 이로 인해 타입 시스템의 일부가 처음에는 다소 혼란스럽게 느껴질 수 있습니다. 바로 동적 크기 타입(Dynamically Sized Types)의 개념입니다. DST 또는 unsized 타입이라고도 불리는 이러한 타입은 런타임에서만 크기를 알 수 있는 값을 사용하여 코드를 작성할 수 있게 해줍니다.

이 책 전체에서 사용해 온 동적 크기 타입인 str의 세부 사항을 살펴봅시다. 맞습니다. &str이 아니라 str 자체는 DST입니다. 사용자가 입력한 텍스트를 저장하는 경우와 같이 많은 상황에서 런타임까지 문자열의 길이를 알 수 없습니다. 즉, str 타입의 변수를 만들 수도 있고, str 타입의 인수를 받을 수도 없습니다. 작동하지 않는 다음 코드를 고려해 보세요:

fn main() {
    let s1: str = "Hello there!";
    let s2: str = "How's it going?";
}

Rust는 특정 타입의 모든 값에 대해 동일한 양의 메모리를 할당해야 합니다. 만약 Rust가 이 코드를 허용했다면, 이 두 str 값은 동일한 크기의 공간을 차지해야 합니다. 하지만 두 값의 길이는 다릅니다. s1에는 12바이트의 저장 공간이 필요하고 s2에는 15바이트가 필요합니다. 이것이 동적 크기 타입의 변수를 만들 수 없는 이유입니다.

그렇다면 어떻게 해야 할까요? 이 경우 이미 답을 알고 있습니다. s1와 s2의 타입을 str 대신 문자열 슬라이스(&str)로 만듭니다. 4장의 “String Slices” 섹션에서 배운 것처럼, 슬라이스 데이터 구조는 슬라이스의 시작 위치와 길이만 저장합니다. 따라서 &T가 T의 위치를 가리키는 메모리 주소를 저장하는 단일 값인 반면, 문자열 슬라이스는 두 값, 즉 str의 주소와 그 길이입니다. 이 때문에 컴파일 타임에 문자열 슬라이스 값의 크기를 알 수 있습니다. 그것은 usize 길이의 두 배입니다. 즉, 문자열 슬라이스가 가리키는 문자열이 얼마나 길든 우리는 항상 문자열 슬라이스의 크기를 알 수 있습니다. 일반적으로 이것이 Rust에서 동적 크기 타입이 사용되는 방식입니다. 동적 정보의 크기를 저장하는 추가 메타데이터가 있습니다. 동적 크기 타입의 황금 규칙은 동적 크기 타입의 값을 항상 어떤 종류의 포인터 뒤에 두어야 한다는 것입니다.

결합할 수 있습니다. str 모든 종류의 포인터 : 예를 들어, Box<str> 또는 Rc<str>. 사실, 당신은 전에 이것을 보았지만 다른 동적으로 크기의 유형 : 특성. 모든 특성은 특성의 이름을 사용하여 참조 할 수있는 동적으로 크기의 유형입니다. 에서 "공유 된 행동을 추상화하기 위해 Trait 객체 사용" 무시 제 18 장에서, 우리는 특성 객체로 특성을 사용하기 위해, 우리는 포인터 뒤에 그들을 넣어해야한다고 언급, 같은 &dyn Trait 또는 Box<dyn Trait> (Rc<dyn Trait> 또한 일할 것입니다.)

DST를 다루기 위해 Rust는 타입의 크기가 컴파일 타임에 알려져 있는지 여부를 결정하기 위해 Sized 트레이트를 제공합니다. 이 트레이트는 컴파일 타임에 크기가 알려진 모든 타입에 대해 자동으로 구현됩니다. 또한, Rust는 모든 제네릭 함수에 Sized에 대한 바운드를 암시적으로 추가합니다. 즉, 다음과 같은 제네릭 함수 정의는:

fn generic<T>(t: T) {
    // --snip--
}

실제로는 다음과 같이 작성한 것과 동일하게 취급됩니다.

fn generic<T: Sized>(t: T) {
    // --snip--
}

기본적으로 일반 함수는 컴파일 시간에 크기가 알려진 타입에서만 작동합니다. 그러나 다음 특수 구문을 사용하면 이 제한을 완화할 수 있습니다.

fn generic<T: ?Sized>(t: &T) {
    // --snip--
}

?Sized에 트레이트 바운드를 적용하는 것은 “T가 Sized일 수도 있고 아닐 수도 있다”는 것을 의미하며, 이 표기법은 일반 타입이 컴파일 시간에 크기가 알려져야 한다는 기본 규칙을 무시합니다. 이 의미를 가진 ?Trait 구문은 Sized에서만 사용할 수 있으며, 다른 트레이트에는 사용할 수 없습니다.
