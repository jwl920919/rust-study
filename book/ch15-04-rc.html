The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

Rc<T>참조 카운팅 스마트 포인터(Reference-Counted Smart Pointer)

대부분의 경우 소유권은 명확합니다. 어떤 변수가 특정 값을 소유하고 있는지 정확히 알 수 있습니다. 그러나 단일 값이 여러 소유자를 가질 수 있는 경우도 있습니다. 예를 들어 그래프 데이터 구조에서는 여러 간선이 동일한 노드를 가리킬 수 있으며, 이 노드는 개념적으로 해당 노드를 가리키는 모든 간선에 의해 소유됩니다. 노드를 가리키는 간선이 하나도 없으면 소유자가 없으므로, 이 경우에만 노드를 정리할 수 있습니다.

참조 카운팅(reference counting)의 약자인 Rust 타입 Rc<T>을 사용하여 명시적으로 여러 소유권을 활성화해야 합니다. Rc<T> 타입은 값에 대한 참조 수를 추적하여 해당 값이 아직 사용 중인지 여부를 결정합니다. 값에 대한 참조가 0개라면, 어떤 참조도 무효화되지 않도록 값을 안전하게 정리할 수 있습니다.

Rc<T>를 가족 거실의 TV로 상상해 보겠습니다. 한 사람이 TV를 보러 들어오면 TV를 켭니다. 다른 사람들도 방에 들어와 TV를 볼 수 있습니다. 마지막 사람이 방을 나가는 순간, 더 이상 사용되지 않으므로 TV를 끕니다. 만약 다른 사람들이 아직 시청하고 있는데 누군가 TV를 끄면, 남은 시청자들이 큰 소란을 일으킬 것입니다!

프로그램의 여러 부분이 읽기 위해 힙에 데이터를 할당하고 싶지만, 컴파일 시점에 어느 부분이 마지막으로 데이터를 사용하게 될지 결정할 수 없는 경우 Rc<T> 타입을 사용합니다. 만약 어느 부분이 마지막으로 사용하게 될지 알고 있다면, 그 부분을 데이터의 소유자로 지정하면 컴파일 시점에 적용되는 일반적인 소유권 규칙이 그대로 적용될 것입니다.

Rc<T>는 단일 스레드 시나리오에서만 사용할 수 있습니다. 16장에서 동시성을 다룰 때, 멀티스레드 프로그램에서 참조 카운팅을 수행하는 방법에 대해 설명하겠습니다.

Cons 변형은 자신이 보유하는 데이터를 소유합니다. 따라서 b 리스트를 생성할 때, a는 b로 이동되고 b가 a를 소유하게 됩니다. 그런 다음, c을 생성할 때 a을 다시 사용하려고 하면, a이 이미 이동되었기 때문에 허용되지 않습니다.

대신 Cons의 정의를 참조로 변경할 수 있지만, 그러면 라이프타임 매개변수를 지정해야 합니다. 라이프타임 매개변수를 지정하면 리스트의 모든 요소가 최소한 리스트 전체와 동일한 수명 동안 존재하도록 명시하는 것입니다. 이는 Listing 15-17의 요소와 리스트에 해당하지만, 모든 시나리오에 적용되는 것은 아닙니다.

대신, List을 Rc<T>로 대체하여 Box<T>의 정의를 변경하겠습니다. Listing 15-18에 나와 있듯이, 각 Cons 변형은 이제 값과 Rc<T>를 가질 것입니다. List을 가리키는 b를 생성할 때, a의 소유권을 가져오는 대신 Rc<List>이 가지고 있는 a을 복제(clone)합니다. 이를 통해 참조 수가 1개에서 2개로 증가하며, a과 b이 Rc<List> 내부 데이터의 소유권을 공유하게 됩니다. a을 생성할 때도 c을 복제하여 참조 수를 2개에서 3개로 늘립니다. Rc::clone을 호출할 때마다 Rc<List> 내부 데이터에 대한 참조 카운트가 증가하며, 참조가 0개가 될 때까지 데이터는 정리되지 않습니다.

Rc<T>는 prelude에 포함되어 있지 않으므로, 스코프에 포함시키기 위해 use 문장을 추가해야 합니다. main에서 5와 10을 포함하는 리스트를 생성하고 이를 a라는 새로운 Rc<List>에 저장합니다. 그런 다음 b와 c를 생성할 때 Rc::clone 함수를 호출하고, a에 있는 Rc<List>에 대한 참조를 인자로 전달합니다. useRc<T>main510Rc<List>abcRc::cloneRc<List>a

Rc::clone(&a) 대신에 a.clone()을 호출할 수도 있었지만, Rust의 관례는 이 경우 Rc::clone을 사용하는 것입니다. Rc::clone의 구현은 대부분의 타입의 clone 구현처럼 모든 데이터의 깊은 복사를 수행하지 않습니다. Rc::clone 호출은 참조 카운트만 증가시키며, 이는 많은 시간을 소요하지 않습니다. 데이터의 깊은 복사는 많은 시간을 소요할 수 있습니다. 참조 카운팅을 위해 Rc::clone을 사용함으로써, 깊은 복사 유형의 클론과 참조 카운트를 증가시키는 유형의 클론을 시각적으로 구별할 수 있습니다. 코드에서 성능 문제를 찾을 때, 깊은 복사 클론만 고려하면 되고 Rc::clone 호출은 무시할 수 있습니다.

참조 횟수를 증가시키기 위한 클로닝

Listing 15-18의 예제를 수정하여, a에 있는 Rc<List>에 대한 참조를 생성하고 드롭할 때 참조 횟수가 어떻게 변하는지 확인할 수 있도록 하겠습니다. Rc<List>a

Listing 15-19에서는 main을 수정하여 c 리스트 주위에 내부 스코프를 두도록 하겠습니다. 그러면 c가 스코프 밖으로 나갈 때 참조 횟수가 어떻게 변하는지 확인할 수 있습니다. maincc

참조 횟수가 변경되는 프로그램의 각 지점에서, Rc::strong_count 함수를 호출하여 얻은 참조 횟수를 출력합니다. 이 함수의 이름이 count가 아닌 strong_count인 이유는, Rc<T> 타입에는 weak_count도 있기 때문입니다. weak_count의 용도는 “Weak<T>를 사용하여 참조 사이클 방지”에서 살펴보겠습니다. Rc::strong_countstrong_countcountRc<T>weak_countweak_countWeak<T>

이 코드는 다음과 같이 출력합니다.

$ cargo run
   Compiling cons-list v0.1.0 (file:///projects/cons-list)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.45s
     Running `target/debug/cons-list`
count after creating a = 1
count after creating b = 2
count after creating c = 3
count after c goes out of scope = 2

Rc<List>의 a은 초기 참조 카운트가 1임을 알 수 있습니다. clone을 호출할 때마다 카운트가 1씩 증가합니다. c이 스코프를 벗어나면 카운트가 1씩 감소합니다. Rc::clone을 호출하여 참조 카운트를 증가시키는 것처럼, 참조 카운트를 감소시키기 위해 함수를 호출할 필요가 없습니다. Drop 트레이트 구현은 Rc<T> 값이 스코프를 벗어나면 참조 카운트를 자동으로 감소시킵니다.

이 예제에서 볼 수 없는 것은 b과 a이 main의 끝에서 스코프를 벗어나면 카운트가 0이 되고, Rc<List>이 완전히 정리된다는 점입니다. Rc<T>을 사용하면 하나의 값이 여러 소유자를 가질 수 있으며, 카운트는 소유자 중 하나라도 존재하는 한 값이 유효한 상태로 유지되도록 보장합니다.

불변 참조를 통해 Rc<T>은 프로그램의 여러 부분 간에 데이터를 읽기 전용으로 공유할 수 있게 합니다. Rc<T>이 여러 개의 가변 참조도 허용했다면, 4장에서 논의한 빌림 규칙 중 하나를 위반했을 수 있습니다. 동일한 위치에 여러 개의 가변 빌림이 있으면 데이터 레이스와 불일치가 발생할 수 있기 때문입니다. 하지만 데이터를 변경할 수 있다는 것은 매우 유용합니다! 다음 섹션에서는 내부 가변성 패턴과, 이 불변성 제한을 극복하기 위해 RefCell<T>와 함께 사용할 수 있는 Rc<T> 타입에 대해 논의하겠습니다.
