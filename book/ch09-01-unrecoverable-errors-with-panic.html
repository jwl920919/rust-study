The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

panic!을 사용한 복구할 수 없는 오류 panic!

때때로 코드에서 문제가 발생하여 우리가 할 수 있는 일이 없는 경우가 있습니다. 이러한 경우 Rust에는 panic! 매크로가 있습니다. 실제로 패닉을 일으키는 방법은 두 가지입니다. 패닉을 유발하는 작업을 수행하는 것(예: 배열의 끝을 넘어 접근하는 것)과 panic! 매크로를 명시적으로 호출하는 것입니다. 두 경우 모두 프로그램에서 패닉이 발생합니다.

패닉 발생 시 스택 언와인딩 또는 중단

기본적으로 패닉이 발생하면 프로그램은 언와인딩(unwinding)을 시작합니다. 이는 Rust가 스택을 역순으로 거슬러 올라가며 만나는 각 함수의 데이터를 정리하는 것을 의미합니다. 그러나 스택을 역순으로 거슬러 올라가며 정리하는 것은 상당한 작업입니다. 따라서 Rust는 정리를 수행하지 않고 프로그램을 즉시 종료하는 중단(aborting)이라는 대안을 선택할 수 있도록 허용합니다.

프로그램이 사용했던 메모리는 운영 체제가 정리해야 합니다. 프로젝트에서 생성된 바이너리의 크기를 가능한 한 작게 유지해야 하는 경우, panic = 'abort'를 Cargo.toml 파일의 적절한 [profile] 섹션에 추가하여 패닉 발생 시 언와인딩 대신 중단(abort)하도록 설정할 수 있습니다. 예를 들어, 릴리스 모드에서 패닉 발생 시 중단하려면 다음을 추가하십시오.

[profile.release]
panic = 'abort'

간단한 프로그램에서 panic!를 호출해 보겠습니다:

프로그램을 실행하면 다음과 같은 출력을 볼 수 있습니다:

$ cargo run
   Compiling panic v0.1.0 (file:///projects/panic)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.25s
     Running `target/debug/panic`

thread 'main' (6018279) panicked at src/main.rs:2:5:
crash and burn
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

panic! 호출은 마지막 두 줄에 포함된 오류 메시지를 발생시킵니다. 첫 번째 줄은 패닉 메시지와 패닉이 발생한 소스 코드의 위치를 보여줍니다. src/main.rs:2:5는 src/main.rs 파일의 2번째 줄, 5번째 문자임을 나타냅니다.

이 경우, 표시된 줄은 우리 코드의 일부이며 해당 줄로 이동하면 panic! 매크로 호출을 볼 수 있습니다. 다른 경우, panic! 호출은 우리 코드가 호출하는 다른 코드에 있을 수 있습니다. 이때 오류 메시지에 보고된 파일 이름과 줄 번호는 panic! 매크로가 호출된 다른 사람의 코드 위치이며, 결국 panic! 호출로 이어진 우리 코드의 줄이 아닙니다.

panic! 호출이 발생한 함수들의 백트레이스를 사용하면 문제를 일으키는 우리 코드의 부분을 파악할 수 있습니다. panic! 백트레이스를 사용하는 방법을 이해하려면, 우리 코드에 버그가 있어 라이브러리에서 panic! 호출이 발생하는 경우를 살펴보고 직접 매크로를 호출하는 경우와 어떻게 다른지 확인해 보겠습니다. 목록 9-1에는 유효한 인덱스 범위를 넘어 벡터의 인덱스에 접근하려는 코드가 포함되어 있습니다.

여기서 우리는 벡터의 100번째 요소(인덱싱은 0에서 시작하므로 인덱스 99에 해당)에 접근하려고 하지만, 벡터에는 요소가 세 개만 있습니다. 이 상황에서 Rust는 패닉을 일으킵니다. [] 연산자는 요소를 반환해야 하지만, 유효하지 않은 인덱스를 전달하면 Rust가 반환할 수 있는 올바른 요소가 없기 때문입니다.

C에서는 데이터 구조의 끝을 넘어 읽는 것은 정의되지 않은 동작입니다. 메모리가 해당 구조에 속하지 않더라도, 데이터 구조의 해당 요소에 해당하는 메모리 위치에 있는 값을 얻을 수 있습니다. 이를 버퍼 오버리드(buffer overread)라고 하며, 공격자가 인덱스를 조작하여 데이터 구조 뒤에 저장된 읽을 수 없어야 하는 데이터에 접근할 수 있게 되면 보안 취약점으로 이어질 수 있습니다.

이러한 종류의 취약점으로부터 프로그램을 보호하기 위해, 존재하지 않는 인덱스의 요소를 읽으려고 하면 Rust는 실행을 중단하고 계속 진행하는 것을 거부합니다. 다음을 시도해 보겠습니다:

$ cargo run
   Compiling panic v0.1.0 (file:///projects/panic)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.27s
     Running `target/debug/panic`

thread 'main' (6017887) panicked at src/main.rs:4:6:
index out of bounds: the len is 3 but the index is 99
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

이 오류는 v에서 벡터의 인덱스 99에 접근하려고 하는 main.rs의 4번째 줄을 가리킵니다.

note: 줄은 RUST_BACKTRACE 환경 변수를 설정하면 오류의 원인이 된 정확한 내용을 담은 백트레이스를 얻을 수 있음을 알려줍니다. 백트레이스는 이 지점에 도달하기까지 호출된 모든 함수의 목록입니다. Rust의 백트레이스는 다른 언어와 동일한 방식으로 작동합니다. 백트레이스를 읽는 핵심은 맨 위에서부터 읽다가 자신이 작성한 파일을 발견할 때까지 읽는 것입니다. 그곳이 문제가 시작된 위치입니다. 그 위치 위쪽의 줄은 자신의 코드가 호출한 코드이고, 아래쪽의 줄은 자신의 코드를 호출한 코드입니다. 이 앞뒤 줄에는 Rust 코어 코드, 표준 라이브러리 코드, 또는 사용 중인 크레이트가 포함될 수 있습니다. RUST_BACKTRACE 환경 변수를 0를 제외한 아무 값으로든 설정하여 백트레이스를 가져오도록 해 보겠습니다. Listing 9-2는 이와 유사한 출력을 보여줍니다.

출력이 매우 많습니다! 운영체제와 Rust 버전에 따라 표시되는 정확한 출력이 다를 수 있습니다. 이러한 정보를 포함한 백트레이스를 얻으려면 디버그 심볼을 활성화해야 합니다. 여기에서처럼 cargo build 또는 cargo run 플래그 없이 --release를 사용할 때 디버그 심볼은 기본적으로 활성화됩니다.

Listing 9-2의 출력에서, 백트레이스의 6번째 줄은 문제를 일으키는 우리 프로젝트의 줄, 즉 src/main.rs의 4번째 줄을 가리킵니다. 프로그램이 패닉(panic)하지 않기를 원한다면, 우리가 작성한 파일을 언급하는 첫 번째 줄이 가리키는 위치에서 조사를 시작해야 합니다. Listing 9-1에서 의도적으로 패닉을 일으키는 코드를 작성한 경우, 패닉을 수정하는 방법은 벡터 인덱스 범위를 초과하는 요소를 요청하지 않는 것입니다. 앞으로 코드가 패닉할 때, 어떤 값으로 어떤 동작을 수행하여 패닉이 발생했는지와 대신 코드가 무엇을 해야 하는지 파악해야 합니다.

panic!로 돌아가서 panic!를 사용하여 “에” panic! 하지 않을 것 panic!” 섹션의 오류 조건을 처리하지 않아야 할 때이 장의 뒷부분에서. 다음으로 Result를 사용하여 오류를 복구하는 방법을 살펴 보겠습니다.
