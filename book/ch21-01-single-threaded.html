The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

단일 스레드 웹 서버 만들기

우리는 단일 스레드 웹 서버를 동작시키는 것부터 시작하겠습니다. 시작하기 전에, 웹 서버 구축에 관여하는 프로토콜에 대한 간략한 개요를 살펴보겠습니다. 이 책에서는 이러한 프로토콜의 세부 사항을 다루지 않지만, 간단한 개요만으로도 필요한 정보를 얻을 수 있습니다.

웹 서버에 관여하는 두 가지 주요 프로토콜은 HTTP(Hypertext Transfer Protocol)와 TCP(Transmission Control Protocol)입니다. 두 프로토콜 모두 요청-응답(request-response) 프로토콜로, 클라이언트가 요청을 시작하고 서버가 요청을 수신한 뒤 클라이언트에 응답을 제공합니다. 이러한 요청과 응답의 내용은 프로토콜에 의해 정의됩니다.

TCP는 정보가 한 서버에서 다른 서버로 어떻게 전달되는지에 대한 세부 사항을 설명하지만, 그 정보가 무엇인지는 지정하지 않는 저수준 프로토콜입니다. HTTP는 요청과 응답의 내용을 정의함으로써 TCP 위에 구축됩니다. 기술적으로 HTTP를 다른 프로토콜과 함께 사용하는 것도 가능하지만, 대부분의 경우 HTTP는 TCP를 통해 데이터를 전송합니다. 우리는 TCP와 HTTP 요청 및 응답의 원시 바이트(raw bytes)를 다룰 것입니다.

TCP 연결 수신하기

웹 서버는 TCP 연결을 수신해야 하므로, 이것이 우리가 작업할 첫 번째 부분입니다. 표준 라이브러리는 이를 수행할 수 있도록 std::net 모듈을 제공합니다. 평소와 같이 새 프로젝트를 만들어 봅시다.

$ cargo new hello
     Created binary (application) `hello` project
$ cd hello

이제 127.0.0.1:7878에 나열 21-1의 코드를 입력하여 시작합니다. 이 코드는 로컬 주소 127.0.0.1:7878에서 들어오는 TCP 스트림을 수신 대기합니다. 들어오는 스트림을 받으면 Connection established!를 출력합니다.

TcpListener를 사용하면 주소 127.0.0.1:7878에서 TCP 연결을 수신할 수 있습니다. 주소에서 콜론(:) 앞 부분은 컴퓨터를 나타내는 IP 주소입니다. 이 값은 모든 컴퓨터에서 동일하며, 저자의 컴퓨터를 특정하여 나타내는 것이 아닙니다. 콜론 뒤의 7878는 포트 번호입니다. 이 포트를 선택한 이유는 두 가지입니다. 첫째, HTTP는 일반적으로 이 포트에서 제공되지 않으므로, 사용자가 실행 중인 다른 웹 서버와 충돌할 가능성이 낮습니다. 둘째, 7878은 전화기 번호판에서 'rust'를 나타내는 숫자입니다.

이 시나리오에서 bind 함수는 new 함수와 유사하게 작동하여 새로운 TcpListener 인스턴스를 반환합니다. 이 함수가 bind라고 불리는 이유는 네트워킹에서 특정 포트에 연결하여 수신 대기하는 것을 '포트에 바인딩한다'고 부르기 때문입니다.

bind 함수는 Result<T, E>을 반환합니다. 이는 바인딩이 실패할 수 있음을 의미합니다. 예를 들어, 동일한 프로그램을 두 번 실행하여 두 프로그램이 같은 포트를 수신 대기하는 경우입니다. 학습 목적으로 기본적인 서버만 작성하는 것이므로 이러한 오류를 처리하는 데 신경 쓰지 않겠습니다. 대신 오류가 발생하면 unwrap를 사용하여 프로그램을 중단하겠습니다.

TcpListener의 incoming 메서드는 스트림의 시퀀스(더 구체적으로 TcpStream 타입의 스트림)를 제공하는 반복자를 반환합니다. 하나의 스트림은 클라이언트와 서버 사이의 열린 연결을 나타냅니다. Connection은 클라이언트가 서버에 연결하고, 서버가 응답을 생성하며, 서버가 연결을 닫는 전체 요청 및 응답 프로세스를 가리키는 이름입니다. 따라서 우리는 TcpStream에서 읽어서 클라이언트가 무엇을 보냈는지 확인한 후, 스트림에 응답을 작성하여 데이터를 클라이언트로 되돌려 보냅니다. 전체적으로 이 for 루프는 각 연결을 순서대로 처리하여 우리가 처리할 스트림의 일련의 시퀀스를 생성합니다.

현재로서는 unwrap를 호출하여 스트림에 오류가 있는 경우 프로그램을 종료하는 방식으로 처리합니다. 오류가 없으면 프로그램은 메시지를 출력합니다. 성공 케이스에 대한 추가 기능은 다음 목록에서 추가하겠습니다. 클라이언트가 서버에 연결할 때 incoming 메서드에서 오류를 수신할 수 있는 이유는 우리가 실제로 연결(connections)을 반복하는 것이 아니라 연결 시도(connection attempts)를 반복하기 때문입니다. 연결이 성공하지 못할 수 있는 이유는 여러 가지가 있으며, 그중 많은 부분이 운영체제에 특화되어 있습니다. 예를 들어, 많은 운영체제는 동시에 지원할 수 있는 열린 연결 수에 한계가 있습니다. 이 한도를 초과하는 새로운 연결 시도는 일부 열린 연결이 닫힐 때까지 오류를 발생시킵니다.

이 코드를 실행해 보겠습니다! 터미널에서 cargo run를 실행한 후 웹 브라우저에서 127.0.0.1:7878을 입력하세요. 서버가 현재 데이터를 반환하지 않기 때문에 브라우저에는 "Connection reset"과 같은 오류 메시지가 표시되어야 합니다. 하지만 터미널을 보면, 브라우저가 서버에 연결되었을 때 출력된 여러 메시지를 볼 수 있을 것입니다!

     Running `target/debug/hello`
Connection established!
Connection established!
Connection established!

브라우저 요청 하나에 대해 여러 메시지가 출력되는 경우가 있습니다. 그 이유는 브라우저가 페이지에 대한 요청뿐만 아니라 브라우저 탭에 표시되는 favicon.ico 아이콘과 같은 다른 리소스에 대한 요청도 보내기 때문일 수 있습니다.

또한 서버가 어떤 데이터로도 응답하지 않기 때문에 브라우저가 서버에 여러 번 연결을 시도할 수도 있습니다. stream가 스코프를 벗어나 루프 끝에서 드롭(drop)되면, drop 구현의 일부로서 연결이 닫힙니다. 브라우저는 문제가 일시적일 수 있으므로 재시도(retry)하여 닫힌 연결을 처리하는 경우가 있습니다.

브라우저는 또한 나중에 요청을 보내면 해당 요청이 더 빠르게 처리될 수 있도록, 요청을 보내지 않고 서버에 여러 연결을 여는 경우가 있습니다. 이 경우 서버는 해당 연결을 통해 요청이 있는지 여부에 관계없이 각 연결을 확인합니다. 예를 들어, 많은 버전의 Chrome 기반 브라우저가 이렇게 동작합니다. 개인 정보 보호 모드를 사용하거나 다른 브라우저를 사용하면 이 최적화를 비활성화할 수 있습니다.

중요한 점은 TCP 연결에 대한 핸들을 성공적으로 얻었다는 것입니다!

특정 버전의 코드를 실행한 후에는 ctrl-C를 눌러 프로그램을 중지하십시오. 그런 다음, 각 코드 변경 사항을 적용한 후 cargo run 명령을 실행하여 프로그램을 다시 시작함으로써 최신 코드가 실행 중인지 확인하십시오.

요청 읽기

브라우저에서 요청을 읽는 기능을 구현해 봅시다! 먼저 연결을 얻고, 그 연결로 작업을 수행하는 두 가지 관심사를 분리하기 위해 연결을 처리하는 새로운 함수를 만들겠습니다. 이 새로운 handle_connection 함수에서 TCP 스트림에서 데이터를 읽고 출력하여 브라우저에서 전송되는 데이터를 확인할 수 있습니다. 코드를 Listing 21-2와 같이 변경하십시오.

오시는 길 std::io::BufReader 그리고 std::io::prelude 스트림에서 읽고 쓸 수 있는 형질과 타입에 접근할 수 있는 범위로. for 루프 인 더 main 함수는, 우리가 연결했다는 메세지를 출력하는 대신에, 우리는 이제 새로운 것을 호출합니다. handle_connection 기능 및 통행 stream 그것을 위해.

handle_connection 함수에서, BufReader에 대한 참조를 감싸는 새로운 stream 인스턴스를 생성합니다. BufReader는 std::io::Read 트레이트 메서드에 대한 호출을 관리함으로써 버퍼링을 제공합니다.

브라우저가 서버로 보내는 요청의 줄을 수집하기 위해 http_request라는 변수를 생성합니다. Vec<_> 타입 주석을 추가하여 이 줄들을 벡터에 수집하고자 함을 나타냅니다.

BufReader은 std::io::BufRead 트레이트를 구현하며, 이 트레이트는 lines 메서드를 제공합니다. lines 메서드는 줄바꿈 바이트를 발견할 때마다 데이터 스트림을 분할하여 Result<String, std::io::Error> 타입의 반복자를 반환합니다. 각 String 값을 얻기 위해 map을 적용하고 unwrap을 호출하여 각 Result을 처리합니다. 데이터가 유효한 UTF-8이 아니거나 스트림에서 읽는 과정에서 문제가 발생하면 Result에 오류가 포함될 수 있습니다. 다시 한번 강조하지만, 프로덕션 프로그램에서는 이러한 오류를 더 세심하게 처리해야 하지만, 여기서는 단순성을 위해 오류 발생 시 프로그램을 중단하도록 선택했습니다.

브라우저는 줄바꿈 문자를 두 번 연속으로 보내어 HTTP 요청의 끝을 알립니다. 따라서 스트림에서 하나의 요청을 추출하려면 빈 문자열인 줄을 받을 때까지 줄을 읽어야 합니다. 줄을 벡터에 모두 수집한 후에는, 웹 브라우저가 서버로 보내는 지시사항을 확인할 수 있도록 예쁜 디버그 포맷으로 출력합니다.

이 코드를 실행해 보겠습니다! 프로그램을 시작하고 웹 브라우저에서 다시 요청을 보내십시오. 브라우저에서는 여전히 오류 페이지가 표시되지만, 터미널에서 프로그램의 출력은 다음과 유사한 형태가 될 것입니다:

HTTP 요청을 더 자세히 살펴보기

HTTP는 텍스트 기반 프로토콜이며, 요청은 다음과 같은 형식을 가집니다:

Method Request-URI HTTP-Version CRLF
headers CRLF
message-body

첫 번째 줄은 클라이언트가 요청하는 내용에 대한 정보를 담고 있는 요청 줄입니다. 요청 줄의 첫 번째 부분은 클라이언트가 이 요청을 수행하는 방식을 설명하는 방법, 즉 GET 또는 POST과 같은 메서드를 나타냅니다. 우리 클라이언트는 GET 요청을 사용했으며, 이는 정보를 요청한다는 의미입니다.

요청 줄의 다음 부분은 /이며, 이는 클라이언트가 요청하는 균일 리소스 식별자(URI)를 나타냅니다. URI는 균일 리소스 로케이터(URL)와 거의 같지만 완전히 동일하지는 않습니다. 이 장의 목적에서는 URI와 URL의 차이가 중요하지 않지만, HTTP 사양에서는 URI라는 용어를 사용하므로 여기서는 URI를 URL로 생각하면 됩니다.

마지막 부분은 클라이언트가 사용하는 HTTP 버전이며, 요청 줄은 CRLF 시퀀스로 끝납니다. CRLF는 캐리지 리턴과 라인 피드를 의미하며, 이는 타자기 시대부터 사용된 용어입니다! CRLF 시퀀스는 \r\n로도 쓸 수 있으며, 여기서 \r는 캐리지 리턴, \n는 라인 피드를 나타냅니다. CRLF 시퀀스는 요청 줄을 나머지 요청 데이터와 구분합니다. CRLF가 출력되면 \r\n 대신 새로운 줄이 시작되는 것을 볼 수 있습니다.

지금까지 프로그램을 실행하여 받은 요청 줄 데이터를 보면, GET가 메서드이고 /가 요청 URI이며 HTTP/1.1가 버전임을 알 수 있습니다.

요청 줄 다음에 Host:에서 시작하는 나머지 줄은 헤더입니다. GET 요청에는 본문이 없습니다.

다른 브라우저에서 요청을 하거나 127.0.0.1:7878/test와 같은 다른 주소를 요청하여 요청 데이터가 어떻게 달라지는지 확인해 보세요.

이제 브라우저가 무엇을 요청하는지 알았으니, 데이터를 보내 보겠습니다!

응답 작성하기

클라이언트 요청에 대한 응답으로 데이터를 전송하는 기능을 구현하겠습니다. 응답은 다음과 같은 형식을 가집니다.

HTTP-Version Status-Code Reason-Phrase CRLF
headers CRLF
message-body

첫 번째 줄은 상태 줄(status line)입니다. 이 줄에는 응답에 사용된 HTTP 버전, 요청 결과를 요약하는 숫자 상태 코드, 그리고 상태 코드를 텍스트로 설명하는 이유 문구(reason phrase)가 포함됩니다. CRLF 시퀀스 이후에는 헤더, 또 다른 CRLF 시퀀스, 그리고 응답 본문이 위치합니다.

다음은 HTTP 버전 1.1을 사용하고 상태 코드가 200이며, 이유 문구가 OK이고, 헤더와 본문이 없는 응답의 예시입니다.

HTTP/1.1 200 OK\r\n\r\n

상태 코드 200은 표준적인 성공 응답입니다. 이 텍스트는 아주 작은 성공적인 HTTP 응답입니다. 성공적인 요청에 대한 응답으로 이 내용을 스트림에 작성해 보겠습니다. handle_connection 함수에서 요청 데이터를 출력하던 println!을 제거하고 Listing 21-3의 코드로 대체하십시오.

상기 새로운 라인은 The new line defines response 성공 메시지의 데이터를 담고있는 변수입니다. 그런 다음 호출합니다 as_bytes 제품정보 response 문자열 데이터를 바이트로 변환합니다. write_all 메서드 켜짐 stream 받아라 A &[u8] 그리고 직접 그 바이트를 연결의 아래 보냅니다. 때문에 write_all 작업이 실패 할 수 있습니다, 우리는 사용 unwrap 이전과 같은 오류 결과에. 다시, 실제 응용 프로그램에서, 당신은 여기에 오류 처리를 추가 할 것입니다.

이러한 변경 사항을 적용하고 코드를 실행한 뒤 요청을 보내 보겠습니다. 더 이상 터미널에 데이터를 출력하지 않으므로 Cargo의 출력 외에는 아무것도 볼 수 없습니다. 웹 브라우저에서 127.0.0.1:7878을 열면 오류 대신 빈 페이지가 표시되어야 합니다. 이제 HTTP 요청을 수신하고 응답을 보내는 과정을 직접 코드로 구현해 보았습니다!

빈 페이지보다 더 많은 내용을 반환하는 기능을 구현해 보겠습니다. src 디렉토리가 아닌 프로젝트 디렉토리의 루트에 hello.html 파일을 생성합니다. 원하는 HTML을 입력할 수 있으며, Listing 21-4는 하나의 예시를 보여줍니다.

이것은 제목과 일부 텍스트가 포함된 최소한의 HTML5 문서입니다. 요청을 수신하면 서버에서 이 내용을 반환하도록 Listing 21-5에 표시된 대로 handle_connection를 수정하여 HTML 파일을 읽고, 응답 본문으로 추가한 다음 전송합니다.

fs를 use 문에 추가하여 표준 라이브러리의 파일 시스템 모듈을 현재 범위로 가져왔습니다. 파일의 내용을 문자열로 읽는 코드는 익숙해 보일 것입니다. Listing 12-4의 I/O 프로젝트에서 파일 내용을 읽을 때 이 코드를 사용했기 때문입니다.

다음으로 format!를 사용하여 파일의 내용을 성공 응답의 본문으로 추가합니다. 유효한 HTTP 응답을 보장하기 위해 Content-Length 헤더를 추가합니다. 이 헤더는 응답 본문의 크기로 설정되며, 이 경우 hello.html의 크기가 됩니다.

cargo run로 이 코드를 실행하고 브라우저에서 127.0.0.1:7878을 로드하면 HTML이 렌더링된 것을 볼 수 있습니다!

현재 http_request의 요청 데이터를 무시하고 무조건적으로 HTML 파일의 내용을 반환하고 있습니다. 즉, 브라우저에서 127.0.0.1:7878/something-else를 요청해도 동일한 HTML 응답을 받게 됩니다. 현재 우리의 서버는 매우 제한적이며 대부분의 웹 서버가 수행하는 기능을 하지 못합니다. 요청에 따라 응답을 맞춤화하고, /에 대한 잘 형성된 요청에 대해서만 HTML 파일을 반환하도록 개선하고 싶습니다.

요청을 검증하고 선택적으로 응답하기

현재 웹 서버는 클라이언트가 무엇을 요청했는지와 관계없이 파일에 있는 HTML을 반환합니다. 브라우저가 /을 요청하는지 확인한 후 HTML 파일을 반환하고, 다른 경로를 요청하면 오류를 반환하는 기능을 추가하겠습니다. 이를 위해 handle_connection함수를 Listing 21-6에 나와 있는 것처럼 수정해야 합니다. 이 새로운 코드는 수신된 요청의 내용을 우리가 알고 있는 / 요청의 형태와 비교하여 if와 else 블록을 통해 요청을 다르게 처리합니다.

HTTP 요청의 첫 번째 줄만 살펴볼 것이므로, 전체 요청을 벡터로 읽는 대신 next을 호출하여 반복자에서 첫 번째 항목을 가져옵니다. 첫 번째 unwrap은 Option을 처리하며, 반복자에 항목이 없으면 프로그램을 중단합니다. 두 번째 unwrap은 Result을 처리하며, Listing 21-2에서 추가한 unwrap 안의 map과 동일한 효과를 가집니다.

그런 다음 request_line를 확인하여, 해당 값이 / 경로에 대한 GET 요청의 요청 줄과 일치하는지 살펴봅니다. 일치하는 경우 if 블록은 HTML 파일의 내용을 반환합니다.

request_line가 / 경로에 대한 GET 요청과 같지 않다면, 다른 요청을 받았다는 뜻입니다. 잠시 후 else 블록에 코드를 추가하여 나머지 모든 요청에 응답하도록 하겠습니다.

지금 이 코드를 실행하고 127.0.0.1:7878을 요청해 보세요. hello.html에 있는 HTML을 받아야 합니다. 127.0.0.1:7878/something-else와 같은 다른 요청을 하면, Listing 21-1과 Listing 21-2의 코드를 실행할 때 확인했던 것과 같은 연결 오류가 발생합니다.

이제 Listing 21-7의 코드를 else 블록에 추가하여 상태 코드 404가 포함된 응답을 반환하겠습니다. 이는 요청한 콘텐츠를 찾을 수 없음을 나타냅니다. 또한 최종 사용자에게 응답을 알리는 페이지를 브라우저에 렌더링하기 위해 일부 HTML을 반환합니다.

여기서 응답은 상태 코드 404와 이유 문구 NOT FOUND를 포함한 상태 라인을 가집니다. 응답 본문은 404.html 파일에 포함된 HTML이 됩니다. 오류 페이지를 위해 hello.html 파일과 같은 위치에 404.html 파일을 만들어야 합니다. 원하는 HTML을 자유롭게 사용하거나, 리스트 21-8의 예제 HTML을 사용할 수 있습니다.

이러한 변경 사항을 적용한 후 서버를 다시 실행합니다. 127.0.0.1:7878을 요청하면 hello.html의 내용이 반환되어야 하고, 127.0.0.1:7878/foo와 같은 다른 요청은 404.html의 오류 HTML이 반환되어야 합니다.

리팩토링

현재 if와 else 블록에는 많은 중복이 있습니다. 두 블록 모두 파일을 읽고 파일의 내용을 스트림에 씁니다. 유일한 차이점은 상태 라인과 파일 이름입니다. 이 차이점을 별도의 if와 else 문으로 분리하여 상태 라인과 파일 이름의 값을 변수에 할당함으로써 코드를 더 간결하게 만들어 보겠습니다. 이후 이 변수를 사용하여 조건 없이 파일을 읽고 응답을 작성할 수 있습니다. 리스트 21-9는 큰 if와 else 블록을 대체한 후의 결과 코드를 보여줍니다.

이제 if와 else 블록은 상태 라인과 파일 이름에 대한 적절한 값만 튜플로 반환합니다. 그리고 19장에서 설명한 바와 같이, status_line와 filename 문에서 패턴을 사용하여 이 두 값을 let에 할당하기 위해 구조 분해를 사용합니다.

이전에 중복된 코드는 이제 if 및 else 블록 외부에 있으며 status_line 및 filename 변수를 사용합니다. 이를 통해 두 경우의 차이를 쉽게 볼 수 있으며, 파일 읽기 및 응답 쓰기 작업을 변경하려면 코드를 업데이트할 장소가 하나만 있음을 의미합니다. Listing 2-9의 코드 동작은 동일할 것입니다.

현재 서버는 단일 스레드로 실행되므로 한 번에 하나의 요청만 처리할 수 있습니다. 느린 요청을 시뮬레이션하여 이것이 어떤 문제를 일으킬 수 있는지 살펴보고, 서버가 동시에 여러 요청을 처리할 수 있도록 수정하겠습니다.
