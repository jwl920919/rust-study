The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

열거형 정의

구조체는 관련 필드와 데이터를 함께 그룹화하는 방법을 제공합니다. Rectangle 그와 함께 width 그리고 height, 열거형은 값이 가능한 값 집합 중 하나라고 말하는 방법을 제공합니다. 예를 들어 다음과 같이 말할 수 있습니다. Rectangle 다음을 포함하는 일련의 가능한 도형들 중 하나입니다. Circle 그리고 Triangle이를 위해 러스트는 이러한 가능성을 열거형으로 인코딩할 수 있습니다.

코드에서 표현하고 싶은 상황을 살펴보고, 이 경우 열거형이 구조체보다 유용하고 더 적합한 이유를 알아보겠습니다. IP 주소로 작업해야 한다고 가정해 봅시다. 현재 IP 주소에는 버전 4와 버전 6이라는 두 가지 주요 표준이 사용됩니다. 이 두 가지가 프로그램이 마주할 IP 주소의 유일한 가능성이기 때문에, 가능한 모든 변형을 열거할 수 있습니다. 열거형이라는 이름도 여기서 유래합니다.

모든 IP 주소는 버전 4 주소이거나 버전 6 주소일 수 있지만, 동시에 둘 다일 수는 없습니다. IP 주소의 이 특성은 열거형 데이터 구조를 적합하게 만듭니다. 열거형 값은 그 변형 중 하나만 될 수 있기 때문입니다. 버전 4와 버전 6 주소는 모두 기본적으로 IP 주소이므로, 코드가 모든 종류의 IP 주소에 적용되는 상황을 처리할 때 동일한 타입으로 취급되어야 합니다.

IpAddrKind 열거형을 정의하고 IP 주소가 될 수 있는 가능한 종류인 V4과 V6를 나열하여 코드에서 이 개념을 표현할 수 있습니다. 다음은 열거형의 변형입니다:

enum IpAddrKind {
    V4,
    V6,
}

fn main() {
    let four = IpAddrKind::V4;
    let six = IpAddrKind::V6;

    route(IpAddrKind::V4);
    route(IpAddrKind::V6);
}

fn route(ip_kind: IpAddrKind) {}

IpAddrKind는 이제 코드의 다른 곳에서 사용할 수 있는 사용자 정의 데이터 타입입니다.

열거형 값

IpAddrKind의 두 가지 변형 각각에 대한 인스턴스를 다음과 같이 만들 수 있습니다:

enum IpAddrKind {
    V4,
    V6,
}

fn main() {
    let four = IpAddrKind::V4;
    let six = IpAddrKind::V6;

    route(IpAddrKind::V4);
    route(IpAddrKind::V6);
}

fn route(ip_kind: IpAddrKind) {}

enum의 변형은 식별자 아래에 네임스페이스되며, 이중 콜론(::)으로 구분합니다. 이는 유용한데, 이제 IpAddrKind::V4와 IpAddrKind::V6 값이 모두 동일한 타입인 IpAddrKind이기 때문입니다. 예를 들어, 어떤 IpAddrKind 값이든 인수로 받는 함수를 정의할 수 있습니다.

enum IpAddrKind {
    V4,
    V6,
}

fn main() {
    let four = IpAddrKind::V4;
    let six = IpAddrKind::V6;

    route(IpAddrKind::V4);
    route(IpAddrKind::V6);
}

fn route(ip_kind: IpAddrKind) {}

그리고 이 함수를 두 변형 중 어느 것으로든 호출할 수 있습니다:

enum IpAddrKind {
    V4,
    V6,
}

fn main() {
    let four = IpAddrKind::V4;
    let six = IpAddrKind::V6;

    route(IpAddrKind::V4);
    route(IpAddrKind::V6);
}

fn route(ip_kind: IpAddrKind) {}

enum을 사용하면 더 많은 이점이 있습니다. IP 주소 타입에 대해 더 생각해보면, 현재 실제 IP 주소 데이터를 저장할 방법이 없습니다. 우리는 단지 그것이 어떤 종류인지만 알고 있을 뿐입니다. 5장에서 구조체에 대해 배웠으므로, Listing 6-1과 같이 구조체를 사용하여 이 문제를 해결하려는 유혹을 느낄 수 있습니다.

여기서 두 개의 필드를 가진 IpAddr 구조체를 정의했습니다. kind 필드는 이전에 정의한 열거형인 IpAddrKind 타입이고, address 필드는 String 타입입니다. 이 구조체의 인스턴스가 두 개 있습니다. 첫 번째는 home이며, kind 값으로 IpAddrKind::V4을 가지고 있고, 연관된 주소 데이터는 127.0.0.1입니다. 두 번째 인스턴스는 loopback입니다. kind 값으로 IpAddrKind의 다른 변형인 V6을 가지고 있으며, 연관된 주소는 ::1입니다. 구조체를 사용하여 kind 값과 address 값을 함께 묶었으므로, 이제 변형은 값과 연관됩니다.

그러나 enum만 사용하여 동일한 개념을 표현하는 것이 더 간결합니다. 구조체 안에 enum을 넣는 대신, 각 enum 변형에 직접 데이터를 넣을 수 있습니다. IpAddr enum의 이 새로운 정의에 따르면, V4 및 V6 변형 모두 String 값과 연관됩니다:

fn main() {
    enum IpAddr {
        V4(String),
        V6(String),
    }

    let home = IpAddr::V4(String::from("127.0.0.1"));

    let loopback = IpAddr::V6(String::from("::1"));
}

enum의 각 변형에 직접 데이터를 첨부하므로 추가적인 struct가 필요하지 않습니다. 여기서 enum이 어떻게 작동하는지에 대한 또 다른 세부 사항을 더 쉽게 볼 수 있습니다. 우리가 정의하는 각 enum 변형의 이름은 또한 enum의 인스턴스를 생성하는 함수가 됩니다. 즉, IpAddr::V4()은 String 인수를 받아 IpAddr 타입의 인스턴스를 반환하는 함수 호출입니다. enum을 정의한 결과로 이 생성자 함수가 자동으로 정의됩니다.

구조체가 아닌 enum을 사용하는 것의 또 다른 장점이 있습니다. 각 변형은 서로 다른 타입과 양의 연관 데이터를 가질 수 있습니다. 버전 4 IP 주소에는 항상 0과 255 사이의 값을 갖는 네 개의 숫자 구성 요소가 있습니다. 만약 V4 주소를 네 개의 u8 값으로 저장하되, 여전히 V6 주소를 하나의 String 값으로 표현하고 싶다면, 구조체로는 이를 할 수 없습니다. enum은 이 경우를 쉽게 처리합니다:

fn main() {
    enum IpAddr {
        V4(u8, u8, u8, u8),
        V6(String),
    }

    let home = IpAddr::V4(127, 0, 0, 1);

    let loopback = IpAddr::V6(String::from("::1"));
}

우리는 버전 4와 버전 6 IP 주소를 저장하기 위해 데이터 구조를 정의하는 몇 가지 다른 방법을 보여주었습니다. 그러나 IP 주소를 저장하고 어떤 종류의 IP 주소를 인코딩하기를 원하기 때문에 표준 라이브러리에는 우리가 사용할 수 있는 정의가 있습니다! 표준 라이브러리가 IpAddr를 정의하는 방법을 살펴 보겠습니다. 우리가 정의하고 사용했던 정확한 열거형과 변형이 있지만 변형의 각 주소 데이터를 다른 형태로 포함시킵니다.

#![allow(unused)]
fn main() {
struct Ipv4Addr {
    // --snip--
}

struct Ipv6Addr {
    // --snip--
}

enum IpAddr {
    V4(Ipv4Addr),
    V6(Ipv6Addr),
}
}

이 코드는 열거형 변형 안에 문자열, 숫자 타입, 구조체 등 다양한 종류의 데이터를 넣을 수 있음을 보여줍니다. 심지어 다른 열거형도 포함할 수 있습니다! 또한 표준 라이브러리의 타입은 여러분이 생각해 낼 수 있는 것보다 훨씬 복잡하지 않은 경우가 많습니다.

표준 라이브러리에 IpAddr에 대한 정의가 포함되어 있지만, 표준 라이브러리의 정의를 현재 스코프에 가져오지 않았기 때문에 충돌 없이 자체 정의를 만들고 사용할 수 있습니다. 7장에서 타입을 스코프에 가져오는 방법에 대해 자세히 다루겠습니다.

열거형의 또 다른 예시로 Listing 6-2를 살펴봅시다. 이 열거형은 변형 안에 다양한 타입의 데이터를 포함하고 있습니다.

이 열거형에는 서로 다른 타입을 가진 네 가지 변형이 있습니다:

  • Quit: 관련 데이터가 전혀 없습니다
  • Move: 구조체처럼 이름이 지정된 필드를 가집니다
  • Write: 단일 String 포함
  • ChangeColor: 세 개의 i32 값 포함

Listing 6-2의 변형과 같은 열거형을 정의하는 것은 다른 종류의 구조체 정의를 정의하는 것과 유사합니다. 다만 열거형은 struct 키워드를 사용하지 않으며, 모든 변형이 Message 유형 아래에 함께 묶여 있다는 점이 다릅니다. 다음 구조체들은 이전 열거형 변형들이 담고 있는 것과 동일한 데이터를 담을 수 있습니다.

struct QuitMessage; // unit struct
struct MoveMessage {
    x: i32,
    y: i32,
}
struct WriteMessage(String); // tuple struct
struct ChangeColorMessage(i32, i32, i32); // tuple struct

fn main() {}

그러나 각기 다른 구조체를 사용하면 각각 고유한 유형을 가지므로, Listing 6-2에 정의된 단일 유형인 Message 열거형처럼 이러한 메시지 유형 중 하나를 인자로 받는 함수를 쉽게 정의할 수 없습니다.

열거형과 구조체 사이에는 또 하나의 유사성이 있습니다. impl을 사용하여 구조체에 메서드를 정의할 수 있듯이, 열거형에도 메서드를 정의할 수 있습니다. 다음은 Message 열거형에 정의할 수 있는 call이라는 이름의 메서드입니다: call Message

fn main() {
    enum Message {
        Quit,
        Move { x: i32, y: i32 },
        Write(String),
        ChangeColor(i32, i32, i32),
    }

    impl Message {
        fn call(&self) {
            // method body would be defined here
        }
    }

    let m = Message::Write(String::from("hello"));
    m.call();
}

메서드 본문에서는 self을 사용하여 메서드를 호출한 대상의 값을 가져옵니다. 이 예제에서는 Message::Write(String::from("hello")) 값을 가진 변수 m을 만들었고, m.call()이 실행될 때 call 메서드 본문에서 self는 이 값이 됩니다.

표준 라이브러리에서 매우 일반적이고 유용한 또 다른 열거형인 Option을 살펴보겠습니다.

Option 열거형

이 섹션에서는 표준 라이브러리가 정의한 또 다른 열거형인 Option에 대한 사례 연구를 살펴봅니다. Option 타입은 값이 존재하거나 존재하지 않을 수 있는 매우 일반적인 상황을 표현합니다.

예를 들어, 비어 있지 않은 목록에서 첫 번째 항목을 요청하면 값을 얻을 수 있습니다. 빈 목록에서 첫 번째 항목을 요청하면 아무것도 얻지 못합니다. 이 개념을 타입 시스템으로 표현하면 컴파일러가 처리해야 하는 모든 경우를 처리했는지 확인할 수 있습니다. 이 기능은 다른 프로그래밍 언어에서 매우 흔하게 발생하는 버그를 방지할 수 있습니다.

프로그래밍 언어 설계는 어떤 기능을 포함할지에 대해 논의되는 경우가 많지만, 어떤 기능을 제외할지도 중요합니다. Rust는 다른 많은 언어에 있는 null 기능이 없습니다. null은 해당 위치에 값이 없음을 의미하는 값입니다. null이 있는 언어에서 변수는 항상 null이거나 null이 아닌 두 가지 상태 중 하나에 있습니다.

null의 발명가인 Tony Hoare는 2009년 발표된 "Null References: The Billion Dollar Mistake"에서 다음과 같이 말했습니다.

저는 이것을 10억 달러짜리 실수라고 부릅니다. 그 당시 저는 객체 지향 언어에서 참조를 위한 최초의 포괄적인 타입 시스템을 설계하고 있었습니다. 저의 목표는 컴파일러가 자동으로 검사를 수행하여 참조의 모든 사용이 절대적으로 안전하도록 하는 것이었습니다. 하지만 구현이 매우 쉬웠기 때문에 null 참조를 포함하려는 유혹에 저항할 수 없었습니다. 이로 인해 수많은 오류, 취약점, 시스템 충돌이 발생하여 지난 40년 동안 아마도 10억 달러 상당의 고통과 피해를 초래했을 것입니다.

null 값의 문제는 null 값을 null이 아닌 값으로 사용하려고 하면 어떤 종류의 오류가 발생한다는 것입니다. 이 null 또는 null이 아닌 속성이 널리 퍼져 있기 때문에 이러한 종류의 오류를 범하기가 매우 쉽습니다.

그러나 null이 표현하려는 개념은 여전히 유용합니다. null은 어떤 이유로 인해 현재 유효하지 않거나 존재하지 않는 값을 의미합니다.

문제는 컨셉이 아니라 특정 구현에 있습니다. 따라서 러스트에는 null이 없지만 값이 존재하거나 존재하지 않는 개념을 인코딩 할 수있는 열거형이 있습니다. 이 열거형은 Option<T>이며 다음과 같이 표준 라이브러리 Standard Library입니다.

#![allow(unused)]
fn main() {
enum Option<T> {
    None,
    Some(T),
}
}

Option<T> 열거형은 매우 유용하여 프리lude에 이미 포함되어 있습니다. 명시적으로 스코프에 가져올 필요가 없습니다. 그 변형들도 프리lude에 포함되어 있습니다. Option:: 접두사 없이 Some과 None를 직접 사용할 수 있습니다. Option<T> 열거형은 여전히 일반 열거형이며, Some(T)와 None은 여전히 Option<T> 타입의 변형입니다.

<T> 구문은 아직 다루지 않은 Rust의 기능입니다. 이는 제네릭 타입 매개변수이며, 10장에서 제네릭을 더 자세히 다룹니다. 지금은 <T>이 Option 열거형의 Some 변형이 어떤 타입이든 하나의 데이터 조각을 저장할 수 있음을 의미하고, T 대신 사용되는 각 구체적 타입이 전체 Option<T> 타입을 서로 다른 타입으로 만든다는 것만 알면 됩니다. 숫자 타입과 문자 타입을 저장하기 위해 Option 값을 사용하는 몇 가지 예시는 다음과 같습니다:

fn main() {
    let some_number = Some(5);
    let some_char = Some('e');

    let absent_number: Option<i32> = None;
}

의 종류 some_number 있습니다. Option<i32>. 의 종류 some_char 있습니다. Option<char>, 이것은 다른 타입입니다. 러스트는 이 타입들을 추론할 수 있습니다. 왜냐하면 우리는 그 안에 값을 지정했기 때문입니다. Some 변형. 를 위해 absent_number, 러스트는 우리가 전체적으로 주석을 달기를 요구합니다. Option type: 컴파일러가 해당 형식을 유추할 수 없음 Some variant는 a를 보고만 있을 것이다. None value. 여기서, 우리는 러스트에게 우리가 의미하는 absent_number 유형이 되기 위해 Option<i32>.

Some 값이 있으면 값이 존재한다는 것을 알 수 있으며, 그 값은 Some 안에 보관됩니다. None 값이 있는 경우, 이는 어떤 의미에서 null과 동일한 의미를 가집니다. 즉, 유효한 값을 가지고 있지 않다는 뜻입니다. 그렇다면 null을 사용하는 것보다 Option<T>을 사용하는 것이 왜 더 나은가요?

간단히 말해, Option<T>과 T(여기서 T는 어떤 유형이든 될 수 있음)는 서로 다른 유형이므로, 컴파일러는 Option<T> 값을 반드시 유효한 값인 것처럼 사용할 수 없게 합니다. 예를 들어, 이 코드는 i8에 Option<i8>을 더하려고 하므로 컴파일되지 않습니다.

fn main() {
    let x: i8 = 5;
    let y: Option<i8> = Some(5);

    let sum = x + y;
}

Intense! 실제로 이 오류 메시지는 Rust가 i8과 Option<i8>을 어떻게 더해야 하는지 이해하지 못한다는 것을 의미합니다. 두 값은 서로 다른 타입이기 때문입니다. Rust에서 i8과 같은 타입의 값을 가지고 있을 때, 컴파일러는 우리가 항상 유효한 값을 가지고 있는지 보장합니다. 따라서 그 값을 사용하기 전에 null을 확인하지 않아도 자신 있게 진행할 수 있습니다. Option<i8>(또는 우리가 작업하는 값의 타입이 무엇이든)을 가질 때만 값이 없을 수 있다는 점을 걱정해야 하며, 컴파일러는 그 값을 사용하기 전에 해당 경우를 처리하도록 보장합니다.

즉, Option<T>를 T로 변환한 후에야 T 작업을 수행할 수 있습니다. 일반적으로 이는 null 관련 가장 흔한 문제 중 하나, 즉 실제로 null인 값을 null이 아닌 것으로 가정하는 실수를 잡아내는 데 도움이 됩니다.

null이 아닌 값을 잘못 가정하는 위험을 제거하면 코드를 더 신뢰할 수 있습니다. null일 수 있는 값을 사용하려면 해당 값의 타입을 명시적으로 Option<T>로 지정해야 합니다. 그런 다음 해당 값을 사용할 때 값이 null인 경우를 명시적으로 처리해야 합니다. Option<T>이 아닌 타입을 가진 값이 있는 모든 위치에서 값이 null이 아니라고 안전하게 가정할 수 있습니다. 이는 Rust가 null의 범용성을 제한하고 Rust 코드의 안전성을 높이기 위해 의도적으로 내린 설계 결정입니다.

T 타입의 값이 있을 때 Some 변형에서 Option<T> 값을 꺼내어 사용할 수 있도록 하는 방법은 무엇일까요? Option<T> enum에는 다양한 상황에서 유용한 많은 메서드가 있으며, 이를 #문서에서 확인할 수 있습니다. Option<T>의 메서드에 익숙해지면 Rust를 배우는 여정에서 매우 유용할 것입니다.

일반적으로 Option<T> 값을 사용하려면 각 변형을 처리하는 코드가 필요합니다. Some(T) 값이 있을 때만 실행되며 내부의 T를 사용할 수 있는 코드가 필요하고, None 값이 있을 때만 실행되며 T 값이 사용 불가능한 다른 코드가 필요합니다. match 식은 enum과 함께 사용할 때 이러한 역할을 수행하는 제어 흐름 구성 요소입니다. enum의 변형에 따라 다른 코드를 실행하며, 해당 코드는 일치하는 값 안에 있는 데이터를 사용할 수 있습니다.
