The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

트레이트 객체를 사용하여 공유된 동작을 추상화하기

8장에서 벡터의 한 가지 제한 사항은 한 가지 타입의 요소만 저장할 수 있다는 점을 언급했습니다. Listing 8-9에서는 정수, 실수, 텍스트를 저장할 수 있는 변형을 가진 SpreadsheetCell 열거형을 정의하여 이 문제를 우회하는 해결책을 만들었습니다. 이를 통해 각 셀에 서로 다른 타입의 데이터를 저장하면서도 셀 한 줄을 나타내는 벡터를 가질 수 있었습니다. 이는 코드가 컴파일될 때 이미 알고 있는 고정된 타입 집합으로 교환 가능한 항목을 다룰 때 완벽하게 좋은 해결책입니다.

그러나 때로는 라이브러리 사용자가 특정 상황에서 유효한 형식 집합을 확장 할 수 있기를 원합니다. 우리가 어떻게이를 달성 할 수 있는지 보여주기 위해, 우리는 항목 목록을 통해 반복하는 예제 그래픽 사용자 인터페이스 (GUI) 도구를 만들 것입니다. draw GUI 도구의 일반적인 기술인 화면에 그리는 방법. 우리는 라이브러리 크레이트라는 것을 만들 것입니다. gui 그것은 GUI 라이브러리의 구조를 포함합니다. 이 크레이트에는 사람들이 사용할 몇 가지 유형이 포함될 수 있습니다. Button 또는 TextField. 또한, gui 사용자는 그려질 수 있는 그들의 자신의 유형을 창조하고 싶을 것이다: 예를 들면, 1명의 프로그래머는 Image그리고 또 다른 하나는 SelectBox.

라이브러리를 작성하는 시점에는 다른 프로그래머가 만들고자 할 수 있는 모든 타입을 알 수 없고 정의할 수도 없습니다. 하지만 gui이 서로 다른 타입의 여러 값을 추적해야 하고, 각 값에 대해 draw 메서드를 호출해야 한다는 것은 알고 있습니다. draw 메서드를 호출할 때 정확히 어떤 일이 일어나는지 알 필요은 없으며, 해당 값에 우리가 호출할 수 있는 그 메서드가 존재한다는 것만 알면 됩니다.

상속이 있는 언어에서는 Component라는 이름을 가진 클래스를 정의하고, 이 클래스에 draw라는 메서드를 추가하는 방식으로 이 문제를 해결할 수 있습니다. Button, Image, 그리고 SelectBox와 같은 다른 클래스들은 Component에서 상속을 받아 draw 메서드도 함께 상속받게 됩니다. 각 클래스는 draw 메서드를 오버라이드하여 자체적인 동작을 정의할 수 있지만, 프레임워크는 모든 타입을 Component 인스턴스인 것처럼 취급하고 draw를 호출할 수 있습니다. 하지만 Rust에는 상속이 없으므로, 사용자가 라이브러리와 호환되는 새로운 타입을 만들 수 있도록 gui 라이브러리를 구성하는 다른 방식이 필요합니다.

공통 동작을 위한 트레이트 정의

우리가 gui에 원하는 동작을 구현하려면, Draw이라는 이름의 트레이트를 정의하고 그 안에 draw라는 이름의 메서드 하나를 포함시킵니다. 그런 다음, 트레이트 객체를 인수로 받는 벡터를 정의할 수 있습니다. 트레이트 객체는 우리가 지정한 트레이트를 구현하는 타입의 인스턴스와, 런타임에 해당 타입의 트레이트 메서드를 조회하는 데 사용되는 테이블을 가리킵니다. 트레이트 객체를 생성하려면 참조나 Box<T> 스마트 포인터와 같은 어떤 종류의 포인터를 지정하고, dyn 키워드를 사용한 후, 관련 트레이트를 지정합니다. (트레이트 객체가 포인터를 사용해야 하는 이유는 20장의 “동적 크기 타입과 Sized 트레이트”에서 다룹니다.) 트레이트 객체를 제네릭 타입이나 구체적 타입 대신 사용할 수 있습니다. 트레이트 객체를 사용하는 모든 위치에서, Rust의 타입 시스템은 컴파일 타임에 해당 컨텍스트에서 사용되는 모든 값이 트레이트 객체의 트레이트를 구현하도록 보장합니다. 따라서 컴파일 타임에 가능한 모든 타입을 알 필요가 없습니다.

Rust에서는 다른 언어의 객체와 구별하기 위해 struct와 enum을 '객체(object)'라고 부르는 것을 자제합니다. struct 또는 enum에서는 struct 필드에 있는 데이터와 impl 블록에 있는 동작이 분리되어 있는 반면, 다른 언어에서는 데이터와 동작이 하나의 개념으로 결합된 것을 흔히 객체라고 부릅니다. Trait 객체는 다른 언어의 객체와 다릅니다.

Listing 18-3은 Draw라는 하나의 메서드를 사용하여 draw라는 트레잇을 정의하는 방법을 보여줍니다.

이 문법은 10장에서 트레잇을 정의하는 방법에 대해 논의할 때 보았던 것과 비슷해 보입니다. 이제 새로운 문법을 살펴보겠습니다. Listing 18-4에서는 Screen이라는 구조체를 정의합니다. 이 구조체는 components이라는 이름의 벡터를 포함합니다. 이 벡터의 타입은 Box<dyn Draw>이며, 이는 트레잇 객체입니다. Box 안에 있는 Draw 트레잇을 구현하는 모든 타입을 대신할 수 있는 것입니다.

Screen 구조체에서, 우리는 run라는 메소드를 정의할 것입니다. draw 메소드를 각각의 components에서 호출할 것입니다.

이 방식은 트레잇 바운드를 가진 제네릭 타입 파라미터를 사용하는 구조체 정의와 다르게 작동합니다. 제네릭 타입 파라미터는 한 번에 하나의 구체적인 타입으로만 대체될 수 있지만, 트레잇 객체는 런타임에 여러 구체적인 타입이 트레잇 객체의 역할을 할 수 있도록 허용합니다. 예를 들어, Listing 18-6에서처럼 제네릭 타입과 트레잇 바운드를 사용하여 Screen 구조체를 정의할 수도 있습니다.

이 제한으로 인해 Screen 인스턴스는 Button 또는 TextField 타입의 구성 요소만 가진 목록을 포함할 수 있습니다. 항상 동질적인 컬렉션만 사용할 예정이라면, 제네릭과 트레이트 바운드를 사용하는 것이 좋습니다. 컴파일 타임에 구체적인 타입을 사용하도록 단형화(monomorphized)되므로 정의가 더 효율적이기 때문입니다.

반면, 트레이트 객체를 사용하는 메서드에서는 하나의 Screen 인스턴스가 Vec<T> 를 포함할 수 있으며, 여기에는 Box<Button> 와 Box<TextField> 가 함께 들어갈 수 있습니다. 이 방식이 어떻게 작동하는지 살펴본 후, 런타임 성능에 미치는 영향을 논의하겠습니다.

트레이트 구현하기

이제 Draw 트레이트를 구현하는 몇 가지 타입을 추가하겠습니다. Button 타입을 제공합니다. 다시 한번 강조하지만, 실제 GUI 라이브러리를 구현하는 것은 이 책의 범위를 벗어나므로, draw 메서드의 본문에는 유용한 구현이 없습니다. 구현이 어떻게 보일지 상상해 보려면, Button 구조체는 width, height, 그리고 label 필드를 가질 수 있으며, 이는 Listing 18-7에 나와 있습니다.

width, height, 그리고 label 필드는 Button 의 필드와 다른 구성 요소의 필드와 다를 수 있습니다. 예를 들어, TextField 타입은 동일한 필드 외에 placeholder 필드를 가질 수 있습니다. 화면에 그릴 각 타입은 Draw 트레이트를 구현하지만, draw 메서드에서 해당 특정 타입을 그리는 방법을 정의하기 위해 서로 다른 코드를 사용합니다. 여기서는 실제 GUI 코드 없이 Button 가 그렇게 하고 있습니다. 예를 들어, Button 타입에는 사용자가 버튼을 클릭할 때 발생하는 동작과 관련된 메서드를 포함하는 추가적인 impl 블록이 있을 수 있습니다. 이러한 종류의 메서드는 TextField 같은 타입에는 적용되지 않습니다.

우리 라이브러리를 사용하는 누군가가 SelectBox, width, 그리고 height 필드를 가진 options 구조체를 구현하기로 결정한다면, Listing 18-8에 나와 있듯이 Draw 타입에도 SelectBox 트레이트를 구현해야 합니다.

이제 우리 라이브러리의 사용자는 main 함수를 작성하여 Screen 인스턴스를 생성할 수 있습니다. Screen 인스턴스에 SelectBox과 Button를 각각 Box<T>에 넣어 트레이트 객체로 만든 후 추가할 수 있습니다. 그런 다음 Screen 인스턴스에 run 메서드를 호출하면, 각 구성 요소에 대해 draw가 호출됩니다. Listing 18-9에 이 구현이 나와 있습니다.

라이브러리를 작성할 당시 누군가가 SelectBox 유형을 추가할 수 있다는 사실을 알지 못했지만, Screen 구현은 새로운 유형을 대상으로 작동하여 그릴 수 있었습니다. 이는 SelectBox 트레이트를 구현한다는 뜻이며, Draw 메서드를 구현한다는 것을 의미합니다. draw

이 개념, 즉 값의 구체적인 타입이 아니라 값이 응답하는 메시지만에 관심을 갖는다는 개념은 동적 타입 언어의 오리 타이핑(duck typing) 개념과 유사합니다. 오리처럼 걷고 오리처럼 울면, 그것은 오리가 아니겠습니까! run에서 Screen의 구현을 보면, run는 각 구성 요소의 구체적인 타입을 알 필요가 없습니다. 구성 요소가 Button 또는 SelectBox의 인스턴스인지 확인하지 않고, 단순히 구성 요소의 draw 메서드를 호출할 뿐입니다. Box<dyn Draw>의 값 타입으로 components 벡터의 타입을 지정함으로써, 우리는 Screen 메서드를 호출할 수 있는 값을 필요로 하는 draw을 정의한 것입니다.

트레이트 객체와 Rust의 타입 시스템을 사용하여 덕 타이핑을 사용하는 코드와 유사한 코드를 작성하는 이점은, 런타임에 값이 특정 메서드를 구현하는지 확인하거나, 값이 메서드를 구현하지 않았는데도 호출하여 오류가 발생하는 것을 걱정할 필요가 없다는 것입니다. 값이 트레이트 객체가 요구하는 트레이트를 구현하지 않으면 Rust는 코드를 컴파일하지 않습니다.

동적 디스패치 수행

10장의 “제네릭을 사용하는 코드의 성능” 섹션에서 컴파일러가 제네릭에 대해 수행하는 단형화(monomorphization) 과정에 대해 논의했습니다. 컴파일러는 제네릭 타입 매개변수 대신 사용하는 각 구체적인 타입에 대해, 제네릭이 아닌 함수와 메서드 구현을 생성합니다. 단형화를 통해 생성된 코드는 정적 디스패치(static dispatch)를 수행합니다. 정적 디스패치는 컴파일러가 컴파일 시점에 어떤 메서드를 호출하는지 알고 있는 경우를 말합니다. 이는 동적 디스패치(dynamic dispatch)와 반대되는 개념으로, 동적 디스패치는 컴파일러가 컴파일 시점에 어떤 메서드를 호출하는지 알 수 없는 경우를 말합니다. 동적 디스패치의 경우, 컴파일러는 런타임에 어떤 메서드를 호출할지 알 수 있도록 코드를 생성합니다.

트레이트 객체를 사용할 때 Rust는 동적 디스패치를 사용해야 합니다. 컴파일러는 트레이트 객체를 사용하는 코드와 함께 사용될 수 있는 모든 타입을 알 수 없으므로, 어떤 타입에 구현된 어떤 메서드를 호출해야 하는지 알 수 없습니다. 대신 Rust는 런타임에 트레이트 객체 내부의 포인터를 사용하여 호출할 메서드를 결정합니다. 이 조회 과정은 정적 디스패치에서는 발생하지 않는 런타임 비용을 발생시킵니다. 동적 디스패치는 또한 컴파일러가 메서드 코드를 인라인(inline) 처리하는 것을 방지하여 일부 최적화를 막습니다. Rust에는 동적 디스패치를 사용할 수 있는 위치와 사용할 수 없는 위치에 대한 규칙이 있으며, 이를 dyn 호환성이라고 합니다. 이러한 규칙은 이번 논의의 범위를 벗어납니다. 자세한 내용은 참고 문서에서 확인할 수 있습니다. 하지만 18-5번 목록에서 작성한 코드에 추가적인 유연성을 부여하고 18-9번 목록에서 이를 지원할 수 있었으므로, 이는 고려해야 할 트레이드오프입니다.
