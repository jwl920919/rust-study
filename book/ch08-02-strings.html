The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

String으로 UTF-8 인코딩된 텍스트 저장하기

4장에서 문자열에 대해 다루었지만, 이제 더 깊이 살펴볼 것입니다. Rust를 처음 접하는 개발자들은 세 가지 복합적인 이유로 인해 문자열에서 자주 막히게 됩니다. Rust가 잠재적인 오류를 노출하려는 성향, 많은 개발자가 생각하는 것보다 문자열이 더 복잡한 데이터 구조라는 점, 그리고 UTF-8 때문입니다. 이러한 요소들이 결합되어 다른 프로그래밍 언어에서 넘어온 개발자에게는 어렵게 느껴질 수 있습니다.

문자열은 바이트의 컬렉션으로 구현되며, 해당 바이트가 텍스트로 해석될 때 유용한 기능을 제공하는 메서드를 추가로 제공합니다. 이 때문에 문자열은 컬렉션의 맥락에서 다루어집니다. 이 섹션에서는 생성, 업데이트, 읽기 등 모든 컬렉션 타입에 공통적으로 존재하는 String에 대한 작업을 설명합니다. 또한, String이 다른 컬렉션과 다른 점, 즉 사람과 컴퓨터가 String 데이터를 해석하는 방식의 차이로 인해 인덱싱이 복잡해지는 점에 대해서도 논의합니다. String

문자열 정의하기

먼저 문자열이라는 용어가 무엇을 의미하는지 정의하겠습니다. Rust 코어 언어에는 문자열 타입이 하나뿐인데, 이는 문자열 슬라이스인 str이며, 보통 빌림 형태인 &str로 사용됩니다. 4장에서는 다른 곳에 저장된 UTF-8 인코딩 문자열 데이터를 참조하는 문자열 슬라이스에 대해 다루었습니다. 예를 들어, 문자열 리터럴은 프로그램의 바이너리에 저장되므로 문자열 슬라이스에 해당합니다.

Rust 표준 라이브러리가 제공하며 핵심 언어에 내장되어 있지 않은 String 타입은 확장 가능하고, 변경 가능하며, 소유권을 가지며, UTF-8 인코딩된 문자열 타입입니다. Rustacean들이 Rust에서 “문자열”이라고 말할 때, 이는 String 또는 문자열 슬라이스 &str 타입 중 하나를 가리킬 수 있으며, 반드시 그중 하나만 지칭하는 것은 아닙니다. 이 섹션은 주로 String에 대해 다루지만, 두 타입 모두 Rust 표준 라이브러리에서 널리 사용되며, String와 문자열 슬라이스 모두 UTF-8 인코딩됩니다.

fn main() {
    let s1 = String::from("tic");
    let s2 = String::from("tac");
    let s3 = String::from("toe");

    let s = s1 + "-" + &s2 + "-" + &s3;
}

이 시점에서 s의 값은 tic-tac-toe입니다. +와 " 문자가 섞여 있어 어떤 문자열이 생성되었는지 한눈에 파악하기 어렵습니다. 문자열을 더 복잡한 방식으로 조합해야 할 때는 format! 매크로를 사용하는 것이 좋습니다.

fn main() {
    let s1 = String::from("tic");
    let s2 = String::from("tac");
    let s3 = String::from("toe");

    let s = format!("{s1}-{s2}-{s3}");
}

이 코드는 또한 s를 tic-tac-toe로 설정합니다. format! 매크로는 println!처럼 작동하지만, 출력을 화면에 출력하는 대신 내용을 담은 String를 반환합니다. format!를 사용하는 버전의 코드는 훨씬 읽기 쉽고, format! 매크로가 생성하는 코드는 참조를 사용하므로 이 호출은 매개변수 중 어느 것의 소유권도 가져가지 않습니다.

내부 표현

String는 Vec<u8>을 감싸는 래퍼입니다. Listing 8-14의 올바르게 인코딩된 UTF-8 예제 문자열을 살펴봅시다. 먼저, 이 문자열입니다:

fn main() {
    let hello = String::from("السلام عليكم");
    let hello = String::from("Dobrý den");
    let hello = String::from("Hello");

이 경우 len는 4입니다. 즉, 문자열 "Hola"를 저장하는 벡터의 길이는 4바이트입니다. 이 문자들은 UTF-8로 인코딩될 때 각각 1바이트를 차지합니다. 그러나 다음 줄은 놀라움을 줄 수 있습니다(이 문자열은 숫자 3이 아닌 키릴 문자 대문자 Ze로 시작한다는 점에 유의하세요).

fn main() {
    let hello = String::from("السلام عليكم");
    let hello = String::from("Dobrý den");
    let hello = String::from("Hello");
    let hello = String::from("שלום");
    let hello = String::from("नमस्ते");
    let hello = String::from("こんにちは");
    let hello = String::from("안녕하세요");
    let hello = String::from("你好");
    let hello = String::from("Olá");
    let hello = String::from("Здравствуйте");
    let hello = String::from("Hola");
}

문자열의 길이를 묻는다면 12라고 답할 수 있습니다. 하지만 Rust의 답은 24입니다. 이는 UTF-8로 “Здравствуйте”를 인코딩하는 데 필요한 바이트 수이며, 해당 문자열의 각 유니코드 스칼라 값이 2바이트의 저장 공간을 차지하기 때문입니다. 따라서 문자열의 바이트 인덱스는 항상 유효한 유니코드 스칼라 값과 대응하지 않습니다. 이를 보여주기 위해 다음 잘못된 Rust 코드를 살펴보세요:

let hello = "Здравствуйте";
let answer = &hello[0];

이미 알고 있듯이 answer은 З, 즉 첫 번째 문자가 아닙니다. UTF-8로 인코딩하면 З의 첫 번째 바이트는 208이고 두 번째 바이트는 151입니다. 따라서 answer가 사실이어야 할 것 같지만, 208은 자체적으로 유효한 문자가 아닙니다. 사용자가 이 문자열의 첫 번째 문자를 요청했을 때 208을 반환하는 것은 사용자의 의도와 맞지 않을 가능성이 높습니다. 하지만 Rust가 바이트 인덱스 0에서 가진 유일한 데이터가 바로 그것입니다. 사용자는 일반적으로 문자열에 라틴 문자만 포함되어 있더라도 바이트 값이 반환되는 것을 원하지 않습니다. 만약 208이 바이트 값을 반환하는 유효한 코드였다면, &"hi"[0]을 반환했을 것입니다. 104이 아니라 h입니다.

결국 답은 다음과 같습니다. 예상치 못한 값을 반환하여 즉시 발견되지 않을 수 있는 버그를 유발하는 것을 피하기 위해, Rust는 이 코드를 아예 컴파일하지 않고 개발 과정 초기에 오해를 방지합니다.

바이트, 스칼라 값, 그리고 그래프 클러스터

UTF-8에 대해 알아야 할 또 다른 점은, Rust의 관점에서 문자열을 바라보는 관련 있는 세 가지 방식이 있다는 것입니다. 바로 바이트, 스칼라 값, 그리고 그래프 클러스터(우리가 '문자'라고 부르는 것에 가장 가까운 개념)입니다.

데바나가리 문자로 작성된 힌디어 단어 “नमस्ते”를 살펴보면, 이는 다음과 같이 보이는 u8 값의 벡터로 저장됩니다:

[224, 164, 168, 224, 164, 174, 224, 164, 184, 224, 165, 141, 224, 164, 164,
224, 165, 135]

이것은 18바이트이며, 컴퓨터가 궁극적으로 이 데이터를 저장하는 방식입니다. Rust의 char 타입인 유니코드 스칼라 값으로 보면, 해당 바이트는 다음과 같이 보입니다:

['न', 'म', 'स', '्', 'त', 'े']

여기에는 6개의 char 값이 있지만, 네 번째와 여섯 번째는 문자가 아닙니다. 이들은 단독으로 의미를 가지지 않는 발음 부호입니다. 마지막으로, 그래프 클러스터로 보면 사람이 인식하는 힌디어 단어의 네 글자를 얻을 수 있습니다:

["न", "म", "स्", "ते"]

Rust는 컴퓨터가 저장하는 원시 문자열 데이터를 해석하는 다양한 방법을 제공합니다. 이를 통해 각 프로그램은 데이터가 어떤 인간 언어로 작성되었든 필요한 방식으로 해석을 선택할 수 있습니다.

Rust가 문자를 얻기 위해 String로 인덱싱하는 것을 허용하지 않는 마지막 이유는, 인덱싱 작업은 항상 일정한 시간(O(1))에 수행되어야 한다고 기대하기 때문입니다. 하지만 String의 경우 이러한 성능을 보장할 수 없습니다. Rust는 처음부터 인덱스 위치까지 내용을 순회하며 유효한 문자가 몇 개인지 확인해야 하기 때문입니다.

문자열 슬라이싱

문자열 인덱싱은 반환 타입이 바이트 값, 문자, 글리프 클러스터, 문자열 슬라이스 중 무엇이어야 하는지 명확하지 않기 때문에 종종 권장되지 않습니다. 따라서 문자열 슬라이스를 만들기 위해 인덱스를 사용해야 한다면, Rust는 더 구체적인 지시를 요구합니다.

단일 숫자를 사용해 []로 인덱싱하는 대신, 범위를 사용해 []를 적용하면 특정 바이트를 포함하는 문자열 슬라이스를 생성할 수 있습니다:

#![allow(unused)]
fn main() {
let hello = "Здравствуйте";

let s = &hello[0..4];
}

여기서 s는 문자열의 첫 4바이트를 포함하는 &str입니다. 앞서 언급했듯이 각 문자는 2바이트를 차지하므로, s의 값은 Зд가 됩니다.

만약 &hello[0..1]처럼 문자 바이트의 일부만 슬라이스하려고 하면, Rust는 벡터에서 유효하지 않은 인덱스에 접근한 경우와 마찬가지로 런타임에 패닉을 일으킵니다:

$ cargo run
   Compiling collections v0.1.0 (file:///projects/collections)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.43s
     Running `target/debug/collections`

thread 'main' (6017738) panicked at src/main.rs:4:19:
end byte index 1 is not a char boundary; it is inside 'З' (bytes 0..2 of string)
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

범위를 사용해 문자열 슬라이스를 만들 때는 주의해야 합니다. 잘못된 범위를 사용하면 프로그램이 충돌할 수 있기 때문입니다.

문자열 반복

문자열의 일부로 작업하는 가장 좋은 방법은 문자(char)인지 바이트인지 명시하는 것입니다. 개별 유니코드 스칼라 값의 경우 chars 메서드를 사용합니다. “Зд”에서 chars를 호출하면 두 개의 char 값으로 분리되어 반환되며, 이 결과를 반복하여 각 요소에 접근할 수 있습니다.

#![allow(unused)]
fn main() {
for c in "Зд".chars() {
    println!("{c}");
}
}

이 코드는 다음과 같이 출력합니다:

З
д

또는 bytes 메서드를 사용하면 각 원시 바이트를 반환하므로, 도메인에 따라 적합할 수 있습니다:

#![allow(unused)]
fn main() {
for b in "Зд".bytes() {
    println!("{b}");
}
}

이 코드는 이 문자열을 구성하는 4바이트를 출력합니다:

208
151
208
180

다만, 유효한 유니코드 스칼라 값은 1바이트보다 많은 바이트로 구성될 수 있음을 기억하십시오.

Devanagari 스크립트와 마찬가지로 문자열에서 grapheme 클러스터를 가져 오는 것은 복잡하므로이 기능은 표준 라이브러리에서 제공하지 않습니다. 이것이 필요한 기능이라면 크레이트.io에서 크레이트를 사용할 수 있습니다.

문자열의 복잡성 처리

요약하자면, 문자열은 복잡합니다. 다른 프로그래밍 언어들은 이 복잡성을 프로그래머에게 어떻게 제시할지에 대해 각기 다른 선택을 합니다. Rust는 String 데이터의 올바른 처리를 모든 Rust 프로그램의 기본 동작으로 선택했습니다. 이는 프로그래머가 UTF-8 데이터 처리에 대해 사전에 더 많은 고민을 해야 함을 의미합니다. 이러한 트레이드오프는 다른 프로그래밍 언어에서 드러나는 것보다 문자열의 복잡성을 더 많이 노출하지만, 개발 라이프사이클 후반부에 비-ASCII 문자와 관련된 오류를 처리해야 하는 상황을 방지합니다.

좋은 소식은 표준 라이브러리가 String 및 &str 유형을 기반으로 이러한 복잡한 상황을 올바르게 처리하는 데 도움이 되는 다양한 기능을 제공한다는 것입니다. 문자열에서 검색하는 데 유용한 contains와 문자열의 일부를 다른 문자열로 치환하는 데 유용한 replace 같은 메서드에 대한 문서를 꼭 확인해 보세요.
