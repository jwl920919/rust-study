The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

스레드를 사용하여 코드를 동시에 실행

대부분의 최신 운영 체제에서 실행되는 프로그램의 코드는 프로세스 내에서 실행되며, 운영 체제는 동시에 여러 프로세스를 관리합니다. 프로그램 내부에서는 동시에 실행되는 독립적인 부분도 가질 수 있습니다. 이러한 독립적인 부분을 실행하는 기능을 스레드라고 합니다. 예를 들어 웹 서버는 여러 스레드를 사용하여 동시에 여러 요청에 응답할 수 있습니다.

프로그램의 계산을 여러 스레드로 나누어 여러 작업을 동시에 실행하면 성능을 향상시킬 수 있지만, 복잡성도 증가합니다. 스레드가 동시에 실행될 수 있기 때문에 서로 다른 스레드에서 코드의 각 부분이 실행되는 순서에 대한 내재적인 보장은 없습니다. 이로 인해 다음과 같은 문제가 발생할 수 있습니다:

  • 스레드가 일관되지 않은 순서로 데이터나 리소스에 접근하는 레이스 조건
  • 두 스레드가 서로를 기다리며 어떤 스레드도 계속 진행하지 못하는 데드락
  • 특정 상황에서만 발생하여 재현하고 안정적으로 수정하기 어려운 버그

Rust는 스레드 사용으로 인한 부정적인 영향을 완화하려고 하지만, 멀티스레드 환경에서의 프로그래밍은 여전히 신중한 고려가 필요하며, 단일 스레드 프로그램과 다른 코드 구조를 요구합니다.

프로그래밍 언어는 스레드를 몇 가지 다른 방식으로 구현하며, 많은 운영 체제는 프로그래밍 언어가 새 스레드를 생성할 때 호출할 수 있는 API를 제공합니다. Rust 표준 라이브러리는 1:1 스레드 구현 모델을 사용하여, 프로그램이 언어 스레드 하나당 운영 체제 스레드 하나를 사용하도록 합니다. 1:1 모델과 다른 트레이드오프를 가진 다른 스레드 모델을 구현하는 크레이트도 있습니다. (다음 장에서 다룰 Rust의 비동기 시스템은 동시성에 대한 또 다른 접근 방식을 제공합니다.)

thread::sleep 호출은 스레드가 짧은 시간 동안 실행을 중단하도록 강제하여 다른 스레드가 실행될 수 있게 합니다. 스레드는 아마도 번갈아 실행되겠지만, 이는 보장되지 않습니다. 운영 체제가 스레드를 스케줄링하는 방식에 따라 달라지기 때문입니다. 이 실행에서는 생성된 스레드의 출력 문이 코드에서 먼저 나타나지만, 메인 스레드가 먼저 출력했습니다. 또한 생성된 스레드에게 i까지 출력하라고 지시했지만, 메인 스레드가 종료되기 전에 9까지만 출력했습니다. 5

모든 스레드가 종료될 때까지 기다리기

Listing 16-1의 코드는 메인 스레드가 종료되어 생성된 스레드가 대부분 조기에 중단될 뿐만 아니라, 스레드 실행 순서에 대한 보장이 없기 때문에 생성된 스레드가 아예 실행되지 않을 수도 있습니다!

생성된 스레드가 실행되지 않거나 조기에 종료되는 문제를 수정하려면 thread::spawn의 반환 값을 변수에 저장하면 됩니다. thread::spawn의 반환 타입은 JoinHandle<T>입니다. JoinHandle<T>은 소유권을 가진 값으로, 이 값에 join 메서드를 호출하면 해당 스레드가 종료될 때까지 대기합니다. Listing 16-2에서는 Listing 16-1에서 생성한 스레드의 JoinHandle<T>를 사용하고, main이 종료되기 전에 생성된 스레드가 종료되도록 join을 호출하는 방법을 보여줍니다.

핸들에서 join를 호출하면 핸들이 나타내는 스레드가 종료될 때까지 현재 실행 중인 스레드가 차단됩니다. 스레드를 차단한다는 것은 해당 스레드가 작업을 수행하거나 종료하는 것을 막는다는 뜻입니다. 메인 스레드의 join 루프 뒤에 for 호출을 배치했기 때문에, Listing 16-2를 실행하면 다음과 유사한 출력이 생성됩니다.

스레드와 함께 move 클로저 사용하기move

move 키워드를 thread::spawn에 전달하는 클로저와 함께 자주 사용합니다. 클로저가 환경에서 사용하는 값의 소유권을 가져가므로, 해당 값의 소유권을 한 스레드에서 다른 스레드로 이전하기 때문입니다. 13장의 “참조를 캡처하거나 소유권을 이동하기”참조 캡처 또는 소유권 이동에서 클로저의 맥락에서 move를 논의했습니다. 이제 move와 thread::spawn 사이의 상호작용에 더 집중하겠습니다.

Listing 16-1에서 thread::spawn에 전달하는 클로저는 인수를 받지 않습니다. 이는 생성된 스레드의 코드에서 메인 스레드의 데이터를 사용하지 않기 때문입니다. 생성된 스레드에서 메인 스레드의 데이터를 사용하려면, 해당 스레드의 클로저가 필요한 값을 캡처해야 합니다. Listing 16-3은 메인 스레드에서 벡터를 생성하고 생성된 스레드에서 사용하려는 시도를 보여줍니다. 그러나 잠시 후 확인할 수 있듯이, 이 코드는 아직 작동하지 않습니다.

클로저가 v를 사용하므로 v를 캡처하여 클로저 환경의 일부로 만듭니다. thread::spawn는 이 클로저를 새 스레드에서 실행하므로, 새 스레드 안에서 v에 액세스할 수 있어야 합니다. 하지만 이 예제를 컴파일하면 다음과 같은 오류가 발생합니다.

Listing 16-4는 v에 대한 참조가 유효하지 않을 가능성이 더 높은 시나리오를 제공합니다.

Rust가 이 코드를 실행하도록 허용한다면, 생성된 스레드가 전혀 실행되지 않고 즉시 백그라운드에 배치될 가능성이 있습니다. 생성된 스레드 내부에는 v에 대한 참조가 있지만, 메인 스레드는 15장에서 논의한 v 함수를 사용하여 drop를 즉시 해제합니다. 그런 다음 생성된 스레드가 실행을 시작하면 v은 더 이상 유효하지 않으므로, 이에 대한 참조도 유효하지 않게 됩니다. 어쩔 수 없네요!

Rust의 소유권 규칙이 다시 우리를 구해 주었습니다! Listing 16-3의 코드에서 오류가 발생한 이유는 Rust가 보수적으로 v를 스레드에 빌려주기만 했기 때문입니다. 이는 메인 스레드가 이론적으로 생성된 스레드의 참조를 무효화할 수 있음을 의미합니다. Rust에게 v의 소유권을 생성된 스레드로 이동하라고 지시함으로써, 메인 스레드가 더 이상 v를 사용하지 않음을 Rust에게 보증하게 됩니다. Listing 16-4를 같은 방식으로 변경하면, 메인 스레드에서 v를 사용하려고 할 때 소유권 규칙을 위반하게 됩니다. move 키워드는 Rust의 보수적인 빌림 기본값을 무시할 뿐, 소유권 규칙을 위반하도록 허용하지는 않습니다.

이제 스레드가 무엇인지와 스레드 API에서 제공하는 메서드를 다루었으므로, 스레드를 사용할 수 있는 몇 가지 상황을 살펴보겠습니다.
