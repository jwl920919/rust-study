The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

Unsafe Rust

지금까지 살펴본 모든 코드에는 Rust의 메모리 안전 보장이 컴파일 시간에 적용되었습니다. 그러나 Rust에는 이러한 메모리 안전 보장을 적용하지 않는 두 번째 언어가 숨겨져 있습니다. 바로 unsafe Rust입니다. unsafe Rust는 일반 Rust와 마찬가지로 작동하지만 우리에게 추가적인 기능을 제공합니다.

unsafe Rust가 존재하는 이유는 정적 분석이 본질적으로 보수적이기 때문입니다. 컴파일러가 코드가 보증을 준수하는지 여부를 결정할 때, 잘못된 프로그램을 허용하는 것보다 올바른 프로그램을 거부하는 것이 더 나은 선택입니다. 코드가 실제로는 문제가 없더라도, Rust 컴파일러가 확신할 수 있는 정보가 충분하지 않으면 해당 코드를 거부합니다. 이러한 경우 unsafe 코드를 사용하여 컴파일러에게 "나를 믿어라. 내가 무엇을 하는지 알고 있다"라고 알릴 수 있습니다. 하지만 주의하세요. unsafe Rust를 잘못 사용하면 null 포인터 참조와 같은 메모리 안전성 문제로 인해 문제가 발생할 수 있습니다.

Rust에 unsafe라는 대안이 있는 또 다른 이유는 기반 컴퓨터 하드웨어가 본질적으로 안전하지 않기 때문입니다. Rust가 unsafe 작업을 허용하지한다면 특정 작업을 수행할 수 없게 됩니다. Rust는 운영 체제와 직접 상호 작용하거나 심지어 자체 운영 체제를 작성하는 것과 같은 저수준 시스템 프로그래밍을 수행할 수 있도록 해야 합니다. 저수준 시스템 프로그래밍을 지원하는 것이 이 언어의 목표 중 하나입니다. unsafe Rust로 무엇을 할 수 있는지, 그리고 어떻게 하는지 살펴보겠습니다.

Unsafe Superpowers 수행하기

unsafe Rust로 전환하려면 unsafe 키워드를 사용하고 unsafe 코드를 포함하는 새로운 블록을 시작합니다. unsafe Rust에서는 safe Rust에서는 할 수 없는 다섯 가지 작업을 수행할 수 있으며, 우리는 이를 unsafe superpowers라고 부릅니다. 이러한 superpowers에는 다음 기능이 포함됩니다:

  1. raw 포인터를 dereference합니다.
  2. unsafe 함수 또는 메서드를 호출합니다.
  3. 가변 정적 변수에 접근하거나 수정합니다.
  4. 안전하지 않은 트레이트를 구현합니다.
  5. union의 필드에 접근합니다.

unsafe가 빌림 검사기를 끄거나 Rust의 다른 안전 검사를 비활성화하지 않는다는 점을 이해하는 것이 중요합니다. 안전하지 않은 코드에서 참조를 사용하는 경우에도 여전히 검사됩니다. unsafe 키워드는 컴파일러가 메모리 안전을 검사하지 않는 다섯 가지 기능에만 접근할 수 있게 합니다. 따라서 안전하지 않은 블록 안에서도 어느 정도의 안전성은 유지됩니다.

또한 unsafe는 블록 내부의 코드가 반드시 위험하거나 메모리 안전 문제가 있음을 의미하지 않습니다. 프로그래머로서 unsafe 블록 내부의 코드가 유효한 방식으로 메모리에 접근하도록 보장해야 합니다.

사람은 실수를 할 수 있지만, 이 다섯 가지 안전하지 않은 작업을 unsafe로 표시된 블록 안에만 사용하도록 요구함으로써 메모리 안전과 관련된 모든 오류가 unsafe 블록 내에 있음을 알 수 있습니다. unsafe 블록을 작게 유지하세요. 나중에 메모리 버그를 조사할 때 그 이점을 체감하게 될 것입니다.

안전하지 않은 코드를 최대한 격리하려면, 해당 코드를 안전한 추상화 안에 포함시키고 안전한 API를 제공하는 것이 가장 좋습니다. 이 내용은unsafe 함수와 메서드를 다룰 때 이 장의 후반부에서 자세히 논의하겠습니다. 표준 라이브러리의 일부는 감사(audit)가 완료된 안전하지 않은 코드 위에 안전한 추상화로 구현되어 있습니다. 안전한 추상화로 안전하지 않은 코드를 감싸면, unsafe 사용이 사용자나 개발자가 해당 기능을 사용하고자 하는 모든 곳으로 새어나가는 것을 방지할 수 있습니다. 이는 안전한 추상화를 사용하는 것이 안전하기 때문입니다. unsafe

이제 다섯 가지 안전하지 않은 기능을 차례로 살펴보겠습니다. 또한 안전하지 않은 코드에 대해 안전한 인터페이스를 제공하는 추상화도 함께 살펴보겠습니다.

원시 포인터 참조 해제

4장에서 “잘못된 참조” 섹션에서 컴파일러가 참조가 항상 유효하도록 보장한다고 언급했습니다. 안전하지 않은 Rust에는 참조와 유사한 원시 포인터라는 두 가지 새로운 타입이 있습니다. 참조와 마찬가지로 원시 포인터는 불변이거나 가변일 수 있으며, 각각 *const T와 *mut T로 표기합니다. 여기서 별표(*)는 참조 해제 연산자가 아니라 타입 이름의 일부입니다. 원시 포인터의 맥락에서 불변이란, 포인터가 참조 해제된 후 직접 재할당될 수 없다는 것을 의미합니다.

참조와 스마트 포인터와 달리, 원시 포인터는 다음과 같은 특징을 가집니다:

  • 불변 포인터와 가변 포인터, 또는 동일한 위치에 대한 여러 가변 포인터를 동시에 가질 수 있어 빌림 규칙을 무시할 수 있습니다.
  • 유효한 메모리를 가리킨다는 보장이 없습니다.
  • null일 수 있습니다.
  • 자동 정리를 수행하지 않습니다.

Rust가 이러한 보증을 강제하지 않도록 선택함으로써, 보장된 안전성을 포기하고 대신 더 높은 성능이나 Rust의 보장이 적용되지 않는 다른 언어 또는 하드웨어와 인터페이스할 수 있는 능력을 얻을 수 있습니다.

이 코드에는 unsafe 키워드가 포함되어 있지 않습니다. 안전한 코드에서 원시 포인터를 생성할 수 있지만, 잠시 후 살펴볼 것처럼 unsafe 블록 외부에서 원시 포인터를 역참조할 수는 없습니다.

raw borrow 연산자를 사용하여 원시 포인터를 만들었습니다. &raw const num은 *const i32 불변 원시 포인터를, &raw mut num은 *mut i32 가변 원시 포인터를 생성합니다. 로컬 변수에서 직접 만들었기 때문에 이 특정 원시 포인터들이 유효하다는 것을 알 수 있지만, 모든 원시 포인터에 대해 같은 가정을 할 수는 없습니다.

Listing 20-2는 메모리의 임의의 위치를 가리키는 원시 포인터를 생성하는 방법을 보여줍니다. 임의의 메모리를 사용하는 것은 정의되지 않은 동작입니다. 해당 주소에 데이터가 있을 수도 있고 없을 수도 있으며, 컴파일러가 메모리 접근이 없도록 코드를 최적화할 수도 있고, 프로그램이 세그멘테이션 폴트로 종료될 수도 있습니다. 일반적으로 이러한 코드를 작성할 좋은 이유는 없으며, 특히 raw borrow 연산자를 사용할 수 있는 경우 더욱 그러합니다. 하지만 불가능한 것은 아닙니다.

safe 코드에서 raw 포인터를 생성할 수 있지만, raw 포인터를 역참조하여 가리키는 데이터를 읽을 수는 없습니다. Listing 20-3에서는 unsafe 블록이 필요한 raw 포인터에 역참조 연산자 *를 사용하고 있습니다. unsafe

포인터를 생성하는 것 자체로는 아무런 해가 되지 않습니다. 포인터가 가리키는 값에 접근하려고 할 때 비로소 잘못된 값을 다루게 될 수 있습니다.

Listing 20-1과 20-3에서 *const i32와 *mut i32 원시 포인터를 생성했는데, 이 포인터들은 모두 num가 저장되어 있는 동일한 메모리 위치를 가리키고 있습니다. 만약 num에 대한 불변 참조와 가변 참조를 동시에 생성하려고 했다면, Rust의 소유권 규칙상 가변 참조와 불변 참조가 동시에 존재할 수 없으므로 코드가 컴파일되지 않았을 것입니다. 원시 포인터의 경우 동일한 위치에 대한 가변 포인터와 불변 포인터를 생성할 수 있으며, 가변 포인터를 통해 데이터를 변경할 수 있습니다. 이는 데이터 레이스를 유발할 수 있으므로 주의해야 합니다.

이러한 위험에도 불구하고 왜 원시 포인터를 사용해야 할까요? 한 가지 주요 사용 사례는 다음 섹션에서 볼 수 있듯이 C 코드와 인터페이스를 구축할 때입니다. 또 다른 경우는 빌림 검사기가 이해하지 못하는 안전한 추상화를 구축할 때입니다. 이제 unsafe 함수를 소개한 후, unsafe 코드를 사용하는 안전한 추상화의 예를 살펴보겠습니다.

unsafe 함수 또는 메서드 호출

안전하지 않은 블록에서 수행할 수 있는 두 번째 유형의 작업은 안전하지 않은 함수를 호출하는 것입니다. 안전하지 않은 함수와 메서드는 일반 함수와 메서드와 똑같이 보이지만, 정의의 나머지 부분 앞에 unsafeunsafeunsafe 키워드가 추가로 붙어 있습니다. 이 문맥에서 unsafe 키워드는 해당 함수를 호출할 때 우리가 준수해야 하는 요구사항이 있음을 나타냅니다. Rust는 우리가 이러한 요구사항을 충족했는지 보장할 수 없기 때문입니다. 안전하지 않은 블록 내에서 안전하지 않은 함수를 호출함으로써, 우리는 해당 함수의 문서를 읽었고 함수의 계약 사항을 준수하는 데 대한 책임을 지겠다는 것을 의미합니다. unsafe

다음은 dangerous라는 unsafe 함수입니다. 이 함수의 본문에서는 아무 동작도 수행하지 않습니다.

fn main() {
    unsafe fn dangerous() {}

    unsafe {
        dangerous();
    }
}

우리는 그들을 불러야 합니다. dangerous 분리 된 기능 unsafe 블록. 우리가 전화하려고하면 dangerous 없이 The unsafe 블록, 우리는 오류를 얻을 것이다 :

unsafe 블록을 사용하면, Rust에 함수의 문서를 읽었고 올바르게 사용하는 방법을 이해했으며, 함수의 계약을 준수하고 있음을 보증하게 됩니다.

unsafe 함수의 본문에서 안전하지 않은 작업을 수행하려면 일반 함수 내부에서와 마찬가지로 unsafe 블록을 사용해야 하며, 이를 잊으면 컴파일러가 경고합니다. 이는 함수 전체 본문에서 안전하지 않은 작업이 항상 필요한 것은 아니므로, unsafe 블록을 가능한 한 작게 유지하는 데 도움이 됩니다.

안전하지 않은 코드에 대한 안전한 추상화 만들기

함수에 안전하지 않은 코드가 포함되어 있다고 해서 반드시 전체 함수를 unsafe로 표시해야 하는 것은 아닙니다. 실제로 안전하지 않은 코드를 안전한 함수로 감싸는 것은 일반적인 추상화 기법입니다. 예를 들어, 표준 라이브러리의 split_at_mut 함수는 일부 안전하지 않은 코드를 필요로 합니다. 이 함수를 어떻게 구현할 수 있는지 살펴보겠습니다. 이 안전한 메서드는 가변 슬라이스에 정의되어 있으며, 인수로 주어진 인덱스 위치에서 슬라이스를 분할하여 하나의 슬라이스를 두 개로 만듭니다. Listing 20-4는 split_at_mut의 사용 방법을 보여줍니다.

안전한 Rust만 사용해서는 이 함수를 구현할 수 없습니다. Listing 20-5와 같은 시도는 컴파일에 실패합니다. 단순화를 위해, split_at_mut을 메서드가 아닌 함수로 구현하고, 제네릭 타입 T가 아닌 i32 값의 슬라이스에 대해서만 구현하겠습니다. T

이 함수는 먼저 슬라이스의 전체 길이를 가져옵니다. 그런 다음 매개변수로 주어진 인덱스가 슬라이스 범위 내에 있는지 확인하기 위해, 해당 인덱스가 길이보다 작거나 같은지 검사합니다. 이 단언(assertion)은 슬라이스를 분할할 인덱스로 길이보다 큰 값을 전달하는 경우, 해당 인덱스를 사용하기 전에 함수가 panic하도록 보장합니다.

그런 다음 튜플로 두 개의 가변 슬라이스를 반환합니다. 하나는 원본 슬라이스의 시작 위치부터 mid 인덱스까지, 다른 하나는 mid부터 슬라이스의 끝까지입니다.

Rust의 빌림 검사기는 슬라이스의 서로 다른 부분을 빌리고 있다는 사실을 이해하지 못합니다. 검사기는 단순히 같은 슬라이스에서 두 번 빌리고 있다는 사실만 알 뿐입니다. 두 슬라이스가 겹치지 않으므로 슬라이스의 서로 다른 부분을 빌리는 것은 근본적으로 문제없지만, Rust는 이 사실을 알아낼 만큼 지능적이지 않습니다. 코드가 안전하다는 것을 우리가 알지만 Rust가 알지 못하는 경우에는 unsafe 코드를 사용해야 할 때입니다.

외부 함수를 사용해 extern 외부 코드를 호출하는 방법

때때로 Rust 코드는 다른 언어로 작성된 코드와 상호작용해야 할 수 있습니다. 이를 위해 Rust에는 extern라는 키워드가 있습니다. 이 키워드는 FFI(Foreign Function Interface)의 생성과 사용을 용이하게 합니다. FFI는 프로그래밍 언어가 함수를 정의하고, 다른(외부) 프로그래밍 언어가 해당 함수를 호출할 수 있도록 하는 방법입니다.

Listing 20-8은 C 표준 라이브러리의 abs 함수와 통합을 설정하는 방법을 보여줍니다. extern 블록 내에서 선언된 함수는 일반적으로 Rust 코드에서 호출하는 것이 안전하지 않으므로, extern 블록도 unsafe로 표시해야 합니다. 그 이유는 다른 언어들이 Rust의 규칙과 보증을 강제하지 않고, Rust가 이를 검사할 수 없기 때문에 안전성을 보장할 책임이 프로그래머에게 있기 때문입니다.

내부 The unsafe extern "C" 블록, 우리는 우리가 호출 할 다른 언어에서 외부 함수의 이름과 서명을 나열합니다. "C" 어떤 것을 정의하는가 애플리케이션 바이너리 인터페이스(ABI) 외부 함수 사용: ABI는 어셈블리 수준에서 함수를 호출하는 방법을 정의합니다. "C" ABI는 가장 일반적이며 C 프로그래밍 언어의 ABI를 따릅니다. 모든 ABIs 러스트 지원에 대한 정보는 다음에서 사용할 수 있습니다. 러스트 참조.

unsafe extern 블록 안에 선언된 모든 항목은 암묵적으로 안전하지 않습니다. 그러나 일부 FFI 함수는 있습니다. 예를 들어, C 표준 라이브러리의 abs 함수는 메모리 안전에 대한 고려 사항이 없으며, 어떤 i32 값으로든 호출할 수 있음을 알고 있습니다. 이와 같은 경우, safe 키워드를 사용하여 이 특정 함수가 unsafe extern 블록 안에 있더라도 호출하는 것이 안전하다고 명시할 수 있습니다. 이렇게 변경하면 더 이상 unsafe 블록 없이도 호출할 수 있으며, 이는 Listing 20-9에 나와 있습니다.

safe로 함수를 마킹하는 것만으로는 본질적으로 안전해지지 않습니다. 이는 Rust에 해당 함수가 안전하다고 약속하는 것과 같습니다. 이 약속이 지켜지도록 하는 것은 여전히 개발자의 책임입니다!

다른 언어에서 Rust 함수 호출하기

우리는 또한 사용할 수 있습니다 extern 다른 언어로 러스트 함수를 호출할 수 있는 인터페이스를 만듭니다. 전체를 만드는 대신 extern 블록을 추가하려면To add the extern 키워드를 지정하고 바로 전에 사용할 ABI를 지정 fn 관련된 기능을 위한 키워드. 우리는 또한 추가할 필요가 있습니다 #[unsafe(no_mangle)] 러스트 컴파일러에게 이 함수의 이름을 변경하지 말라고 하는 주석. 망글링은 컴파일 프로세스의 다른 부분에 대한 정보가 더 많이 포함되어 있지만 사람이 읽을 수 없는 다른 이름으로 컴파일러가 이름을 변경할 때입니다. 모든 프로그래밍 언어 컴파일러는 이름을 약간 다르게 작성하므로 러스트 함수가 다른 언어에서 이름을 지정할 수 있으려면 러스트 컴파일러의 이름을 사용하지 않도록 설정해야 합니다. 이는 라이브러리에서 이름 충돌이 있을 수 있으므로 사람이 안전하게 내보낼 수 있습니다.

다음 예제에서는 call_from_c 함수를 공유 라이브러리로 컴파일한 후 C 코드에서 링크하여 C 코드에서 호출할 수 있도록 하는 방법을 보여 줍니다.

}

이 extern 사용법은 unsafe 블록이 아니라 속성에서만 extern를 요구합니다.

Rust에서 전역 변수는 정적 변수라고 합니다. Listing 20-10은 문자열 슬라이스를 값으로 갖는 정적 변수의 선언과 사용 예시를 보여줍니다.

정적 변수는 3장의 “상수 선언” 섹션에서 다룬 상수와 유사합니다. 정적 변수의 이름은 관례적으로 SCREAMING_SNAKE_CASE을 따릅니다. 정적 변수는 'static 라이프타임의 참조만 저장할 수 있습니다. 이는 Rust 컴파일러가 라이프타임을 파악할 수 있으므로 명시적으로 주석으로 표기할 필요가 없음을 의미합니다. 불변 정적 변수에 접근하는 것은 안전합니다.

일반 변수와 마찬가지로, mut 키워드를 사용하여 가변성을 지정합니다. COUNTER에서 읽거나 쓰는 모든 코드는 unsafe 블록 안에 있어야 합니다. 안전하지 않은 함수를 작성할 때마다 SAFETY로 시작하는 주석을 작성하여 호출자가 함수를 안전하게 호출하기 위해 무엇을 해야 하는지 설명하는 것이 관용적입니다. 마찬가지로, 안전하지 않은 작업을 수행할 때마다 SAFETY로 시작하는 주석을 작성하여 안전 규칙이 어떻게 준수되는지 설명하는 것이 관용적입니다.

또한 컴파일러는 기본적으로 컴파일러 lint를 통해 가변 정적 변수에 대한 참조를 만들려는 시도를 거부합니다. #[allow(static_mut_refs)] 주석을 추가하여 해당 lint의 보호 기능을 명시적으로 비활성화하거나, raw borrow 연산자 중 하나를 사용하여 생성된 raw 포인터를 통해 가변 정적 변수에 접근해야 합니다. 여기에는 이 코드 목록의 println!에서처럼 참조가 보이지 않게 생성되는 경우도 포함됩니다. 정적 가변 변수에 대한 참조를 raw 포인터를 통해 생성하도록 요구하면, 이러한 변수를 사용할 때의 안전 요구 사항을 더 명확하게 파악하는 데 도움이 됩니다. println!

Miri를 사용하여 unsafe 코드 검사

unsafe 코드를 작성할 때, 작성한 코드가 실제로 안전하고 올바른지 확인하고 싶을 수 있습니다. 이를 위한 가장 좋은 방법 중 하나는 Miri를 사용하는 것입니다. Miri는 정의되지 않은 동작(undefined behavior)을 감지하는 공식 Rust 도구입니다. 빌림 검사기(borrow checker)가 컴파일 시간에 작동하는 정적 도구인 반면, Miri는 런타임에 작동하는 동적 도구입니다. Miri는 프로그램을 실행하거나 테스트 스위트를 실행하여 코드를 검사하고, Rust가 작동해야 하는 규칙을 위반하는 시점을 감지합니다.

Miri를 사용하려면 Rust의 nightly 빌드가 필요합니다(부록 G: Rust는 어떻게 만들어지는가 및 “Nightly Rust”에서 더 자세히 다룹니다). 부록 G: Rust는 어떻게 만들어지는가 그리고 “Nightly Rust” 명령을 입력하면 nightly 버전의 Rust와 Miri 도구를 모두 설치할 수 있습니다. rustup +nightly component add miri. 이 작업은 프로젝트가 사용하는 Rust 버전을 변경하지 않으며, 원할 때 사용할 수 있도록 시스템에 도구만 추가합니다. cargo +nightly miri run 또는 cargo +nightly miri test 명령을 입력하여 프로젝트에서 Miri를 실행할 수 있습니다.

Miri는 정수를 포인터로 캐스팅하고 있다는 점을 올바르게 경고합니다. 이는 문제가 될 수 있지만, Miri는 포인터가 어떻게 생성되었는지 알 수 없기 때문에 실제로 문제가 존재하는지 판단할 수 없습니다. 그런 다음, Miri는 Listing 20-7에 정의되지 않은 동작이 존재하는 위치에서 오류를 반환합니다. 이는 포인터가 더 이상 유효하지 않은 상태(dangling pointer)이기 때문입니다. Miri 덕분에 이제 정의되지 않은 동작의 위험이 있다는 것을 알게 되었고, 코드를 안전하게 만드는 방법에 대해 생각할 수 있습니다. 일부 경우 Miri는 오류를 수정하는 방법에 대한 권장 사항까지 제시할 수 있습니다.

Miri는 unsafe 코드를 작성할 때 발생할 수 있는 모든 오류를 포착하지는 못합니다. Miri는 동적 분석 도구이므로 실제로 실행되는 코드에 있는 문제만 감지합니다. 따라서 작성한 unsafe 코드에 대한 신뢰도를 높이기 위해 좋은 테스트 기법과 함께 사용해야 합니다. 또한 Miri는 코드가 사운드하지(unsound) 않을 수 있는 모든 경우를 다루지 않습니다.

다른 말로 하면, Miri가 문제를 감지하면 버그가 있다는 것을 알 수 있지만, Miri가 버그를 감지하지 않는다고 해서 문제가 없다는 의미는 아닙니다. 그럼에도 Miri는 많은 문제를 감지할 수 있습니다. 이 장의 다른 unsafe 코드 예제에서 Miri를 실행해 보고 어떤 결과를 내놓는지 확인해 보세요!

Miri에 대한 자세한 내용은 GitHub 저장소에서 확인할 수 있습니다.

안전하지 않은 코드를 올바르게 사용

사용 unsafe 방금 논의 된 다섯 가지 초강대국 중 하나를 사용하는 것이 잘못되었거나 심지어 눈살을 찌푸리지는 않지만 얻는 것이 더 까다 롭습니다. unsafe 컴파일러가 메모리 안전을 유지할 수 없기 때문에 코드가 정확합니다. 사용할 이유가있을 때 unsafe 코드, 당신은 그렇게 할 수 있고, 명시적 unsafe 주석을 사용하면 문제가 발생할 때 문제의 원인을 쉽게 추적할 수 있습니다. 안전하지 않은 코드를 작성할 때마다 Miri를 사용하여 작성한 코드가 러스트의 규칙을 준수한다는 확신을 가질 수 있습니다.

안전하지 않은 Rust(unsafe Rust)를 효과적으로 다루는 방법에 대해 더 깊이 알고 싶다면, unsafe에 대한 Rust 공식 가이드인 unsafe, 루스토노미콘(The Rustonomicon)을 읽어 보십시오.
