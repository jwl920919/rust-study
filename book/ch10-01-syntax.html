The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

제네릭 데이터 형식

제네릭을 사용하면 함수 시그니처나 구조체와 같은 항목에 대한 정의를 만들 수 있으며, 이후 다양한 구체적인 데이터 형식과 함께 사용할 수 있습니다. 먼저 제네릭을 사용하여 함수, 구조체, 열거형, 메서드를 정의하는 방법을 살펴보고, 제네릭이 코드 성능에 미치는 영향을 논의하겠습니다.

함수 정의에서

제네릭을 사용하는 함수를 정의할 때, 제네릭을 보통 매개변수와 반환 값의 데이터 형식을 지정하는 함수 시그니처 위치에 배치합니다. 이렇게 하면 코드가 더 유연해지고, 함수 호출자에게 더 많은 기능을 제공하면서도 코드 중복을 방지할 수 있습니다.

largest 함수를 계속 다루면서, Listing 10-4에서는 슬라이스에서 가장 큰 값을 찾는 두 함수를 보여줍니다. 이후 이 두 함수를 제네릭을 사용하는 단일 함수로 결합하겠습니다.

largest_i32 함수는 Listing 10-3에서 추출한 것으로, 슬라이스에서 가장 큰 i32 값을 찾습니다. largest_char 함수는 슬라이스에서 가장 큰 char 값을 찾습니다. 함수 본문은 동일한 코드를 포함하므로, 단일 함수에 제네릭 형식 매개변수를 도입하여 중복을 제거하겠습니다.

새로운 단일 함수에서 타입을 파라미터화하려면, 함수의 값 파라미터에 이름을 붙이듯이 타입 파라미터에도 이름을 지정해야 합니다. 어떤 식별자든 타입 파라미터 이름으로 사용할 수 있습니다. 다만, 관례상 Rust의 타입 파라미터 이름은 짧고, 보통 한 글자만 사용합니다. 또한 Rust의 타입 이름 규약은 UpperCamelCase입니다. 'type'의 줄임말인 T은 대부분의 Rust 프로그래머가 기본으로 선택하는 이름입니다. T

함수 본문에서 매개변수를 사용할 때, 컴파일러가 해당 이름의 의미를 알 수 있도록 서명에서 매개변수 이름을 선언해야 합니다. 마찬가지로, 함수 서명에서 타입 매개변수 이름을 사용할 때도 사용 전에 타입 매개변수 이름을 선언해야 합니다. 제네릭 largest 함수를 정의하려면, 함수 이름과 매개변수 목록 사이에 꺾쇠(<>) 안에 타입 이름 선언을 배치합니다.

fn largest<T>(list: &[T]) -> &T {

이 정의를 “largest 함수는 어떤 타입 T에 대해 일반적입니다.”라고 읽습니다. 이 함수에는 list라는 이름의 매개변수가 하나 있으며, 이는 T 타입의 값으로 이루어진 슬라이스입니다. largest 함수는 동일한 타입인 T의 값에 대한 참조를 반환합니다.

Listing 10-5에서는 서명에서 제네릭 데이터 타입을 사용하여 결합된 largest 함수 정의를 보여줍니다. 이 목록에서는 또한 i32 값의 슬라이스나 char 값의 슬라이스로 함수를 호출하는 방법도 보여줍니다. 참고로 이 코드는 아직 컴파일되지 않습니다.

구조체 정의에서

또한 <> 구문을 사용하여 하나 이상의 필드에서 제네릭 타입 매개변수를 사용하도록 구조체를 정의할 수도 있습니다. Listing 10-6에서는 Point<T> 구조체를 정의하여 어떤 타입이든 x 및 y 좌표 값을 저장합니다.

구조체 정의에서 제네릭을 사용하는 구문은 함수 정의에서 사용하는 구문과 유사합니다. 먼저, 구조체 이름 바로 뒤에 있는 각괄호 안에 타입 매개변수의 이름을 선언합니다. 그런 다음, 구조체 정의에서 구체적인 데이터 타입을 지정해야 하는 위치에 제네릭 타입을 사용합니다.

단일 제네릭 타입만 사용하여 Point<T>을 정의했기 때문에, 이 정의는 Point<T> 구조체가 어떤 타입 T에 대해 제네릭이며, 필드 x과 y는 그 타입이 무엇이든 동일한 타입이라는 것을 의미합니다. Listing 10-7처럼 서로 다른 타입의 값을 가진 Point<T> 인스턴스를 생성하면, 코드는 컴파일되지 않습니다.

이 예제에서 정수 값 5을 x에 할당하면, 컴파일러에게 이 Point<T> 인스턴스에 대해 제네릭 타입 T이 정수임을 알립니다. 그런 다음, x과 동일한 타입으로 정의된 y에 대해 4.0를 지정하면 다음과 같은 타입 불일치 오류가 발생합니다:

열거형 정의에서

구조체에서와 마찬가지로, 열거형의 변형에 제네릭 데이터 타입을 포함하도록 정의할 수 있습니다. 6장에서 사용했던 표준 라이브러리가 제공하는 Option<T> 열거형을 다시 한 번 살펴보겠습니다.

#![allow(unused)]
fn main() {
enum Option<T> {
    Some(T),
    None,
}
}

이 정의는 이제 당신에게 더 의미가 있어야합니다. 당신이 볼 수 있듯이, Option<T> enum은 형식에 대해 일반입니다. T 두 가지 변형이 있습니다: Some타입의 값 하나를 가지고 있는 T그리고 A None variant는 어떤 값도 가지고 있지 않습니다. Option<T> enum, 우리는 선택적 값의 추상적 개념을 표현할 수 있습니다. Option<T> 옵션 값의 유형에 관계없이이 추상화를 사용할 수 있습니다.

열거형은 여러 제네릭 타입을 사용할 수도 있습니다. 9장에서 사용했던 Result 열거형의 정의가 한 가지 예입니다.

#![allow(unused)]
fn main() {
enum Result<T, E> {
    Ok(T),
    Err(E),
}
}

Result 열거형은 두 가지 타입인 T과 E에 대해 제네릭이며, 두 가지 변형을 가집니다. Ok은 T 타입의 값을, Err은 E 타입의 값을 보유합니다. 이 정의는 어떤 연산이 성공할 수 있는(어떤 타입 T의 값을 반환) 경우나 실패할 수 있는(어떤 타입 E의 오류를 반환) 경우 어디에서나 Result 열거형을 사용하는 데 편리합니다. 실제로 Listing 9-3에서 파일을 열 때 이 방식을 사용했으며, 파일이 성공적으로 열리면 T에 std::fs::File 타입이, 파일 열기에 문제가 있으면 E에 std::io::Error 타입이 채워졌습니다.

코드에서 포함하는 값의 타입만 다른 여러 구조체 또는 열거형 정의를 발견하면, 제네릭 타입을 사용하여 중복을 피할 수 있습니다.

메서드 정의에서

구조체와 열거형에 메서드를 구현할 수 있으며(5장에서 했던 것처럼), 그 정의에서 제네릭 타입도 사용할 수 있습니다. Listing 10-9는 Listing 10-6에서 정의한 Point<T> 구조체에 x이라는 이름의 메서드를 구현한 모습을 보여줍니다.

여기서 x라는 이름의 메서드를 Point<T>에 정의하여 x 필드의 데이터에 대한 참조를 반환합니다.

T를 impl 바로 뒤에 선언해야 하는 점에 주목하세요. 이렇게 해야 T를 사용해 Point<T> 타입에 메서드를 구현하고 있음을 명시할 수 있습니다. T 뒤에 제네릭 타입으로 impl를 선언하면, Rust는 Point의 각괄호 안에 있는 타입이 구체적인 타입이 아니라 제네릭 타입임을 식별할 수 있습니다. struct 정의에서 선언한 제네릭 파라미터와 다른 이름을 선택할 수도 있지만, 같은 이름을 사용하는 것이 관례입니다. impl에서 제네릭 타입을 선언하는 메서드를 작성하면, 제네릭 타입을 대체하는 구체적인 타입이 무엇이든 해당 타입의 모든 인스턴스에 대해 그 메서드가 정의됩니다.

타입에 메서드를 정의할 때 제네릭 타입에 대한 제약 조건을 지정할 수도 있습니다. 예를 들어, 임의의 제네릭 타입을 가진 Point<f32> 인스턴스가 아닌 Point<T> 인스턴스에 대해서만 메서드를 구현할 수 있습니다. Listing 10-10에서는 구체적인 타입인 f32를 사용하므로, impl 뒤에 타입을 선언하지 않습니다.

이 코드는 Point<f32> 타입에만 distance_from_origin 메서드가 있음을 의미합니다. Point<T> 타입이 T이 아닌 다른 f32 인스턴스에는 이 메서드가 정의되지 않습니다. 이 메서드는 좌표 (0.0, 0.0)인 원점에서 해당 점까지의 거리를 측정하며, 부동 소수점 타입에서만 사용할 수 있는 수학 연산을 사용합니다.

구조체 정의의 제네릭 타입 매개변수는 항상 해당 구조체의 메서드 시그니처에서 사용하는 것과 같지는 않습니다. Listing 10-11은 예제를 명확히 하기 위해 Point 구조체에 제네릭 타입 X1과 Y1을, mixup 메서드 시그니처에 X2과 Y2를 사용합니다. 이 메서드는 self Point(X1 타입)의 x 값과 전달된 Point(Y2 타입)의 y 값으로 새로운 Point 인스턴스를 생성합니다.

main에서 Point를 정의합니다. i32는 값이 x인 5 타입의 f64와 값이 y인 10.4 타입의 p2를 가집니다. Point 변수는 값이 x인 문자열 슬라이스 타입의 "Hello"와 값이 char인 y 타입의 c를 가진 mixup 구조체입니다. p1에 인수로 p2를 전달하여 p3를 호출하면 i32를 얻게 됩니다. x는 x이 p1에서 왔기 때문에 p3 타입을 가집니다. char 변수는 y이 y에서 왔기 때문에 p2 타입을 가집니다. println! 매크로 호출은 p3.x = 5, p3.y = c를 출력합니다.

이 예제의 목적은 일부 일반 매개 변수가 다음과 같이 선언 된 상황을 설명하는 것입니다. impl 그리고 일부는 메소드 정의와 함께 선언됩니다. 여기, 제네릭 파라미터 X1 그리고 Y1 선언된 후 impl 왜냐하면 그들은 구조체 정의와 함께 가기 때문입니다. X2 그리고 Y2 선언된 후 fn mixup 왜냐하면 그것은 단지 방법과 관련이 있기 때문입니다.

제네릭을 사용한 코드의 성능

제네릭 타입 매개변수를 사용할 때 런타임 비용이 발생하는지 궁금해할 수 있습니다. 좋은 소식은 제네릭 타입을 사용해도 구체적인 타입을 사용하는 경우보다 프로그램 실행이 느려지지 않는다는 것입니다.

Rust는 컴파일 타임에 제네릭을 사용하는 코드에 대해 단형화(monomorphization)를 수행하여 이를 달성합니다. 단형화는 컴파일 시 사용되는 구체적인 타입을 채워 넣어 제네릭 코드를 구체적인 코드로 변환하는 과정입니다. 이 과정에서 컴파일러는 Listing 10-5에서 제네릭 함수를 생성할 때 사용한 단계의 반대를 수행합니다. 즉, 컴파일러는 제네릭 코드가 호출되는 모든 위치를 확인하고, 해당 제네릭 코드가 호출된 구체적인 타입에 대한 코드를 생성합니다.

표준 라이브러리의 제네릭 Option<T> enum을 사용하여 이 동작 방식을 살펴보겠습니다.

#![allow(unused)]
fn main() {
let integer = Some(5);
let float = Some(5.0);
}

러스트가 이 코드를 컴파일할 때, 그것은 단형화(monomorphization)를 수행합니다. 그 과정에서, 컴파일러는 사용된 값들을 읽습니다. Option<T> 사례 및 식별의 두 종류 Option<T>하나 : One i32 그리고 다른 하나는 f64. 이와 같이, 그것은 일반적인 정의를의 확장합니다 Option<T> 두 가지 특징이 특징인 i32 그리고 f64따라서 일반적인 정의를 특정 정의로 대체합니다.

단형화된 버전의 코드는 다음과 유사합니다(컴파일러는 여기에서 설명을 위해 사용하는 이름과 다른 이름을 사용합니다).

제네릭 Option<T>은 컴파일러가 생성한 구체적인 정의들로 대체됩니다. Rust는 제네릭 코드를 각 인스턴스에서 타입을 명시적으로 지정하는 코드로 컴파일하기 때문에, 제네릭을 사용하는 데 런타임 비용이 발생하지 않습니다. 코드가 실행될 때 각 정의를 수동으로 복제해 둔 것과 동일한 성능을 발휘합니다. 이러한 단형화(monomorphization) 과정 덕분에 Rust의 제네릭은 런타임에서 매우 높은 효율을 보입니다.
