The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

모듈 트리에서 항목을 참조하기 위한 경로

Rust가 모듈 트리에서 항목을 어디에서 찾을 수 있는지 알려주기 위해, 파일 시스템을 탐색할 때 경로를 사용하는 것과 동일한 방식으로 경로를 사용합니다. 함수를 호출하려면 해당 함수의 경로를 알아야 합니다.

경로는 두 가지 형태를 가질 수 있습니다.

  • 절대 경로는 크레이트 루트에서 시작하는 전체 경로입니다. 외부 크레이트의 코드에 대해서는 절대 경로가 크레이트 이름으로 시작하고, 현재 크레이트의 코드에 대해서는 리터럴 crate로 시작합니다.
  • 상대 경로는 현재 모듈에서 시작하여 self, super 또는 현재 모듈의 식별자를 사용합니다.

절대 경로와 상대 경로 모두 이중 콜론(::)으로 구분된 하나 이상의 식별자가 뒤에 이어집니다.

Listing 7-1로 돌아가서, add_to_waitlist 함수를 호출한다고 가정해 보겠습니다. 이는 다음과 같은 질문과 같습니다. add_to_waitlist 함수의 경로는 무엇입니까? Listing 7-3에는 일부 모듈과 함수가 제거된 Listing 7-1이 포함되어 있습니다.

크레이트 루트에 정의된 새로운 함수 add_to_waitlist에서 eat_at_restaurant 함수를 호출하는 두 가지 방법을 보여 드리겠습니다. 이 경로들은 올바르지만, 이 예제가 있는 그대로 컴파일되는 것을 막는 또 다른 문제가 남아 있습니다. 그 이유는 잠시 후에 설명하겠습니다.

eat_at_restaurant 함수는 우리 라이브러리 크레이트의 공개 API의 일부이므로 pub 키워드로 표시합니다. “pub 키워드로 경로 노출하기” 섹션에서 pub에 대해 더 자세히 다룹니다.

우리가 처음 전화했을 때 add_to_waitlist 기능 IN eat_at_restaurant, 우리는 절대 경로를 사용합니다. add_to_waitlist 함수는 다음과 같은 크레이트에 정의되어 있습니다. eat_at_restaurant즉, 사용할 수 있는 crate 키워드는 절대 경로를 시작합니다. 그런 다음 다음 다음을 수행 할 때까지 각 연속 모듈을 포함합니다. add_to_waitlist. 같은 구조의 파일시스템을 상상할 수 있습니다. /front_of_house/hosting/add_to_waitlist 실행하려면To run the add_to_waitlist 프로그램; Using crate crate root에서 시작하는 이름은 다음과 같습니다. / 쉘의 파일 시스템 루트에서 시작합니다.

우리가 부르는 두 번째 add_to_waitlist 에서 eat_at_restaurant, 상대 경로를 사용합니다. 경로는 다음과 같이 시작됩니다. front_of_house, 모듈 트리의 동일한 수준에서 정의된 모듈의 이름 eat_at_restaurant. 여기서 파일 시스템 상응은 경로를 사용하는 것입니다. front_of_house/hosting/add_to_waitlist. 모듈 이름으로 시작하면 경로가 상대적입니다.

상대 경로와 절대 경로 중 어떤 것을 사용할지는 프로젝트에 따라 달라지는 결정입니다. 항목을 사용하는 코드와 항목 정의 코드를 함께 이동할 가능성이 높은지, 아니면 별도로 이동할 가능성이 높은지에 따라 선택해야 합니다. 예를 들어, front_of_house 모듈과 eat_at_restaurant 함수를 customer_experience라는 이름의 모듈로 이동한다면, add_to_waitlist에 대한 절대 경로를 업데이트해야 하지만, 상대 경로는 여전히 유효합니다. 반면, eat_at_restaurant 함수를 dining라는 이름의 모듈로만 별도로 이동한다면, add_to_waitlist 호출에 대한 절대 경로는 그대로 유지되지만, 상대 경로는 업데이트해야 합니다. 일반적으로 코드 정의와 항목 호출을 서로 독립적으로 이동할 가능성이 더 높기 때문에, 절대 경로를 지정하는 것을 선호합니다.

목록 7-3을 컴파일하여 왜 아직 컴파일되지 않는지 확인해 보겠습니다. 발생하는 오류는 목록 7-4에 나와 있습니다.

오류 메시지는 모듈 hosting이 비공개라고 알려 줍니다. 즉, hosting 모듈과 add_to_waitlist 함수에 대한 올바른 경로를 가지고 있지만, Rust는 비공개 섹션에 접근할 권한이 없기 때문에 이를 사용할 수 없습니다. Rust에서는 모든 항목(함수, 메서드, 구조체, 열거형, 모듈, 상수)이 기본적으로 상위 모듈에 대해 비공개입니다. 함수나 구조체와 같은 항목을 비공개로 만들려면 해당 항목을 모듈 안에 두면 됩니다.

부모 모듈의 항목은 자식 모듈 내부의 비공개 항목을 사용할 수 없지만, 자식 모듈의 항목은 조상 모듈의 항목을 사용할 수 있습니다. 이는 자식 모듈이 구현 세부 사항을 감싸고 숨기지만, 자식 모듈은 자신이 정의된 컨텍스트를 볼 수 있기 때문입니다. 비유를 계속하자면, 프라이버시 규칙을 레스토랑의 백오피스처럼 생각할 수 있습니다. 백오피스에서 일어나는 일은 레스토랑 고객에게는 비공개이지만, 해당 레스토랑을 운영하는 사무실 관리자는 레스토랑 안의 모든 것을 보고 처리할 수 있습니다.

Rust는 내부 구현 세부 사항을 숨기는 것이 기본이 되도록 모듈 시스템을 이 방식으로 설계했습니다. 이렇게 하면 외부 코드를 깨뜨리지 않고 내부 코드의 어떤 부분을 변경할 수 있는지 알 수 있습니다. 하지만 Rust는 pub 키워드를 사용하여 항목을 공개함으로써 자식 모듈 코드의 내부 부분을 외부 조상 모듈에 노출하는 옵션도 제공합니다.

pub 키워드로 경로 노출하기

Listing 7-4의 오류에서 hosting 모듈이 비공개라고 알려주었습니다. 부모 모듈의 eat_at_restaurant 함수가 자식 모듈의 add_to_waitlist 함수에 접근할 수 있도록 하려면, Listing 7-5에 나와 있듯이 hosting 모듈에 pub 키워드를 붙여야 합니다.

불행히도, Listing 7-5의 코드는 여전히 Listing 7-6과 같이 컴파일러 오류를 발생시킵니다.

무슨 일이 일어 났습니까? 추가 pub 앞의 키워드 mod hosting 모듈을 public으로 만듭니다. 이 변경으로, 우리가 접근할 수 있다면 front_of_house우리는 액세스할 수 있습니다. hosting. 그러나 상품정보 또는 hosting 아직 비공개입니다. 모듈을 공개하는 것은 그 내용을 공개하지 않습니다. pub module의 keyword는 ancestor modules에서만 참조할 수 있고, 내부 코드에는 접근하지 않습니다. modules는 container이기 때문에, module을 public으로만 만들어서 할 수 있는 일은 많지 않습니다. 우리는 더 나아가 module 내에서 하나 이상의 item을 public으로 만들 필요가 있습니다.

Listing 7-6의 오류 메시지는 add_to_waitlist 함수가 비공개라고 알려 줍니다. 비공개 규칙은 모듈뿐만 아니라 구조체, 열거형, 함수, 메서드에도 적용됩니다.

이제 코드가 컴파일됩니다! 비공개 규칙에 따라 pub 키워드를 추가하면 eat_at_restaurant에서 이러한 경로를 사용할 수 있는 이유를 이해하기 위해 절대 경로와 상대 경로를 살펴 보겠습니다.

절대 경로에서는 크레이트 모듈 트리의 루트인 crate에서 시작합니다. front_of_house 모듈은 크레이트 루트에 정의되어 있습니다. front_of_house는 비공개이지만, eat_at_restaurant 함수가 front_of_house와 동일한 모듈에 정의되어 있기 때문에(즉, eat_at_restaurant와 front_of_house는 형제 관계이므로) front_of_house에서 eat_at_restaurant에 참조할 수 있습니다. 다음으로 hosting 모듈은 pub로 표시되어 있습니다. hosting의 부모 모듈에 접근할 수 있으므로 hosting에도 접근할 수 있습니다. 마지막으로, add_to_waitlist 함수는 pub로 표시되어 있고, 이 함수의 부모 모듈에 접근할 수 있으므로 이 함수 호출이 성공합니다!

상대 경로의 논리는 첫 번째 단계를 제외하면 절대 경로와 동일합니다. 크레이트 루트에서 시작하는 대신 경로는 front_of_house에서 시작합니다. front_of_house 모듈은 eat_at_restaurant와 동일한 모듈 내에 정의되어 있으므로, eat_at_restaurant이 정의된 모듈에서 시작하는 상대 경로는 유효합니다. 그 다음, hosting와 add_to_waitlist가 pub로 표시되어 있으므로 나머지 경로는 유효하며, 이 함수 호출은 성공합니다!

다른 프로젝트에서 코드를 사용할 수 있도록 라이브러리 크레이트를 공유할 계획이라면, 공개 API는 크레이트 사용자가 코드와 상호 작용하는 방법을 결정하는 계약입니다. 사람들이 더 쉽게 크레이트에 의존할 수 있도록 공개 API의 변경을 관리하는 데 고려해야 할 사항이 많습니다. 이러한 고려 사항은 이 책의 범위를 벗어납니다. 이 주제에 관심이 있다면 Rust API Guidelines를 참조하십시오.

바이너리와 라이브러리가 포함된 패키지의 모범 사례

패키지는 src/main.rs 바이너리 크레이트 루트와 src/lib.rs 라이브러리 크레이트 루트를 모두 포함할 수 있으며, 두 크레이트 모두 기본적으로 패키지 이름을 갖습니다. 일반적으로 라이브러리와 바이너리 크레이트를 모두 포함하는 패키지는 바이너리 크레이트에 실행 파일을 시작하고 라이브러리 크레이트에 정의된 코드를 호출하는 데 필요한 최소한의 코드만 포함합니다. 이를 통해 라이브러리 크레이트의 코드를 공유할 수 있으므로, 다른 프로젝트가 해당 패키지가 제공하는 대부분의 기능을 활용할 수 있습니다.

모듈 트리는 src/lib.rs에 정의되어야 합니다. 그러면 공개 항목은 패키지 이름으로 시작하는 경로를 사용하여 바이너리 크레이트에서 사용할 수 있습니다. 바이너리 크레이트는 완전히 외부의 크레이트가 라이브러리 크레이트를 사용하는 것과 마찬가지로 라이브러리 크레이트의 사용자가 되며, 오직 공개 API만 사용할 수 있습니다. 이는 좋은 API를 설계하는 데 도움이 됩니다. 당신은 저자일 뿐만 아니라 클라이언트이기도 하니까요!

super로 시작하는 상대 경로super

경로 시작 부분에 super를 사용하면 현재 모듈이나 크레이트 루트가 아닌 부모 모듈에서 시작하는 상대 경로를 구성할 수 있습니다. 이는 파일 시스템에서 부모 디렉토리로 이동하는 .. 구문을 사용하는 것과 같은 원리입니다. super를 사용하면 부모 모듈에 있는 항목을 참조할 수 있습니다. 이는 해당 모듈이 부모 모듈과 밀접한 관련이 있지만, 나중에 모듈 트리 내에서 부모 모듈이 다른 위치로 이동할 수 있는 경우 모듈 트리를 재배열하는 작업을 용이하게 합니다.

Listing 7-8의 코드는 요리사가 잘못된 주문을 수정한 뒤 직접 고객에게 전달하는 상황을 모델링합니다. fix_incorrect_order 함수는 back_of_house 모듈에 정의되어 있으며, deliver_order로 시작하는 경로를 지정하여 부모 모듈에 정의된 deliver_order 함수를 호출합니다. 이 경로는 super로 시작합니다.

fix_incorrect_order 함수는 back_of_house 모듈에 있으므로, super를 사용하여 back_of_house의 상위 모듈로 이동할 수 있습니다. 이 경우 상위 모듈은 루트인 crate입니다. 그곳에서 deliver_order를 찾아 찾습니다. 성공입니다! back_of_house 모듈과 deliver_order 함수는 서로 같은 관계를 유지할 가능성이 높으며, 크레이트의 모듈 트리를 재구성하기로 결정하면 함께 이동할 것입니다. 따라서 이 코드가 다른 모듈로 이동하더라도 향후 코드 업데이트가 필요한 곳이 적도록 super을 사용했습니다.

구조체와 열거형 공개

pub를 사용하여 구조체와 열거형도 공개로 지정할 수 있습니다. 다만 구조체와 열거형에 pub을 사용할 때는 몇 가지 추가적인 사항이 있습니다. 구조체 정의 앞에 pub를 붙이면 구조체 자체는 공개가 되지만, 구조체의 필드는 여전히 비공개로 유지됩니다. 각 필드를 개별적으로 공개할지 비공개로 둘지 결정할 수 있습니다. Listing 7-9에서는 back_of_house::Breakfast 구조체를 공개로 정의했으며, toast 필드는 공개로, seasonal_fruit 필드는 비공개로 설정했습니다. 이는 식당에서 고객이 식사와 함께 제공되는 빵의 종류는 선택할 수 있지만, 셰프가 계절과 재고 상황에 따라 어떤 과일을 함께 제공할지 결정하는 상황을 모델링한 것입니다. 제공 가능한 과일은 자주 바뀌므로, 고객은 과일을 선택하거나 어떤 과일을 받을지 확인할 수 없습니다.

toast 구조체의 back_of_house::Breakfast 필드가 공개(public)되어 있으므로, eat_at_restaurant 함수에서 점(dot) 표기법을 사용하여 toast 필드에 값을 읽고 쓸 수 있습니다. seasonal_fruit 필드는 비공개(private)이므로 eat_at_restaurant 함수에서 사용할 수 없다는 점에 유의하세요. seasonal_fruit 필드의 값을 수정하는 줄의 주석을 해제하여 어떤 오류가 발생하는지 확인해 보세요! seasonal_fruit

또한, back_of_house::Breakfast 구조체는 private 필드를 가지고 있으므로, Breakfast 인스턴스를 생성하는 public associated 함수를 제공해야 합니다. 여기서는 해당 함수 이름을 summer 로 지었습니다. 만약 Breakfast 에 그런 함수가 없었더라면, Breakfast 에서 eat_at_restaurant 인스턴스를 생성할 수 없었을 것입니다. 그 이유는 seasonal_fruit 에서 private 필드인 eat_at_restaurant 의 값을 설정할 수 없기 때문입니다.

반면, 열거형을 공개로 지정하면 그 열거형의 모든 변형(variant)이 자동으로 공개됩니다. Listing 7-10에 보여지듯, pub 키워드 앞에 enum만 붙이면 됩니다.

Appetizer 열거형을 공개로 지정했으므로, Soup와 Salad 변형을 eat_at_restaurant에서 사용할 수 있습니다.

변형이 public이 아니라면 enum은 큰 실용성이 없습니다. 모든 enum 변형에 pub를 붙여야 하는 것은 번거로우므로, enum 변형은 기본적으로 public입니다. 반면 struct는 필드가 public이 아니더라도 유용한 경우가 많으므로, struct 필드는 pub로 명시적으로 지정하지 않는 한 기본적으로 private인 일반적인 규칙을 따릅니다.

아직 다루지 않은 pub와 관련된 상황이 하나 더 있습니다. 바로 마지막 모듈 시스템 기능인 use 키워드입니다. 먼저 use 자체에 대해 설명한 뒤, pub과 use를 결합하는 방법을 보여 드리겠습니다.
