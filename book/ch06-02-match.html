The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

match 제어 흐름 구조

러스트는 매우 강력한 제어 흐름 구조를 가지고 있습니다. match 즉, 일련의 패턴에 대해 값을 비교 한 다음 패턴 일치를 기반으로 코드를 실행할 수 있습니다. 패턴은 리터럴 값, 변수 이름, 와일드 카드 및 기타 여러 가지로 구성 될 수 있습니다. 창세기. Chapter 19 무시 본의 모든 다른 종류 및 그들이 하는 무슨을 커버합니다. 의 힘 match 패턴의 표현력과 컴파일러가 모든 가능한 경우를 처리한다는 사실에서 비롯됩니다.

match 표현식을 동전 분류기처럼 생각해 보세요. 동전은 크기가 서로 다른 구멍이 나 있는 트랙을 따라 내려가며, 각 동전은 자신에게 맞는 첫 번째 구멍으로 떨어집니다. 이와 마찬가지로, 값은 match의 각 패턴을 순서대로 통과하며, 값이 '맞는' 첫 번째 패턴에서 해당 패턴에 연결된 코드 블록으로 들어가 실행됩니다.

동전에 대해 이야기했으니, 이번에는 match를 사용하여 동전을 예제로 들어보겠습니다. Listing 6-3에 나와 있듯이, 알 수 없는 미국 동전을 인자로 받는 함수를 작성할 수 있습니다. 이 함수는 동전 분류기와 유사한 방식으로 어떤 동전인지 판별하고, 그 가치를 센트 단위로 반환합니다.

match 함수의 value_in_cents 문을 단계별로 살펴보겠습니다. 먼저, match 키워드 뒤에 표현식을 나열하는데, 이 경우 해당 값은 coin입니다. 이는 if와 함께 사용되는 조건식과 매우 유사해 보이지만, 큰 차이가 있습니다. if의 경우 조건이 부울 값으로 평가되어야 하지만, 여기서는 어떤 타입이든 가능합니다. 이 예제에서 coin의 타입은 첫 번째 줄에서 정의한 Coin 열거형입니다.

다음은 match의 팔(arm)입니다. 팔은 패턴과 코드 두 부분으로 구성됩니다. 첫 번째 팔에는 Coin::Penny이라는 값이 패턴으로 사용되며, => 연산자가 패턴과 실행할 코드를 구분합니다. 이 경우 코드는 단순히 값 1입니다. 각 팔은 쉼표로 구분됩니다.

match 표현식이 실행되면, 결과 값을 각 팔의 패턴과 순서대로 비교합니다. 어떤 패턴이 값과 일치하면, 그 패턴에 연결된 코드가 실행됩니다. 만약 그 패턴이 값과 일치하지 않으면, 동전 분류기에서처럼 실행은 다음 팔로 이어집니다. 필요한 만큼 많은 수의 팔을 가질 수 있습니다. Listing 6-3의 예제에서는 match에 네 개의 팔이 있습니다.

각 팔(arm)에 해당하는 코드는 표현식이며, 일치하는 팔에서 평가된 표현식의 결과가 전체 match 표현식의 반환 값이 됩니다.

match arm의 코드가 짧으면 Listing 6-3처럼 각 arm이 단순히 값을 반환하는 경우 대괄호를 사용하지 않는 것이 일반적입니다. match arm에서 여러 줄의 코드를 실행하려면 대괄호를 사용해야 하며, 이 경우 arm 뒤에 오는 쉼표는 선택 사항입니다. 예를 들어, 다음 코드는 메서드가 Coin::Penny로 호출될 때마다 “Lucky penny!”를 출력하지만, 여전히 블록의 마지막 값인 1을 반환합니다. Coin::Penny1

enum Coin {
    Penny,
    Nickel,
    Dime,
    Quarter,
}

fn value_in_cents(coin: Coin) -> u8 {
    match coin {
        Coin::Penny => {
            println!("Lucky penny!");
            1
        }
        Coin::Nickel => 5,
        Coin::Dime => 10,
        Coin::Quarter => 25,
    }
}

fn main() {}

값에 바인딩하는 패턴

match arm의 또 다른 유용한 기능은 패턴과 일치하는 값의 일부에 바인딩할 수 있다는 점입니다. 이를 통해 enum 변형에서 값을 추출할 수 있습니다.

예를 들어, 열거형 변형 중 하나를 변경하여 그 안에 데이터를 저장하도록 해 보겠습니다. 1999년부터 2008년까지 미국은 50개 주 각각의 디자인을 한 면에 새긴 25센트 동전을 발행했습니다. 다른 동전에는 주 디자인이 없으므로, 25센트 동전만 이 추가 정보를 가집니다. Listing 6-4에서 수행한 것처럼, Quarter 변형을 변경하여 그 안에 UsState 값을 저장하도록 하면 이 정보를 열거형에 추가할 수 있습니다. enumQuarterUsState

친구가 50개 주 모두의 25센트 동전을 수집하려고 한다고 가정해 보겠습니다. 동전 종류별로 잔돈을 정리하면서, 각 25센트 동전에 해당하는 주 이름도 함께 말해 주면 친구가 아직 없는 동전을 수집함에 추가할 수 있습니다.

이 코드에 대한 일치 식에서 우리는 호출 된 변수를 추가합니다. state 변형의 값과 일치하는 패턴으로 Coin::Quarter. 때 Coin::Quarter 경기, the state 변수는 해당 분기의 상태 값에 바인딩됩니다. 그런 다음 사용할 수 있습니다. state 그 팔의 코드에서, 이렇게 :

#[derive(Debug)]
enum UsState {
    Alabama,
    Alaska,
    // --snip--
}

enum Coin {
    Penny,
    Nickel,
    Dime,
    Quarter(UsState),
}

fn value_in_cents(coin: Coin) -> u8 {
    match coin {
        Coin::Penny => 1,
        Coin::Nickel => 5,
        Coin::Dime => 10,
        Coin::Quarter(state) => {
            println!("State quarter from {state:?}!");
            25
        }
    }
}

fn main() {
    value_in_cents(Coin::Quarter(UsState::Alaska));
}

우리가 전화한다면 value_in_cents(Coin::Quarter(UsState::Alaska)), coin 될 것이다 Coin::Quarter(UsState::Alaska). 우리가 그 값을 각 매치 암과 비교할 때, 우리가 도달 할 때까지 그들 중 어느 것도 일치하지 않습니다. Coin::Quarter(state). 그 시점에서, 바인딩은 state 가치가 될 것입니다. UsState::Alaska. 우리는 다음에서 그 바인딩을 사용할 수 있습니다 println! expression : 내부 상태 값을 외부로 내보내는 것 Coin 에 대한 enum 변형 Quarter.

Option<T> match 패턴

이전 섹션에서는 T을 사용할 때 Some 케이스에서 내부의 Option<T> 값을 꺼내고 싶었습니다. Option<T>도 match을 사용해 처리할 수 있으며, 이는 Coin enum을 다룰 때와 같습니다. 동전을 비교하는 대신 Option<T>의 변형을 비교하지만, match 표현식이 작동하는 방식은 동일합니다.

Option<i32>을 인자로 받는 함수를 작성한다고 가정해 보겠습니다. 내부에 값이 있으면 그 값에 1을 더합니다. 내부에 값이 없으면 함수는 None 값을 반환하고, 어떤 연산도 수행하지 않아야 합니다.

이 함수는 match 덕분에 매우 쉽게 작성할 수 있으며, Listing 6-5와 같은 형태가 됩니다.

plus_one의 첫 번째 실행을 자세히 살펴보겠습니다. plus_one(five)을 호출하면 x 본문에 있는 변수 plus_one에는 Some(5) 값이 저장됩니다. 이후 이 값을 각 매치 암과 비교합니다.

fn main() {
    fn plus_one(x: Option<i32>) -> Option<i32> {
        match x {
            None => None,
            Some(i) => Some(i + 1),
        }
    }

    let five = Some(5);
    let six = plus_one(five);
    let none = plus_one(None);
}

Some(5) 값은 None 패턴과 일치하지 않으므로, 다음 매치 암으로 진행합니다.

fn main() {
    fn plus_one(x: Option<i32>) -> Option<i32> {
        match x {
            None => None,
            Some(i) => Some(i + 1),
        }
    }

    let five = Some(5);
    let six = plus_one(five);
    let none = plus_one(None);
}

Some(5)이 Some(i)과 일치합니까? 일치합니다! 동일한 변이(변형)이기 때문입니다. i에 포함된 값에 Some이 바인딩되므로, i는 값 5를 갖게 됩니다. 5. 매치 암의 코드가 실행되므로, i에 1을 더하고 합계인 6을 포함하는 새로운 Some 값을 생성합니다. 6

이제 Listing 6-5에서 plus_one의 두 번째 호출을 살펴봅시다. 이 경우 x은 None입니다. match에 진입하여 첫 번째 암(arm)과 비교합니다.

fn main() {
    fn plus_one(x: Option<i32>) -> Option<i32> {
        match x {
            None => None,
            Some(i) => Some(i + 1),
        }
    }

    let five = Some(5);
    let six = plus_one(five);
    let none = plus_one(None);
}

일치했습니다! 더할 값이 없으므로 프로그램은 중단되고 None 오른쪽의 => 값을 반환합니다. 첫 번째 팔(arm)이 일치했기 때문에 다른 팔은 비교되지 않습니다.

match와 enum을 결합하는 것은 많은 상황에서 유용합니다. Rust 코드에서 이 패턴을 자주 볼 수 있습니다. match는 enum에 대해 매칭하고, 내부 데이터에 변수를 바인딩한 다음, 이를 기반으로 코드를 실행합니다. 처음에는 약간 까다로울 수 있지만, 익숙해지면 모든 언어에서 이 기능이 있었으면 하고 바라게 될 것입니다. 사용자들 사이에서 꾸준히 인기 있는 기능입니다.

match는 모든 경우를 다룹니다

match에 대해 논의해야 할 또 다른 측면이 있습니다. 각 팔(arm)의 패턴은 모든 가능한 경우를 포괄해야 합니다. 다음에 보이는 plus_one 함수의 버전은 버그가 있어 컴파일되지 않습니다.

fn main() {
    fn plus_one(x: Option<i32>) -> Option<i32> {
        match x {
            Some(i) => Some(i + 1),
        }
    }

    let five = Some(5);
    let six = plus_one(five);
    let none = plus_one(None);
}

None 케이스를 처리하지 않았기 때문에 이 코드는 버그를 유발합니다. 다행히 Rust는 이러한 버그를 감지하는 방법을 알고 있습니다. 이 코드를 컴파일하면 다음과 같은 오류가 발생합니다:

Rust는 가능한 모든 경우를 다루지 못했다는 것을 알고 있으며, 심지어 어떤 패턴을 놓쳤는지도 알고 있습니다! Rust의 매치는 포괄적(exhaustive)입니다. 코드가 유효하려면 모든 가능성을 빠짐없이 다뤄야 합니다. 특히 Option<T>의 경우, Rust는 None 케이스를 명시적으로 처리하는 것을 잊어버리는 것을 방지함으로써, 값이 있을 수 있는 상황에서 null을 가정하는 실수를 막아 줍니다. 이를 통해 앞서 논의한 10억 달러짜리 실수를 불가능하게 만듭니다.

캐치올 패턴과 _ 플레이스홀더

열거형(enum)을 사용하면 몇 가지 특정 값에 대해 특별한 조치를 취하고, 나머지 모든 값에는 하나의 기본 조치를 취할 수 있습니다. 주사위를 굴려서 3이 나오면 플레이어가 움직이지 않고 대신 멋진 새 모자를 얻는 게임을 구현한다고 상상해 보겠습니다. 7이 나오면 플레이어는 멋진 모자를 잃습니다. 나머지 모든 값의 경우, 플레이어는 게임 보드에서 해당 숫자만큼 이동합니다. 다음 match 문은 이 논리를 구현합니다. 주사위 굴림 결과는 랜덤 값 대신 하드코딩되어 있으며, 실제 구현은 이 예제의 범위를 벗어나므로 나머지 로직은 본문이 없는 함수로 표현되어 있습니다: match

fn main() {
    let dice_roll = 9;
    match dice_roll {
        3 => add_fancy_hat(),
        7 => remove_fancy_hat(),
        other => move_player(other),
    }

    fn add_fancy_hat() {}
    fn remove_fancy_hat() {}
    fn move_player(num_spaces: u8) {}
}

처음 두 개의 경우(arm)에서 패턴은 리터럴 값 3과 7입니다. 나머지 모든 가능한 값을 다루는 마지막 경우의 패턴은 other라는 이름으로 지정한 변수입니다. other 경우에서 실행되는 코드는 이 변수를 move_player 함수에 전달하여 사용합니다.

이 코드는 u8가 가질 수 있는 모든 가능한 값을 나열하지 않았음에도 컴파일됩니다. 마지막 패턴이 특별히 나열되지 않은 모든 값과 일치하기 때문입니다. 이 캐치올 패턴은 match이 포괄적이어야 한다는 요구 사항을 충족시킵니다. 패턴은 순서대로 평가되므로 캐치올 암을 마지막에 배치해야 합니다. 캐치올 암을 더 앞에 배치하면 다른 암은 절대 실행되지 않으므로, 캐치올 뒤에 암을 추가하면 Rust가 경고합니다!

Rust에는 캐치올이 필요하지만 그 값을 사용하지 않으려는 경우 사용할 수 있는 패턴이 있습니다. _는 어떤 값과도 일치하지만 그 값에 바인딩하지 않는 특별한 패턴입니다. 이는 Rust에게 해당 값을 사용하지 않을 것임을 알려주므로, Rust는 사용되지 않는 변수에 대해 경고하지 않습니다.

게임 규칙을 변경해 보겠습니다. 이제 3 또는 7 이외의 값이 나오면 다시 굴려야 합니다. 더 이상 캐치올 값을 사용할 필요가 없으므로, other라는 변수 대신 _를 사용하도록 코드를 변경할 수 있습니다: other

fn main() {
    let dice_roll = 9;
    match dice_roll {
        3 => add_fancy_hat(),
        7 => remove_fancy_hat(),
        _ => reroll(),
    }

    fn add_fancy_hat() {}
    fn remove_fancy_hat() {}
    fn reroll() {}
}

이 예제는 마지막 암에서 나머지 모든 값을 명시적으로 무시하기 때문에 완전성(exhaustiveness) 요구 사항을 충족합니다. 아무것도 빠뜨리지 않은 것입니다.

마지막으로, 게임 규칙을 한 번 더 변경하여 3 또는 7 이외의 값이 나오면 턴 동안 아무 일도 일어나지 않도록 하겠습니다. 튜플 타입 섹션에서 언급한 단위 값(빈 튜플 타입)을 _ 암에 해당하는 코드로 사용하여 이를 표현할 수 있습니다:

fn main() {
    let dice_roll = 9;
    match dice_roll {
        3 => add_fancy_hat(),
        7 => remove_fancy_hat(),
        _ => (),
    }

    fn add_fancy_hat() {}
    fn remove_fancy_hat() {}
}

여기서 Rust에 이전 arm의 패턴과 일치하지 않는 다른 값을 사용하지 않을 것이며, 이 경우 어떤 코드도 실행하지 않겠다고 명시적으로 알려줍니다.
