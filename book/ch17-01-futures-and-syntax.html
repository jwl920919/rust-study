미래와 비동기 구문

러스트에서 비동기 프로그래밍의 핵심 요소는 선물과 러스트의 async 및 await 키워드입니다.

A 미래 is a value that may not be ready now but will be ready at some point in the future. (이 같은 개념은 많은 언어에서 나타나며, 때로는 다음과 같은 다른 이름으로도 나타난다.) 작업 또는 약속.) 러스트는 다음을 제공합니다. Future 다른 비동기 작업이 서로 다른 데이터 구조로 구현될 수 있지만 공통 인터페이스로 구현될 수 있도록 하는 빌딩 블록의 특성입니다. 러스트에서, futures는 Future 특성. 각 미래는 만들어진 진전과 "준비"가 무엇을 의미하는지에 대한 자체 정보를 보유하고 있습니다.

async 키워드를 블록 및 함수에 적용하여 중단 및 재개할 수 있도록 지정할 수 있습니다. 비동기 블록 또는 비동기 함수 내에서 await 키워드를 사용하여 미래를 기다릴 수 있습니다(즉, 준비가 될 때까지 기다릴 수 있음). 비동기 블록 또는 함수 내에서 미래를 기다리는 지점은 해당 블록 또는 함수가 일시 중지 및 재개할 수 있는 잠재적 지점입니다.

C# 및 JavaScript와 같은 일부 다른 언어도 비동기 프로그래밍을 위해 async 및 await 키워드를 사용합니다. 이러한 언어에 익숙하다면 러스트가 구문을 처리하는 방식에 몇 가지 중요한 차이가 있음을 알 수 있습니다. 그 이유는 다음과 같습니다!

러스트가 async 키워드로 표시된 블록을 볼 때, 그것을 Future 트레잇을 구현하는 고유한 익명의 데이터 타입으로 컴파일합니다. 러스트가 async로 표시된 함수를 볼 때, 그것을 비동기 함수로 컴파일합니다. 비동기 함수의 반환 타입은 컴파일러가 만든 익명의 데이터 타입입니다.

따라서 async fn를 작성하는 것은 반환 유형의 미래를 반환하는 함수를 작성하는 것과 같습니다. 컴파일러에게, Listing 17-1의 async fn page_title와 같은 함수 정의는 다음과 같이 정의된 비 비동기 함수와 대략 동일합니다:

#![allow(unused)]
fn main() {
extern crate trpl; // required for mdbook test
use std::future::Future;
use trpl::Html;

fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        let text = trpl::get(url).await.text().await;
        Html::parse(&text)
            .select_first("title")
            .map(|title| title.inner_html())
    }
}
}

변환된 버전의 각 부분을 살펴봅시다:

  • 를 사용하여 Using the impl Trait 우리는 10 장에서 다시 논의 구문 “매개 변수로서의 트레이트” 무시 섹션.
  • 반환된 값은 The returned value Future associated 한 타입의 Output. 주의 사항 Output 타입은 Option<String>상기 원본 리턴 타입은 The original return type async fn 버전 page_title.
  • 원래 함수의 본문에 호출 된 모든 코드는 async move 블록에 싸여 있습니다. 블록은 표현식임을 기억하십시오. 이 전체 블록은 함수에서 반환 된 표현식입니다.
  • 이 비동기 블록은 방금 설명한대로 Option<String> 유형으로 값을 생성합니다. 이 값은 반환 유형에서 Output 유형과 일치합니다. 이것은 당신이 본 다른 블록과 같습니다.
  • 새로운 기능 바디는 async move 매개 변수를 사용하는 방법 때문에 url 블록입니다. (나중에 async 대 async move에 대해 더 자세히 이야기 할 것입니다.)

await 키워드를 사용할 수 있는 유일한 장소는 비동기 함수나 블록이며, 러스트는 main 함수를 async로 표시하지 않습니다.

main를 async로 표시할 수 없는 이유는 비동기 코드에 런타임이 필요하기 때문입니다. 비동기 코드 실행의 세부사항을 관리하는 러스트 크레이트입니다. 프로그램의 main 함수는 런타임을 초기화할 수 있지만, 런타임 자체는 아닙니다. (왜 이런 경우가 발생하는지 조금 더 알아보겠습니다.) 코드를 실행하는 모든 러스트 프로그램은 적어도 하나의 동기화를 실행합니다.

비동기 번들을 지원하는 대부분의 언어는 런타임이지만, 러스트는 그렇지 않습니다. 대신, 사용할 수 있는 많은 다른 비동기 런타임이 있으며, 각각은 타겟팅하는 사용 사례에 적합한 다른 트레이드 오프를 만듭니다. 예를 들어, 많은 CPU 코어와 많은 양의 RAM을 가진 높은 처리량 웹 서버는 단일 코어, 적은 양의 RAM 및 힙 할당 능력을 가진 마이크로 컨트롤러와는 매우 다른 요구를 가지고 있습니다. 이러한 런타임 버전을 제공하는 크레이트는 종종 I 같은 런타임 파일을 제공합니다.

각 대기 지점(즉, 코드가 await 키워드를 사용하는 모든 장소)은 컨트롤이 런타임에 다시 전달되는 장소를 나타냅니다. 이 작업을 수행하기 위해 러스트는 비동기 블록에 관련된 상태를 추적하여 런타임이 다른 작업을 시작한 다음 첫 번째 작업을 다시 진행할 준비가 되었을 때 다시 돌아올 수 있도록 해야 합니다. 이것은 보이지 않는 상태 머신입니다.

#![allow(unused)]

extern crate trpl; // required for mdbook test

enum PageTitleFuture<'a> {
    Initial { url: &'a str },
    GetAwaitPoint { url: &'a str },
    TextAwaitPoint { response: trpl::Response },
}
}

그러나 코드를 수동으로 변환하기 위해 코드를 작성하는 것은 지루하고 오류가 발생하기 쉽습니다. 특히 나중에 코드에 더 많은 기능과 상태를 추가해야 할 때 더욱 그렇습니다. 다행스럽게도, 러스트 컴파일러는 비동기 코드에 대한 상태 머신 데이터 구조를 자동으로 생성하고 관리합니다. 데이터 구조에 대한 일반적인 차입 및 소유권 규칙은 여전히 적용되며, 컴파일러는 우리를 위해 검사하는 것을 처리하고 유용한 오류 메시지를 제공합니다. 우리는 나중에 그 중 몇 가지를 통해 작업 할 것입니다.

궁극적으로, 무언가는 이 상태 머신을 실행해야 하고, 무언가는 런타임입니다. (이것이 런타임을 살펴볼 때 실행자에 대한 언급을 발견할 수 있는 이유입니다. 실행기는 비동기 코드를 실행하는 런타임의 일부입니다.)

이제 컴파일러가 왜 우리가 만드는 것을 멈추게했는지 알 수 있습니다. main Listing 17-3에서 그 자체로 async 함수를 반환합니다. main 만약 비동기 함수라면, 어떤 미래를 위해 상태 머신을 관리해야 할 필요가 있을 것입니다. main 돌아왔지만, main 프로그램의 출발점입니다! 대신, 우리는 trpl::block_on 기능 IN main runtime을 설정하고 future가 반환되는 async 블록이 완성될 때까지

참고: 일부 런타임은 매크로를 제공하므로 비동기 main 함수를 작성할 수 있습니다. 이러한 매크로는 async fn main() { ... }를 일반 fn main로 재작성합니다. 이는 Listing 17-4에서 우리가 한 것과 동일한 작업을 수행합니다. trpl::block_on가 하는 것처럼 미래를 완료하기 위해 실행되는 함수를 호출합니다.

이제 이 조각들을 모아서 우리가 어떻게 동시 코드를 작성할 수 있는지 봅시다.

서로에 대해 두 개의 URL을 경주

Listing 17-5에서, 우리는 page_title를 커맨드 라인으로부터 전달된 두 개의 다른 URL들과 함께 호출하고 그것들을 먼저 완료될 미래를 선택함으로써 경주합니다.

page_title를 각 사용자 제공 URL에 대해 호출하는 것으로 시작합니다. 우리는 결과를 title_fut_1 및 title_fut_2로 저장합니다. 선물은 게으르고 아직 기다리지 않았기 때문에 아직 아무 것도하지 않는다는 것을 기억하십시오. 그런 다음 미래를 trpl::select로 전달하여 값을 반환합니다.

상기 후드는, The hood, trpl::select 그것은 더 일반적인에 건설된다 select 상기 함수는 The function futures 크레이트. futures 크레이트의 select 기능은 많은 것을 할 수 있습니다 trpl::select 함수는 할 수 없지만 현재 건너뛸 수 있는 몇 가지 추가 복잡성이 있습니다.

미래는 합법적으로 "승리"할 수 있으므로 반환하는 것은 의미가 없습니다. Result. 대신, trpl::select 전에 보지 못한 타입을 반환하고, trpl::Either. 그 Either 종류는 a와 약간 비슷합니다. Result 즉, 두 가지 경우가 있습니다. 달리 Result하지만, 성공이나 실패에 대한 개념이 전혀 없습니다. Either. 대신, Left 그리고 Right "one or the other"를 발음한 사람:

#![allow(unused)]
fn main() {
enum Either<A, B> {
    Left(A),
    Right(B),
}
}

select 함수는 첫 번째 인수가 이기면 그 미래의 출력으로 Left를 반환하고 두 번째 미래 인수의 출력으로 Right를 반환합니다. 이는 함수를 호출할 때 인수가 나타나는 순서와 일치합니다. 첫 번째 인수는 두 번째 인수의 왼쪽에 있습니다.

우리는 또한 page_title를 업데이트하여 전달 된 동일한 URL을 반환합니다. 이렇게하면 먼저 반환되는 페이지에 <title>가 없으면 여전히 의미있는 메시지를 인쇄 할 수 있습니다. 해당 정보를 사용할 수 있으므로 println! 출력을 업데이트하여 URL이 먼저 완료되었는지와 <title>가 웹 페이지인지를 나타냅니다.
