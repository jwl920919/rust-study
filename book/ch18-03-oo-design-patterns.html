The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

객체 지향 디자인 패턴 구현

상태 패턴은 객체 지향 디자인 패턴입니다. 이 패턴의 핵심은 값이 내부적으로 가질 수 있는 상태 집합을 정의하는 것입니다. 상태는 상태 객체 집합으로 표현되며, 값의 동작은 현재 상태에 따라 달라집니다. 'draft', 'review', 'published' 상태 객체 중 하나를 가질 필드를 가진 블로그 포스트 구조체 예제를 통해 이 개념을 살펴보겠습니다.

상태 객체는 기능을 공유합니다. 물론 Rust에서는 객체와 상속 대신 구조체와 트레이트를 사용합니다. 각 상태 객체는 자신의 동작과 다른 상태로 전환될 시점을 관리하는 책임을 집니다. 상태 객체를 보유하는 값은 각 상태의 다른 동작이나 상태 간 전환 시점에 대해 알지 못합니다.

상태 패턴을 사용하는 이점은 프로그램의 비즈니스 요구 사항이 변경될 때, 상태를 보유하는 값의 코드나 그 값을 사용하는 코드를 수정할 필요가 없다는 것입니다. 규칙을 변경하거나 더 많은 상태 객체를 추가하려면 상태 객체 중 하나의 코드만 업데이트하면 됩니다.

먼저, 보다 전통적인 객체 지향 방식으로 상태 패턴을 구현하겠습니다. 그런 다음 Rust에서 좀 더 자연스러운 접근 방식을 사용할 것입니다. 상태 패턴을 사용하여 블로그 포스트 워크플로를 단계적으로 구현해 보겠습니다.

최종 기능은 다음과 같습니다.

  1. 블로그 포스트는 빈 초안으로 시작합니다.
  2. 초안이 완료되면 포스트에 대한 검토가 요청됩니다.
  3. 게시물이 승인되면 게시됩니다.
  4. 승인되지 않은 게시물이 실수로 게시되는 것을 방지하기 위해, 게시된 블로그 게시물만 콘텐츠를 출력하도록 합니다.

게시물에 대해 시도하는 다른 변경 사항은 아무런 영향을 미치지 않아야 합니다. 예를 들어 리뷰를 요청하기 전에 블로그 게시물 초안을 승인하려고 하면, 게시물은 게시되지 않은 초안 상태로 남아 있어야 합니다.

전통적인 객체 지향 스타일 시도

동일한 문제를 해결하기 위해 코드를 구조화하는 방법은 무한하며, 각각 다른 트레이드오프가 있습니다. 이 섹션의 구현은 전통적인 객체 지향 스타일에 더 가깝습니다. Rust로 작성할 수는 있지만, Rust의 강점 중 일부를 활용하지는 않습니다. 나중에, 객체 지향 디자인 패턴을 여전히 사용하지만 객체 지향 경험이 있는 프로그래머에게는 덜 익숙해 보이는 방식으로 구조화된 다른 해결책을 보여줄 것입니다. 두 해결책을 비교하여 다른 언어의 코드와 달리 Rust 코드를 설계할 때의 트레이드오프를 경험해 보겠습니다.

Listing 18-11은 이 워크플로우를 코드 형태로 보여줍니다. 이는 blog라는 이름의 라이브러리 크레이트에서 구현할 API의 사용 예입니다. 아직 blog 크레이트를 구현하지 않았기 때문에 컴파일되지 않습니다.

사용자가 Post::new를 통해 새로운 초안 블로그 게시물을 만들 수 있도록 허용합니다. 또한 텍스트가 블로그 게시물에 추가되도록 허용합니다. 승인 전에 게시물의 내용을 즉시 가져오려고 하면, 게시물이 아직 초안 상태이므로 텍스트를 가져오지 않아야 합니다. 데모 목적으로 코드에 assert_eq!를 추가했습니다. 이 부분에 대한 훌륭한 단위 테스트는 content 메서드가 초안 블로그 게시물에서 빈 문자열을 반환한다고 주장하는 것이지만, 이 예제에서는 테스트를 작성하지 않을 것입니다.

다음으로, 게시물의 검토 요청을 활성화하고, 검토를 기다리는 동안 content이 빈 문자열을 반환하도록 설정합니다. 게시물이 승인을 받으면 게시 상태로 변경되어야 하며, 이는 content이 호출될 때 게시물의 텍스트가 반환됨을 의미합니다.

크레이트에서 우리가 상호작용하는 유일한 타입은 Post 타입입니다. 이 타입은 상태 패턴을 사용하며, 게시물이 될 수 있는 다양한 상태인 초안, 검토, 게시 중 하나를 나타내는 상태 객체를 값으로 가집니다. 한 상태에서 다른 상태로 변경되는 과정은 Post 타입 내부에서 관리됩니다. 상태는 라이브러리 사용자가 Post 인스턴스에 호출한 메서드에 따라 변경되지만, 사용자는 상태 변경을 직접 관리할 필요가 없습니다. 또한 사용자는 검토 전에 게시물을 게시하는 것과 같은 상태 관련 실수를 할 수 없습니다.

검토 요청, 게시물의 상태 변경

다음으로, 게시물의 검토를 요청하는 기능을 추가해야 합니다. 이 기능은 게시물의 상태를 Draft에서 PendingReview로 변경해야 합니다. Listing 18-15에 이 코드가 나와 있습니다.

Post에 request_review에 대한 가변 참조를 인자로 받는 self라는 공개 메소드를 제공합니다. 그런 다음 request_review의 현재 상태에 대해 내부 Post 메소드를 호출합니다. 이 두 번째 request_review 메소드는 현재 상태를 소비하고 새로운 상태를 반환합니다.

request_review 메서드를 State 트레이트에 추가합니다. 이제 이 트레이트를 구현하는 모든 타입은 request_review 메서드를 구현해야 합니다. 메서드의 첫 번째 매개변수로 self, &self, 또는 &mut self를 사용하는 대신, self: Box<Self>을 사용합니다. 이 구문은 해당 메서드가 해당 타입을 보유하는 Box에 대해 호출될 때만 유효하다는 것을 의미합니다. 이 구문은 Box<Self>에 대한 소유권을 가져가며, 이전 상태를 무효화하여 Post의 상태 값이 새로운 상태로 변환될 수 있게 합니다.

기존 상태를 소비하려면 request_review 메소드가 상태 값의 소유권을 가져야 합니다. 여기서 Option의 state 필드에 있는 Post이 중요한 역할을 합니다. Rust는 구조체에 값이 없는 필드를 허용하지 않기 때문에, take 메소드를 호출하여 Some 값을 state 필드에서 꺼내고 그 자리에 None를 두어야 합니다. 이렇게 하면 state 값을 빌리는 대신 Post에서 이동시킬 수 있습니다. 그런 다음, 게시물의 상태 값을 이 작업의 결과인 state로 설정합니다.

state을 None 코드로 직접 설정하는 대신, 임시로 self.state = self.state.request_review();로 설정해야 합니다. 이렇게 해야 state 값에 대한 소유권을 확보할 수 있습니다. 이를 통해 Post가 state로 변환된 후에도 이전 상태 값을 사용할 수 없도록 보장합니다.

Draft의 request_review 메서드는 게시물이 검토를 기다리는 상태를 나타내는 새로운 PendingReview 구조체의 박스화된(boxed) 인스턴스를 반환합니다. PendingReview 구조체도 request_review 메서드를 구현하지만, 어떤 변환도 수행하지 않습니다. 대신, 이미 PendingReview 상태인 게시물에 대해 검토를 요청할 경우에도 PendingReview 상태를 유지해야 하므로 자기 자신을 반환합니다.

이제 우리는 상태 패턴의 장점을 볼 수 있습니다 : request_review 메서드 켜짐 Post #아무래도 똑같다 state 가치. 각 국가는 자신의 규칙에 대한 책임이 있습니다.

content의 Post 메서드는 그대로 두어 빈 문자열 슬라이스를 반환하도록 하겠습니다. 이제 Post 상태와 PendingReview 상태 모두에서 Draft를 가질 수 있지만, PendingReview 상태에서도 동일한 동작을 원합니다. 이제 assert_eq!까지 두 번째 assert_eq! 호출까지 정상적으로 작동합니다.

approve에 추가하여 content 동작 변경

approve 메서드는 request_review 메서드와 유사합니다. Listing 18-16에 나와 있듯이, 현재 상태가 승인될 때 가져야 하는 값으로 state를 설정합니다.

approve 메서드를 State 트레이트에 추가하고, State를 구현하는 새로운 구조체인 Published 상태를 추가합니다.

PendingReview의 request_review이 작동하는 방식과 유사하게, Draft에서 approve 메서드를 호출하면 아무런 효과가 없습니다. 이는 approve가 self를 반환하기 때문입니다. PendingReview에서 approve을 호출하면 Published 구조체의 새로운 박스화된 인스턴스를 반환합니다. Published 구조체는 State 트레이트를 구현하며, request_review 메서드와 approve 메서드 모두에서 게시물이 해당 경우에도 Published 상태를 유지해야 하므로 자기 자신을 반환합니다.

이제 content의 Post 메서드를 업데이트해야 합니다. content에서 반환되는 값이 Post의 현재 상태에 따라 달라지도록 하려면, Post가 자신의 상태에 정의된 content 메서드를 호출하도록 위임(delegation)하는 방식으로 구현합니다. Listing 18-17에 이를 보여줍니다. state

목표는 이 모든 규칙을 State 트레잇을 구현하는 구조체 안에 유지하는 것이므로, content 값의 state 메서드를 호출하고 포스트 인스턴스(즉, self)를 인수로 전달합니다. 그런 다음, content 값의 state 메서드 호출 결과로 반환된 값을 반환합니다.

as_ref 값의 소유권을 얻는 것이 아니라 그 안에 있는 값에 대한 참조를 원하기 때문에 Option에서 Option 메서드를 호출합니다. state은 Option<Box<dyn State>> 타입이므로, as_ref를 호출하면 Option<&Box<dyn State>>이 반환됩니다. as_ref를 호출하지 않았다면, 함수 인수의 빌림된 state에서 &self를 이동시킬 수 없기 때문에 오류가 발생합니다.

그런 다음 unwrap을 호출합니다. Post의 메서드가 실행을 마칠 때 state에 항상 Some 값이 들어 있도록 보장하므로, 여기서는 패닉이 발생하지 않는다고 확신할 수 있습니다. 컴파일러가 이해하지 못하더라도 None 값이 절대 나오지 않는다고 우리가 알고 있는 경우입니다. 9장의 “컴파일러보다 더 많은 정보를 알고 있을 때” 절에서 이런 상황을 살펴보았습니다.

이 시점에서 content을(를) 호출하면, &Box<dyn State>에 대한 deref 강제 변환이 &와 Box에 적용되어, content 메서드가 궁극적으로 State 트레잇을 구현하는 타입에서 호출됩니다. 즉, content을(를) State 트레잇 정의에 추가해야 하며, Listing 18-18에서 보듯이 현재 어떤 상태를 가지고 있는지에 따라 어떤 내용을 반환할지에 대한 로직을 여기에 넣게 됩니다.

content 메서드에 빈 문자열 슬라이스를 반환하는 기본 구현을 추가합니다. content 따라서 Draft와 PendingReview 구조체에서는 content 메서드를 구현할 필요가 없습니다. content Draft Published 구조체는 content 메서드를 오버라이드하여 post.content의 값을 반환합니다. PendingReview Published content post.content 편리하지만, State의 content 메서드가 Post의 내용을 결정하도록 하는 것은 State의 책임과 Post의 책임 사이의 경계를 흐리게 만듭니다. content State Post State Post

왜 열거형(enum)을 사용하지 않는가?

포스트의 다양한 상태를 변형(variant)으로 가진 열거형(enum)을 사용하지 않은 이유에 대해 궁금해했을 수 있습니다. 열거형 사용도 충분히 가능한 해결책입니다. 직접 시도해 보고 최종 결과를 비교하여 어떤 방식이 더 나은지 판단해 보세요. 열거형을 사용하는 방식의 한 가지 단점은, 열거형의 값을 확인하는 모든 곳에서 가능한 모든 변형을 처리하기 위해 match 식 또는 유사한 표현식을 사용해야 한다는 것입니다. 이는 트레이트 객체(trait object)를 사용하는 방식보다 반복적인 코드가 더 많이 발생할 수 있습니다.

상태 패턴 평가하기

Rust는 객체 지향 상태 패턴을 구현하여, 포스트가 각 상태에서 가져야 할 다양한 동작을 캡슐화할 수 있음을 보여 주었습니다. Post의 메서드는 다양한 동작에 대해 알지 못합니다. 코드를 구성한 방식 덕분에, 게시된 포스트가 어떻게 동작할 수 있는지 알기 위해 한 곳만 확인하면 됩니다. 바로 State 구조체에 대한 Published 트레이트 구현입니다.

상태 패턴을 사용하지 않는 대안 구현을 만든다면, match의 메서드에서 Post 식을 사용하거나, 포스트의 상태를 검사하고 동작을 변경하는 메인 코드 부분에 main 식을 사용할 수 있습니다. 이 경우, 포스트가 게시된 상태일 때 발생하는 모든 영향을 이해하려면 여러 곳을 확인해야 합니다.

상태 패턴을 사용하면 Post의 메서드와 Post를 사용하는 곳에서 match 식이 필요하지 않습니다. 또한 새 상태를 추가하려면 새 구조체를 만들고 해당 구조체 한 곳에서만 트레이트 메서드를 구현하면 됩니다.

상태 패턴을 사용한 구현은 추가 기능을 확장하기 쉽습니다. 상태 패턴을 사용하는 코드를 유지보수하는 것이 얼마나 간단한지 확인하려면 다음 제안 중 몇 가지를 시도해 보세요.

  • 추가 reject 게시물의 상태를 변경 하는 방법 PendingReview 뒤로 가기 Draft.
  • 2 통화 필수 approve 국가가 바뀔 수 있기 전에 Published.
  • 게시물이 Draft 상태일 때만 사용자가 텍스트 콘텐츠를 추가할 수 있도록 허용합니다. 힌트: 상태 객체는 콘텐츠에서 변경될 수 있는 부분의 책임을 지되, Post를 수정하는 책임은 지지 않도록 하세요.

상태 패턴의 한 가지 단점은 상태가 상태 간의 전환을 구현하기 때문에 일부 상태가 서로 결합된다는 점입니다. 예를 들어, PendingReview와 Published 사이에 Scheduled 같은 새로운 상태를 추가한다면, PendingReview의 코드를 수정하여 Scheduled로 전환하도록 변경해야 합니다. 새로운 상태를 추가할 때 PendingReview를 변경할 필요가 없으면 작업량이 줄어들지만, 이는 다른 디자인 패턴으로 전환해야 함을 의미합니다.

또 다른 단점은 일부 로직을 중복했다는 점입니다. 중복을 줄이려면 request_review 트레이트의 approve 및 State 메서드에 self을 반환하는 기본 구현을 제공해 볼 수 있습니다. 하지만 이렇게 하면 동작하지 않습니다. State를 트레이트 객체로 사용할 때, 트레이트는 구체적인 self의 타입을 정확히 알 수 없으므로 컴파일 타임에 반환 타입을 결정할 수 없습니다. (이것은 앞서 언급한 dyn 호환성 규칙 중 하나입니다.)

다른 중복은 상기의 유사한 구현을 포함한다. request_review 그리고 approve 메서드 On Post. 두 방법 다 사용 Option::take 와 함께 state 분야의 Post그리고 if state 있습니다. Some, 그들은 같은 방법의 래핑 값의 구현에 위임하고의 새로운 값을 설정 state 결과 필드. 우리는 방법에 많은이 있다면 Post 이 패턴을 따라, 우리는 반복을 제거하기 위해 매크로를 정의하는 것을 고려할 수 있습니다 (참조 “매크로” 무시 챕터 20)

객체 지향 언어에서 정의된 상태 패턴을 그대로 구현하면 Rust의 강점을 최대한 활용하지 못합니다. blog 크레이트에서 적용할 수 있는 몇 가지 변경 사항을 살펴 보겠습니다. 이 변경 사항들은 잘못된 상태와 상태 전이를 컴파일 타임 오류로 만들 수 있습니다.

상태와 동작을 타입으로 인코딩하기

다른 트레이드오프를 얻기 위해 상태 패턴을 다시 생각해 보는 방법을 보여드리겠습니다. 상태와 전환을 완전히 캡슐화하여 외부 코드가 이를 알 수 없도록 하는 대신, 상태를 서로 다른 타입으로 인코딩하겠습니다. 이렇게 하면 Rust의 타입 검사 시스템이 게시된 게시물만 허용되는 곳에서 초안 게시물을 사용하려는 시도를 컴파일러 오류를 통해 방지합니다.

Listing 18-11의 main 첫 부분을 살펴봅시다:

Post::new을 사용하여 여전히 초안 상태에서 새 게시물을 만들 수 있으며, 게시물의 내용에 텍스트를 추가할 수도 있습니다. 하지만 대신, 빈 문자열을 반환하는 content 메서드를 초안 게시물에 두는 대신, 초안 게시물에는 아예 content 메서드가 없도록 하겠습니다. 이렇게 하면 초안 게시물의 내용을 얻으려고 할 때 해당 메서드가 존재하지 않는다는 컴파일러 오류가 발생합니다. 그 결과, 해당 코드가 컴파일되지 않으므로 실수로 프로덕션 환경에서 초안 게시물의 내용을 표시하는 일이 불가능해집니다. Listing 18-19는 Post 구조체와 DraftPost 구조체의 정의 및 각각의 메서드를 보여줍니다.

Post과 DraftPost 구조체 모두 블로그 게시물 텍스트를 저장하는 비공개 content 필드를 가지고 있습니다. 상태 인코딩을 구조체의 타입으로 옮기고 있기 때문에 더 이상 state 필드가 없습니다. Post 구조체는 게시된 게시물을 나타내며, content을 반환하는 content 메서드를 가지고 있습니다.

여전히 Post::new 함수가 있지만, Post의 인스턴스를 반환하는 대신 DraftPost의 인스턴스를 반환합니다. content은 비공개이며 Post를 반환하는 함수가 없기 때문에, 현재 시점에서 Post의 인스턴스를 생성할 수 없습니다.

DraftPost 구조체는 add_text 메서드를 가지고 있으므로 이전처럼 content에 텍스트를 추가할 수 있습니다. 하지만 주의할 점은 DraftPost에 content 메서드가 정의되어 있지 않다는 것입니다. 이제 프로그램은 모든 게시물이 초안 게시물로 시작하도록 보장하며, 초안 게시물의 내용은 표시할 수 없습니다. 이러한 제약 조건을 우회하려는 시도는 컴파일러 오류로 이어집니다.

그렇다면 어떻게 게시된 게시물을 얻을 수 있을까요? 초안 게시물이 게시되기 전에 검토되고 승인되어야 한다는 규칙을 강제하고 싶습니다. 검토 대기 상태의 게시물은 여전히 어떤 내용도 표시해서는 안 됩니다. Listing 18-20에 나와 있듯이, PendingReviewPost 구조체를 추가하고, request_review 구조체에 DraftPost 메서드를 정의하여 PendingReviewPost을 반환하도록 하며, approve 구조체에 PendingReviewPost 메서드를 정의하여 Post을 반환하도록 함으로써 이러한 제약 조건을 구현하겠습니다.

request_review와 approve 메서드는 self의 소유권을 가져가므로, self와 DraftPost 인스턴스를 소모하여 각각 PendingReviewPost과 게시된 PendingReviewPost로 변환합니다. 이렇게 하면 Post에 DraftPost을 호출한 후에도 잔여하는 request_review 인스턴스가 없으며, 그 외의 상태도 마찬가지입니다. PendingReviewPost 구조체에는 content 메서드가 정의되어 있지 않으므로, 그 내용을 읽으려 하면 DraftPost과 마찬가지로 컴파일러 오류가 발생합니다. Post 메서드가 정의된 게시된 content 인스턴스를 얻는 유일한 방법은 approve에 PendingReviewPost 메서드를 호출하는 것이며, PendingReviewPost을 얻는 유일한 방법은 request_review에 DraftPost 메서드를 호출하는 것이므로, 이제 블로그 게시물 워크플로우를 타입 시스템에 인코딩하게 되었습니다.

하지만 main에도 몇 가지 작은 변경 사항이 필요합니다. request_review과 approve 메서드는 호출된 구조체를 수정하는 대신 새로운 인스턴스를 반환하므로, 반환된 인스턴스를 저장하기 위해 let post =과 같은 섀도잉 할당을 추가해야 합니다. 또한 초안 상태와 검토 대기 상태의 게시물 내용이 빈 문자열이라는 단언도 더 이상 사용할 수 없고, 필요하지도 않습니다. 해당 상태의 게시물 내용을 사용하려는 코드는 이제 컴파일할 수 없기 때문입니다. main의 업데이트된 코드는 Listing 18-21에 나와 있습니다.

main를 재할당하기 위해 post에 필요한 변경 사항으로 인해, 이 구현은 더 이상 객체 지향 상태 패턴을 완전히 따르지 않습니다. 상태 간의 변환은 더 이상 Post 구현 내에 완전히 캡슐화되지 않기 때문입니다. 그러나 이로 인한 이점은 타입 시스템과 컴파일 타임에 수행되는 타입 검사 덕분에 잘못된 상태가 이제 불가능해졌다는 것입니다! 이를 통해 게시되지 않은 게시물의 내용 표시와 같은 특정 버그가 프로덕션 환경에 도달하기 전에 발견됩니다.

blog 크레이트에서 Listing 18-21 이후의 상태로, 이 섹션 시작 부분에 제시된 작업을 수행해 보세요. 이 코드 버전의 설계에 대해 어떻게 생각하는지 확인하는 데 도움이 됩니다. 참고로, 일부 작업은 이 설계에서 이미 완료되어 있을 수 있습니다.

Rust는 객체 지향 디자인 패턴을 구현할 수 있지만, 상태를 타입 시스템에 인코딩하는 것과 같은 다른 패턴도 Rust에서 사용할 수 있습니다. 이러한 패턴들은 서로 다른 트레이드오프를 가지고 있습니다. 객체 지향 패턴에 익숙하더라도, Rust의 기능을 활용하기 위해 문제를 다시 생각해 보면 컴파일 타임에 일부 버그를 방지하는 등의 이점을 얻을 수 있습니다. 소유권과 같이 객체 지향 언어에 없는 특정 기능 때문에, 객체 지향 패턴이 항상 Rust에서 최선의 해결책은 아닙니다.

요약

이 장을 읽고 난 후 Rust를 객체 지향 언어라고 생각하든 아니든, 이제 Rust에서 트레이트 객체를 사용해 일부 객체 지향 기능을 활용할 수 있다는 것을 알게 되었습니다. 동적 디스패치는 런타임 성능의 일부 양보를 대가로 코드의 유연성을 높여 줍니다. 이 유연성을 활용하면 코드의 유지보수성을 높이는 데 도움이 되는 객체 지향 패턴을 구현할 수 있습니다. Rust는 소유권과 같이 객체 지향 언어에 없는 다른 기능도 갖추고 있습니다. 객체 지향 패턴이 항상 Rust의 강점을 살리는 최선의 방법은 아니지만, 선택 가능한 옵션 중 하나입니다.

다음으로, Rust의 또 다른 특징인 패턴을 살펴보겠습니다. 패턴은 많은 유연성을 가능하게 하는 기능입니다. 이 책 전반에 걸쳐 패턴을 간략히 살펴봤지만, 아직 그 전체 기능을 확인하지는 못했습니다. 이제 시작해 보겠습니다.
