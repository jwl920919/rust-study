The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

사용 Box<T> 힙에 있는 데이터를 가리키기 위해

가장 직관적인 스마트 포인터는 박스(Box)입니다. 박스의 타입은 Box<T>로 표기합니다. 박스는 데이터를 스택이 아닌 힙에 저장할 수 있게 해줍니다. 스택에 남아 있는 것은 힙 데이터에 대한 포인터입니다. 스택과 힙의 차이에 대해 복습하려면 4장을 참조하세요.

박스는 데이터를 스택 대신 힙에 저장한다는 점을 제외하면 성능 오버헤드가 없습니다. 하지만 박스는 추가적인 기능도 많지 않습니다. 박스는 주로 다음과 같은 상황에서 가장 자주 사용됩니다:

  • 컴파일 시간에 크기를 알 수 없는 타입이 있고, 정확한 크기가 필요한 컨텍스트에서 해당 타입의 값을 사용하려는 경우
  • 대량의 데이터를 가지고 있고 소유권을 이전하되, 그 과정에서 데이터가 복사되지 않도록 보장하고 싶은 경우
  • 값을 소유하되, 특정 타입인지보다는 특정 트레이트를 구현하는 타입인지에만 관심이 있는 경우

첫 번째 상황을 “박스로 재귀 타입 활성화하기”에서 시연하겠습니다. 두 번째 경우에서는 대량의 데이터 소유권을 이전하는 데 시간이 오래 걸릴 수 있습니다. 이는 데이터가 스택 위에서 복사되기 때문입니다. 이 상황에서 성능을 개선하려면 대량의 데이터를 힙에 있는 박스에 저장할 수 있습니다. 그러면 스택 위에서 복사되는 것은 작은 크기의 포인터 데이터만 되고, 해당 포인터가 참조하는 데이터는 힙의 한 위치에 그대로 유지됩니다. 세 번째 경우는 트레이트 객체로 알려져 있으며, 18장의 “공유된 동작을 추상화하기 위한 트레이트 객체 사용”에서는 이 주제를 다룹니다. 따라서 여기서 배우는 내용은 해당 섹션에서 다시 적용하게 됩니다!

Box<T>의 힙 저장 사용 사례를 논의하기 전에, 구문과 Box<T>에 저장된 값에 접근하는 방법을 다루겠습니다.

Listing 15-1은 박스를 사용하여 힙에 i32 값을 저장하는 방법을 보여줍니다.

변수 b을 힙에 할당된 값 5을 가리키는 Box의 값으로 정의합니다. 이 프로그램은 b = 5을 출력합니다. 이 경우, 이 데이터가 스택에 있었다면 접근하는 방식과 유사하게 박스 안의 데이터에 접근할 수 있습니다. 소유권이 있는 값과 마찬가지로, 박스가 스코프를 벗어나면, main의 끝에서 b가 스코프를 벗어나는 것처럼, 해제됩니다. 해제는 박스(스택에 저장됨)와 박스가 가리키는 데이터(힙에 저장됨) 모두에 대해 수행됩니다.

힙에 단일 값만 저장하는 것은 유용하지 않으므로, 이러한 방식으로 박스를 단독으로 사용하는 경우는 드뭅니다. 기본적으로 스택에 저장되는 단일 i32 값과 같은 데이터를 사용하는 것이 대부분의 상황에서 더 적합합니다. 박스가 없으면 정의할 수 없는 타입을 정의할 수 있는 사례를 살펴보겠습니다.

박스를 사용하여 재귀 타입 활성화

재귀 타입의 값은 그 자체의 일부로서 같은 타입의 다른 값을 가질 수 있습니다. 재귀 타입은 Rust가 컴파일 시간에 타입이 차지하는 크기를 알아야 하므로 문제를 일으킵니다. 재귀 타입의 값 중첩은 이론적으로 무한히 계속될 수 있으므로, Rust는 해당 값에 필요한 크기를 알 수 없습니다. 박스는 크기가 정해져 있으므로, 재귀 타입 정의에 박스를 삽입함으로써 재귀 타입을 사용할 수 있게 됩니다.

재귀 타입의 예로 cons 리스트를 살펴보겠습니다. 이는 함수형 프로그래밍 언어에서 흔히 볼 수 있는 데이터 타입입니다. 우리가 정의할 cons 리스트 타입은 재귀를 제외하면 단순합니다. 따라서 이 예제의 개념은 재귀 타입이 포함된 더 복잡한 상황에 직면할 때마다 유용할 것입니다.

Cons List 이해하기

cons list는 Lisp 프로그래밍 언어와 그 방언에서 유래한 데이터 구조로, 중첩된 쌍으로 구성되며 Lisp 버전의 연결 목록(linked list)입니다. 이름은 Lisp에서 두 인수를 받아 새로운 쌍을 생성하는 cons 함수(construct function의 줄임말)에서 왔습니다. 값과 다른 쌍으로 이루어진 쌍에 대해 cons을 호출하면, 재귀적인 쌍으로 이루어진 cons list를 구성할 수 있습니다.

예를 들어, 다음은 1, 2, 3으로 이루어진 1, 2, 3 목록을 포함하는 cons 목록의 의사 코드 표현입니다. 각 쌍은 괄호로 묶여 있습니다.

(1, (2, (3, Nil)))

cons 목록의 각 항목에는 현재 항목의 값과 다음 항목의 값이라는 두 가지 요소가 포함됩니다. 목록의 마지막 항목에는 다음 항목이 없으며, Nil라고 불리는 값만 포함됩니다. cons 목록은 cons 함수를 재귀적으로 호출하여 생성됩니다. 재귀의 기본 경우를 나타내는 표준 이름은 Nil입니다. 참고로, 이는 6장에서 논의된 'null' 또는 'nil' 개념과 동일하지 않으며, 후자는 유효하지 않거나 존재하지 않는 값을 의미합니다.

cons 목록은 Rust에서 일반적으로 사용되는 데이터 구조가 아닙니다. Rust에서 항목 목록을 다룰 때는 대부분의 경우 Vec<T>를 사용하는 것이 더 나은 선택입니다. 더 복잡한 재귀 데이터 형식은 다양한 상황에서 유용하지만, 이 장에서는 cons 목록을 통해 박스가 재귀 데이터 형식을 정의하는 데 어떻게 사용되는지, 큰 방해 요소 없이 살펴볼 수 있습니다.

크기가 알려진 재귀 타입 가져오기

Rust는 재귀적으로 정의된 타입에 대해 얼마나 많은 공간을 할당해야 할지 계산할 수 없으므로, 컴파일러는 다음과 같은 유용한 제안을 포함하여 오류를 보고합니다:

help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
  |
2 |     Cons(i32, Box<List>),
  |               ++++    +

이 제안에서 간접 저장(indirection)이란 값을 직접 저장하는 대신, 값에 대한 포인터를 저장하여 값을 간접적으로 저장하도록 데이터 구조를 변경해야 함을 의미합니다.

왜냐하면 A Box<T> 러스트는 항상 얼마나 많은 공간 a를 알고 Box<T> needs: 포인터의 크기는 가리키는 데이터의 양에 따라 변경되지 않습니다. 즉, Box<T> 내부 The Cons variant 다른 List 직접 가치. Box<T> 다음을 가리킬 것입니다. List 그 값은 힙에 있을 것입니다. Cons variant. 개념적으로, 우리는 여전히 다른 리스트를 가지고 있는 리스트를 가지고 있지만, 이 구현은 이제 서로 내부가 아닌 서로 옆에 아이템을 놓는 것과 같습니다.

Cons 변형에는 i32의 크기加上 박스의 포인터 데이터를 저장할 공간이 필요합니다. Nil 변형은 값을 저장하지 않으므로, Cons 변형보다 스택에서 더 적은 공간을 필요로 합니다. 이제 어떤 List 값이든 i32의 크기加上 박스의 포인터 데이터 크기를 차지한다는 것을 알 수 있습니다. 박스를 사용함으로써 무한한 재귀 체인을 끊었으므로, 컴파일러는 List 값을 저장하는 데 필요한 크기를 계산할 수 있습니다. Figure 15-2는 이제 Cons 변형이 어떻게 보이는지 보여줍니다.

박스는 간접 참조와 힙 할당만 제공합니다. 이 장에서 다룰 다른 스마트 포인터 타입처럼 다른 특별한 기능을 가지고 있지 않습니다. 또한 이러한 특수 기능으로 인한 성능 오버헤드도 없으므로, 간접 참조가 필요한 유일한 기능인 cons 리스트와 같은 경우에 유용할 수 있습니다. 박스의 더 많은 사용 사례는 18장에서 다룹니다.

Box<T> 타입은 Deref 트레잇을 구현하기 때문에 스마트 포인터입니다. 이 트레잇은 Box<T> 값을 참조처럼 취급할 수 있게 합니다. Box<T> 값이 스코프를 벗어나면, 박스가 가리키는 힙 데이터도 Drop 트레잇 구현 덕분에 함께 정리됩니다. 이 두 트레잇은 이 장의 나머지 부분에서 다룰 다른 스마트 포인터 타입이 제공하는 기능에 더욱 중요할 것입니다. 이 두 트레잇을 더 자세히 살펴보겠습니다.
