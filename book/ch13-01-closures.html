The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

클로저

Rust의 클로저는 변수에 저장하거나 다른 함수에 인수로 전달할 수 있는 익명 함수입니다. 클로저를 한 곳에서 정의한 후 다른 곳에서 호출하여 다른 컨텍스트에서 평가할 수 있습니다. 함수와 달리 클로저는 정의된 범위에서 값을 캡처할 수 있습니다. 이러한 클로저 기능이 어떻게 코드 재사용과 동작 커스터마이징을 가능하게 하는지 살펴보겠습니다.

환경 캡처

먼저 나중에 사용하기 위해 정의된 환경에서 값을 캡처하는 클로저 사용법을 살펴보겠습니다. 시나리오는 다음과 같습니다. 가끔씩 저희 T-셔츠 회사는 프로모션으로 메일링 리스트에 있는 사람에게 독점적인 한정판 셔츠를 증정합니다. 메일링 리스트에 있는 사람은 프로필에 좋아하는 색상을 선택적으로 추가할 수 있습니다. 무료 셔츠를 받는 사람이 좋아하는 색상을 설정해 두었다면 그 색상의 셔츠를 받습니다. 좋아하는 색상을 지정하지 않았다면 회사가 현재 가장 많이 보유한 색상의 셔츠를 받습니다.

이를 구현하는 방법에는 여러 가지가 있습니다. 이 예제에서는 enum을 사용할 것입니다. ShirtColor 그 변이가 있습니다 Red 그리고 Blue (단순함을 위해 사용할 수 있는 색상의 수를 제한). 우리는 Inventory 필드 이름을 가진 struct shirts 포함되는 A Vec<ShirtColor> 현재 재고가 있는 셔츠 색상을 나타냅니다. giveaway 에 정의됨 Inventory 무료 셔츠 우승자의 선택 사항인 셔츠 색상 선호도를 가져오고, 그 사람이 얻을 셔츠 색상을 반환합니다. 이 설정은 Listing 13-1에 나와 있습니다.

store에서 정의된 스토어에는 이 한정판 프로모션을 위해 배부할 파란 셔츠 2개와 빨간 셔츠 1개가 남아 있습니다. main를 호출하여 빨간 셔츠를 선호하는 사용자와 선호도가 없는 사용자 각각에 대해 giveaway 메서드를 실행합니다.

다시 말하지만, 이 코드는 다양한 방식으로 구현할 수 있습니다. 여기서는 클로저에 집중하기 위해 giveaway 메서드의 본문에서 클로저를 사용하는 것을 제외하고는 이미 학습한 개념들만 사용했습니다. giveaway 메서드에서는 Option<ShirtColor> 타입의 매개변수로 사용자 설정을 받아 user_preference에 대해 unwrap_or_else 메서드를 호출합니다. unwrap_or_else 메서드는 Option<T>에 대해 표준 라이브러리가 정의한 것입니다. 이 메서드는 인수를 하나 받습니다. 인수가 없고 T 값을 반환하는 클로저입니다(Option<T>의 Some 변형체에 저장된 것과 동일한 타입으로, 이 경우 ShirtColor입니다). Option<T>이 Some 변형체인 경우, unwrap_or_else은 Some 내부의 값을 반환합니다. Option<T>이 None 변형체인 경우, unwrap_or_else은 클로저를 호출하고 클로저가 반환한 값을 반환합니다.

클로저 표현식 || self.most_stocked()을 unwrap_or_else의 인수로 지정합니다. 이 클로저는 자체적으로 매개변수를 받지 않습니다(클로저에 매개변수가 있었다면 두 개의 세로 파이프 사이에 나타났을 것입니다). 클로저의 본문은 self.most_stocked()을 호출합니다. 여기서 클로저를 정의하고 있으며, unwrap_or_else의 구현부는 결과가 필요한 경우 나중에 클로저를 평가합니다.

이 코드를 실행하면 다음과 같이 출력됩니다.

$ cargo run
   Compiling shirt-company v0.1.0 (file:///projects/shirt-company)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.27s
     Running `target/debug/shirt-company`
The user with preference Some(Red) gets Red
The user with preference None gets Blue

한 가지 흥미로운 점은 현재 Inventory 인스턴스의 self.most_stocked()를 호출하는 클로저를 전달했다는 것입니다. 표준 라이브러리는 우리가 정의한 Inventory나 ShirtColor 타입, 또는 이 상황에서 사용하려는 로직을 알 필요가 없습니다. 클로저는 현재 Inventory 인스턴스인 self를 불변 참조로 캡처하고, unwrap_or_else 메서드에 전달한 코드와 함께 사용합니다. 반면 함수는 이런 식으로 환경을 캡처하지 못합니다.

클로저 타입 추론 및 주석

함수와 클로저 사이에는 더 많은 차이점이 있습니다. 클로저는 일반적으로 fn 함수처럼 매개변수의 타입이나 반환 값의 타입을 명시적으로 지정할 필요가 없습니다. 함수에 타입 주석이 필요한 이유는, 해당 타입이 사용자에게 노출되는 명시적 인터페이스의 일부이기 때문입니다. 이 인터페이스를 엄격하게 정의하는 것은 모든 사용자가 함수가 어떤 타입의 값을 사용하고 반환하는지에 대해 합의하도록 보장하는 데 중요합니다. 반면, 클로저는 이러한 방식으로 노출되는 인터페이스에 사용되지 않습니다. 클로저는 변수에 저장되고, 이름을 붙이지 않고 라이브러리의 사용자에게 노출시키지 않은 채로 사용됩니다.

클로저는 일반적으로 임의의 시나리오가 아니라 좁은 컨텍스트 내에서만 짧고 관련이 있습니다. 이러한 제한된 컨텍스트 내에서 컴파일러는 대부분의 변수 타입을 추론하는 것과 유사하게 매개변수 타입과 반환 타입을 추론할 수 있습니다(컴파일러가 클로저 타입 주석을 필요로 하는 경우는 드뭅니다).

변수와 마찬가지로, 엄격히 필요한 것보다 더 자세한 표현을 감수하더라도 명시성과 명확성을 높이려면 타입 주석을 추가할 수 있습니다. 클로저의 타입 주석은 Listing 13-2에 표시된 정의와 같습니다. 이 예제에서는 Listing 13-1에서처럼 클로저를 인수로 전달하는 위치에 정의하는 대신, 클로저를 정의하고 변수에 저장합니다.

타입 주석을 추가하면 클로저의 문법이 함수의 문법과 더 유사해 보입니다. 여기에서는 비교를 위해 매개변수에 1을 더하는 함수와 동일한 동작을 하는 클로저를 정의합니다. 관련 부분을 정렬하기 위해 몇 개의 공백을 추가했습니다. 이는 파이프 기호의 사용과 선택적 구문의 양을 제외하면 클로저 문법이 함수 문법과 유사하다는 점을 보여줍니다.

fn  add_one_v1   (x: u32) -> u32 { x + 1 }
let add_one_v2 = |x: u32| -> u32 { x + 1 };
let add_one_v3 = |x|             { x + 1 };
let add_one_v4 = |x|               x + 1  ;

첫 번째 줄은 함수 정의를, 두 번째 줄은 완전히 주석이 달린 클로저 정의를 보여줍니다. 세 번째 줄에서는 클로저 정의에서 타입 주석을 제거합니다. 네 번째 줄에서는 클로저 본문이 하나의 식만 가지고 있기 때문에 선택 사항인 중괄호를 제거합니다. 이들은 모두 호출될 때 동일한 동작을 생성하는 유효한 정의입니다. add_one_v3과 add_one_v4은 타입이 사용처에서 추론되므로 컴파일하려면 클로저가 평가되어야 합니다. 이는 let v = Vec::new();에 타입 주석을 추가하거나 어떤 타입의 값을 삽입해야 Rust가 타입을 추론할 수 있는 것과 유사합니다. 참조 캡처 또는 소유권 이동

클로저는 세 가지 방법으로 환경에서 값을 캡처할 수 있으며, 이는 함수가 매개변수를 받는 세 가지 방식과 직접적으로 대응합니다. 즉, 불변 빌림, 가변 빌림, 소유권 획득입니다. 클로저는 본문이 캡처된 값을 어떻게 사용하는지에 따라 이 중 어떤 방식을 사용할지 결정합니다.

이 예제는 변수가 클로저 정의에 바인딩될 수 있음을 보여 줍니다. 이후에는 변수 이름 뒤에 괄호를 붙여 함수 이름인 것처럼 클로저를 호출할 수 있습니다.

클로저 borrows_mutably의 정의와 호출 사이에 더 이상 println!이 없다는 점에 유의하세요. borrows_mutably가 정의될 때 list에 대한 가변 참조를 캡처합니다. 클로저가 호출된 후에는 클로저를 다시 사용하지 않으므로 가변 빌로우가 종료됩니다. 클로저 정의와 클로저 호출 사이에 출력용 불변 빌로우는 허용되지 않습니다. 가변 빌로우가 존재할 때 다른 빌로우는 허용되지 않기 때문입니다. 해당 위치에 println!을 추가하여 어떤 오류 메시지가 발생하는지 확인해 보세요!

클로저 본문이 소유권을 엄격하게 필요로 하지 않더라도, 클로저가 환경에서 사용하는 값의 소유권을 갖도록 강제하려면 매개변수 목록 앞에 move 키워드를 사용할 수 있습니다.

이 기법은 새 스레드에 클로저를 전달하여 데이터를 이동하고, 새 스레드가 해당 데이터를 소유하도록 할 때 주로 유용합니다. 16장에서는 병렬성에 대해 다룰 때 스레드를 사용하는 이유를 자세히 논의하겠습니다. 하지만 지금은 move 키워드가 필요한 클로저를 사용하여 새 스레드를 생성하는 과정을 간단히 살펴보겠습니다. Listing 13-6은 벡터를 주 스레드가 아닌 새 스레드에서 출력하도록 수정한 Listing 13-4를 보여줍니다.

새 스레드를 만들고 실행할 클로저를 인수로 전달합니다. 클로저 본문은 목록을 출력합니다. Listing 13-4에서는 목록을 출력하는 데 필요한 최소한의 접근 권한인 불변 참조로 list를 캡처했습니다. 이번 예제에서도 클로저 본문은 불변 참조만 필요하지만, move 키워드를 클로저 앞에 적어 list를 클로저 안으로 이동시켜야 합니다. 메인 스레드가 join을 호출하기 전에 다른 작업을 하면 새 스레드와 메인 스레드 중 어느 쪽이 먼저 끝날지 알 수 없습니다. 메인 스레드가 list의 소유권을 유지한 채 먼저 끝나면 목록이 해제되어 새 스레드의 참조가 무효가 될 수 있습니다. 그래서 컴파일러는 새 스레드에 전달하는 클로저 안으로 list를 이동하도록 요구합니다. move를 제거하거나 새 스레드가 끝난 뒤 메인 스레드에서 list를 사용해 컴파일 오류를 확인해 보세요.

클로저 밖으로 캡처된 값 이동하기

클로저가 정의된 환경에서 값의 참조를 캡처하거나 소유권을 캡처하면(이로 인해 어떤 값이 클로저로 이동되는지가 결정됨), 클로저 본문의 코드는 클로저가 나중에 평가될 때 참조나 값에 어떤 일이 발생하는지를 정의합니다(이로 인해 어떤 값이 클로저 밖으로 이동되는지가 결정됨).

클로저 본문은 다음 중 하나를 수행할 수 있습니다. 캡처된 값을 클로저 밖으로 이동하거나, 캡처된 값을 변경하거나, 값을 이동하거나 변경하지 않거나, 처음부터 환경에서 아무것도 캡처하지 않거나.

클로저가 환경의 값을 캡처하고 처리하는 방식은 클로저가 어떤 트레이트를 구현하는지에 영향을 미칩니다. 트레이트는 함수와 구조체가 사용할 수 있는 클로저의 종류를 지정하는 방법입니다. 클로저 본문이 값을 처리하는 방식에 따라, 클로저는 Fn 트레이트 중 하나, 둘, 또는 세 가지를 모두 자동으로 구현합니다.

  • FnOnce은 한 번만 호출할 수 있는 클로저에 적용됩니다. 모든 클로저는 호출할 수 있으므로 적어도 이 트레이트를 구현합니다. 캡처된 값을 바디 밖으로 이동시키는 클로저는 한 번만 호출할 수 있으므로 FnOnce만 구현하고 다른 Fn 트레이트는 구현하지 않습니다.
  • FnMut은 캡처된 값을 바디 밖으로 이동시키지 않지만 캡처된 값을 변경(mutate)할 수 있는 클로저에 적용됩니다. 이러한 클로저는 두 번 이상 호출할 수 있습니다.
  • Fn은 캡처된 값을 바디 밖으로 이동하지 않고 캡처된 값을 변경하지 않는 클로저, 그리고 환경에서 아무것도 캡처하지 않는 클로저에 적용됩니다. 이러한 클로저는 환경을 변경하지 않고 두 번 이상 호출할 수 있으며, 이는 클로저를 여러 번 동시에 호출하는 경우와 같이 중요합니다.

Listing 13-1에서 사용한 unwrap_or_else의 Option<T> 메서드 정의를 살펴봅시다.

impl<T> Option<T> {
    pub fn unwrap_or_else<F>(self, f: F) -> T
    where
        F: FnOnce() -> T
    {
        match self {
            Some(x) => x,
            None => f(),
        }
    }
}

T은 Option의 Some 변형체 내 값의 타입을 나타내는 제네릭 타입이라는 점을 떠올려 보세요. 이 타입 T은 또한 unwrap_or_else 함수의 반환 타입이기도 합니다. 예를 들어 Option<String>에 대해 unwrap_or_else을 호출하는 코드는 String을 얻게 됩니다.

다음으로, unwrap_or_else 함수에는 추가적인 제네릭 타입 매개변수 F가 있습니다. F 타입은 f라는 이름의 매개변수의 타입이며, 이는 unwrap_or_else를 호출할 때 우리가 제공하는 클로저입니다.

제네릭 타입 F에 지정된 트레이트 바운드는 FnOnce() -> T이며, 이는 F가 한 번만 호출될 수 있고 인수를 받지 않으며 T을 반환해야 함을 의미합니다. 트레이트 바운드에서 FnOnce을 사용하는 것은 unwrap_or_else가 f을 한 번 이상 호출하지 않는다는 제약 조건을 표현합니다. unwrap_or_else의 본문에서 볼 수 있듯이, Option이 Some인 경우 f은 호출되지 않습니다. Option이 None인 경우, f은 한 번 호출됩니다. 모든 클로저가 FnOnce을 구현하므로, unwrap_or_else은 세 가지 종류의 클로저를 모두 수용할 수 있으며 가능한 한 유연합니다.

참고 : 우리가 원하는 것이 환경에서 값을 캡처 할 필요가 없다면, 우리는 함수 중 하나를 구현하는 무언가가 필요한 클로저가 아닌 함수 이름을 사용할 수 있습니다. Fn 특성. 예를 들어, Option<Vec<T>> 가치, 우리는 호출 할 수 있습니다 unwrap_or_else(Vec::new) 값이 비어있는 경우 새 벡터를 가져옵니다 None. 컴파일러는 자동으로 다음 중 하나를 구현합니다. Fn 특성은 함수 정의에 적용됩니다.

이제 슬라이스에 정의된 표준 라이브러리 메서드 sort_by_key를 살펴보고, 이것이 unwrap_or_else와 어떻게 다른지, 그리고 왜 sort_by_key의 트레이트 바운드에 FnMut 대신 FnOnce를 사용하는지 알아보겠습니다. 이 클로저는 현재 고려 중인 슬라이스의 항목에 대한 참조 형태로 하나의 인자를 받고, 정렬할 수 있는 타입의 값을 반환합니다. K 이 함수는 각 항목의 특정 속성에 따라 슬라이스를 정렬할 때 유용합니다. Listing 13-7에서는 Rectangle 인스턴스의 목록을 가지고, sort_by_key을 사용하여 width 속성이 낮은 값에서 높은 값으로 정렬합니다.

반면, Listing 13-8은 환경에서 값을 이동시키기 때문에 FnOnce 트레이트만 구현하는 클로저의 예를 보여줍니다. 컴파일러는 이 클로저를 sort_by_key과 함께 사용하지 못하게 합니다.

이 방법은 작동하지 않으며, sort_by_key가 목록을 정렬할 때 클로저를 몇 번 호출하는지 세려는 억지스럽고 복잡한 시도입니다. 클로저 환경에 있는 String 값 value를 sort_operations 벡터에 넣어 횟수를 세려고 합니다. 클로저가 value를 캡처한 뒤 소유권을 벡터로 옮기므로, 이 클로저는 한 번만 호출할 수 있습니다. 두 번째로 호출하면 넘겨줄 value가 남아 있지 않아 작동하지 않습니다. 따라서 이 클로저는 FnOnce만 구현합니다. 이 코드를 컴파일하면 sort_by_key가 FnMut을 요구하므로 클로저 밖으로 value를 이동할 수 없다는 오류가 발생합니다:

오류는 클로저 본문에서 value을 환경 밖으로 이동하는 줄을 가리킵니다. 이 문제를 해결하려면 클로저 본문이 환경 밖으로 값을 이동하지 않도록 변경해야 합니다. 환경에 카운터를 유지하고 클로저 본문에서 그 값을 증가시키는 것이 클로저 호출 횟수를 세는 더 직관적인 방법입니다. Listing 13-9의 클로저는 sort_by_key과 함께 작동합니다. 왜냐하면 이 클로저는 num_sort_operations 카운터에 대한 가변 참조만 캡처하므로 한 번 이상 호출할 수 있기 때문입니다.
