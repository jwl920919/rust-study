The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

RefCell<T> 내부 가변성 패턴(Interior Mutability Pattern)

내부 가변성(Interior mutability)은 Rust에서 데이터에 대한 불변 참조가 존재하는 경우에도 데이터를 변경할 수 있게 해 주는 디자인 패턴입니다. 일반적으로 이러한 동작은 빌림 규칙에 의해 허용되지 않습니다. 데이터를 변경하기 위해 이 패턴은 데이터 구조 내부에서 unsafe 코드를 사용하여 Rust의 변경과 빌림을 관리하는 일반적인 규칙을 우회합니다. unsafe 코드는 컴파일러가 규칙을 검사하는 대신 개발자가 수동으로 규칙을 검사하고 있음을 컴파일러에 알리는 역할을 하며, unsafe 코드에 대한 자세한 내용은 20장에서 다룹니다.

컴파일러가 이를 보장할 수 없더라도, 빌림 규칙이 런타임에 준수될 수 있음을 확인할 수 있는 경우에만 내부 가변성 패턴을 사용하는 유형을 사용할 수 있습니다. 이때 포함된 unsafe 코드는 안전한 API로 래핑되며, 외부 유형은 여전히 불변입니다.

내부 가변성 패턴을 따르는 RefCell<T> 타입을 살펴봄으로써 이 개념을 탐구해 보겠습니다.

런타임에서 빌림 규칙 강제

Rc<T>과 달리, RefCell<T> 타입은 보유 중인 데이터에 대한 단일 소유권을 나타냅니다. 그렇다면 RefCell<T>와 Box<T> 같은 타입의 차이는 무엇일까요? 4장에서 배운 빌림 규칙을 떠올려 보겠습니다.

  • 어떤 시점에서도 가변 참조 하나 또는 불변 참조 여러 개를 가질 수 있지만, 둘을 동시에 가질 수는 없습니다.
  • 참조는 항상 유효해야 합니다.

참조와 Box<T>를 사용하면 빌림 규칙의 불변 조건이 컴파일 시간에 강제됩니다. RefCell<T>를 사용하면 이러한 불변 조건이 런타임에 강제됩니다. 참조를 사용할 때 이 규칙을 위반하면 컴파일러 오류가 발생합니다. RefCell<T>를 사용할 때 이 규칙을 위반하면 프로그램이 패닉하여 종료됩니다.

빌림 규칙을 컴파일 시간에 검사하는 장점은 개발 과정에서 오류를 더 일찍 발견할 수 있고, 모든 분석이 미리 완료되므로 런타임 성능에 영향을 미치지 않는다는 것입니다. 이러한 이유로 빌림 규칙을 컴파일 시간에 검사하는 것이 대부분의 경우 최선의 선택이며, 이것이 Rust의 기본 동작입니다.

대신 빌림 규칙을 런타임에 검사하는 이점은 컴파일 시간 검사에서는 허용되지 않던 특정 메모리 안전 시나리오를 허용할 수 있다는 것입니다. Rust 컴파일러와 같은 정적 분석은 본질적으로 보수적입니다. 코드의 일부 속성은 코드 분석만으로 감지하는 것이 불가능합니다. 가장 유명한 예는 할팅 문제(Halting Problem)인데, 이는 이 책의 범위를 벗어났지만 흥미로운 연구 주제입니다.

일부 분석은 불가능하기 때문에, Rust 컴파일러가 코드가 소유권 규칙을 준수하는지 확신할 수 없다면 올바른 프로그램을 거부할 수 있습니다. 이것이 보수적인 이유입니다. Rust가 잘못된 프로그램을 받아들이면 사용자는 Rust가 제공하는 보장을 신뢰할 수 없게 됩니다. 반면 Rust가 올바른 프로그램을 거부하면 프로그래머는 불편을 겪지만, 치명적인 문제는 발생하지 않습니다. RefCell<T> 타입은 코드가 빌림 규칙을 따르는 것을 확신하지만 컴파일러가 이를 이해하고 보장하지 못할 때 유용합니다.

Rc<T>와 마찬가지로, RefCell<T>는 단일 스레드 시나리오에서만 사용할 수 있으며, 멀티스레드 컨텍스트에서 사용하려고 하면 컴파일 시간 오류가 발생합니다. 16장에서 멀티스레드 프로그램에서 RefCell<T>의 기능을 얻는 방법에 대해 다룰 것입니다.

다음은 Box<T>, Rc<T> 또는 RefCell<T>를 선택하는 이유를 요약한 것입니다.

  • Rc<T>는 동일한 데이터에 대한 여러 소유자를 가능하게 합니다. Box<T> 및 RefCell<T>에는 단일 소유자가 있습니다.
  • Box<T>는 컴파일 시간에 검사되는 불변 또는 가변 빌림을 허용합니다. Rc<T>는 컴파일 시간에 검사되는 불변 빌림만 허용합니다. RefCell<T>는 런타임에 검사되는 불변 또는 가변 빌림을 허용합니다.
  • RefCell<T>는 런타임에 가변 빌림을 허용하므로, RefCell<T>이 불변이어도 RefCell<T> 내부의 값을 변경할 수 있습니다.

불변 값 내부에서 값을 변경하는 것은 내부 가변성 패턴입니다. 내부 가변성이 유용한 상황과 그 원리를 살펴보겠습니다.

내부 가변성 사용

빌림 규칙에 따라, 불변 값을 가지고 있을 때 가변 빌림을 할 수 없습니다. 예를 들어, 다음 코드는 컴파일되지 않습니다:

fn main() {
    let x = 5;
    let y = &mut x;
}

이 코드를 컴파일하려고 하면 다음과 같은 오류가 발생합니다:

$ cargo run
   Compiling borrowing v0.1.0 (file:///projects/borrowing)
error[E0596]: cannot borrow `x` as mutable, as it is not declared as mutable
 --> src/main.rs:3:13
  |
3 |     let y = &mut x;
  |             ^^^^^^ cannot borrow as mutable
  |
help: consider changing this to be mutable
  |
2 |     let mut x = 5;
  |         +++

For more information about this error, try `rustc --explain E0596`.
error: could not compile `borrowing` (bin "borrowing") due to 1 previous error

그러나 값이 자신의 메서드에서 스스로를 변경하되, 다른 코드에는 불변으로 보이는 것이 유용한 상황이 있습니다. 값의 메서드 외부에서는 값을 변경할 수 없습니다. RefCell<T>를 사용하는 것은 내부 가변성을 얻는 한 가지 방법이지만, RefCell<T>은 빌림 규칙을 완전히 우회하지 않습니다. 컴파일러의 빌림 검사기는 이러한 내부 가변성을 허용하며, 빌림 규칙은 런타임에 검사됩니다. 규칙을 위반하면 컴파일러 오류 대신 panic!가 발생합니다.

RefCell<T>를 사용하여 불변 값을 변경할 수 있는 실용적인 예제를 살펴보고, 이것이 왜 유용한지 확인해 보겠습니다.

모의 객체로 테스트하기

테스트 중에는 프로그래머가 특정 동작을 관찰하고 올바르게 구현되었는지 확인하기 위해 한 타입을 다른 타입으로 대체하는 경우가 있습니다. 이러한 대체 타입을 테스트 더블(test double)이라고 합니다. 영화 제작에서 스턴트 더블이 배우를 대신해 특히 어려운 장면을 수행하는 것과 같은 의미로 이해할 수 있습니다. 테스트 더블은 테스트를 실행할 때 다른 타입을 대신합니다. 목 객체(mock object)는 테스트 중 발생하는 내용을 기록하여 올바른 동작이 수행되었는지 확인할 수 있도록 하는 테스트 더블의 한 종류입니다.

Rust는 다른 언어에서 말하는 객체와 동일한 의미의 객체를 가지고 있지 않으며, 일부 다른 언어처럼 표준 라이브러리에 목 객체 기능이 내장되어 있지도 않습니다. 하지만 목 객체와 동일한 목적을 수행하는 구조체를 만들 수 있습니다.

다음은 테스트할 시나리오입니다. 최대 값에 대해 현재 값을 추적하고, 현재 값이 최대 값에 얼마나 근접했는지에 따라 메시지를 보내는 라이브러리를 만들 것입니다. 예를 들어 이 라이브러리는 사용자가 허용된 API 호출 수에 대한 할당량을 추적하는 데 사용할 수 있습니다.

라이브러리는 값이 최대치에 얼마나 근접했는지와 언제 어떤 메시지를 보내야 하는지를 추적하는 기능만 제공합니다. 이 라이브러리를 사용하는 애플리케이션은 메시지를 전송하는 메커니즘을 제공해야 합니다. 애플리케이션은 사용자에게 메시지를 직접 표시하거나, 이메일을 보내거나, 문자 메시지를 보내거나, 다른 작업을 수행할 수 있습니다. 라이브러리는 이러한 세부 사항을 알 필요가 없습니다. 필요한 것은 우리가 제공하는 Messenger 트레이트를 구현한 것뿐입니다. MessengerListing 15-20은 라이브러리 코드를 보여줍니다.

이 코드의 중요한 부분 중 하나는 Messenger 트레이트가 self에 대한 불변 참조와 메시지 텍스트를 인자로 받는 send이라는 메서드를 하나 가지고 있다는 것입니다. 이 트레이트는 목 객체가 실제 객체와 동일한 방식으로 사용될 수 있도록 구현해야 하는 인터페이스입니다. 다른 중요한 부분은 LimitTracker의 set_value 메서드 동작을 테스트하고 싶다는 것입니다. value 매개변수에 전달할 값을 변경할 수 있지만, set_value은 어설션을 수행할 수 있는 값을 반환하지 않습니다. Messenger 트레이트를 구현하는 어떤 것과 max의 특정 값으로 LimitTracker을 생성하면, value에 서로 다른 숫자를 전달할 때 메신저가 적절한 메시지를 보내도록 지시받는다고 말할 수 있어야 합니다.

send을 호출할 때 이메일이나 문자 메시지를 보내는 대신, 전송하라는 메시지를 단순히 기록만 하는 모의 객체가 필요합니다. LimitTracker의 새로운 인스턴스를 생성하고, 이 모의 객체를 사용하는 set_value를 만든 다음, LimitTracker의 set_value 메서드를 호출한 뒤, 모의 객체가 우리가 기대하는 메시지를 가지고 있는지 확인할 수 있습니다. Listing 15-21은 이를 위해 모의 객체를 구현하려는 시도를 보여 주지만, 빌림 검사기는 이를 허용하지 않습니다.

이 테스트 코드는 MockMessenger 구조체를 정의합니다. 이 구조체는 sent_messages 필드를 가지며, Vec 또는 String 값의 벡터로 전송하도록 지시받은 메시지를 추적합니다. 또한 new 연관 함수를 정의하여, 빈 메시지 목록으로 시작하는 새로운 MockMessenger 값을 생성하는 것이 편리하도록 합니다. 그런 다음 Messenger 트레이트를 MockMessenger에 구현하여, MockMessenger을 LimitTracker에 전달할 수 있게 합니다. send 메서드의 정의에서, 매개변수로 전달된 메시지를 받아 MockMessenger 목록인 sent_messages에 저장합니다.

테스트에서는 LimitTracker이 value을 max 값의 75퍼센트보다 큰 값으로 설정하도록 지시받았을 때 발생하는 일을 테스트합니다. 먼저, 메시지 목록이 비어 있는 상태에서 시작하는 새로운 MockMessenger을 생성합니다. 그런 다음, 새로운 LimitTracker을 생성하고 새로운 MockMessenger에 대한 참조와 100인 max 값을 전달합니다. LimitTracker의 set_value 메서드를 100의 75퍼센트보다 큰 값인 80으로 호출합니다. 그런 다음, MockMessenger이 추적하는 메시지 목록에 이제 하나의 메시지가 포함되어야 한다고 어설션합니다.

그러나 여기에서 보여지듯이, 이 테스트에는 한 가지 문제가 있습니다:

$ cargo test
   Compiling limit-tracker v0.1.0 (file:///projects/limit-tracker)
error[E0596]: cannot borrow `self.sent_messages` as mutable, as it is behind a `&` reference
  --> src/lib.rs:58:13
   |
58 |             self.sent_messages.push(String::from(message));
   |             ^^^^^^^^^^^^^^^^^^ `self` is a `&` reference, so it cannot be borrowed as mutable
   |
help: consider changing this to be a mutable reference in the `impl` method and the `trait` definition
   |
 2 ~     fn send(&mut self, msg: &str);
 3 | }
...
56 |     impl Messenger for MockMessenger {
57 ~         fn send(&mut self, message: &str) {
   |

For more information about this error, try `rustc --explain E0596`.
error: could not compile `limit-tracker` (lib test) due to 1 previous error

메시지를 추적하도록 MockMessenger을 수정할 수 없습니다. send 메서드가 self에 대한 불변 참조를 받기 때문입니다. 또한, 에러 텍스트의 제안대로 impl 메서드와 트레이트 정의 모두에서 &mut self을 사용하라는 제안을 따를 수도 없습니다. 테스트를 위해만 Messenger 트레이트를 변경하고 싶지 않습니다. 대신, 기존 설계와 함께 테스트 코드가 올바르게 작동하는 방법을 찾아야 합니다.

이것은 내부 가변성(interior mutability)이 도움이 될 수 있는 상황입니다! sent_messages을 RefCell<T> 안에 저장하고, 그러면 send 메서드가 sent_messages을 수정하여 확인한 메시지를 저장할 수 있게 됩니다. 목록 15-22는 그 모습을 보여줍니다.

sent_messages 필드는 이제 RefCell<Vec<String>> 대신 Vec<String> 타입입니다. new 함수에서, 빈 벡터 주위에 새로운 RefCell<Vec<String>> 인스턴스를 생성합니다.

send 메서드의 구현에서, 첫 번째 매개변수는 여전히 트레이트 정의와 일치하는 self의 불변 빌로우입니다. self.sent_messages의 RefCell<Vec<String>>에서 borrow_mut을 호출하여 RefCell<Vec<String>> 내부의 값, 즉 벡터에 대한 가변 참조를 얻습니다. 그런 다음, 벡터에 대한 가변 참조에서 push을 호출하여 테스트 중에 전송된 메시지를 추적할 수 있습니다.

마지막으로 수정해야 할 부분은 어설션입니다. 내부 벡터에 몇 개의 항목이 있는지 확인하려면 borrow의 RefCell<Vec<String>>을 호출하여 벡터에 대한 불변 참조를 가져옵니다.

이제 RefCell<T>를 사용하는 방법을 살펴보았으니, 내부 작동 방식을 자세히 알아봅시다!

런타임에서 빌림 추적

불변 참조와 가변 참조를 생성할 때는 각각 &과 &mut 구문을 사용합니다. RefCell<T>의 경우, borrow과 borrow_mut 메서드를 사용하는데, 이들은 RefCell<T>에 속하는 안전 API의 일부입니다. borrow 메서드는 스마트 포인터 타입인 Ref<T>을 반환하고, borrow_mut 메서드는 스마트 포인터 타입인 RefMut<T>을 반환합니다. 두 타입 모두 Deref을 구현하므로, 일반 참조처럼 다룰 수 있습니다.

RefCell<T>은 현재 활성인 Ref<T>과 RefMut<T> 스마트 포인터의 수를 추적합니다. borrow을 호출할 때마다, RefCell<T>은 활성인 불변 빌로우의 수를 증가시킵니다. Ref<T> 값이 스코프를 벗어나면, 불변 빌로우의 수는 1 감소합니다. 컴파일 타임 빌로우 규칙과 마찬가지로, RefCell<T>은 어떤 시점에서도 여러 불변 빌로우 또는 하나의 가변 빌로우를 허용합니다.

이러한 규칙을 위반하려고 하면, 참조의 경우 컴파일러 오류가 발생하지 않고 RefCell<T>의 구현이 런타임에 패닉을 일으킵니다. Listing 15-23은 Listing 15-22의 send 구현을 수정한 것입니다. 우리는 의도적으로 동일한 스코프에서 두 개의 가변 빌림이 활성화되도록 하여, RefCell<T>가 런타임에 이를 방지하는 것을 보여주고자 합니다.

one_borrow 변수에 RefMut<T> 메서드가 반환하는 borrow_mut 스마트 포인터를 저장합니다. 그런 다음 two_borrow 변수에 동일한 방식으로 또 다른 가변 빌림을 생성합니다. 이는 동일한 스코프에서 두 개의 가변 참조를 만드는 것으로 허용되지 않습니다. 라이브러리의 테스트를 실행하면 Listing 15-23의 코드는 오류 없이 컴파일되지만, 테스트는 실패합니다:

가변 데이터의 다중 소유자 허용

RefCell<T>를 사용하는 일반적인 방법은 Rc<T>와 함께 사용하는 것입니다. Rc<T>를 사용하면 특정 데이터의 소유자가 여러 개가 될 수 있지만, 해당 데이터에 대한 접근은 불변(immutable)으로만 가능합니다. Rc<T>를 포함하는 RefCell<T>를 가지고 있다면, 여러 소유자가 존재하면서도 변경할 수 있는 값을 얻을 수 있습니다!
