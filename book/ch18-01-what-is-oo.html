The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

객체 지향 언어의 특성

프로그래밍 커뮤니티에서는 어떤 기능이 있어야 해당 언어를 객체 지향으로 볼 수 있는지에 대해 합의가 이루어져 있지 않습니다. Rust는 OOP를 포함한 다양한 프로그래밍 패러다임의 영향을 받았습니다. 예를 들어, 13장에서는 함수형 프로그래밍에서 유래한 기능들을 살펴보았습니다. 논쟁의 여지가 있지만, OOP 언어들은 객체, 캡슐화, 상속이라는 공통적인 특성을 공유합니다. 이제 각 특성이 무엇을 의미하는지, 그리고 Rust가 이를 지원하는지 살펴봅시다.

데이터와 동작을 포함하는 객체

에리히 가마, 리처드 헬름, 랄프 존슨, 존 블리시즈(애덤스-웨슬리, 1994)의 저서 Design Patterns: Elements of Reusable Object-Oriented Software는 통상 The Gang of Four 책이라고 불리며, 객체 지향 디자인 패턴의 목록을 담고 있습니다. 이 책은 객체 지향 프로그래밍(OOP)을 다음과 같이 정의합니다:

객체 지향 프로그램은 객체로 구성됩니다. 객체는 데이터와 그 데이터를 조작하는 프로시저를 모두 패키징합니다. 이러한 프로시저는 일반적으로 메소드 또는 오퍼레이션이라고 불립니다.

이 정의를 적용하면 Rust는 객체 지향 언어입니다. struct와 enum은 데이터를 가지며, impl 블록은 struct와 enum에 메소드를 제공합니다. 메소드를 가진 struct와 enum은 객체라고 불리지는 않지만, Gang of Four의 객체 정의에 따라 동일한 기능을 제공합니다.

구현 세부 정보를 숨기는 캡슐화

OOP와 일반적으로 연관되는 또 다른 측면은 캡슐화입니다. 캡슐화란 객체의 구현 세부 정보가 해당 객체를 사용하는 코드에서 접근할 수 없음을 의미합니다. 따라서 객체와 상호작용하는 유일한 방법은 공개된 API를 사용하는 것입니다. 객체를 사용하는 코드는 객체의 내부에 직접 접근하여 데이터나 동작을 변경할 수 없어야 합니다. 이를 통해 프로그래머는 객체를 사용하는 코드를 변경할 필요 없이 객체의 내부를 변경하고 리팩토링할 수 있습니다.

7장에서 캡슐화를 제어하는 방법에 대해 논의했습니다. pub 키워드를 사용하여 코드 내의 어떤 모듈, 타입, 함수, 메서드를 공개할지 결정할 수 있으며, 기본적으로 나머지는 모두 비공개입니다. 예를 들어, AveragedCollection 구조체를 정의할 수 있습니다. 이 구조체는 i32 값의 벡터를 포함하는 필드를 가질 수 있습니다. 또한, 벡터 내 값들의 평균을 포함하는 필드도 가질 수 있습니다. 즉, 누군가가 필요할 때마다 평균을 계산할 필요가 없다는 뜻입니다. 다시 말해, AveragedCollection는 계산된 평균을 캐시해 줍니다. Listing 18-1에는 AveragedCollection 구조체의 정의가 나와 있습니다.

구조체는 다른 코드가 사용할 수 있도록 pub로 표시되어 있지만, 구조체 내부의 필드는 비공개로 유지됩니다. 이 경우 값이 목록에서 추가되거나 제거될 때마다 평균도 업데이트되도록 보장해야 하므로 중요합니다. 이를 위해 Listing 18-2에 나와 있듯이 구조체에 add, remove, average 메서드를 구현합니다.

공개 메서드 add, remove, average는 AveragedCollection 인스턴스의 데이터에 접근하거나 수정하는 유일한 방법입니다. list에 add 메서드를 사용하여 항목을 추가하거나 remove 메서드를 사용하여 항목을 제거할 때, 각 메서드의 구현은 average 필드를 업데이트하는 작업을 처리하는 비공개 update_average 메서드를 호출합니다.

list와 average 필드를 비공개로 유지함으로써, 외부 코드가 list 필드에 직접 항목을 추가하거나 제거할 수 없도록 합니다. 그렇지 않으면 average가 변경될 때 list 필드가 동기화되지 않을 수 있습니다. average 메서드는 average 필드의 값을 반환하여, 외부 코드가 평균을 읽을 수는 있지만 수정할 수는 없도록 합니다. average

AveragedCollection 구조체의 구현 세부 사항을 캡슐화했기 때문에, 향후 데이터 구조와 같은 측면을 쉽게 변경할 수 있습니다. 예를 들어, HashSet<i32> 필드에 Vec<i32> 대신 list를 사용할 수 있습니다. add, remove, average 공개 메서드의 시그니처가 동일하게 유지되는 한, AveragedCollection를 사용하는 코드는 변경할 필요가 없습니다. 만약 list을 공개로 만들었다면, 상황이 달라질 수 있습니다. HashSet<i32>와 Vec<i32>는 항목을 추가하고 제거하는 메서드가 다르기 때문에, 외부 코드가 list를 직접 수정하고 있었다면 변경이 필요할 가능성이 높습니다.

캡슐화가 객체 지향 언어로 간주되기 위한 필수 요소라면, Rust는 그 요구 사항을 충족합니다. 코드의 다른 부분에 pub를 사용할지 여부를 선택할 수 있기 때문에 구현 세부 사항을 캡슐화할 수 있습니다.

타입 시스템으로서의 상속과 코드 공유로서의 상속

상속은 한 개체가 다른 개체의 정의에서 요소를 물려받아, 다시 정의하지 않고도 부모 개체의 데이터와 동작을 얻을 수 있게 하는 메커니즘입니다.

언어가 객체 지향적이려면 상속이 필수적이라면, Rust는 그런 언어가 아닙니다. 매크로를 사용하지 않고 부모 구조체의 필드와 메서드 구현을 상속받는 구조체를 정의할 수 있는 방법은 없습니다.

그러나 프로그래밍 도구상자에서 상속을 사용하는 데 익숙하다면, 처음부터 상속을 사용하려는 이유에 따라 Rust에서 다른 해결책을 사용할 수 있습니다.

상속을 선택하는 주된 이유는 두 가지입니다. 하나는 코드 재사용입니다. 한 타입에 대해 특정 동작을 구현한 후, 상속을 통해 다른 타입에서도 그 구현을 재사용할 수 있습니다. Rust에서는 트레이트 메서드의 기본 구현을 사용하여 제한된 방식으로 이를 수행할 수 있습니다. Listing 10-14에서 summarize 트레이트에 Summary 메서드의 기본 구현을 추가했을 때를 떠올려 보세요. Summary 트레이트를 구현하는 모든 타입은 추가 코드가 없어도 summarize 메서드를 사용할 수 있습니다. 이는 메서드 구현을 가진 부모 클래스와 해당 메서드 구현을 상속받은 자식 클래스의 관계와 유사합니다. 또한 summarize 트레이트를 구현할 때 Summary 메서드의 기본 구현을 재정의할 수도 있는데, 이는 부모 클래스에서 상속받은 메서드 구현을 자식 클래스에서 재정의하는 것과 비슷합니다.

상속을 사용하는 또 다른 이유는 타입 시스템과 관련이 있습니다. 자식 타입을 부모 타입과 동일한 위치에서 사용할 수 있도록 하는 것입니다. 이를 다형성(polymorphism)이라고도 하며, 특정 특성을 공유하는 경우 런타임에 여러 개체를 서로 대체할 수 있음을 의미합니다.

다형성

많은 사람에게 다형성은 상속과 동의어입니다. 하지만 실제로 다형성은 여러 타입의 데이터로 동작할 수 있는 코드를 지칭하는 더 일반적인 개념입니다. 상속의 경우, 이러한 타입은 일반적으로 하위 클래스입니다.

Rust는 대신 제네릭을 사용하여 다양한 가능한 타입을 추상화하고, 트레이트 바운드를 통해 해당 타입이 제공해야 할 것에 제약을 부과합니다. 이를 때때로 경계 있는 매개변수적 다형성(bounded parametric polymorphism)이라고 합니다.

Rust는 상속을 제공하지 않음으로써 다른 트레이드오프를 선택했습니다. 상속은 종종 필요한 것보다 더 많은 코드를 공유할 위험이 있습니다. 서브클래스는 항상 부모 클래스의 모든 특성을 공유해야 하는 것은 아니지만, 상속을 사용하면 그렇게 됩니다. 이는 프로그램의 설계를 덜 유연하게 만들 수 있습니다. 또한 서브클래스에 적용되지 않아 의미가 없거나 오류를 일으킬 수 있는 메서드를 호출할 가능성도 생깁니다. 게다가 일부 언어는 단일 상속만 허용하여(서브클래스가 하나의 클래스에서만 상속할 수 있음을 의미) 프로그램 설계의 유연성을 더욱 제한합니다.

이러한 이유로 Rust는 런타임에 다형성을 달성하기 위해 상속 대신 트레이트 객체를 사용하는 다른 접근 방식을 취합니다. 트레이트 객체가 어떻게 작동하는지 살펴보겠습니다.
