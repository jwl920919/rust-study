The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

비동기(async)를 활용한 동시성 적용

이 섹션에서는 16장에서 스레드로 해결했던 동일한 동시성 문제에 비동기(async)를 적용합니다. 이미 해당 장에서 핵심 개념에 대해 충분히 다루었으므로, 이 섹션에서는 스레드와 퓨처(future)의 차이점에 초점을 맞춥니다.

많은 경우, 비동기(async)를 사용하여 동시성을 처리하는 API는 스레드를 사용하는 API와 매우 유사합니다. 그러나 다른 경우에는 상당한 차이가 있습니다. 스레드와 비동기 간에 API가 유사해 보일지라도 동작 방식이 종종 다르며, 거의 항상 성능 특성도 다릅니다.

지금까지 살펴본 바와 같이, async와 스레드는 서로 다른 문법을 사용하지만 비슷한 결과를 제공합니다. join 핸들에 join을 호출하는 대신 await를 사용하고, sleep 호출도 await로 처리하는 방식입니다. await join sleep

더 큰 차이점은 이 작업을 수행하기 위해 별도의 운영체제 스레드를 생성할 필요가 없다는 점입니다. 사실, 여기서 태스크를 생성할 필요도 없습니다. async 블록은 익명 future로 컴파일되므로, 각 루프를 async 블록에 넣고 런타임이 trpl::join 함수를 사용하여 둘 다 완료될 때까지 실행하도록 할 수 있습니다.

다음에서 “모든 실 이 끝나기 를 기다리면서” 무시 제 16 장에서, 우리는 방법을 사용하는 방법을 보여 주었다 join 상기 방법은 The method JoinHandle 당신이 부를 때 반환되는 유형 std::thread::spawn. 그 trpl::join 함수는 비슷하지만, 미래를 위한 함수입니다. 두 개의 미래를 주면, 그것은 하나의 새로운 미래를 만들어냅니다. 그 미래를 출력하는 튜플은 한 번 전달한 각 미래의 출력을 포함합니다. 둘 다 complete. 따라서 Listing 17-8에서 우리는 trpl::join 둘 다 기다리기 fut1 그리고 fut2 완료합니다. 우리는 하지 않음 대기중 fut1 그리고 fut2 하지만 그 대신 우리가 만들어가는 미래는 trpl::join. 우리는 출력을 무시합니다, 왜냐하면 그것은 단지 두 개의 단위 값을 포함하는 튜플이기 때문입니다.

이제 매번 정확히 동일한 순서를 볼 수 있습니다. 이는 스레드와 목록 17-7의 trpl::spawn_task에서 확인한 것과 매우 다릅니다. 그 이유는 trpl::join 함수가 공평하기(fair) 때문입니다. 즉, 각 future를 동일한 빈도로 확인하고 번갈아 가며 처리하며, 다른 future가 준비되어 있으면 한 future가 앞서 달리지 못하게 합니다. 스레드의 경우 운영 체제가 어떤 스레드를 확인하고 얼마나 오래 실행할지 결정합니다. 비동기 Rust의 경우 런타임이 어떤 태스크를 확인하는지 결정합니다. (실제로 비동기 런타임은 내부적으로 병렬성 관리를 위해 운영 체제 스레드를 사용할 수 있으므로, 공정성을 보장하는 것은 런타임에 더 많은 작업을 요구할 수 있지만 여전히 가능합니다!) 런타임은 모든 작업에 대해 공정성을 보장할 의무가 없으며, 공정성을 원하든 원하지 않든 선택할 수 있도록 다양한 API를 제공하는 경우가 많습니다.

future를 대기하는 방식에 대한 다음 변형 중 일부를 시도해 보고 그 결과를 확인해 보세요:

  • 루프 중 하나 또는 둘 다의 async 블록을 제거합니다.
  • 각 async 블록을 정의한 직후 즉시 대기합니다.
  • 첫 번째 루프만 async 블록으로 감싸고, 두 번째 루프의 본문 이후에 생성된 future를 대기합니다.

추가 과제로, 코드를 실행하기 전에 각 경우에 출력이 무엇인지 예측해 보세요!

메시지 전달을 사용하여 두 태스크 간에 데이터 전송

future 간에 데이터를 공유하는 것도 익숙할 것입니다. 이번에는 message passing을 다시 사용하지만, type과 함수의 비동기 버전을 사용할 것입니다. 스레드 기반과 future 기반 동시성 간의 주요 차이점 중 일부를 설명하기 위해, 16장의 "메시지 전달을 통해 스레드 간에 데이터 전송" 섹션에서 했던 것과 약간 다른 경로를 따르겠습니다. Listing 17-9에서는 별도의 태스크를 생성하지 않고, 단순히 하나의 async 블록으로 시작합니다.

여기서 우리는 16장에서 스레드와 함께 사용한 다중 생산자, 단일 소비자 채널 API의 비동기 버전인 trpl::channel을 사용합니다. 이 API의 비동기 버전은 스레드 기반 버전과 약간 다릅니다. 불변 수신기가 아닌 가변 수신기 rx를 사용하며, recv 메서드는 값을 직접 반환하는 대신 await해야 하는 future를 생성합니다. 이제 보내는 쪽에서 받는 쪽으로 메시지를 보낼 수 있습니다. 별도의 스레드나 태스크를 생성할 필요가 없다는 점에 유의하세요. 단순히 rx.recv 호출을 await하기만 하면 됩니다.

synchronous 동기화 Receiver::recv 방법 std::mpsc::channel 이 메시지를 수신 할 때까지 블록. trpl::Receiver::recv 메소드는 비동기이기 때문에 그렇지 않습니다. 차단하는 대신 메시지가 수신되거나 채널의 전송 측이 닫힐 때까지 제어권을 런타임으로 되돌려줍니다. 대조적으로, 우리는 send 호출, 그것은 차단하지 않기 때문에. 그것은 필요하지 않습니다, 때문에 채널로 보내는 것은 무제한입니다.

참고: 이 비동기 코드는 모두 trpl::block_on 호출 내의 async 블록에서 실행되므로, 내부의 모든 코드는 차단을 피할 수 있습니다. 그러나 블록 외부의 코드는 block_on 함수가 반환될 때까지 차단됩니다. 이것이 trpl::block_on 함수의 핵심 목적입니다. 특정 비동기 코드 집합에서 어디를 차단할지 선택할 수 있게 해주며, 이를 통해 동기 코드와 비동기 코드 간 전환 지점을 결정할 수 있습니다.

이 예제에 대해 두 가지를 주목하세요. 첫째, 메시지는 즉시 도착합니다. 둘째, 여기에서 future를 사용하지만 아직 동시성이 발생하지 않습니다. Listing의 모든 작업은 future가 관여하지 않는 경우와 마찬가지로 순차적으로 수행됩니다.

Listing 17-10에 표시된 것처럼, 일련의 메시지를 보내고 그 사이에 sleep을 호출하여 첫 번째 부분을 다루어 보겠습니다.

메시지를 보내는 것 외에도 메시지를 받아야 합니다. 이 경우 들어오는 메시지의 개수를 알고 있으므로 rx.recv().await를 네 번 호출하여 수동으로 처리할 수 있습니다. 하지만 실제 환경에서는 일반적으로 도착할 메시지의 개수가 알 수 없으므로, 더 이상 메시지가 없음을 확인하기까지 계속 대기해야 합니다.

Listing 16-10에서, 우리는 for 동기 채널로부터 수신된 모든 항목을 처리하기 위해 루프합니다. 러스트는 아직 a를 사용할 방법이 없습니다. for 루프와 함께 asynchronous하게 생산된 그러나 일련의 항목, 그래서 우리는 우리가 전에 본 적이 없는 루프를 사용 해야: while let 조건부 루프입니다. 이것은 루프 버전의 if let 우리가 본 건축은 "Control Flow를 사용하여 제어 if let 그리고 let...else” 무시 6 장의 섹션. 지정하는 패턴이 값과 일치하는 한 루프는 계속 실행됩니다.

rx.recv 호출은 future를 생성하며, 우리는 이를 await합니다. 런타임은 future가 준비될 때까지 일시 중지합니다. 메시지가 도착하면 future는 Some(message)로 해석됩니다. 채널이 닫히면 메시지가 도착했는지 여부에 관계없이 future는 None로 해석되어 더 이상 값이 없음을 나타내므로, 폴링(polling), 즉 await를 중단해야 합니다.

while let 루프는 이 모든 것을 하나로 묶어 줍니다. rx.recv().await 호출 결과가 Some(message)이면 메시지에 접근할 수 있으며, if let와 마찬가지로 루프 본문에서 이를 사용할 수 있습니다. 결과가 None이면 루프가 종료됩니다. 루프가 한 번 완료될 때마다 다시 await 지점에 도달하므로, 런타임은 다음 메시지가 도착할 때까지 다시 일시 중지합니다.

이제 코드는 성공적으로 모든 메시지를 보내고 받습니다. 불행히도 여전히 몇 가지 문제가 있습니다. 첫째, 메시지는 0.5초 간격으로 도착하지 않습니다. 프로그램 시작 후 2초(2,000밀리초) 뒤에 한꺼번에 도착합니다. 둘째, 이 프로그램은 절대 종료되지 않습니다! 대신 새 메시지를 영원히 기다립니다. ctrl-C를 사용하여 종료해야 합니다.

하나의 async 블록 내에서 코드는 선형적으로 실행됩니다

각 메시지 사이에 지연이 발생하기보다는 전체 지연 후에 메시지가 한꺼번에 들어오는 이유를 살펴봅시다. 주어진 async 블록 내에서 await 키워드가 코드에 나타나는 순서는 프로그램 실행 시 실행되는 순서와 동일합니다.

Listing 17-10에는 비동기 블록이 하나만 있으므로 그 안의 모든 작업은 순차적으로 실행됩니다. 여전히 동시성이 발생하지 않습니다. tx.send 호출이 모두 실행되며, 이 사이에 trpl::sleep 호출과 그에 따른 await 지점들이 섞여 있습니다. 그런 다음 while let 루프가 await 호출의 await 지점들을 차례로 처리하기 시작합니다. recv

각 메시지 사이에 수면 지연이 발생하는, 우리가 원하는 동작을 얻으려면 Listing 17-11에서 보인 것처럼 tx과 rx 작업을 각각 별도의 비동기 블록에 넣어야 합니다. 그러면 런타임이 Listing 17-8에서와 마찬가지로 trpl::join를 사용하여 각 작업을 독립적으로 실행할 수 있습니다. 다시 한번 강조하지만, 우리는 개별 future가 아니라 trpl::join 호출의 결과를 await합니다. 만약 개별 future를 순서대로 await했다면, 결국 순차적인 흐름으로 되돌아가게 되며, 이는 우리가 피하고자 하는 상황입니다. 하지 않음 할.

Listing 17-11의 업데이트된 코드를 사용하면, 메시지는 2초 후에 한꺼번에 출력되는 대신 500밀리초 간격으로 출력됩니다.

소유권을 비동기 블록으로 이동하기

그러나 이 프로그램은 여전히 종료되지 않습니다. 이는 while let 루프가 trpl::join와 상호작용하는 방식 때문입니다.

  • trpl::join에서 반환되는 future는 전달된 두 future가 모두 완료된 후에만 완료됩니다.
  • tx_fut future는 vals에서 마지막 메시지를 전송한 후 수면을 마친 시점에 완료됩니다.
  • rx_fut future는 while let 루프가 끝날 때까지 완료되지 않습니다.
  • while let 루프는 rx.recv이 None를 반환할 때까지 끝나지 않습니다.
  • rx.recv를 대기하면 채널의 다른 쪽 끝이 닫힌 후에만 None가 반환됩니다.
  • 채널은 rx.close를 호출하거나 발신자 측인 tx이 드롭되는 경우에만 닫힙니다.
  • rx.close를 어디에서도 호출하지 않으며, tx은 trpl::block_on로 전달되는 최외단 비동기 블록이 종료될 때까지 드롭되지 않습니다.
  • trpl::join의 완료에 차단되어 있으므로 블록을 끝낼 수 없으며, 이는 이 목록의 맨 위로 돌아가는 것과 같습니다.

지금 메시지를 보내는 async 블록은 tx을 빌립니다. 메시지를 보내는 데 소유권이 필요하지 않기 때문입니다. 반면 tx를 이동하면 해당 블록이 끝날 때 값이 drop됩니다. 13장의 참조 캡처 또는 소유권 이동 절에서 클로저에 move 키워드를 사용하는 방법을 배웠습니다. 또 16장의 스레드에서 move 클로저 사용하기 절에서 살펴봤듯이, 스레드를 다룰 때는 데이터를 클로저 안으로 옮겨야 하는 경우가 많습니다. async 블록에도 같은 원리가 적용되므로 move 키워드는 클로저에서와 마찬가지로 async 블록에서도 작동합니다.

Listing 17-12에서, 메시지를 보내는 데 사용되는 블록을 async에서 async move로 변경합니다.

이 버전의 코드를 실행하면 마지막 메시지를 보내고 받은 후 정상적으로 종료됩니다. 다음으로, 여러 개의 future에서 데이터를 보내려면 무엇을 변경해야 하는지 살펴보겠습니다.

여러 future를 join! 매크로로 결합하기

이 async 채널은 다중 생산자(multiple-producer) 채널이기도 하므로, 예제 17-13에서 보인 것처럼 여러 future에서 메시지를 보내려면 clone에 tx을 호출할 수 있습니다.

첫째, 우리는 복제 tx, 만들기 tx1 첫 번째 비동기 블록 바깥으로 이동합니다. tx1 우리가 전에 했던 것처럼 그 블록으로 tx. 그런 다음 나중에 원본을 이동합니다. tx 으로 A 새로운 async block은 약간 더 느린 지연에 더 많은 메시지를 보내는 곳입니다. 우리는 이 새로운 async 블록을 async 블록 다음에 메시지를 수신하기 위해 넣었지만, 메시지 이전에도 보낼 수 있습니다. 열쇠는 선물이 생성되는 순서가 아니라 선물이 기다려지는 순서입니다.

메시지를 보내는 두 async 블록 모두 async move 블록이어야 합니다. 그래야 tx과 tx1가 해당 블록이 끝나면 drop됩니다. 그렇지 않으면 처음부터 겪었던 동일한 무한 루프에 빠지게 됩니다.

마지막으로 추가된 future를 처리하기 위해 trpl::join에서 trpl::join!로 전환합니다. join! 매크로는 컴파일 타임에 future의 수가 알려진 경우, 임의의 수의 future를 await할 수 있습니다. future의 수가 알려지지 않은 컬렉션을 await하는 방법은 이 장의 후반부에서 다룹니다.

이제 두 전송 future에서 보내는 모든 메시지를 볼 수 있습니다. 전송 future는 전송 후 각각 약간 다른 지연을 사용하므로, 메시지도 서로 다른 간격으로 수신됩니다.

received 'hi'
received 'more'
received 'from'
received 'the'
received 'messages'
received 'future'
received 'for'
received 'you'

future 간에 메시지를 전달하여 데이터를 보내는 방법, async 블록 안의 코드가 순차적으로 실행되는 방식, 소유권을 async 블록으로 이동하는 방법, 그리고 여러 future를 join하는 방법을 살펴보았습니다. 다음으로, 런타임이 다른 태스크로 전환할 수 있도록 알려주는 방법과 그 이유를 논의해 보겠습니다.
