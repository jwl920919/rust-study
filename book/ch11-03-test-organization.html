The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

시험 기관

이 장의 시작 부분에서 언급했듯이, 테스트는 복잡한 분야이며, 서로 다른 사람들이 서로 다른 용어와 조직을 사용합니다. 러스트 커뮤니티는 두 가지 주요 범주의 측면에서 테스트에 대해 생각합니다. 단위 테스트와 통합 테스트. 단위 테스트는 작고 더 집중되어 있으며, 한 번에 하나의 모듈을 분리하여 테스트하고 개인 인터페이스를 테스트 할 수 있습니다. 통합 테스트는 전적으로 라이브러리 외부에 있으며 다른 외부 코드와 동일한 방식으로 코드를 사용합니다. 공용 인터페이스 만 사용하고 잠재적으로 여러 모듈을 테스트 할 수 있습니다.

두 종류의 테스트를 작성 하는 것은 라이브러리의 조각이 개별적으로 그리고 함께 기대 하는 것을 수행 하 고 있는지 확인 하는 데 중요 합니다.

단위 테스트

단위 테스트의 목적은 코드의 나머지 부분과 격리된 각 코드 단위를 테스트하여 코드가 어디에 있고 예상대로 작동하지 않는지 신속하게 찾아내는 것입니다. 테스트하는 코드를 각 파일의 src 디렉토리에 단위 테스트를 넣습니다. 이 컨벤션은 각 파일에 tests라는 모듈을 만들어 테스트 기능을 포함하고 cfg(test)로 모듈에 주석을 달기 위한 것입니다.

이름 * tests 모듈 및 #[cfg(test)]

이름 * #[cfg(test)] 상기 주석은 Annotation on the tests module은 러스트에게 테스트 코드를 컴파일하고 실행할 때만 러스트에게 알려줍니다. cargo test당신이 달릴 때 cargo build. 테스트가 포함되어 있지 않기 때문에 라이브러리를 빌드하고 결과적으로 컴파일 된 아티팩트의 공간을 절약하려는 경우 컴파일 시간을 절약합니다. 통합 테스트가 다른 디렉토리에 있기 때문에 필요하지 않습니다. #[cfg(test)] 주석. 그러나 단위 테스트는 코드와 동일한 파일로 진행되므로 #[cfg(test)] 컴파일된 결과에 포함되지 않도록 지정해야 합니다.

이 장의 첫 번째 섹션에서 새로운 adder 프로젝트를 생성했을 때 Cargo는 다음 코드를 생성했습니다.

파일명: src/lib.rs

pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        let result = add(2, 2);
        assert_eq!(result, 4);
    }
}

자동으로 생성된 tests 모듈, 속성 cfg 스탠드 for 설정 그리고 러스트에게 다음 항목은 특정 설정 옵션이 주어졌을 때만 포함되어야 한다고 말합니다. 이 경우, 설정 옵션은 다음과 같습니다. test러스트는 컴파일 및 실행 테스트를 위해 러스트에서 제공합니다. cfg 속성, Cargo는 우리가 적극적으로 테스트를 실행하는 경우에만 테스트 코드를 컴파일합니다. cargo test. 이것은 주석이 달린 기능 이외에 이 단위 안에 있을지도 모른 어떤 조수 기능든지, 포함합니다 #[test].

개인 기능 테스트

테스트 커뮤니티 내에서 비공개 함수가 직접 테스트되어야 하는지에 대한 논쟁이 있습니다. 다른 언어들은 비공개 함수를 테스트하는 것을 어렵거나 불가능하게 만듭니다. 어떤 테스트 이데올로기를 고수하든, 러스트의 개인 정보 보호 규칙을 통해 비공개 함수를 테스트할 수 있습니다. 비공개 함수 internal_adder를 사용하여 Listing 11-12의 코드를 고려하십시오.

유의할 점 internal_adder 기능은 것과 같이 표를 하지 않습니다 pub. 테스트는 단지 러스트 코드이고, tests module은 또 다른 모듈입니다. 우리가 논의 한 것처럼 "모듈 트리에서 항목을 참조하는 경로" 무시 , 자식 모듈의 항목은 조상 모듈의 항목을 사용할 수 있습니다. 이 테스트에서, 우리는에 속하는 모든 항목을 가지고 tests 범위로 단위의 부모 use super::*그리고 테스트가 호출할 수 있습니다.The test can call. internal_adder. 비공개 함수를 테스트해야 한다고 생각하지 않는다면, 러스트에는 그렇게 하도록 강요하는 것이 없습니다.

통합 테스트

러스트에서는 통합 테스트가 라이브러리의 외부에 완전히 있습니다. 다른 코드와 마찬가지로 라이브러리를 사용합니다. 즉, 라이브러리의 공개 API의 일부인 함수만 호출할 수 있습니다. 그 목적은 라이브러리의 많은 부분이 제대로 작동하는지 테스트하는 것입니다. 통합될 때 올바르게 작동하는 코드 단위에 문제가 있을 수 있으므로 통합 코드의 테스트 커버리지도 중요합니다. 통합 테스트를 만들려면 먼저 테스트 디렉토리가 필요합니다.

이름 * 시험 전화번호부

통합 테스트의 하위 모듈

더 많은 통합 테스트를 추가하면 테스트 디렉토리에 더 많은 파일을 만들어 구성 할 수 있습니다. 예를 들어 테스트 기능을 테스트하는 기능으로 그룹화 할 수 있습니다. 앞에서 언급했듯이 테스트 디렉토리의 각 파일은 별도의 크레이트로 컴파일되어 최종 사용자가 크레이트를 사용하는 방식을보다 밀접하게 모방하기 위해 별도의 범위를 만드는 데 유용합니다. 그러나 이는 테스트 디렉토리의 파일이 동일한 동작을 공유하지 않는다는 것을 의미합니다.

의 다양한 동작 The different action of 시험 디렉토리 파일은 여러 통합 테스트 파일에서 사용할 수 있는 도우미 함수 집합이 있을 때 가장 눈에 띄며 다음 단계의 단계를 수행하려고 합니다. "모듈을 다른 파일로 분리" 무시 7 장의 섹션은 공통 모듈로 추출합니다. 예를 들어, 테스트/common.rs 함수 이름을 지정하려면To set a function named setup 그 안에, 우리는 몇 가지 코드를 추가할 수 있습니다 setup 우리는 여러 테스트 파일에서 여러 테스트 함수를 호출 할:

파일 이름: tests/common.rs

mod common;

fn it_adds_two() {

    let result = add_two(2);
    assert_eq!(result, 4);
}

mod common; 선언은 Listing 7-21에서 설명한 모듈 선언과 동일합니다. 그런 다음 테스트 함수에서 common::setup() 함수를 호출할 수 있습니다.

Binary Crate에 대한 통합 테스트

만약 우리의 프로젝트가 src/main.rs 파일만 포함하고 src/lib.rs 파일이 없는 바이너리 크레이트라면, 우리는 tests 디렉토리에 통합 테스트를 만들 수 없고 use 문으로 src/main.rs 파일에 정의된 함수를 범위 안에 가져올 수 없습니다. 오직 라이브러리 크레이트만이 다른 크레이트들이 사용할 수 있는 함수를 노출시킵니다. 바이너리 크레이트들은 그들 스스로 실행되도록 되어 있습니다.

이것은 바이너리를 제공하는 러스트 프로젝트가 src/lib.rs 파일에 있는 논리를 호출하는 간단한 src/main.rs 파일을 가지고 있는 이유 중 하나입니다. 이 구조를 사용하여 통합 테스트는 use로 라이브러리 크레이트를 테스트하여 중요한 기능을 사용할 수 있도록 할 수 있습니다. 중요한 기능이 작동하면 src/main.rs 파일의 소량의 코드도 작동하며 소량의 코드도 테스트할 필요가 없습니다.

요약

러스트의 테스트 기능은 코드를 변경하더라도 예상대로 계속 작동하도록 하기 위해 코드가 어떻게 작동해야 하는지를 지정하는 방법을 제공합니다. 단위 테스트는 라이브러리의 다른 부분을 개별적으로 연습하고 개인 구현 세부 사항을 테스트 할 수 있습니다. 통합 테스트는 라이브러리의 많은 부분이 제대로 작동하는지 확인하고 라이브러리의 공개 API를 사용하여 외부 코드가 사용하는 것과 같은 방식으로 코드를 테스트합니다. 러스트의 유형 시스템과 소유권 규칙은 여전히 버그를 방지하는 데 도움이 되지만, 여전히 버그를 방지하는 데 도움이 됩니다.
