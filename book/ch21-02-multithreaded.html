The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

단일 스레드 서버에서 다중 스레드 서버로

현재 서버는 각 요청을 순서대로 처리하므로, 첫 번째 연결의 처리가 완료될 때까지 두 번째 연결을 처리하지 않습니다. 서버가 점점 더 많은 요청을 받게 되면, 이러한 직렬 실행 방식은 점점 더 비효율적이 됩니다. 처리에 시간이 오래 걸리는 요청을 받으면, 이후의 요청들은 새 요청이 빠르게 처리될 수 있더라도 긴 요청이 완료될 때까지 기다려야 합니다. 이 문제를 해결해야 하지만, 먼저 실제 동작을 살펴볼 것입니다.

느린 요청 시뮬레이션

느리게 처리되는 요청이 현재 서버 구현의 다른 요청에 어떤 영향을 미치는지 살펴보겠습니다. Listing 21-10은 /sleep 요청을 처리하도록 구현했으며, 이 요청을 받으면 서버는 5초 동안 대기한 후 응답을 반환하는 느린 응답을 시뮬레이션합니다.

케이스가 세 개가 되면서 if에서 match로 전환했습니다. request_line의 슬라이스에 대해 명시적으로 패턴 매칭을 수행해야 문자열 리터럴 값과 비교할 수 있습니다. match는 동등성 메서드처럼 자동 참조 및 역참조를 수행하지 않기 때문입니다.

첫 번째 arm은 Listing 21-9의 if 블록과 동일합니다. 두 번째 arm은 /sleep 경로에 대한 요청을 일치시킵니다. 해당 요청을 수신하면 서버는 5초간 대기한 후 성공적인 HTML 페이지를 렌더링합니다. 세 번째 arm은 Listing 21-9의 else 블록과 동일합니다.

우리 서버가 얼마나 원시적인지 알 수 있습니다. 실제 라이브러리는 훨씬 간결한 방식으로 여러 요청의 인식을 처리합니다!

cargo run을(를) 실행하여 서버를 시작합니다. 그런 다음 두 개의 브라우저 창을 엽니다. 하나는 http://127.0.0.1:7878이고, 다른 하나는 http://127.0.0.1:7878/sleep입니다. 이전과 마찬가지로 / URI를 여러 번 입력하면 빠르게 응답하는 것을 볼 수 있습니다. 하지만 /sleep을(를) 입력한 뒤 /을(를) 다시 로드하면, /은(는) sleep이(가) 5초 동안 완전히 수면을 마칠 때까지 기다린 후에야 로드되는 것을 확인할 수 있습니다.

느린 요청 뒤에 다른 요청이 쌓이는 것을 방지하기 위해 사용할 수 있는 여러 기법이 있습니다. 17장에서 사용했던 비동기(async)를 사용하는 것도 그중 하나입니다. 이번 장에서 구현할 기법은 스레드 풀입니다.

스레드 풀을 활용한 처리량 향상

스레드 풀은 작업을 처리할 준비를 마치고 대기 중인 생성된 스레드의 그룹입니다. 프로그램이 새로운 작업을 받으면 풀 내의 스레드 중 하나를 해당 작업에 할당하고, 그 스레드가 작업을 처리합니다. 풀의 나머지 스레드는 첫 번째 스레드가 처리하는 동안 들어오는 다른 작업을 처리할 수 있도록 대기합니다. 첫 번째 스레드가 작업을 처리를 마치면 유휴 상태의 스레드 풀로 반환되어 새로운 작업을 처리할 준비를 합니다. 스레드 풀을 사용하면 연결을 동시에 처리할 수 있어 서버의 처리량을 높일 수 있습니다.

DoS 공격으로부터 서버를 보호하기 위해 풀 내의 스레드 수를 적은 숫자로 제한합니다. 만약 프로그램이 들어오는 각 요청마다 새로운 스레드를 생성한다면, 서버에 1,000만 건의 요청을 보내는 누군가가 서버의 모든 자원을 소진하여 요청 처리를 완전히 중단시키는 혼란을 야기할 수 있습니다.

그러면 무제한 스레드를 생성하는 대신 풀에서 대기 중인 스레드 수가 고정됩니다. 들어오는 요청은 처리를 위해 풀로 전송됩니다. 풀은 들어오는 요청의 대기열을 유지합니다. 풀의 각 스레드는 이 대기열에서 요청을 팝업하고 요청을 처리한 다음 다른 요청을 위해 대기열에 요청합니다. 이 디자인을 통해 최대까지 처리할 수 있습니다. N 경쟁을 요구하며, N 스레드 수입니다. 각 스레드가 장기 실행 요청에 응답하는 경우 후속 요청은 여전히 대기열에 백업 할 수 있지만 해당 지점에 도달하기 전에 처리 할 수있는 장기 실행 요청의 수가 증가했습니다.

이 기법은 웹 서버의 처리량을 향상시키는 여러 방법 중 하나일 뿐입니다. 포크/조인 모델, 단일 스레드 비동기 I/O 모델, 멀티스레드 비동기 I/O 모델과 같은 다른 옵션도 탐색해 볼 수 있습니다. 이 주제에 관심이 있다면 다른 솔루션에 대해 더 자세히 읽어보고 구현해 볼 수 있습니다. Rust와 같은 저수준 언어에서는 이러한 모든 옵션이 가능합니다.

스레드 풀을 구현하기 전에, 풀을 사용하는 방식이 어떻게 되어야 하는지 이야기해 보겠습니다. 코드를 설계할 때 클라이언트 인터페이스를 먼저 작성하면 설계를 안내하는 데 도움이 됩니다. 코드의 API를 원하는 호출 방식에 맞게 구조화하여 작성하고, 기능을 구현한 후에 공개 API를 설계하는 대신 그 구조 내에서 기능을 구현합니다.

12장의 프로젝트에서 테스트 주도 개발을 사용한 것과 유사하게, 여기서는 컴파일러 주도 개발을 사용할 것입니다. 원하는 함수를 호출하는 코드를 작성한 뒤, 컴파일러가 보고하는 오류를 확인하여 다음에 무엇을 변경해야 코드가 정상적으로 동작하는지 결정합니다. 다만, 그 전에 시작점으로 사용하지 않을 방식을 먼저 살펴보겠습니다.

각 요청마다 스레드 생성

먼저, 모든 연결에 대해 새 스레드를 생성한다면 코드가 어떻게 보일지 살펴보겠습니다. 앞서 언급했듯이, 무제한으로 스레드를 생성할 수 있는 문제 때문에 이것이 최종 계획은 아닙니다. 하지만 먼저 동작하는 멀티스레드 서버를 만드는 출발점입니다. 이후 스레드 풀을 개선 사항으로 추가하면, 두 가지 해결책을 비교하기가 더 쉬워집니다.

Listing 21-11은 main 반복문 내에서 각 스트림을 처리하기 위해 새 스레드를 생성하도록 for를 변경하는 내용을 보여줍니다.

16장에서 배운 것처럼, thread::spawn는 새 스레드를 생성한 뒤 해당 스레드에서 클로저의 코드를 실행합니다. 이 코드를 실행하고 브라우저에서 /sleep을 로드한 뒤, 다른 두 개의 브라우저 탭에서 /를 요청하면, /sleep이 완료될 때까지 기다리지 않고 / 요청이 처리되는 것을 확인할 수 있습니다. 그러나 앞서 언급했듯이, 제한 없이 새 스레드를 생성하기 때문에 결국 시스템이 과부하 상태에 빠집니다.

17장에서 배운 내용처럼, 비동기(async)와 대기(await)가 특히 빛을 발하는 상황이 바로 이것입니다. 스레드 풀을 구축하면서 비동기 방식으로 구현하면 어떤 점이 달라지거나 같을지 생각해 보세요.

유한한 수의 스레드 생성

이제 execute에 ThreadPool 메서드가 없기 때문에 오류가 발생합니다. “유한한 수의 스레드 만들기” 섹션에서 스레드 풀에 thread::spawn와 유사한 인터페이스를 제공하기로 결정했습니다. 또한, execute 함수를 구현하여 전달받은 클로저를 풀 내의 유휴 스레드 중 하나에 전달해 실행하도록 하겠습니다.

ThreadPool의 execute 메서드가 클로저를 매개변수로 받도록 정의하겠습니다. 13장의 “클로저에서 캡처한 값 이동하기” 절에서 보았듯이, 클로저를 매개변수로 받을 때는 Fn, FnMut, FnOnce 세 트레이트 중 하나를 지정할 수 있습니다. 여기서는 어떤 종류의 클로저가 필요한지 정해야 합니다. 표준 라이브러리의 thread::spawn과 비슷하게 구현할 것이므로, 해당 함수 시그니처의 트레이트 바운드를 살펴보겠습니다:

pub fn spawn<F, T>(f: F) -> JoinHandle<T>
    where
        F: FnOnce() -> T,
        F: Send + 'static,
        T: Send + 'static,

여기서 우리가 주목해야 하는 것은 F 타입 매개변수입니다. T 타입 매개변수는 반환 값과 관련이 있지만, 우리는 그것에 관심을 두지 않습니다. spawn가 FnOnce를 트레이트 바운드로 사용하여 F에 적용하고 있음을 볼 수 있습니다. 이는 아마도 우리가 원하는 방식일 것입니다. 왜냐하면 결국 execute에서 받은 인수를 spawn에 전달할 것이기 때문입니다. 요청을 실행하는 스레드는 해당 요청의 클로저를 한 번만 실행하므로, 이는 FnOnce의 'Once'와 일치합니다. 따라서 우리는 Once이 우리가 사용해야 할 트레이트라는 점에 대해 더욱 확신을 가질 수 있습니다. FnOnce

F 타입 매개변수에는 Send 트레이트 바운드와 'static 라이프타임 바운드가 있으며, 이는 우리의 상황에 유용합니다. 클로저를 한 스레드에서 다른 스레드로 전달해야 하므로 Send이 필요하고, 스레드가 실행하는 데 얼마나 걸리는지 알 수 없으므로 'static이 필요합니다. 이러한 바운드를 가진 F 타입의 제네릭 매개변수를 받는 execute 메서드를 ThreadPool에 만들어 보겠습니다:

이 () 뒤에 FnOnce를 사용하는 이유는, 이 FnOnce가 매개변수를 받지 않고 단위 타입(())을 반환하는 클로저를 나타내기 때문입니다. 함수 정의와 마찬가지로 반환 타입은 서명에서 생략할 수 있지만, 매개변수가 없더라도 괄호는 필수입니다.

채널을 통해 스레드에 요청 보내기

다음으로 다룰 문제는 thread::spawn에 전달되는 클로저가 아무것도 하지 않는다는 점입니다. 현재는 execute 메서드에서 실행할 클로저를 전달받습니다. 하지만 thread::spawn을 생성할 때, Worker의 각 인스턴스를 만들 때마다 실행할 클로저를 제공해야 합니다. ThreadPool

방금 만든 Worker 구조체가 ThreadPool에 있는 큐에서 실행할 코드를 가져와 해당 코드를 스레드로 보내 실행하도록 하고 싶습니다.

16장에서 배운 채널은 두 스레드 간에 통신하는 간단한 방법으로, 이 사용 사례에 적합합니다. 채널을 작업 대기열로 사용하고, execute이 ThreadPool에서 Worker 인스턴스로 작업을 보내면, 해당 인스턴스가 작업을 자신의 스레드로 전달합니다. 계획은 다음과 같습니다.

  1. ThreadPool는 채널을 생성하고 발신자를 유지합니다.
  2. 각 Worker는 수신기를 계속 보유합니다.
  3. 채널을 통해 보내고 싶은 클로저를 저장할 새로운 Job 구조체를 만들겠습니다.
  4. execute 메서드는 실행하려는 작업을 송신기를 통해 보냅니다.
  5. 스레드에서 Worker는 수신기를 통해 반복하며, 수신한 모든 작업의 클로저를 실행합니다.

ThreadPool::new에서 채널을 만들고 ThreadPool 인스턴스가 송신기를 보유하도록 하는 것으로 시작하겠습니다. 이는 목록 21-16에 나와 있습니다. Job 구조체는 현재 아무것도 저장하지 않지만, 채널을 통해 보낼 항목의 타입이 됩니다.

ThreadPool::new에서 새 채널을 만들고 풀이 송신기를 보유하도록 합니다. 이 코드는 성공적으로 컴파일됩니다.

스레드 풀이 채널을 만들 때 채널의 수신기를 각 Worker에 전달해 보겠습니다. Worker 인스턴스가 생성하는 스레드에서 수신기를 사용해야 하므로, 클로저에서 receiver 매개변수를 참조하겠습니다. 목록 21-17의 코드는 아직 컴파일되지 않습니다.

몇 가지 작고 간단한 변경을 했습니다. 수신기를 Worker::new에 전달하고, 클로저 내부에서 이를 사용합니다.

이 코드는 receiver를 여러 Worker 인스턴스에 전달하려고 합니다. 16장에서 배운 것처럼, Rust가 제공하는 채널 구현은 다중 생산자, 단일 소비자 방식입니다. 따라서 이 코드를 수정하기 위해 채널의 소비자 쪽을 단순히 복제할 수 없습니다. 또한 여러 소비자에게 메시지를 여러 번 보내는 것도 원하지 않습니다. 여러 Worker 인스턴스가 하나의 메시지 목록을 공유하여 각 메시지가 정확히 한 번씩 처리되도록 하는 것이 목표입니다.

또한 채널 큐에서 작업을 꺼내는 것은 receiver를 변경하는 작업을 포함하므로, 스레드들은 receiver를 안전하게 공유하고 수정하는 방법이 필요합니다.

16장에서 논의한 스레드 안전 스마트 포인터를 떠올려 보세요. 여러 스레드 간에 소유권을 공유하고 스레드가 값을 변경할 수 있도록 하려면 Arc<Mutex<T>>를 사용해야 합니다. Arc 타입을 사용하면 여러 Worker 인스턴스가 수신기의 소유권을 공유할 수 있으며, Mutex는 한 번에 하나의 Worker만 수신기에서 작업을 가져오도록 보장합니다.

ThreadPool::new에서 수신기를 Arc과 Mutex에 넣습니다. 각 새로운 Worker에 대해 Arc를 복제하여 참조 계수를 증가시킴으로써, Worker 인스턴스들이 수신기의 소유권을 공유할 수 있게 합니다.

드디어 실행을 해보자. execute 메서드 켜짐 ThreadPool. 우리는 또한 변화할 것이다 Job 클로저의 타입을 가지고 있는 트레잇 객체에 대한 타입 별칭에 대한 구조체로부터 execute 받는 사람. 에서 논의 된 바와 같이 타입 동의어 및 타입 별칭(Type Synonyms and Type Alias) 무시 20장에서는 사용 편의성을 위해 긴 타입을 더 짧게 만들 수 있도록 별칭을 입력합니다. Listing 21-19를 보세요.

execute에서 받은 클로저를 사용해 새 Job 인스턴스를 만든 뒤, 채널의 송신 끝으로 작업을 보냅니다. 전송이 실패할 경우를 대비해 send의 결과에 unwrap을 호출합니다. 예를 들어 모든 스레드의 실행을 중단하면 수신 끝에서 새 메시지를 받지 않게 되어 전송이 실패할 수 있습니다. 현재는 스레드 실행을 중단할 방법이 없으며, 스레드 풀의 수명이 유지되는 동안 스레드는 계속 실행됩니다. 실패하지 않을 것이라고 우리는 알지만 컴파일러는 알지 못하므로 unwrap을 사용합니다.

그러나 아직 완전히 끝난 것은 아닙니다! Worker에서 thread::spawn에 전달되는 클로저는 여전히 채널의 수신 단만 참조하고 있습니다. 대신, 클로저가 무한 루프를 돌며 채널의 수신 단에서 작업을 요청하고, 작업을 받으면 실행하도록 해야 합니다. Worker::new에 나열 21-20에 표시된 변경 사항을 적용해 보겠습니다.

먼저 수신기에서 lock을 호출해 뮤텍스를 획득한 다음, 오류가 있으면 unwrap을 호출해 패닉을 일으킵니다. 뮤텍스를 잠근 상태에서 다른 스레드가 패닉을 일으켜 잠금을 해제하지 못하면 뮤텍스가 손상된(poisoned) 상태가 되어 잠금 획득이 실패할 수 있습니다. 이 경우 unwrap을 호출해 현재 스레드도 패닉하게 하는 것이 올바른 선택입니다. 원한다면 unwrap을 의미 있는 오류 메시지를 제공하는 expect로 바꿔도 됩니다.

뮤텍스에 대한 잠금을 획득하면 recv를 호출하여 채널에서 Job를 수신합니다. 마지막에 unwrap를 사용하여 여기서 발생할 수 있는 오류를 무시합니다. 이는 수신자가 종료되면 send 메서드가 Err를 반환하는 것과 유사하게, 전송자를 가진 스레드가 종료된 경우 발생할 수 있는 오류를 처리하는 것입니다.

recv 호출은 블로킹되므로 아직 작업이 없으면 현재 스레드는 작업이 사용 가능해질 때까지 대기합니다. Mutex<T>는 한 번에 하나의 Worker 스레드만 작업을 요청하도록 보장합니다.

17장과 19장에서 while let 루프에 대해 배운 후, Listing 21-21에 나와 있는 것처럼 Worker 스레드 코드를 작성하지 않은 이유가 궁금할 수 있습니다.

이 코드는 컴파일되고 실행되지만, 원하는 스레딩 동작을 가져오지 않습니다: 느린 요청은 여전히 다른 요청이 처리되기를 기다리게 만듭니다. 그 이유는 다소 미묘합니다: Mutex 구조체는 공개된 unlock 메서드가 없습니다. 이는 lock 메서드가 반환하는 LockResult<MutexGuard<T>> 내부의 MutexGuard<T>의 라이프타임에 기반하여 잠금의 소유권이 결정되기 때문입니다. 컴파일 시, 빌로우 체커는 Mutex에 의해 보호되는 리소스는 잠금을 보유하지 않는 한 접근할 수 없다는 규칙을 강제할 수 있습니다. 그러나 이 구현은 MutexGuard<T>의 라이프타임에 주의하지 않으면 잠금이 의도한 것보다 더 오래 보유되도록 할 수도 있습니다.

사용하는 Listing 21-20의 코드 let job = receiver.lock().unwrap().recv().unwrap(); 왜냐하면 with let등호의 오른쪽에 있는 표현식에 사용된 임시 값은 즉시 삭제됩니다. let 성명서가 끝납니다. 그러나, while let (그리고 if let 그리고 match) 는 연관된 블록의 끝까지 임시 값을 드롭하지 않습니다. Listing 21-21에서, lock은 다음과 같은 호출의 기간 동안 유지됩니다. job()#다른 의미 Worker 직원들은 일자리를 얻을 수 없습니다.
