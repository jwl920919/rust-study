The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

메시지 전달을 통해 스레드 간에 데이터 전송

안전한 동시성을 보장하기위한 한 가지 인기있는 접근 방식은 데이터가있는 스레드 또는 액터가 서로 메시지를 전송하여 통신하는 메시지 전달입니다. Go 언어 문서를의 슬로건에 대한 아이디어는 다음과 같습니다. "메모리를 공유하여 통신하지 마십시오. 대신 의사 소통을 통해 메모리를 공유하십시오."

러스트의 표준 라이브러리는 메시지 전송 동시성을 달성하기 위해 채널의 구현을 제공합니다. 채널은 하나의 스레드에서 다른 스레드로 데이터를 전송하는 일반적인 프로그래밍 개념입니다.

프로그래밍에서 채널은 물줄기 또는 강과 같은 방향성 채널과 같다고 상상할 수 있습니다. 고무 오리 같은 것을 강에 넣으면 수로의 끝까지 아래로 여행합니다.

‘채널’에는 두 개 의 반쪽 즉 ‘트랜스미터’와 ‘리시버’가 있다. ‘트랜스미터’의 반쪽 은 ‘고무 오리’를 강 에 넣는 상류 위치 이며, ‘리시버’의 반쪽 은 ‘고무 오리’가 하류 로 끝나는 곳 이다. 당신 의 ‘코드’의 한 부분 은 당신 이 보내려는 자료 를 가지고 ‘트랜스미터’에 있는 방법 을 호출 하고, 또 다른 부분 은 도착 하는 메시지 의 수신 끝 을 검사 한다.

여기서는 값을 생성하고 채널로 보낼 수 있는 하나의 스레드와 값을 수신하고 인쇄할 다른 스레드가 있는 프로그램으로 작업합니다. 채널을 사용하여 스레드 간에 간단한 값을 전송하여 기능을 설명합니다. 이 기술에 익숙해지면 채팅 시스템 또는 여러 스레드가 계산의 일부를 수행하고 집계된 스레드 결과를 보내는 시스템과 같이 서로 통신해야 하는 스레드에 채널을 사용할 수 있습니다.

먼저, Listing 16-6에서, 우리는 채널을 만들 것이지만 그것으로는 아무 것도 하지 않을 것입니다. 이것은 아직 컴파일되지 않을 것입니다. 왜냐하면 러스트는 우리가 채널을 통해 보내고자 하는 값의 타입을 알 수 없기 때문입니다.

우리는 mpsc::channel 함수를 사용하여 새로운 채널을 만듭니다. mpsc는 다중 생산자, 단일 소비자를 의미합니다. 간단히 말해서, 러스트의 표준 라이브러리가 채널을 구현하는 방식은 채널이 값을 생성하는 여러 송신 종료를 가질 수 있지만 이러한 값을 소비하는 수신 종료는 하나만 가질 수 있음을 의미합니다. 하나의 큰 강으로 함께 흐르는 여러 스트림을 상상해보십시오. 모든 스트림을 아래로 보내면 결국 하나의 프로듀서가 추가됩니다.

이름 * mpsc::channel 함수는 튜플을 반환하며, 첫 번째 요소는 전송 끝, 두 번째 요소는 수신 끝, 수신자입니다. 약어 tx 그리고 rx 전통적으로 많은 분야에서 사용됩니다. 전송기 그리고 받는 사람, 각각, 그래서 우리는 각 끝을 나타 내기 위해 변수의 이름을 지정합니다. 우리는 let 튜플을 destructures 패턴과 문; 우리는에서 패턴의 사용을 논의 할 것이다 let 제 19 장에서 진술과 구조 조정. 지금은 알고 사용 let 이런 식으로 진술은 튜플의 조각을 추출하는 편리한 방법입니다 mpsc::channel.

Transmitting end를 스폰된 쓰레드로 옮기고 하나의 문자열을 보내서 스폰된 쓰레드가 메인 쓰레드와 통신하도록 합시다. Listing 16-7과 같이 말이죠. 이것은 마치 상류에 있는 강에 고무 오리를 넣거나 한 쓰레드에서 다른 쓰레드로 채팅 메시지를 보내는 것과 같습니다.

다시 말하지만, thread::spawn를 사용하여 새 스레드를 만든 다음 move를 사용하여 tx를 클로저로 이동하여 생성 된 스레드가 tx를 소유하도록합니다. 생성 된 스레드는 채널을 통해 메시지를 보낼 수 있도록 송신기를 소유해야합니다.

송신기에는 전송하려는 값을 갖는 send 메소드가 있습니다. send 메소드는 Result<T, E> 유형을 반환하므로 수신기가 이미 삭제되어 값을 보낼 곳이 없으면 전송 작업이 오류를 반환합니다. 이 예에서는 오류가 발생하면 unwrap를 패닉으로 호출합니다. 그러나 오류가 발생하면 제대로 검토하십시오.

Listing 16-8에서, 우리는 메인 스레드의 수신자로부터 값을 얻을 것입니다. 이것은 강 끝에 있는 물에서 고무 오리를 찾거나 채팅 메시지를 받는 것과 같습니다.

리시버에는 두 가지 유용한 방법이 있습니다. recv 그리고 try_recv. 우리는 사용하고 recv짧게 for 수신, 메인 스레드의 실행을 차단하고 값이 채널 아래로 전송 될 때까지 기다립니다. 값이 전송되면, recv 를 반환한다. Result<T, E>. 전송기가 닫힐 때, recv 더 이상 값이 오지 않을 것이라는 신호를 보내기 위해 오류를 반환합니다.

이름 * try_recv 메서드는 블록하지 않지만 대신 a를 반환합니다. Result<T, E> 즉시: an Ok 메시지를 가지고 있는 값 중 하나가 사용 가능하고 Err 이번에는 메시지가 없는 경우의 값입니다. try_recv 이 스레드가 메시지를 기다리는 동안 수행 할 다른 작업이있는 경우 유용합니다. try_recv 자주 사용할 수 있는 경우 메시지를 처리하고 다시 확인할 때까지 잠시 동안 다른 작업을 수행합니다.

우리는이 예제에서 recv를 사용 하 여 간단 하 게; 우리는 메시지를 기다리는 것 이외의 메인 스레드에 대 한 다른 작업이 없습니다, 그래서 메인 스레드를 차단 하는 것이 적절 합니다.

채널을 통한 소유권 이전

소유권 규칙은 안전하고 동시적인 코드를 작성하는 데 도움이 되기 때문에 메시지 전송에 중요한 역할을 합니다. 동시 프로그래밍에서 오류를 방지하는 것은 러스트 프로그램 전체에서 소유권에 대해 생각하는 이점입니다. 문제를 방지하기 위해 채널과 소유권이 함께 작동하는 방법을 보여주기 위해 실험을 해 보겠습니다. 채널 아래로 보내면 생성된 스레드에서 val 값을 사용하려고 할 것입니다. Listing 16-9에서 이 코드를 컴파일하는 것이 허용되는 이유를 확인해 보세요.

여기, 우리는 인쇄하려고 val 우리가 그것을 통해 채널을 아래로 보낸 후 tx.send. 이것을 허용하는 것은 좋지 않은 생각입니다: 일단 값이 다른 스레드로 전송되면, 그 스레드는 그 값을 다시 사용하기 전에 수정하거나 삭제할 수 있습니다. 잠재적으로, 다른 스레드의 수정은 일치하지 않거나 존재하지 않는 데이터로 인해 오류나 예상치 못한 결과를 초래할 수 있습니다. 그러나, Listing 16-9에서 코드를 컴파일하려고 하면 러스트는 우리에게 오류를 줍니다:

동시성 실수로 인해 컴파일 타임 오류가 발생했습니다. send 함수는 매개 변수의 소유권을 취하고 값이 이동되면 수신기가 소유권을 갖습니다. 이렇게하면 전송 후 실수로 값을 다시 사용하지 못하게됩니다. 소유권 시스템은 모든 것이 괜찮은지 확인합니다.
