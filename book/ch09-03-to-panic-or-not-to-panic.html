The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

panic!을 할 것인가, 말 것인가 panic!panic!

그렇다면, 언제 panic!를 호출하고 언제 Result을 반환해야 하는지 어떻게 결정해야 할까요? 코드가 패닉하면 복구할 방법이 없습니다. 복구 가능한 방법이 있든 없든 모든 오류 상황에서 panic!를 호출할 수 있지만, 그렇게 하면 호출 측 코드를 대신해 해당 상황이 복구 불가능하다고 결정하는 셈이 됩니다. Result 값을 반환하도록 선택하면 호출 측 코드에 선택지를 제공합니다. 호출 측 코드는 자신의 상황에 적합한 방식으로 복구를 시도하거나, 이 경우의 Err 값은 복구 불가능하다고 판단하여 panic!를 호출함으로써 복구 가능한 오류를 복구 불가능한 오류로 전환할 수 있습니다. 따라서 실패할 수 있는 함수를 정의할 때 Result을 반환하는 것이 좋은 기본 선택입니다.

예제, 프로토타입 코드, 테스트와 같은 상황에서는 Result를 반환하는 대신 panic!을 발생시키는 코드를 작성하는 것이 더 적절합니다. 왜 그런지 살펴본 후, 컴파일러는 실패가 불가능하다고 판단할 수 없지만 사람이라면 판단할 수 있는 상황에 대해 논의하겠습니다. 이 장은 라이브러리 코드에서 panic!을 사용할지 여부를 결정하는 일반적인 지침으로 마무리됩니다.

예제, 프로토타입 코드, 테스트

어떤 개념을 설명하기 위해 예제를 작성할 때, 견고한 오류 처리 코드까지 포함하면 예제가 명확하지 않게 될 수 있습니다. 예제에서는 unwrap처럼 panic!을 발생시킬 수 있는 메서드 호출은, 나머지 코드가 수행하는 작업에 따라 달라질 수 있는 애플리케이션의 오류 처리 방식을 대신하는 자리 표시자로 이해됩니다.

마찬가지로, 프로토타입을 작성하고 아직 오류 처리 방식을 결정할 준비가 되지 않은 상태에서는 unwrap 및 expect 메서드가 매우 유용합니다. 이 메서드들은 프로그램을 더 견고하게 만들 준비가 되었을 때 코드에 명확한 마커를 남겨줍니다.

테스트에서 메서드 호출이 실패하면, 해당 메서드가 테스트 대상 기능이 아니더라도 전체 테스트가 실패해야 합니다. panic!는 테스트가 실패로 표시되는 방법이므로, unwrap 또는 expect를 호출하는 것이 정확히 필요한 동작입니다.

Ok 값, 하지만 논리는 컴파일러가 이해하는 것이 아닙니다. 당신은 여전히 Result 처리해야 할 값: 호출하는 모든 작업에는 특정 상황에서 논리적으로 불가능하더라도 일반적으로 실패 할 가능성이 있습니다. 코드를 수동으로 검사하여 보장 할 수 있다면 Err 변형, 그것은 전화하는 것이 완벽하게 받아 들여집니다. expect 그리고 당신이 결코 가질 수 없을 것이라고 생각하는 이유를 문서화하십시오. Err 인수 텍스트의 변형입니다. 예제는 다음과 같습니다.

fn main() {

    let home: IpAddr = "127.0.0.1"
        .parse()

}

Result 마치 The Err variant는 컴파일러가이 문자열이 항상 유효한 IP 주소임을 알만큼 똑똑하지 않기 때문에 가능합니다. IP 주소 문자열이 프로그램에 하드 코딩되지 않고 사용자로부터 온 경우 했다 실패의 가능성을 가지고, 우리는 확실히 처리 할 것 Result 대신 더 강력한 방법으로. 이 IP 주소가 하드 코딩되어 있다는 가정을 언급하면 변경하라는 메시지가 표시됩니다 expect 나중에 다른 소스에서 IP 주소를 가져와야 할 경우 더 나은 오류 처리 코드.

오류 처리 지침

코드가 잘못된 상태에 빠질 가능성이 있을 때 panic을 발생시키는 것이 좋습니다. 이 맥락에서 잘못된 상태란 잘못된 값, 모순된 값, 또는 누락된 값이 코드로 전달되는 등 어떤 가정, 보장, 계약, 또는 불변 조건이 깨진 경우를 의미하며, 다음 중 하나 이상의 조건이 추가적으로 충족되는 경우를 포함합니다:

  • 잘못된 상태는 사용자가 잘못된 형식으로 데이터를 입력하는 것처럼 때때로 발생할 수 있는 상황과는 달리, 예기치 않게 발생하는 상황을 의미합니다.
  • 이 시점 이후의 코드는 모든 단계에서 문제를 확인하는 대신, 현재 잘못된 상태에 있지 않다는 전제에 의존해야 합니다.
  • 이 정보를 사용하는 타입으로 인코딩하는 좋은 방법은 없습니다. 18장의 “유형으로 상태와 행동을 인코딩하기” 섹션에서 이 의미를 설명하는 예제를 다룹니다.

누군가가 여러분의 코드를 호출하면서 의미가 없는 값을 전달하는 경우, 라이브러리를 사용하는 사람이 해당 상황에서 어떻게 처리할지 결정할 수 있도록 오류를 반환하는 것이 가장 좋습니다. 그러나 계속 진행하는 것이 안전하지 않거나 해로울 수 있는 경우, 최선의 선택은 panic!을 호출하여 라이브러리를 사용하는 사람에게 코드에 버그가 있음을 알리는 것입니다. 이렇게 하면 개발 단계에서 버그를 수정할 수 있습니다. 마찬가지로, 여러분의 통제를 벗어난 외부 코드를 호출했는데 잘못된 상태를 반환하여 여러분이 수정할 방법이 없는 경우에도 panic!을 사용하는 것이 종종 적절합니다.

그러나 실패가 예상되는 상황에서는 Result를 반환하는 것이 panic! 호출을 사용하는 것보다 적절합니다. 예를 들어 파서가 형식이 잘못된 데이터를 받거나, HTTP 요청이 속도 제한에 도달했음을 나타내는 상태 코드를 반환하는 경우가 이에 해당합니다. 이러한 경우 Result를 반환하면 실패가 예상 가능한 상황임을 나타내며, 호출 측 코드가 이를 어떻게 처리할지 결정해야 함을 의미합니다.

코드가 유효하지 않은 값으로 호출될 경우 사용자에게 위험을 초래할 수 있는 작업을 수행한다면, 코드는 먼저 값이 유효한지 확인하고 유효하지 않은 경우 패닉(panic)을 발생시켜야 합니다. 이는 주로 안전상의 이유입니다. 유효하지 않은 데이터로 작업을 시도하면 코드가 취약점에 노출될 수 있기 때문입니다. 표준 라이브러리가 범위를 벗어난 메모리 접근을 시도할 때 panic!를 호출하는 주된 이유도 이것입니다. 현재 데이터 구조에 속하지 않는 메모리에 접근하려는 시도는 일반적인 보안 문제이기 때문입니다. 함수에는 종종 계약(contract)이 있습니다. 즉, 입력이 특정 요구 사항을 충족할 때만 동작이 보장됩니다. 계약이 위반되면 패닉을 발생시키는 것이 합리적입니다. 계약 위반은 항상 호출 측의 버그를 의미하며, 호출 측 코드가 명시적으로 처리해야 할 종류의 오류가 아니기 때문입니다. 실제로 호출 측 코드가 이를 복구할 합리적인 방법은 없으며, 호출 측 프로그래머가 코드를 수정해야 합니다. 특히 위반 시 패닉이 발생하는 함수의 계약은 해당 함수의 API 문서에 설명되어 있어야 합니다.

하지만, 모든 함수에서 많은 에러 체크를 하는 것은 거침없고 짜증나는 일입니다. 다행스럽게도, 러스트의 타입 시스템(컴파일러에 의해 수행되는 타입 체크)을 사용하여 많은 수의 체크를 할 수 있습니다. 만약 여러분의 함수가 파라미터로서 특정한 타입을 가지고 있다면, 여러분은 컴파일러가 여러분이 유효한 값을 가지고 있다는 것을 이미 확인했다는 것을 알고 코드의 로직을 진행할 수 있습니다. 예를 들어, 만약 여러분이 타입이 있다면 Option당신의 프로그램이 기대되는 것은 뭔가 보다는 없음. 당신의 코드는 다음 두 경우를 처리 할 필요가 없습니다 Some 그리고 None variants: 확실히 값을 가지는 하나의 케이스만 가질 것입니다. 함수에 아무것도 전달하지 않으려는 코드는 컴파일되지 않으므로 함수는 런타임에 해당 케이스를 확인할 필요가 없습니다. 또 다른 예는 서명되지 않은 정수형을 사용하는 것입니다. u32즉, 매개 변수가 절대 음수가 아님을 보장합니다.

검증을 위한 사용자 정의 타입

Rust의 타입 시스템을 활용하여 유효한 값을 보장하는 개념을 한 단계 더 발전시켜, 검증을 위한 사용자 정의 타입을 만드는 방법을 살펴보겠습니다. 2장의 숫자 추측 게임을 떠올려 보세요. 당시 코드는 사용자가 1부터 100 사이의 숫자를 추측하도록 요청했습니다. 우리는 사용자가 추측한 숫자가 그 범위 내에 있는지 확인하지 않고 바로 비밀 숫자와 비교했습니다. 단지 추측한 값이 양수인지 확인했을 뿐입니다. 이 경우 결과는 치명적이지 않았습니다. '너무 높음' 또는 '너무 낮음'이라는 출력은 여전히 정확했기 때문입니다. 하지만 사용자가 범위를 벗어난 숫자를 추측하는 경우와, 예를 들어 문자를 입력하는 경우를 구분하여 다른 동작을 수행하고 사용자에게 유효한 추측을 유도하는 것은 유용한 개선 사항이 될 것입니다.

이 작업을 수행하는 한 가지 방법은 추측 값을 i32 대신 u32로 파싱하여 잠재적으로 음수를 허용한 후, 다음과 같이 숫자가 범위 내에 있는지 검사하는 것입니다:

if 식은 값이 범위 밖인지 확인하고, 사용자에게 문제를 알린 후 continue를 호출하여 루프의 다음 반복을 시작하고 다시 추측을 요청합니다. if 식 이후에는 guess가 1과 100 사이임을 알 수 있으므로, guess와 비밀 숫자 사이의 비교를 진행할 수 있습니다.

그러나 이는 이상적인 해결책이 아닙니다. 프로그램이 1과 100 사이의 값으로만 동작하는 것이 절대적으로 중요하고, 이러한 요구 사항을 가진 함수가 많다면 모든 함수에 이와 같은 검사를 포함하는 것은 번거로울 것입니다(또는 성능에 영향을 미칠 수 있습니다).

대신 전용 모듈에 새로운 타입을 만들고, 해당 타입의 인스턴스를 생성하는 함수에 유효성 검사를 넣을 수 있습니다. 이렇게 하면 모든 곳에서 유효성 검사를 반복할 필요가 없습니다. 또한 함수가 서명에서 새로운 타입을 사용하고, 전달받은 값을 안심하고 사용할 수 있게 됩니다. Listing 9-13은 1에서 100 사이의 값만 전달받았을 때 Guess 인스턴스를 생성하도록 Guess 타입을 정의하는 한 가지 방법을 보여줍니다. new

src/guessing_game.rs의 이 코드는 여기에서 보여드리지 않은 src/lib.rs에 mod guessing_game; 모듈 선언을 추가하는 것에 의존합니다. 이 새로운 모듈의 파일 안에서는 Guess이라는 이름의 구조체를 정의합니다. 이 구조체에는 value라는 필드가 있으며, 이 필드에는 i32 타입의 값이 저장됩니다. 이 필드가 숫자를 저장하는 곳입니다.

그다음, new에 Guess이라는 연관 함수를 구현하여 Guess 값을 생성합니다. new 함수는 value라는 이름의 i32 타입 매개변수 하나를 가지며 Guess을 반환하도록 정의됩니다. new 함수 본문에 있는 코드는 value가 1에서 100 사이인지 확인합니다. value이 이 테스트를 통과하지 못하면, panic!을 호출하여 호출 코드를 작성 중인 프로그래머에게 수정해야 할 버그가 있음을 알립니다. 이는 이 범위를 벗어난 값으로 Guess을 생성하면 value이 의존하는 계약이 위반되기 때문입니다. Guess::new이 Guess::new할 수 있는 조건은 공개 API 문서에서 논의되어야 하며, panic! 가능성이 있는 API 문서 작성 규칙은 14장에서 다룹니다. value이 테스트를 통과하면, Guess 필드를 value 매개변수로 설정한 새로운 value을 생성하여 Guess을 반환합니다.

다음으로, value이라는 이름을 가진 메서드를 구현합니다. 이 메서드는 self을(를) 참조하고, 다른 매개변수는 없으며, i32을(를) 반환합니다. 이러한 종류의 메서드는 getter라고도 불리우며, 그 목적은 필드에서 데이터를 가져와 반환하는 것입니다. 이 공개 메서드가 필요한 이유는 Guess 구조체의 value 필드가 비공개이기 때문입니다. value 필드가 비공개인 것은 중요한데, Guess 구조체를 사용하는 코드가 value을(를) 직접 설정할 수 없도록 하기 위함입니다. guessing_game 모듈 외부의 코드 반드시 Guess::new 함수를 사용하여 Guess의 인스턴스를 생성해야 하며, 이를 통해 Guess::new 함수의 조건으로 검사되지 않은 value을(를) 가진 Guess이 존재할 수 없음을 보장합니다.

1부터 100 사이의 숫자만 매개 변수로 받거나 반환하는 함수라면, 서명에서 Guess 대신 i32을 사용한다고 선언할 수 있으며, 함수 본문에서 추가적인 검사를 수행할 필요가 없습니다.

요약

Rust의 오류 처리 기능은 더 견고한 코드를 작성하는 데 도움이 되도록 설계되었습니다. panic! 매크로는 프로그램이 처리할 수 없는 상태에 있음을 알리며, 유효하지 않거나 잘못된 값으로 계속 진행하려는 대신 프로세스를 중지하도록 지시할 수 있습니다. Result enum은 Rust의 타입 시스템을 활용하여 코드가 복구할 수 있는 방식으로 작업이 실패할 수 있음을 나타냅니다. Result를 사용하면 자신의 코드를 호출하는 쪽에게 잠재적인 성공 또는 실패를 처리해야 함을 알릴 수 있습니다. 적절한 상황에서 panic!와 Result를 사용하면 피할 수 없는 문제에 직면했을 때에도 코드가 더 신뢰할 수 있게 됩니다.

이제 표준 라이브러리가 Option 및 Result 열거형에 제네릭을 활용하는 유용한 방법을 살펴보았습니다. 이제 제네릭의 작동 원리와 코드에서 제네릭을 사용하는 방법에 대해 설명하겠습니다.
