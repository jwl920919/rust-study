The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

퓨처와 비동기 구문

Rust에서 비동기 프로그래밍의 핵심 요소는 퓨처와 Rust의 async 및 await 키워드입니다.

미래(future)는 현재 준비가 되어 있지 않을 수 있지만, 미래의 어느 시점에 준비가 될 값을 의미합니다. (이 같은 개념은 많은 언어에서 나타나며, 때로는 작업(task) 또는 약속(promise)와 같은 다른 이름으로도 사용됩니다.) Rust는 서로 다른 비동기 작업이 서로 다른 데이터 구조로 구현되더라도 공통 인터페이스를 가질 수 있도록 FutureFuture 트레이트를 빌딩 블록으로 제공합니다. Rust에서 future는 FutureFuture 트레이트를 구현하는 타입입니다. 각 future는 진행 상황과 '준비됨'이 무엇을 의미하는지에 대한 자체 정보를 보유합니다.

async 키워드를 블록과 함수에 적용하여 중단 및 재개가 가능하도록 지정할 수 있습니다. 비동기 블록 또는 비동기 함수 내에서 await 키워드를 사용하여 퓨처를 기다릴 수 있습니다(즉, 준비가 될 때까지 기다리는 것입니다). 비동기 블록 또는 함수 내에서 퓨처를 기다리는 지점은 해당 블록 또는 함수가 일시 중지되고 재개될 수 있는 잠재적 지점입니다. 퓨처의 값이 아직 사용 가능한지 확인하는 과정을 폴링(polling)이라고 합니다.

C#과 JavaScript와 같은 일부 다른 언어도 비동기 프로그래밍을 위해 async 및 await 키워드를 사용합니다. 이러한 언어에 익숙하다면 Rust가 구문을 처리하는 방식에 몇 가지 중요한 차이가 있음을 알 수 있을 것입니다. 그 이유는 곧 살펴보게 될 것입니다!

Future 태그 보관물: As It Compiles for 를 사용하여 동등한 코드로 루프 Iterator 특성입니다. 러스트는 Future 하지만 필요할 때 자신의 데이터 유형에 대해서도 구현할 수 있습니다. 이 장에서 볼 수 있는 많은 함수는 다음과 같은 자체 구현을 통해 유형을 반환합니다. Future. 우리는 장의 끝에 특색의 정의에 돌려보내고 그것이 작동하는 방법의 더 많은 것으로 파헤칠 것입니다, 그러나 이것은 저희를 전진하는 것을 계속하는 충분한 세부사항 입니다.

이 모든 것이 다소 추상적으로 느껴질 수 있으므로, 첫 번째 비동기 프로그램인 작은 웹 스크레이퍼를 작성해 보겠습니다. 명령줄에서 두 개의 URL을 전달하고, 이 둘을 동시에 가져오며, 먼저 완료된 것의 결과를 반환합니다. 이 예제에는 새로운 구문이 꽤 많이 등장하지만 걱정하지 마세요. 진행하면서 알아야 할 모든 것을 설명해 드리겠습니다.

Tokio는 오늘날 러스트에서 가장 널리 사용되는 비동기 런타임이며, 특히 웹 애플리케이션에서 그렇습니다. 다른 훌륭한 런타임이 있으며, 여러분의 목적에 더 적합할 수 있습니다. tokio 후드 아래 크레이트 trpl 그것은 잘 테스트되고 널리 사용되기 때문입니다.

일부 경우에는 trpl이 이 장에서 다루는 핵심 사항에 집중할 수 있도록 원래 API의 이름을 변경하거나 래핑하기도 합니다. 해당 크레이트가 수행하는 작업을 이해하려면 소스 코드를 확인해 보시기 바랍니다. 어떤 크레이트에서 재수출(re-export)이 이루어지는지 확인할 수 있으며, 크레이트의 동작을 설명하는 상세한 주석도 함께 제공됩니다.

Rust가 async 키워드로 표시된 블록을 보면, 이를 Future 트레잇을 구현하는 고유한 익명 데이터 타입으로 컴파일합니다. Rust가 async로 표시된 함수를 보면, 이를 본문이 async 블록인 비동기 함수가 아닌 함수로 컴파일합니다. 비동기 함수의 반환 타입은 컴파일러가 해당 async 블록을 위해 생성하는 익명 데이터 타입의 타입입니다. asyncFutureasync

따라서 async fn을 작성하는 것은 반환 타입의 future를 반환하는 함수를 작성하는 것과 동일합니다. 컴파일러의 관점에서, Listing 17-1의 async fn page_title과 같은 함수 정의는 다음과 같이 정의된 비동기 함수와 대략 동일합니다: async fnasync fn page_title

#![allow(unused)]
fn main() {
extern crate trpl; // required for mdbook test
use std::future::Future;
use trpl::Html;

fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        let text = trpl::get(url).await.text().await;
        Html::parse(&text)
            .select_first("title")
            .map(|title| title.inner_html())
    }
}
}

변환된 버전의 각 부분을 살펴봅시다:

  • 10장 “매개변수로서의 트레이트” 섹션에서 논의한 impl Trait 구문을 사용합니다. 매개변수로 트레이트 사용하기
  • 반환된 값은 Future 트레이트를 구현하며, 연관 타입으로 Output을(를) 가집니다. Output 타입이 Option<String>임을 주목하세요. 이는 async fn의 async fn 버전에서 원래 반환하던 타입과 동일합니다. page_title
  • 원래 함수 본문에서 호출되는 모든 코드는 async move 블록에 감싸져 있습니다. 블록은 표현식이라는 점을 기억하세요. 이 전체 블록이 함수에서 반환되는 표현식입니다.
  • 이 async 블록은 방금 설명한 대로 Option<String> 타입의 값을 생성합니다. 이 값은 반환 타입의 Output 타입과 일치합니다. 이는 이전에 보았던 다른 블록과 마찬가지입니다.
  • 새로운 함수 본문은 async move 매개변수를 사용하는 방식 때문에 url 블록입니다. (이 장의 후반부에서 async와 async move의 차이에 대해 자세히 설명하겠습니다.)

런타임으로 async 함수 실행

먼저 Listing 17-3에 표시된 단일 페이지의 제목을 가져오겠습니다. 불행히도 이 코드는 아직 컴파일되지 않습니다.

우리는 우리가 명령행 인수를 얻는 데 사용했던 것과 같은 패턴을 따릅니다. “명령 줄 의 논증 을 받아들이다” 무시 12 장의 섹션. 그런 다음 URL 인수를 전달합니다 page_title 그리고 결과를 기다립니다. 미래에 의해 생성 된 값이기 때문에 Option<String>우리는 A를 사용합니다. match expression 페이지가 a를 가지고 있는지 여부를 설명하기 위해 다른 메시지를 인쇄하는 것 <title>.

await 키워드를 사용할 수 있는 유일한 위치는 비동기 함수나 블록이며, Rust는 특수한 main 함수를 async로 표시하지 못하게 합니다.

error[E0752]: `main` function is not allowed to be `async`
 --> src/main.rs:6:1
  |
6 | async fn main() {
  | ^^^^^^^^^^^^^^^ `main` function is not allowed to be `async`

main를 async로 표시할 수 없는 이유는 비동기 코드에 런타임이 필요하기 때문입니다. 런타임은 비동기 코드 실행의 세부 사항을 관리하는 Rust 크레이트입니다. 프로그램의 main 함수는 런타임을 초기화할 수 있지만, 런타임 자체는 아닙니다. (이러한 이유에 대해서는 잠시 후 자세히 살펴보겠습니다.) 비동기 코드를 실행하는 모든 Rust 프로그램은 적어도 한 곳에서 future를 실행하는 런타임을 설정합니다.

비동기를 지원하는 대부분의 언어는 런타임을 번들링하지만, Rust는 그렇지 않습니다. 대신 다양한 비동기 런타임이 있으며, 각각은 대상 사용 사례에 적합한 다른 트레이드오프를 제공합니다. 예를 들어, 많은 CPU 코어와 대량의 RAM을 가진 고처리량 웹 서버는 단일 코어, 적은 RAM, 힙 할당 기능이 없는 마이크로컨트롤러와 매우 다른 요구 사항을 가집니다. 이러한 런타임을 제공하는 크레이트는 파일이나 네트워크 I/O와 같은 일반적인 기능의 비동기 버전도 함께 제공하는 경우가 많습니다.

여기서부터 이 장의 나머지 부분까지, 우리는 block_on 크레이트의 trpl 함수를 사용합니다. 이 함수는 future를 인수로 받아 해당 future가 완료될 때까지 현재 스레드를 차단합니다. 내부적으로 block_on를 호출하면, 전달된 future를 실행하기 위해 tokio 크레이트를 사용해 런타임을 설정합니다(trpl 크레이트의 block_on 동작은 다른 런타임 크레이트의 block_on 함수와 유사합니다). future가 완료되면, block_on는 future가 생성한 값을 반환합니다.

우리는 미래로 돌아갈 수 있습니다. page_title 직접 to block_on 그리고, 그것이 완료되면, 우리는 결과에 일치 할 수 Option<String> Listing 17-3에서 시도했던 것처럼 말이죠. 하지만, 이 장의 대부분의 예제들(그리고 현실 세계의 대부분의 비동기 코드)에 대해서, 우리는 단지 하나의 비동기 함수 호출보다 더 많은 것을 할 것입니다. async 블록과 명시적으로의 결과 대기 page_title Listing 17-4와 같이 호출합니다.

드디어 제대로 동작하는 비동기 코드를 만들었습니다! 하지만 두 사이트를 서로 경쟁시키는 코드를 추가하기 전에, 먼저 퓨처가 어떻게 작동하는지 간단히 살펴보겠습니다.

각 await 지점, 즉 코드가 await 키워드를 사용하는 모든 위치는 제어권이 런타임으로 반환되는 지점을 나타냅니다. 이를 위해 Rust는 비동기 블록에 포함된 상태를 추적해야 합니다. 이렇게 하면 런타임이 다른 작업을 시작하고, 첫 번째 작업을 다시 진행할 준비가 되었을 때 돌아올 수 있습니다. 이는 보이지 않는 상태 머신과 같으며, 각 await 지점마다 현재 상태를 저장하기 위해 다음과 같은 enum을 작성한 것과 같습니다:

#![allow(unused)]
fn main() {
extern crate trpl; // required for mdbook test

enum PageTitleFuture<'a> {
    Initial { url: &'a str },
    GetAwaitPoint { url: &'a str },
    TextAwaitPoint { response: trpl::Response },
}
}

그러나 각 상태 간 전환을 수동으로 작성하는 코드는 지루하고 오류가 발생하기 쉽습니다. 특히 나중에 코드에 더 많은 기능과 상태를 추가해야 할 때 더욱 그렇습니다. 다행히도 Rust 컴파일러는 비동기 코드에 대한 상태 머신 데이터 구조를 자동으로 생성하고 관리합니다. 데이터 구조에 대한 일반적인 빌림 및 소유권 규칙은 여전히 적용되며, 컴파일러는 이를 검사하고 유용한 오류 메시지를 제공합니다. 이 장의 후반부에서 이러한 오류 중 몇 가지를 다룰 예정입니다.

결국 이 상태 머신을 실행하는 것이 필요하며, 그 역할은 런타임이 수행합니다. (런타임을 조사할 때 실행자(executor)에 대한 언급을 볼 수 있는 이유가 바로 이것입니다. 실행자는 비동기 코드를 실행하는 런타임의 일부입니다.)

이제 컴파일러가 왜 우리가 만드는 것을 멈추게했는지 알 수 있습니다. main Listing 17-3에서 그 자체로 async 함수를 반환합니다. main 만약 비동기 함수라면, 어떤 미래를 위해 상태 머신을 관리해야 할 필요가 있을 것입니다. main 돌아왔지만, main 프로그램의 출발점입니다! 대신, 우리는 trpl::block_on 기능 IN main runtime을 설정하고 future가 반환되는 async 블록이 완성될 때까지

참고: 일부 런타임은 async main 함수를 작성할 수 있도록 매크로를 제공합니다. 이러한 매크로는 main를 일반 async fn main() { ... }로 재작성합니다. 이는 fn main에서 우리가 수동으로 수행한 것과 동일한 작업을 수행하며, trpl::block_on처럼 퓨처가 완료될 때까지 실행하는 함수를 호출합니다.

이제 이 조각들을 조합하여 동시성 코드를 작성하는 방법을 살펴보겠습니다.

두 개의 URL을 동시에 경쟁시키는 방법

Listing 17-5에서는 커맨드 라인에서 전달된 두 개의 서로 다른 URL을 인수로 받아 page_title를 호출하고, 먼저 완료되는 future를 선택하는 방식으로 두 future를 경쟁시킵니다.

먼저 사용자가 제공한 각 URL에 대해 page_title을 호출합니다. 그 결과로 생성된 future를 title_fut_1과 title_fut_2에 저장합니다. future는 게으르며 아직 await하지 않았으므로, 이 시점에서는 아무 동작도 수행하지 않는다는 점을 기억하세요. 그런 다음 이 future들을 trpl::select에 전달합니다. 이 함수는 전달된 future 중 어느 것이 먼저 완료되었는지를 나타내는 값을 반환합니다.

참고: 내부적으로 trpl::select은 futures 크레이트에 정의된 더 일반적인 select 함수를 기반으로 구축됩니다. futures 크레이트의 select 함수는 trpl::select 함수가 할 수 없는 많은 일을 수행할 수 있지만, 지금은 건너뛸 수 있는 추가적인 복잡성도 있습니다.

두 future 모두 정당하게 "승리"할 수 있으므로, Result을 반환하는 것은 의미가 없습니다. 대신, trpl::select은 이전에 본 적 없는 타입인 trpl::Either를 반환합니다. Either 타입은 두 가지 경우를 가지므로 Result와 다소 유사합니다. 그러나 Result와 달리, Either에는 성공 또는 실패라는 개념이 내장되어 있지 않습니다. 대신, Left과 Right을 사용하여 "둘 중 하나"를 나타냅니다:

#![allow(unused)]
fn main() {
enum Either<A, B> {
    Left(A),
    Right(B),
}
}

select 함수는 첫 번째 인수가 선택되면 해당 future의 출력으로 Left를 반환하고, 두 번째 인수가 선택되면 그 future의 출력으로 Right를 반환합니다. 이는 함수 호출 시 인수가 나타나는 순서와 일치하며, 첫 번째 인수는 두 번째 인수의 왼쪽에 위치합니다.

또한 page_title을 업데이트하여 전달받은 URL을 그대로 반환하도록 합니다. 이렇게 하면 먼저 반환되는 페이지에서 해석할 수 있는 <title>가 없더라도 여전히 의미 있는 메시지를 출력할 수 있습니다. 이 정보가 확보되었으므로 마무리로 println! 출력을 업데이트하여 어떤 URL이 먼저 완료되었는지, 그리고 해당 URL의 웹 페이지에 <title>가 있는지 없는지를 나타내도록 합니다.

이제 작은 규모의 작동하는 웹 스크레이퍼를 만들었습니다! 몇 개의 URL을 선택하여 명령줄 도구를 실행해 보세요. 일부 사이트는 다른 사이트보다 항상 빠를 수 있고, 다른 경우에는 실행할 때마다 더 빠른 사이트가 달라질 수 있습니다. 더 중요한 것은, 이제 퓨처(futures)를 다루는 기초를 배웠으므로 비동기(async)로 할 수 있는 일을 더 깊이 탐구할 수 있게 되었습니다.
