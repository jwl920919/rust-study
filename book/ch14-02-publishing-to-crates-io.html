The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

Crates.io에 크레이트 게시하기

우리는 crates.io의 패키지를 프로젝트의 종속성으로 사용해 왔지만, 자신의 패키지를 게시하여 다른 사람들과 코드를 공유할 수도 있습니다. crates.io의 크레이트 레지스트리는 패키지의 소스 코드를 배포하므로 주로 오픈 소스 코드를 호스팅합니다.

Rust와 Cargo에는 게시한 패키지를 사람들이 쉽게 찾고 사용할 수 있게 해주는 기능이 있습니다. 다음에서는 이러한 기능 중 일부에 대해 설명하고, 패키지를 게시하는 방법을 소개하겠습니다.

유용한 문서 주석 작성하기

패키지를 정확하게 문서화하면 다른 사용자가 언제 어떻게 사용하는지 알 수 있으므로 문서를 작성하는 데 시간을 투자할 가치가 있습니다. 3장에서는 두 개의 슬래시인 //를 사용하여 Rust 코드를 주석하는 방법에 대해 논의했습니다. Rust에는 HTML 문서를 생성하는 문서 주석이라는 특별한 종류의 주석이 있습니다. 이 HTML은 크레이트의 구현 방식이 아니라, 크레이트를 사용하는 방법에 관심이 있는 프로그래머를 위해 공개된 API 항목에 대한 문서 주석의 내용을 표시합니다.

문서 주석은 두 개의 슬래시 대신 세 개의 슬래시인 ///를 사용하며, 텍스트 서식 지정을 위한 마크다운 표기법을 지원합니다. 문서 주석은 해당 항목 바로 앞에 배치합니다. 목록 14-1은 add_one이라는 이름의 크레이트에서 my_crate 함수에 대한 문서 주석을 보여줍니다.

여기서, 우리는 무엇에 대한 설명을 제공합니다. add_one 함수는 제목으로 섹션을 시작합니다. Examples그리고 어떻게 사용하는지를 보여주는 코드를 제공한다. add_one 함수. 우리는 실행하여이 문서 주석에서 HTML 문서를 생성할 수 있습니다 cargo doc. 이 명령은 rustdoc 러스트와 함께 배포된 툴은 생성된 HTML 문서를 목표/의사 디렉토리.

편의상 cargo doc --open을 실행하면 현재 크레이트의 문서와 모든 종속성의 문서에 대한 HTML을 빌드하고, 결과를 웹 브라우저에서 엽니다. add_one 함수로 이동하면 그림 14-1과 같이 문서 주석의 텍스트가 어떻게 렌더링되는지 확인할 수 있습니다.

자주 사용되는 섹션

Listing 14-1에서는 # Examples Markdown 제목을 사용하여 HTML에서 'Examples'라는 제목의 섹션을 만들었습니다. 다음은 크레이트 작성자가 문서에서 자주 사용하는 다른 섹션들입니다.

  • Panics: 문서화된 함수가 패닉(panic)을 일으킬 수 있는 시나리오입니다. 프로그램이 패닉하지 않도록 하려면 이러한 상황에서 함수를 호출하지 않도록 해야 합니다.
  • Errors: 함수가 Result를 반환하는 경우, 발생할 수 있는 오류의 종류와 이러한 오류가 반환될 수 있는 조건을 설명하면 호출자가 다양한 종류의 오류를 각각 다른 방식으로 처리하는 코드를 작성하는 데 도움이 됩니다.
  • 안전: 함수가 unsafe를 호출하는 경우 (20 장에서 안전에 대해 논의함), 함수가 안전하지 않은 이유를 설명하는 섹션이 있어야하며 함수가 호출자가 유지하기를 기대하는 불변을 포함해야합니다.

대부분의 문서 주석은 이러한 모든 섹션을 필요로 하지 않지만, 사용자들이 알고 싶어 할 코드 측면을 상기시키기 위한 좋은 체크리스트입니다.

문서 주석을 테스트로

문서 주석에 예제 코드 블록을 추가하면 라이브러리 사용법을 시연하는 데 도움이 되며, 추가적인 장점도 있습니다: cargo test을 실행하면 문서에 포함된 코드 예제를 테스트로 실행합니다! 예제가 포함된 문서보다 나은 것은 없습니다. 하지만 문서 작성 이후 코드가 변경되어 예제가 동작하지 않는 것보다 나쁜 것도 없습니다. Listing 14-1의 add_one 함수 문서로 cargo test을 실행하면, 테스트 결과에 다음과 같은 섹션이 표시됩니다:

   Doc-tests my_crate

running 1 test
test src/lib.rs - add_one (line 5) ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.27s

이제 함수나 예제를 변경하여 예제에 포함된 assert_eq!가 패닉하도록 만든 뒤 cargo test를 다시 실행해 보세요. 그러면 문서 테스트가 예제와 코드가 서로 동기화되지 않았음을 감지하는 것을 확인할 수 있습니다!

포함 항목 주석

//! 스타일의 doc comment는 주석 뒤에 오는 항목이 아니라, 주석을 포함하는 항목 자체에 문서를 추가합니다. 일반적으로 크레이트 루트 파일(관례상 src/lib.rs)이나 모듈 내부에서 크레이트나 모듈 전체를 문서화할 때 이러한 doc comment를 사용합니다.

예를 들어, my_crate 함수를 포함하는 add_one 크레이트의 목적을 설명하는 문서를 추가하려면, //! 로 시작하는 문서 주석을 src/lib.rs 파일 의 맨 앞에 추가합니다. Listing 14-2에 나와 있는 것과 같습니다.

//!로 시작하는 마지막 줄 이후에는 코드가 없습니다. 주석을 //! 대신 ///로 시작했기 때문에, 이 주석 뒤에 오는 항목이 아니라 이 주석을 포함하는 항목을 문서화하고 있습니다. 이 경우 해당 항목은 src/lib.rs 파일이며, 이는 크레이트 루트입니다. 이러한 주석은 전체 크레이트를 설명합니다.

cargo doc --open를 실행하면, my_crate의 문서 첫 페이지에 공개 항목 목록 위에 이 주석들이 표시되며, 그 모습은 그림 14-2와 같습니다.

항목 내부의 문서 주석은 특히 크레이트와 모듈을 설명하는 데 유용합니다. 컨테이너의 전반적인 목적을 설명하여 사용자가 크레이트의 구조를 이해하는 데 도움이 되도록 사용하세요.

그림 14-2: 크레이트 전체를 설명하는 주석을 포함하여 렌더링된 my_crate의 문서

편리한 공개 API 내보내기

공개 API의 구조는 크레이트를 게시할 때 중요한 고려 사항입니다. 크레이트를 사용하는 사람들은 개발자보다 구조에 익숙하지 않으며, 크레이트에 모듈 계층 구조가 크다면 사용하려는 요소를 찾는 데 어려움을 겪을 수 있습니다.

7장에서 pub 키워드를 사용하여 항목을 공개하는 방법과 use 키워드를 사용하여 항목을 스코프에 가져오는 방법을 다루었습니다. 그러나 크레이트를 개발하는 동안 개발자에게 의미 있는 구조는 사용자에게는 편리하지 않을 수 있습니다. 여러 레벨로 구성된 계층 구조에 구조체를 정리하고 싶을 수 있지만, 계층 구조의 깊은 곳에 정의한 타입을 사용하려는 사람은 해당 타입의 존재를 알아차리지 못할 수 있습니다. 또한 use my_crate::some_module::another_module::UsefulType; 대신 use my_crate::UsefulType;를 입력해야 하는 것도 번거롭게 느낄 수 있습니다.

좋은 소식은 다른 라이브러리에서 사용할 때 구조가 편리하지 않더라도 내부 조직을 재배열할 필요가 없다는 것입니다. 대신 pub use를 사용하여 비공개 구조와 다른 공개 구조를 만들어 항목을 재내보낼 수 있습니다. 재내보내기는 한 위치에 있는 공개 항목을 가져와서 다른 위치에 정의된 것처럼 다른 위치에서도 공개되도록 합니다.

예를 들어, 예술적 개념을 모델링하기 위해 art라는 이름의 라이브러리를 만들었다고 가정해 보겠습니다. 이 라이브러리에는 두 개의 모듈이 있습니다. kinds 모듈에는 PrimaryColor와 SecondaryColor라는 두 개의 열거형이 포함되어 있고, utils 모듈에는 mix라는 함수가 포함되어 있으며, 이는 Listing 14-3에 나와 있습니다.

그림 14-3은 cargo doc로 생성된 이 크레이트 문서의 첫 페이지가 어떻게 보이는지 보여줍니다.

그림 14-3: art 문서의 첫 페이지로, kinds와 utils 모듈을 나열합니다

PrimaryColor과 SecondaryColor 타입은 첫 페이지에 나열되지 않으며, mix 함수도 마찬가지입니다. kinds과 utils를 클릭해야 볼 수 있습니다.

이 라이브러리에 의존하는 다른 크레이트는 현재 정의된 모듈 구조를 지정하여 use의 아이템을 스코프에 가져오는 use 문장이 필요합니다. Listing 14-4는 art 크레이트의 PrimaryColor와 mix 아이템을 사용하는 크레이트의 예를 보여줍니다. PrimaryColor 그리고 mix는 art 크레이트에서 가져온 아이템입니다.

Listing 14-4의 코드 작성자는 art 크레이트, 그걸 알아내야 했어. PrimaryColor 에 있는 kinds Module 및 mix 에 있는 utils 단위. 의 단위 구조 art 크레이트는 작업 중인 개발자들에게 더 관련성이 있습니다. art crate를 사용하는 것보다. 내부 구조에는 사용 방법을 이해하려는 사람에게 유용한 정보가 포함되어 있지 않습니다. art 크레이트는, 그러나 오히려 혼란을 야기하는데, 왜냐하면 그것을 사용하는 개발자들은 어디를 봐야할 지 알아내야 하기 때문이며, use 성명.

공개 API에서 내부 조직을 제거하려면, 목록 14-3의 art 크레이트 코드를 수정하여 pub use 문장을 추가하고 항목을 최상위 레벨에서 다시 내보내야 합니다. 이는 목록 14-5에 나와 있습니다.

cargo doc가 이 크레이트에 대해 생성하는 API 문서는 이제 그림 14-4와 같이 첫 페이지에 재수출 항목을 나열하고 링크합니다. 이를 통해 PrimaryColor 및 SecondaryColor 유형과 mix 함수를 더 쉽게 찾을 수 있습니다.

그림 14-4: 재수출 항목을 나열하는 art 문서의 첫 페이지

art 크레이트 사용자는 목록 14-4에서 보여준 것처럼 목록 14-3의 내부 구조를 계속 보고 사용할 수 있습니다. 또는 목록 14-6에서 보여준 것처럼 목록 14-5의 더 편리한 구조를 사용할 수도 있습니다.

중첩된 모듈이 많은 경우, pub use를 사용하여 최상위 수준에서 유형을 재수출하면 크레이트 사용자의 경험에 큰 차이를 만들 수 있습니다. pub use의 또 다른 일반적인 용도는 현재 크레이트의 종속성에 대한 정의를 재수출하여 해당 크레이트의 정의를 자신의 크레이트 공개 API의 일부로 만드는 것입니다.

유용한 공개 API 구조를 만드는 것은 과학이라기보다 예술에 가깝습니다. 사용자에게 가장 적합한 API를 찾기 위해 반복적으로 개선할 수 있습니다. pub use를 사용하면 크레이트의 내부 구조를 구성하는 방식에 유연성을 확보하고, 내부 구조를 사용자에게 제시하는 공개 API와 분리할 수 있습니다. 설치한 크레이트의 코드를 살펴보고 내부 구조가 공개 API와 다른지 확인해 보세요.

Crates.io 계정 설정

크레이트를 게시하기 전에 계정을 만들어야 합니다. 크레이트.io 무시 그리고 API 토큰을 얻을. 이렇게하려면에서 홈 페이지를 방문 크레이트.io 무시 그리고 GitHub 계정을 통해 로그인합니다. (GitHub 계정은 현재 필수이지만 나중에 계정을 만드는 다른 방법을 지원할 수 있습니다.) 로그인 한 후에는 다음에서 계정 설정을 방문하십시오. https://crates.io/me/에서 다운로드 무시 그리고 API 키를 검색합니다. 그런 다음 cargo login 메시지가 표시되면 다음과 같이 명령 및 API 키를 붙여 넣습니다.

$ cargo login
abcdefghijklmnopqrstuvwxyz012345

이 명령은 Cargo에 API 토큰을 전달하고 ~/.cargo/credentials.toml 파일에 로컬로 저장합니다. 이 토큰은 기밀 정보이므로 다른 누구와도 공유하지 마십시오. 만약 어떤 이유로든 다른 사람에게 공유했다면, 크레이트.io에서 해당 토큰을 폐기하고 새 토큰을 생성해야 합니다.

새 크레이트에 메타데이터 추가

게시하려는 크레이트가 있다고 가정해 봅시다. 게시하기 전에 크레이트의 Cargo.toml 파일의 [package] 섹션에 메타데이터를 추가해야 합니다.

크레이트는 고유 한 이름이 필요합니다. 크레이트에서 작업하는 동안 현지에서 원하는대로 크레이트의 이름을 지정할 수 있습니다. 그러나 크레이트 이름은 크레이트.io 무시 선착순으로 할당됩니다. 크레이트 이름이 지정되면 다른 사람이 그 이름을 가진 크레이트를 게시 할 수 없습니다. 크레이트를 게시하기 전에 사용하려는 이름을 검색하십시오. 이름이 사용 된 경우 다른 이름을 찾고 편집해야합니다. name 에서 필드는 카고.toml 아래 파일 [package] 섹션은 다음과 같이 게시를 위해 새 이름을 사용합니다.

파일명: Cargo.toml

[package]
name = "guessing_game"

고유한 이름을 선택했더라도, 이 시점에서 cargo publish를 실행하여 크레이트를 게시하면 경고가 표시된 후 오류가 발생합니다.

$ cargo publish
    Updating crates.io index
warning: manifest has no description, license, license-file, documentation, homepage or repository.
See https://doc.rust-lang.org/cargo/reference/manifest.html#package-metadata for more info.
--snip--
error: failed to publish to registry at https://crates.io

Caused by:
  the remote server responded with an error (status 400 Bad Request): missing or empty metadata fields: description, license. Please see https://doc.rust-lang.org/cargo/reference/manifest.html for more information on configuring these fields

이로 인해 오류가 발생합니다. 몇 가지 중요한 정보가 누락되었기 때문입니다. 설명(description)과 라이선스(license)는 필수 항목으로, 사람들이 크레이트의 용도와 사용 조건을 알아야 하므로 반드시 지정해야 합니다. Cargo.toml 파일에는 검색 결과에 크레이트와 함께 표시되므로, 한두 문장 분량의 설명을 추가하세요. licenselicense 필드에는 라이선스 식별자 값을 지정해야 합니다. Linux Foundation의 Software Package Data Exchange(SPDX)에서 이 값으로 사용할 수 있는 식별자를 확인할 수 있습니다. 예를 들어, 크레이트에 MIT License를 적용했음을 지정하려면 SPDX 라이선스 목록MIT 식별자를 추가합니다. MIT

파일명: Cargo.toml

[package]
name = "guessing_game"
license = "MIT"

SPDX에 없는 라이선스를 사용하려면 해당 라이선스 텍스트를 파일에 저장하고, 이 파일을 프로젝트에 포함시킨 다음, license-file를 사용하여 license 키 대신 해당 파일 이름을 지정해야 합니다.

프로젝트에 적합한 라이선스가 무엇인지에 대한 지침은 이 책의 범위를 벗어납니다. Rust 커뮤니티의 많은 사람들이 Rust와 동일한 방식으로 프로젝트를 라이선스하며, MIT OR Apache-2.0의 이중 라이선스를 사용합니다. 이 관행은 프로젝트에 여러 라이선스를 적용하기 위해 OR로 구분된 여러 라이선스 식별자를 지정할 수도 있음을 보여줍니다.

고유한 이름, 버전, 설명, 라이선스를 추가하면 게시할 준비가 된 프로젝트의 Cargo.toml 파일은 다음과 같은 형태가 될 수 있습니다:

파일명: Cargo.toml

[package]
name = "guessing_game"
version = "0.1.0"
edition = "2024"
description = "A fun game where you guess what number the computer has chosen."
license = "MIT OR Apache-2.0"

[dependencies]

Cargo 문서에는 다른 사람들이 크레이트를 더 쉽게 발견하고 사용할 수 있도록 지정할 수 있는 추가 메타데이터에 대한 설명이 포함되어 있습니다.

Crates.io에 게시하기

계정을 만들고, API 토큰을 저장하고, 크레이트 이름을 선택하고, 필요한 메타데이터를 지정했으니 이제 게시할 준비가 되었습니다! 크레이트를 게시하면 다른 사람들이 사용할 수 있도록 crates.io에 특정 버전이 업로드됩니다.

게시는 영구적이기 때문에 주의해야 합니다. 버전을 덮어쓸 수 없으며 특정 상황을 제외하고는 코드를 삭제할 수 없습니다. Crates.io의 주요 목표 중 하나는 크레이트.io의 크레이트에 의존하는 모든 프로젝트의 빌드가 계속 작동하도록 코드의 영구 아카이브 역할을 하는 것입니다. 버전 삭제를 허용하면 해당 목표를 달성할 수 없습니다. 그러나 게시할 수 있는 크레이트 버전의 수에는 제한이 없습니다.

기존 크레이트의 새 버전 게시

크레이트를 변경하고 새 버전을 출시할 준비가 되면, Cargo.toml 파일에 지정된 version 값을 변경하고 다시 게시하십시오. 시맨틱 버전 규칙을 사용하여 수행한 변경 사항의 종류에 따라 적절한 다음 버전 번호를 결정하십시오. 그런 다음 cargo publish를 실행하여 새 버전을 업로드하십시오.

Crates.io에서 버전 비활성화

크레이트의 이전 버전을 완전히 제거할 수는 없지만, 향후 프로젝트가 해당 버전을 새로운 종속성으로 추가하는 것을 막을 수 있습니다. 이는 크레이트 버전이 어떤 이유로든 손상된 경우 유용합니다. 이러한 상황에서 Cargo는 크레이트 버전을 yank하는 기능을 지원합니다.

버전을 yank하면 새 프로젝트가 해당 버전에 의존하는 것을 방지하면서, 이미 해당 버전에 의존하는 기존 프로젝트는 계속 작동할 수 있습니다. 기본적으로 yank는 Cargo.lock 파일이 있는 모든 프로젝트가 중단되지 않으며, 새로 생성되는 Cargo.lock 파일에는 yank된 버전이 사용되지 않음을 의미합니다.

크레이트의 특정 버전을 yank하려면, 이전에 게시한 크레이트의 디렉토리에서 cargo yank를 실행하고 yank할 버전을 지정합니다. 예를 들어, guessing_game라는 이름의 크레이트 버전 1.0.1을 게시한 후 이를 yank하려면, guessing_game의 프로젝트 디렉토리에서 다음 명령을 실행합니다.

$ cargo yank --vers 1.0.1
    Updating crates.io index
        Yank guessing_game@1.0.1

명령에 --undo를 추가하면 yank를 실행 취소하여 프로젝트가 해당 버전을 다시 의존할 수 있게 할 수 있습니다:

$ cargo yank --vers 1.0.1 --undo
    Updating crates.io index
      Unyank guessing_game@1.0.1

yank는 어떤 코드도 삭제하지 않습니다. 예를 들어, 실수로 업로드된 시크릿을 삭제할 수 없습니다. 만약 그런 일이 발생했다면, 즉시 해당 시크릿을 재설정해야 합니다.
