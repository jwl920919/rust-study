일반 데이터 형식

제네릭을 사용하여 함수 시그니처 또는 구조체와 같은 항목에 대한 정의를 만들 수 있습니다. 그런 다음 다양한 구체적인 데이터 형식과 함께 사용할 수 있습니다. 먼저 제네릭을 사용하여 함수, 구조체, 열거형 및 메서드를 정의하는 방법을 살펴 보겠습니다. 그런 다음 제네릭이 코드 성능에 어떤 영향을 미치는지 설명합니다.

Enum 정의에서

구조체에서와 마찬가지로, 우리는 변형에서 일반적인 데이터 유형을 보유하도록 열거형을 정의할 수 있습니다. 6장에서 사용했던 표준 라이브러리가 제공하는 Option<T> 열거형을 한 번 더 살펴보겠습니다.

#![allow(unused)]
fn main() {
enum Option<T> {
    Some(T),
    None,
}
}

이 정의는 이제 당신에게 더 의미가 있어야합니다. 당신이 볼 수 있듯이, Option<T> enum은 형식에 대해 일반입니다. T 두 가지 변형이 있습니다: Some타입의 값 하나를 가지고 있는 T그리고 A None variant는 어떤 값도 가지고 있지 않습니다. Option<T> enum, 우리는 선택적 값의 추상적 개념을 표현할 수 있습니다. Option<T> 옵션 값의 유형에 관계없이이 추상화를 사용할 수 있습니다.

열거형은 여러 일반 형식을 사용할 수도 있습니다. 9장에서 사용한 Result 열거형의 정의는 한 가지 예입니다.

T또는 실패 (어떤 유형의 오류를 반환) E사실, 이것은 우리가 Listing 9-3에서 파일을 여는 데 사용했던 것입니다. T 유형으로 채워졌습니다. std::fs::File 파일이 성공적으로 열렸을 때 E 유형으로 채워졌습니다. std::io::Error 파일을 여는 데 문제가 발생했습니다.

제네릭을 사용한 코드의 성능

제네릭 타입 매개변수를 사용할 때 런타임 비용이 있는지 궁금할 수 있습니다. 좋은 소식은 제네릭 타입을 사용하면 프로그램이 콘크리트 타입보다 느리게 실행되지 않는다는 것입니다.

러스트는 컴파일 타임에 제네릭을 사용하여 코드를 Monomorphization을 수행함으로써 이를 수행합니다. Monomorphization은 제네릭 코드를 컴파일할 때 사용되는 구체적인 타입으로 작성하여 특정 코드로 바꾸는 과정입니다. 이 과정에서 컴파일러는 Listing 10-5에서 제네릭 함수를 생성하는 데 사용한 단계의 반대를 수행합니다: 컴파일러는 제네릭 코드가 호출되는 모든 장소를 살펴보고 제네릭 코드가 호출되는 구체적인 타입에 대한 코드를 생성합니다.

표준 라이브러리의 일반 Option<T> enum을 사용하여 어떻게 작동하는지 살펴 보겠습니다.

#![allow(unused)]
fn main() {
let integer = Some(5);
let float = Some(5.0);
}

러스트가 이 코드를 컴파일할 때, 그것은 단형화(monomorphization)를 수행합니다. 그 과정에서, 컴파일러는 사용된 값들을 읽습니다. Option<T> 사례 및 식별의 두 종류 Option<T>하나 : One i32 그리고 다른 하나는 f64. 이와 같이, 그것은 일반적인 정의를의 확장합니다 Option<T> 두 가지 특징이 특징인 i32 그리고 f64따라서 일반적인 정의를 특정 정의로 대체합니다.

Monomorphized 버전의 코드는 다음과 유사합니다 (컴파일러는 여기에서 그림에 사용하는 것과 다른 이름을 사용합니다).

제네릭 Option<T>는 컴파일러가 만든 특정 정의로 대체됩니다. 러스트는 제네릭 코드를 각 인스턴스의 유형을 지정하는 코드로 컴파일하기 때문에 제네릭을 사용하는 데 런타임 비용을 지불하지 않습니다. 코드가 실행될 때, 각 정의를 손으로 복제한 것처럼 작동합니다. 단형화 과정은 런타임에서 러스트의 제네릭을 매우 효율적으로 만듭니다.
