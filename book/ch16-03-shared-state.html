공유 상태 동시성

메시지 전달은 동시성을 처리하는 좋은 방법이지만 유일한 방법은 아닙니다. 또 다른 방법은 여러 스레드가 동일한 공유 데이터에 액세스하는 것입니다. Go 언어 문서의 슬로건 중이 부분을 다시 생각해보십시오. "메모리를 공유하여 통신하지 마십시오."

메모리를 공유하여 통신하는 것은 어떤 모습일까요? 또한 메시지를 전달하는 애호가가 메모리 공유를 사용하지 않도록 주의하는 이유는 무엇입니까?

모든 프로그래밍 언어의 채널은 단일 소유권과 유사합니다. 왜냐하면 일단 값을 채널 아래로 전송하면 더 이상 그 값을 사용하지 않기 때문입니다. 공유 메모리 동시성은 다중 소유권과 같습니다. 여러 스레드가 동시에 동일한 메모리 위치에 액세스 할 수 있습니다. 스마트 포인터가 여러 소유권을 가능하게 한 15 장에서 보았 듯이 이러한 다른 소유자가 관리해야하기 때문에 여러 소유권이 복잡성을 추가 할 수 있습니다. 러스트의 유형 시스템과 소유권 규칙은 이러한 메모리 관리를 크게 지원합니다.

Mutex로 액세스 제어

Mutex는 뮤텍스에서 주어진 시간에 일부 데이터에 액세스 할 수있는 하나의 스레드 만 허용하는 것처럼 상호 배제의 약어입니다. 뮤텍스에서 데이터에 액세스하려면 스레드가 먼저 뮤텍스의 잠금을 획득하도록 요청하여 액세스 할 수 있다는 신호를 보내야합니다. 잠금은 현재 데이터에 독점적으로 액세스 할 수있는 사람을 추적하는 뮤텍스의 일부인 데이터 구조입니다. 따라서 뮤텍스는 잠금 시스템을 통해 보유하고있는 데이터를 보호하는 것으로 설명됩니다.

뮤텍스는 두 가지 규칙을 기억해야하기 때문에 사용하기가 어렵다는 평판이 있습니다.

  1. 당신은 데이터를 사용하기 전에 잠금을 취득하려고 시도해야합니다.
  2. 뮤텍스 가드가 수행한 데이터가 완료되면 다른 스레드가 잠금을 획득할 수 있도록 데이터의 잠금을 해제해야 합니다.

Mutex에 대한 실제 비유를 들어, 단 하나의 마이크를 가진 회의에서 패널 토론을 상상해보십시오. 패널리스트가 말할 수 있기 전에 마이크를 사용하고 싶다고 요청하거나 신호를 보내야합니다. 마이크를 얻을 때, 그들은 원하는만큼 길게 이야기 할 수 있고 마이크를 말하기 위해 요청하는 다음 패널에게 마이크를 건네 줄 수 있습니다. 패널리스트가 마이크를 다 마쳤을 때 마이크를 건네는 것을 잊어 버리면 다른 사람이 할 수 없습니다!

뮤텍스 관리는 매우 까다로울 수 있습니다. 그렇기 때문에 많은 사람들이 채널에 열광합니다. 그러나 러스트의 타입 시스템과 소유권 규칙 덕분에, 여러분은 잠금을 풀고 잘못 잠금을 해제할 수 없습니다.

Atomic Reference 계산하는 방법 Arc<T>

다행히도 Arc<T>는 동시 상황에서 안전하게 사용할 수 있는 Rc<T>와 같은 유형입니다. a는 원자를 의미하며, 이는 원자 참조 카운트 유형입니다. 원자는 여기에 자세히 설명하지 않는 추가 동시성 기본 유형입니다. 자세한 내용은 std::sync::atomic에 대한 표준 라이브러리 설명서를 참조하십시오. 이 시점에서, 당신은 단지 원시적 인 작업을 공유해야합니다.

그런 다음 모든 기본 유형이 원자가 아닌 이유와 표준 라이브러리 유형이 기본적으로 Arc<T>를 사용하도록 구현되지 않는 이유가 궁금 할 것입니다. 그 이유는 스레드 안전에는 실제로 필요할 때만 지불하려는 성능 페널티가 함께 제공되기 때문입니다. 단일 스레드 내에서 값에 대한 작업을 수행하는 경우 원자가 제공하는 보장을 시행하지 않아도 코드가 더 빨리 실행 될 수 있습니다.

Arc<T>와 Rc<T>는 동일한 API를 가지고 있으므로 use 라인, new 호출 및 clone 호출을 변경하여 프로그램을 수정합니다. Listing 16-15의 코드는 최종적으로 컴파일되고 실행됩니다.

주목해야 할 또 다른 세부 사항은 러스트가 당신이 사용할 때 모든 종류의 논리 오류로부터 당신을 보호 할 수 없다는 것입니다. Mutex<T>. 제 15 장에서 상기를 사용하여 Rc<T> 참조 사이클을 생성의 위험과 함께 제공, 여기서 두 Rc<T> 값은 서로를 참조하며 메모리 누수를 유발합니다. 비슷하게, Mutex<T> 창조의 위험과 함께 온다 교착 상태. 이것은 작업이 두 개의 리소스와 두 개의 스레드를 잠글 필요가 있을 때 각각 하나의 잠금을 획득하여 서로 영원히 기다리게 하는 경우에 발생합니다. 교착 상태에 관심이 있다면 교착 상태가 있는 러스트 프로그램을 생성해 보십시오. 그런 다음, 어떤 언어로든 뮤텍스에 대한 교착 상태 완화 전략을 연구하고 러스트에서 구현해야 합니다. 표준 라이브러리 API 문서 Mutex<T> 그리고 MutexGuard 유용한 정보를 제공합니다.

우리는 Send 및 Sync 특성에 대해 이야기하고 사용자 정의 유형과 함께 사용할 수있는 방법에 대해 이야기함으로써이 장을 마무리합니다.
