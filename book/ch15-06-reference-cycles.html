The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

참조 사이클은 메모리 누수를 일으킬 수 있습니다

Rust의 메모리 안전성 보장은 실수로 메모리가 정리되지 않는 상태(메모리 누수)를 만드는 것을 어렵게 하지만, 불가능하지는 않습니다. 메모리 누수를 완전히 방지하는 것은 Rust의 보장 사항이 아니므로, 메모리 누수는 Rust에서 메모리 안전하다고 간주됩니다. Rc<T>와 RefCell<T>을 사용하여 Rust가 메모리 누수를 허용하는 것을 확인할 수 있습니다. 서로를 참조하는 항목 사이클을 만들 수 있으며, 이는 사이클 내 각 항목의 참조 카운트가 0이 될 수 없어 값이 drop되지 않기 때문에 메모리 누수를 유발합니다.

참조 사이클 만들기

참조 사이클이 어떻게 발생하고 어떻게 방지할 수 있는지, Listing 15-25의 List 열거형과 tail 메서드 정의부터 살펴보겠습니다.

우리는 또 다른 variation을 사용한다. List Listing 15-5의 definition입니다. 두번째 요소는 Cons variant 현재 RefCell<Rc<List>>즉, 수정 할 수있는 능력을 갖는 대신 i32 Listing 15-24에서 했던 것처럼, 우리는 List 값 a Cons variant는 가리키고 있습니다. 우리는 또한 tail 우리가 a가 있는 경우에 저희가 두번째 품목에 접근하게 편리한 만드는 방법 Cons 변형.

Listing 15-26에서, 우리는 main Listing 15-25의 정의를 사용하는 함수입니다. 이 코드는 리스트를 만듭니다. a 그리고 in 리스트 b 상기 리스트는 The list in a. 그런 다음 목록을 수정합니다. a 포인트 투 b레퍼런스 사이클을 생성합니다. println! 이 과정에서 다양한 지점에서 참조 카운트가 무엇인지 보여주는 방법의 진술.

변수 a에 List 값을 가진 Rc<List> 인스턴스를 생성합니다. 이 인스턴스는 초기 목록으로 5, Nil를 가집니다. 그런 다음 변수 b에 List 값을 가진 Rc<List> 인스턴스를 생성합니다. 이 인스턴스는 값 10을 포함하고 a의 목록을 가리킵니다.

a을 수정하여 Nil 대신 b을 가리키도록 하고, 사이클을 생성합니다. tail 메서드를 사용하여 a의 RefCell<Rc<List>>에 대한 참조를 얻고, 이를 변수 link에 넣습니다. 그런 다음 RefCell<Rc<List>>에 borrow_mut 메서드를 사용하여 내부 값을 Nil 값을 가진 Rc<List>에서 b의 Rc<List>으로 변경합니다.

마지막 println!은 잠시 주석 처리한 채로 이 코드를 실행하면 다음과 같은 출력이 표시됩니다.

a의 목록을 b을 가리키도록 변경한 후, a과 b 모두의 Rc<List> 인스턴스의 참조 횟수는 2입니다. main의 끝에서 Rust는 변수 b을 드롭(drop)합니다. 이로 인해 Rc<List> b 인스턴스의 참조 횟수가 2에서 1로 감소합니다. Rc<List>가 힙에 가진 메모리는 이 시점에서 드롭되지 않습니다. 그 참조 횟수가 0이 아니라 1이기 때문입니다. 그런 다음 Rust는 a을 드롭합니다. 이로 인해 Rc<List> a 인스턴스의 참조 횟수도 2에서 1로 감소합니다. 이 인스턴스의 메모리도 드롭할 수 없습니다. 다른 Rc<List> 인스턴스가 여전히 이를 참조하고 있기 때문입니다. 목록에 할당된 메모리는 영원히 수집되지 않은 상태로 남아 있습니다. 이 참조 사이클을 시각화하기 위해 그림 15-4의 다이어그램을 만들었습니다.

그림 15-4: 서로를 참조하는 목록 a과 b의 참조 사이클

마지막 println!의 주석을 풀고 프로그램을 실행하면, 러스트는 a가 b를 가리키고 있는 것을 가리키고 있는 a로 이 사이클을 인쇄하려고 할 것입니다.

실제 프로그램과 비교하면, 이 예제에서 참조 사이클을 생성하는 결과는 그리 심각하지 않습니다. 참조 사이클을 생성한 직후 프로그램이 종료되므로 그렇습니다. 그러나 더 복잡한 프로그램이 사이클 내에서 많은 메모리를 할당하고 오랫동안 이를 유지한다면, 프로그램은 필요한 것보다 더 많은 메모리를 사용하고 시스템을 압도하여 사용 가능한 메모리가 부족해지는 상황을 초래할 수 있습니다.

참조 사이클을 만드는 일은 쉽지 않지만, 불가능한 것도 아닙니다. RefCell<T> 값 안에 Rc<T> 값이 들어 있거나, 내부 가변성과 참조 카운팅을 함께 사용하는 유사한 유형의 중첩 조합을 사용하는 경우, 사이클이 생성되지 않도록 직접 확인해야 합니다. Rust가 이를 자동으로 잡아 주지 않기 때문입니다. 참조 사이클은 프로그램의 논리적 버그에 해당하므로, 자동화 테스트, 코드 리뷰, 기타 소프트웨어 개발 관행을 통해 이를 최소화해야 합니다.

참조 사이클을 피하기 위한 또 다른 해결책은 데이터 구조를 재구성하여 일부 참조는 소유권을 표현하고 일부 참조는 소유권을 표현하지 않도록 하는 것입니다. 이렇게 하면 일부는 소유권 관계이고 일부는 소유권 관계가 아닌 관계로 구성된 사이클을 만들 수 있으며, 값이 드롭될 수 있는지 여부에 영향을 미치는 것은 소유권 관계뿐입니다. Listing 15-25에서는 Cons 변형이 항상 자신의 리스트를 소유해야 하므로 데이터 구조를 재구성하는 것은 불가능합니다. 이제 부모 노드와 자식 노드로 구성된 그래프를 사용하는 예를 살펴보고, 소유권 관계가 아닌 관계가 참조 사이클을 방지하는 적절한 방식인 경우를 알아보겠습니다.

Weak<T>를 사용하여 참조 사이클 방지Weak<T>

지금까지 Rc::clone을 호출하면 Rc<T> 인스턴스의 strong_count이 증가하고, Rc<T> 인스턴스는 strong_count가 0일 때만 정리됨을 시연했습니다. Rc<T> 인스턴스 내부의 값에 대한 약한 참조를 만들 수도 있습니다. Rc::downgrade을 호출하고 Rc<T>에 대한 참조를 전달하면 됩니다. 강한 참조는 Rc<T> 인스턴스의 소유권을 공유하는 방법입니다. 약한 참조는 소유권 관계를 표현하지 않으며, 그 횟수는 Rc<T> 인스턴스가 정리되는 시점에 영향을 미치지 않습니다. 약한 참조가 포함된 어떤 사이클도 관련 값의 강한 참조 횟수가 0이 되면 끊어지므로, 약한 참조는 참조 사이클을 일으키지 않습니다.

Rc::downgrade을 호출하면 Weak<T> 타입의 스마트 포인터를 얻습니다. strong_count 인스턴스의 Rc<T>을 1 증가시키는 대신, Rc::downgrade을 호출하면 weak_count이 1 증가합니다. Rc<T> 타입은 weak_count을 사용하여 Weak<T> 참조가 얼마나 존재하는지 추적하며, 이는 strong_count와 유사합니다. 차이점은 weak_count이 0이 아니어도 Rc<T> 인스턴스가 정리될 수 있다는 것입니다.

Weak<T>이 참조하는 값이 드롭되었을 수 있으므로, Weak<T>이 가리키는 값으로 무언가를 하려면 값이 여전히 존재하는지 확인해야 합니다. Weak<T> 인스턴스에서 upgrade 메서드를 호출하여 이를 수행합니다. 이 메서드는 Option<Rc<T>>를 반환합니다. Rc<T> 값이 아직 드롭되지 않았다면 Some 결과를, Rc<T> 값이 드롭되었다면 None 결과를 얻습니다. upgrade가 Option<Rc<T>>를 반환하므로, Rust는 Some 경우와 None 경우가 처리되도록 보장하며, 잘못된 포인터가 발생하지 않습니다.

예를 들어, 항목이 다음 항목에 대해서만 알고 있는 리스트를 사용하는 대신, 항목이 자식 항목과 부모 항목에 대해 알고 있는 트리를 만들겠습니다.

트리 데이터 구조 만들기

먼저, 자식 노드에 대한 정보를 가진 노드로 트리를 구성하겠습니다. Node라는 이름의 구조체를 만들어, 자신의 i32 값과 자식 Node 값에 대한 참조를 함께 저장하도록 하겠습니다.

파일 이름: src/main.rs

use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
struct Node {
    value: i32,
    children: RefCell<Vec<Rc<Node>>>,
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        children: RefCell::new(vec![]),
    });

    let branch = Rc::new(Node {
        value: 5,
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });
}

우리는 원합니다 A Node 그리고 우리는 그 소유권을 변수와 공유하여 각각의 변수에 접근할 수 있기를 원합니다. Node 나무에서 직접. 이렇게하기 위해, 우리는 정의 Vec<T> 타입의 값이 될 항목 Rc<Node>. 우리는 또한 어떤 노드가 다른 노드의 자식 노드인지 수정하고 싶습니다. RefCell<T> 에서 children 오시는 길 Vec<Rc<Node>>.

다음으로, 구조체 정의를 사용해 Node 인스턴스를 하나 생성합니다. 이름은 leaf이고 값은 3이며 자식이 없습니다. 또 다른 인스턴스는 이름이 branch이고 값이 5이며 leaf를 자식으로 하나 포함합니다. Listing 15-27에 나와 있습니다.

leaf의 Rc<Node>을 복제하고 branch에 저장합니다. 즉, leaf의 Node에는 이제 두 명의 소유자가 있습니다: leaf와 branch입니다. branch.children를 통해 branch에서 leaf로 갈 수 있지만, leaf에서 branch로 가는 방법은 없습니다. 그 이유는 leaf이 branch에 대한 참조를 가지고 있지 않고, 둘이 관련이 있다는 사실을 알지 못하기 때문입니다. leaf이 branch가 자신의 부모임을 알기를 원합니다. 다음에 그렇게 하겠습니다.

자식에서 부모에 대한 참조 추가

자식 노드가 자신의 부모를 인식하도록 하려면, parent 구조체 정의에 Node 필드를 추가해야 합니다. 문제는 parent의 타입을 어떻게 결정할 것인가입니다. Rc<T>를 포함할 수 없다는 것은 알고 있습니다. 그렇게 하면 leaf.parent이 branch를 가리키고 branch.children이 leaf를 가리키는 참조 사이클이 생겨, strong_count 값이 절대 0이 될 수 없기 때문입니다.

관계를 다른 관점에서 보면, 부모 노드는 자식들을 소유해야 합니다. 부모 노드가 drop되면 자식 노드들도 함께 drop되어야 합니다. 그러나 자식은 부모를 소유해서는 안 됩니다. 자식 노드를 drop해도 부모는 여전히 존재해야 합니다. 이는 weak reference를 사용할 때입니다!

따라서 Rc<T> 대신 parent의 유형으로 Weak<T>, 구체적으로는 RefCell<Weak<Node>>를 사용합니다. 이제 Node 구조체 정의는 다음과 같습니다.

파일 이름: src/main.rs

use std::cell::RefCell;
use std::rc::{Rc, Weak};

#[derive(Debug)]
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });

    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade());

    let branch = Rc::new(Node {
        value: 5,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });

    *leaf.parent.borrow_mut() = Rc::downgrade(&branch);

    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade());
}

노드는 부모 노드를 참조할 수 있지만 부모 노드를 소유하지는 않습니다. Listing 15-28에서 main를 이 새로운 정의에 맞게 업데이트하여 leaf 노드가 부모인 branch를 참조할 수 있도록 합니다.

leaf 노드를 생성하는 과정은 parent 필드를 제외하면 Listing 15-27과 유사합니다. leaf는 처음에는 부모가 없으므로, 새로운 빈 Weak<Node> 참조 인스턴스를 생성합니다.

이 시점에서 leaf 메서드를 사용하여 upgrade의 부모에 대한 참조를 얻으려고 하면 None 값을 얻게 됩니다. 첫 번째 println! 문장의 출력에서 이를 확인할 수 있습니다:

leaf parent = None

branch 노드를 생성하면, branch이 부모 노드를 가지고 있지 않기 때문에 parent 필드에 새로운 Weak<Node> 참조도 포함됩니다. 여전히 branch의 자식 중 하나로는 leaf가 있습니다. branch에 Node 인스턴스가 있으면, leaf을 수정하여 부모에 대한 Weak<Node> 참조를 줄 수 있습니다. leaf의 parent 필드인 RefCell<Weak<Node>>에 borrow_mut 메서드를 사용하고, branch의 Rc<Node>에서 branch에 대한 Weak<Node> 참조를 생성하기 위해 Rc::downgrade 함수를 사용합니다.

다시 leaf의 부모를 출력하면, 이번에는 Some 변형을 포함하는 branch 값을 얻게 됩니다. 이제 leaf은 부모에 접근할 수 있습니다! leaf를 출력할 때, Listing 15-26에서 발생했던 스택 오버플로우로 이어지는 사이클도 피할 수 있습니다. Weak<Node> 참조는 (Weak)로 출력됩니다:

leaf parent = Some(Node { value: 5, parent: RefCell { value: (Weak) },
children: RefCell { value: [Node { value: 3, parent: RefCell { value: (Weak) },
children: RefCell { value: [] } }] } })

무한 출력이 없다는 것은 이 코드가 참조 주기를 생성하지 않았음을 의미합니다. Rc::strong_count 및 Rc::weak_count를 호출하여 얻은 값을 확인함으로써 이를 알 수도 있습니다.

strong_count와 weak_count 변경 사항 시각화하기 strong_count 그리고 weak_count

의는 방법을 살펴 보자 strong_count 그리고 weak_count 의 값 The value Rc<Node> instance는 새로운 내부 스코프를 생성하여 branch 그 범위로. 그렇게함으로써, 우리는 어떤 일이 일어나는지 볼 수 있습니다. branch 스코프를 벗어나면 생성되고 삭제됩니다. 수정 사항은 Listing 15-29에 나와 있습니다.

leaf이 생성된 후, 그 Rc<Node>의 strong count는 1이고 weak count는 0입니다. 내부 스코프에서 branch를 생성하고 leaf와 연결하면, 카운트를 출력할 때 Rc<Node>의 branch는 strong count가 1이고 weak count가 1이 됩니다(leaf.parent가 branch을 가리키는 Weak<Node> 때문). leaf의 카운트를 출력하면, branch이 Rc<Node>의 leaf 클론을 branch.children에 저장하고 있으므로 strong count가 2로 증가하지만 weak count는 여전히 0임을 볼 수 있습니다.

내부 스코프가 끝나면 branch이 스코프를 벗어나 Rc<Node>의 strong count가 0으로 감소하므로 Node가 드롭됩니다. leaf.parent의 weak count 1은 Node가 드롭되는지 여부에 영향을 주지 않으므로 메모리 누수가 발생하지 않습니다!

스코프가 끝난 후 leaf의 parent에 접근하려고 하면 다시 None를 얻게 됩니다. 프로그램이 끝날 때, Rc<Node>의 leaf는 strong count가 1이고 weak count가 0입니다. 이는 변수 leaf가 다시 Rc<Node>에 대한 유일한 참조가 되었기 때문입니다.

카운트와 값 드롭을 관리하는 모든 로직은 Rc<T>, Weak<T>, 그리고 Drop 트레이트 구현에 내장되어 있습니다. Weak<T>의 정의에서 자식에서 부모로의 관계를 Node 참조로 지정하면, 참조 사이클과 메모리 누수를 만들지 않으면서도 부모 노드가 자식 노드를 가리키고 그 반대의 경우도 마찬가지입니다.

요약

이 장에서는 Rust가 일반 참조로 기본적으로 제공하는 보증과 트레이드오프와 다른 보증과 트레이드오프를 만들 수 있도록 스마트 포인터를 사용하는 방법을 다루었습니다. Box<T> 타입은 크기가 정해져 있으며 힙에 할당된 데이터를 가리킵니다. Rc<T> 타입은 힙에 있는 데이터에 대한 참조의 수를 추적하여 데이터가 여러 소유자를 가질 수 있도록 합니다. 내부 가변성을 제공하는 RefCell<T> 타입은 불변 타입이 필요하지만 그 타입의 내부 값을 변경해야 하는 상황에서 사용할 수 있습니다. 또한 빌림 규칙을 컴파일 시가 아니라 런타임에 강제합니다.

또한 스마트 포인터의 많은 기능을 가능하게 하는 Deref 트레이트와 Drop 트레이트에 대해 논의했습니다. 메모리 누수를 유발할 수 있는 참조 사이클과 Weak<T>를 사용하여 이를 방지하는 방법에 대해서도 살펴보았습니다.

이 장이 흥미를 유발했다면 직접 스마트 포인터를 구현해 보고 싶을 것입니다. 더 유용한 정보는 The Rustonomicon에서 확인할 수 있습니다.
