The Rust Programming Language

한국어 기계 번역 초안입니다. Rust 코드와 인라인 코드 예제는 공식 최신 원문 그대로 보존했습니다. 번역 용어와 세부 문장은 계속 검토합니다.

Cargo 워크스페이스

12장에서는 바이너리 크레이트와 라이브러리 크레이트를 포함한 패키지를 만들었습니다. 프로젝트가 발전하면서 라이브러리 크레이트가 계속 커지고, 패키지를 여러 라이브러리 크레이트로 더 나누고 싶을 수 있습니다. Cargo는 함께 개발되는 여러 관련 패키지를 관리하는 데 도움이 되는 워크스페이스라는 기능을 제공합니다.

워크스페이스 만들기

A 작업 영역 같은 것을 공유하는 패키지의 집합입니다. 화물.잠금 그리고 출력 디렉토리. 작업 공간을 사용하여 프로젝트를 만들어 봅시다. 작업 공간의 구조에 집중할 수 있도록 사소한 코드를 사용할 것입니다. 작업 공간을 구성하는 데는 여러 가지 방법이 있으므로 하나의 일반적인 방법을 보여 드리겠습니다. 바이너리와 두 개의 라이브러리를 포함하는 작업 공간을 갖게 될 것입니다. 주요 기능을 제공하는 바이너리는 두 개의 라이브러리에 따라 다릅니다. 하나의 라이브러리는 add_one 도서관 및 다른 도서관 add_two 함수. 이 세 개의 크레이트는 동일한 작업 공간의 일부가 될 것입니다. 우리는 작업 공간을위한 새로운 디렉토리를 만드는 것으로 시작할 것입니다.

$ mkdir add
$ cd add

다음으로, add 디렉토리에서 추가 전체 워크스페이스를 구성할 Cargo.toml 파일을 생성합니다. 이 파일에는 카고.toml [package] 섹션이 없습니다. 대신, 워크스페이스에 멤버를 추가할 수 있는 [workspace] 섹션으로 시작합니다. 또한, resolver 값을 "3"으로 설정하여 워크스페이스에서 Cargo의 최신 리졸버 알고리즘을 사용하도록 합니다: [package] [workspace] resolver "3"

파일명: Cargo.toml

[workspace]
resolver = "3"

다음으로, 우리는 adder 실행하여 이진 크레이트 cargo new 내부 The 추가 디렉터리:

$ cargo new adder
     Created binary (application) `adder` package
      Adding `adder` as member of workspace at `file:///projects/add`

워크스페이스 내부에서 cargo new을 실행하면, 새로 생성된 패키지가 워크스페이스의 members 파일에 있는 [workspace] 정의의 members 키에 자동으로 추가됩니다. 다음과 같습니다: 카고.toml

[workspace]
resolver = "3"
members = ["adder"]

이 시점에서 cargo build를 실행하여 워크스페이스를 빌드할 수 있습니다. add 디렉토리의 파일은 다음과 같아야 합니다.

├── Cargo.lock
├── Cargo.toml
├── adder
│   ├── Cargo.toml
│   └── src
│       └── main.rs
└── target

워크스페이스에는 최상위 레벨에 하나의 대상 디렉토리가 있으며, 컴파일된 아티팩트는 이 디렉토리에 배치됩니다. adder 패키지에는 자체 대상 디렉토리가 없습니다. cargo build를 adder 디렉토리 내부에서 실행하더라도 컴파일된 아티팩트는 add/adder/target이 아닌 add/target에 저장됩니다. Cargo가 워크스페이스에서 대상 디렉토리를 이렇게 구성하는 이유는, 워크스페이스 내의 크레이트가 서로 의존하도록 설계되어 있기 때문입니다. 각 크레이트가 자체 대상 디렉토리를 가진다면, 각 크레이트는 워크스페이스 내의 다른 크레이트를 모두 다시 컴파일하여 아티팩트를 자신의 대상 디렉토리에 배치해야 합니다. 하나의 대상 디렉토리를 공유함으로써 크레이트는 불필요한 재빌드를 피할 수 있습니다.

워크스페이스에서 두 번째 패키지 만들기

다음으로, 워크스페이스에 다른 멤버 패키지를 만들고 add_one라고 부르겠습니다. add_one이라는 이름의 새 라이브러리 크레이트를 생성합니다:

$ cargo new add_one --lib
     Created library `add_one` package
      Adding `add_one` as member of workspace at `file:///projects/add`

이제 최상위 Cargo.toml의 members 목록에 add_one 경로가 포함됩니다. members

파일명: Cargo.toml

[workspace]
resolver = "3"
members = ["adder", "add_one"]

이제 add 디렉토리에 다음과 같은 디렉토리와 파일이 있어야 합니다:

├── Cargo.lock
├── Cargo.toml
├── add_one
│   ├── Cargo.toml
│   └── src
│       └── lib.rs
├── adder
│   ├── Cargo.toml
│   └── src
│       └── main.rs
└── target

add_one/src/lib.rs 파일에 add_one 함수를 추가해 보겠습니다:

파일 이름: add_one/src/lib.rs

pub fn add_one(x: i32) -> i32 {
    x + 1
}

이제 adder 패키지의 바이너리가 add_one 패키지의 라이브러리에 의존하도록 설정할 수 있습니다. 먼저 adder/Cargo.toml 파일에 add_one에 대한 경로 의존성을 추가해야 합니다. adder add_one add_one

파일 이름: adder/Cargo.toml

[dependencies]
add_one = { path = "../add_one" }

Cargo는 워크스페이스 내의 크레이트가 서로 의존한다고 가정하지 않으므로, 의존성 관계를 명시적으로 지정해야 합니다.

다음으로, adder 크레이트에서 add_one 크레이트의 add_one 함수를 사용해 보겠습니다. adder/src/main.rs 파일을 열고 main 함수를 Listing 14-7과 같이 add_one 함수를 호출하도록 수정합니다. add_one add_one adder main add_one

최상위 add 디렉토리에서 cargo build를 실행하여 워크스페이스를 빌드해 보겠습니다! cargo build

$ cargo build
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.22s

add 디렉토리에서 바이너리 크레이트를 실행하려면, cargo run 명령에 -p 인수를 사용하고 패키지 이름을 지정하여 워크스페이스에서 실행할 패키지를 선택할 수 있습니다: -p cargo run

$ cargo run -p adder
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running `target/debug/adder`
Hello, world! 10 plus one is 11!

이것은 add_one 크레이트에 의존하는 adder/src/main.rs 파일의 코드를 실행합니다.

외부 패키지에 의존하기

각 크레이트의 디렉토리에 Cargo.lock 파일을 두는 대신, 작업 공간 최상위 레벨에 Cargo.lock 파일이 하나만 있음을 주목하십시오. 이렇게 하면 모든 크레이트가 동일한 버전의 모든 의존성을 사용하도록 보장됩니다. rand 패키지를 adder/Cargo.toml 파일과 add_one/Cargo.toml 파일에 추가하면, Cargo는 이 두 패키지를 하나의 rand 버전으로 해석하고 이를 유일한 Cargo.lock 파일에 기록합니다. 작업 공간의 모든 크레이트가 동일한 의존성을 사용하도록 하면 크레이트 간에 항상 호환성이 유지됩니다. 이제 add_one 크레이트에서 rand 크레이트를 사용할 수 있도록, [dependencies] 파일의 [dependencies] 섹션에 add_one/Cargo.toml 파일을 수정하여 rand 크레이트를 추가하겠습니다. add_one

파일 이름: add_one/Cargo.toml

[dependencies]
rand = "0.10.1"

이제 add_one/src/lib.rs 파일에 use rand;를 추가하고, add 디렉토리에서 cargo build을 실행하여 전체 작업 공간을 빌드하면 rand 크레이트가 가져와서 컴파일됩니다. 스코프에 가져온 rand을 참조하지 않기 때문에 경고가 하나 표시됩니다.

$ cargo build
    Updating crates.io index
  Downloaded rand v0.10.1
   --snip--
   Compiling rand v0.10.1
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
warning: unused import: `rand`
 --> add_one/src/lib.rs:1:5
  |
1 | use rand;
  |     ^^^^
  |
  = note: `#[warn(unused_imports)]` (part of `#[warn(unused)]`) on by default

warning: `add_one` (lib) generated 1 warning (run `cargo fix --lib -p add_one` to apply 1 suggestion)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.95s

최상위 레벨 화물.잠금 이제 의존성에 대한 정보가 있습니다. add_one 온 rand. 그러나, 비록 rand 작업 공간의 어딘가에 사용되며, 추가하지 않는 한 작업 공간의 다른 크레이트에서 사용할 수 없습니다. rand 그들의 카고.toml 파일도 마찬가지입니다. 예를 들어, use rand; 에 대하여 애드너/src/main.rs 파일명 The adder 패키지, 우리는 오류를 얻을 것이다 :

$ cargo build
  --snip--
   Compiling adder v0.1.0 (file:///projects/add/adder)
error[E0432]: unresolved import `rand`
 --> adder/src/main.rs:2:5
  |
2 | use rand;
  |     ^^^^ no external crate `rand`

이 문제를 해결하려면 Edit 카고.toml 파일명 The adder 패키지 및 그 표시 rand 이에 대한 의존성 또한 중요합니다. adder 패키지 추가 rand 에 대한 종속성의 목록에 adder 에서 화물.잠금, 그러나 추가 사본 없음 rand 화물은 작업 공간의 모든 패키지에 있는 모든 상자가 rand 패키지는 호환되는 버전을 지정하는 한 동일한 버전을 사용합니다. rand, 저희에게 공간을 절약하고 작업 공간에 있는 크레이트가 서로 양립할 것이라는 점을 보증.

작업 공간의 크레이트가 동일한 의존성의 호환되지 않는 버전을 지정하는 경우, Cargo는 각 버전을 해석하지만 가능한 한 적은 수의 버전으로 해석하려고 시도합니다.

워크스페이스에 테스트 추가

또 다른 개선 사항으로, add_one::add_one 함수에 대한 테스트를 add_one 크레이트에 추가해 보겠습니다.

파일 이름: add_one/src/lib.rs

pub fn add_one(x: i32) -> i32 {
    x + 1
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        assert_eq!(3, add_one(2));
    }
}

이제 최상위 add 디렉토리에서 cargo test를 실행하십시오. 이 워크스페이스 구조에서 cargo test를 실행하면 워크스페이스 내 모든 크레이트의 테스트가 실행됩니다.

$ cargo test
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.20s
     Running unittests src/lib.rs (target/debug/deps/add_one-93c49ee75dc46543)

running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

     Running unittests src/main.rs (target/debug/deps/adder-3a47283c568d2b6a)

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests add_one

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

출력의 첫 번째 섹션은 it_works 크레이트의 add_one 테스트가 통과했음을 보여줍니다. 다음 섹션은 adder 크레이트에서 테스트가 하나도 발견되지 않았음을, 마지막 섹션은 add_one 크레이트에서 문서화 테스트가 하나도 발견되지 않았음을 보여줍니다.

또한 최상위 디렉토리에서 -p 플래그를 사용하고 테스트하려는 크레이트의 이름을 지정하여 워크스페이스 내 특정 크레이트의 테스트만 실행할 수 있습니다.

$ cargo test -p add_one
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running unittests src/lib.rs (target/debug/deps/add_one-93c49ee75dc46543)

running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests add_one

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

이 출력은 cargo test가 add_one 크레이트의 테스트만 실행하고 adder 크레이트의 테스트는 실행하지 않았음을 보여줍니다.

워크스페이스의 크레이트를 crates.io에 게시하는 경우, 워크스페이스 내 각 크레이트를 별도로 게시해야 합니다. cargo test와 마찬가지로, -p 플래그를 사용하고 게시하려는 크레이트의 이름을 지정하여 워크스페이스 내 특정 크레이트를 게시할 수 있습니다.

추가 연습으로, add_two 크레이트와 비슷한 방식으로 이 워크스페이스에 add_one 크레이트를 추가해 보세요!

프로젝트가 커짐에 따라 워크스페이스 사용을 고려해 보세요. 워크스페이스를 사용하면 하나의 큰 코드 덩어리보다 작고 이해하기 쉬운 구성 요소로 작업할 수 있습니다. 또한, 워크스페이스에 크레이트를 모아 두면 동시에 변경되는 경우가 많을 때 크레이트 간의 조율이 더 쉬워집니다.
